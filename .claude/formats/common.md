# 팀 양식 사양 — 공통 골격

**이 파일은 전 제품 공통 규칙이다.** 제품마다 갈리는 값은 `profile-{제품}.md` 에 있다.
케이스를 쓰려면 **이 파일 + 해당 제품 프로파일 두 개를 함께** 읽어야 한다.

| 파일 | 담는 것 |
|------|---------|
| **`common.md`** (이 파일) | 컬럼 골격 · 헤더 원문 · `-` vs 빈칸 · atomic · 태그 체계 · C-ID/CH-ID 규칙 · 변경분 모드 · 권위 규칙 |
| `profile-viola.md` | VIOLA — 백틱 문체, 지배 구분 `표시`, TC ID 전역 연속 |
| `profile-trombone.md` | TROMBONE — **대괄호 문체**, 지배 구분 `정상`, TC ID 모듈별 연속 |
| `profile-bootfactory.md` | BootFactory — VIOLA 문체 승계 (실측 근거 없음, 파생) |

> **프로파일을 섞지 마라.** VIOLA와 TROMBONE은 **절차의 백틱 사용률이 65% 대 0.0%(0/3,953행)** 로
> 정반대다. 절충값이 존재하지 않는 항목이며, 헷갈리면 케이스가 팀 컨벤션에서 통째로 벗어난다.

## 권위 규칙 — 사양과 대상 시트가 충돌할 때

케이스를 쓰기 전 `sheet-analyst` 가 **대상 시트의 헤더 1행 + 마지막 20~50행**을 읽어 사양과 대조한다.
충돌 시 무엇이 이기는지는 항목별로 다르다.

| 항목 | 권위 | 근거 |
|------|------|------|
| 컬럼 구조·순서·이름 | **대상 시트** | 어긋나면 값이 엉뚱한 칸에 들어간다. 사후 복구가 가장 비싸다 → **불일치 시 작성 중단 + 사용자 확인** |
| TC ID 마지막 번호 | **대상 시트** | 계속 자라는 값. 사양에 고정값을 두지 않는다 |
| enum 허용값 | **사양 기준** | 시트에 사양 외 값이 있으면 **보고 후 진행 여부 확인** (오타일 수도, 신규 enum일 수도) |
| 문체·검증 단위·미사용 컬럼 정책 | **사양** | 실행마다 흔들리면 안 되는 값 |

### 이 사양이 낡았는지 알아내는 능력의 한계

드리프트 검증(`sheet-analyst` 모드 A)은 **헤더 1행 + 마지막 20~50행**만 읽는다.
**잡히지 않는 쪽을 알고 있어야 한다.**

| 팀 시트의 변화 | 잡는가 |
|----------------|-------|
| 컬럼 추가·삭제·이름·순서 변경 | **잡는다** (헤더 대조, Critical) |
| TC ID 증가 | **잡는다** (꼬리 실측) |
| 사양에 없는 enum 등장 | **잡는다** (꼬리 표본에 나타나면, Major) |
| **문체 전환** — 백틱 ↔ 대괄호, 명사형 → 서술형, `N. ` 접두 폐지 | **잡지 못한다** |
| **검증 단위 전환** — atomic → scenario | **잡지 못한다** |
| **미사용 컬럼 사용 시작** | **잡지 못한다** |
| **탭별 3 Depth 실사용 범위 변화** | **잡지 못한다** |

판정 항목이 헤더·enum·마지막 ID 세 가지로 한정된 **의도적 범위 제한**이다. 아래 신호가 보이면 갱신한다:

- 리뷰에서 **문체·검증 단위 위반이 반복 지적**된다 (사양이 맞고 시트가 바뀐 경우일 수 있다)
- 팀원이 양식·작성 방식을 바꿨다고 말한다
- 프로파일의 **측정일이 오래됐다**
- 생성된 케이스가 기존 행과 나란히 놓였을 때 이질적으로 보인다

갱신 전이라도 문체 위반이 반복되면 **사양과 시트 중 어느 쪽이 최신인지 사람이 판단한다.**
사양을 무조건 정답으로 두고 시트를 고치라고 하지 않는다.

## enum — 공통

### 우선순위 (G) — 4종

`P1` / `P2` / `P3` / `P4`. **`P0`/`P5`/`High`·`Low` 등 신규 값 금지.**
분포와 구분×우선순위 결합 규칙은 **프로파일**에 있다 (제품마다 정반대인 항목이 있다).

### 구분 (H) — 6종

`정상` / `비정상` / `표시` / `엣지` / `인터랙션` / `부수`. **신규 값 금지.**
**지배 구분과 목표 분포는 프로파일**에 있다 — VIOLA는 `표시` 56%, TROMBONE은 `정상` 65%로 **정반대다.**

**생성 분포 기준:** 프로파일의 실측 분포가 케이스 생성 시의 목표다 (`testcase-generator` 1-0).
±15%p 이상 벗어나면 사유를 기재한다.

> **하드코딩 금지.** 2026-08-24 기준선 측정에서 VIOLA 분포를 스킬 본문에 하드코딩한 탓에
> TROMBONE 출력이 `정상` **−44.9%p** / `표시` **+29.4%p** 편차를 냈다. 분포는 항상 프로파일에서 읽는다.

### 3 Depth (K)

enum 범위는 **프로파일**. 공통 규칙만 여기 둔다:

- `X > Y > Z` 세분화 표기 **금지** (전 제품 사례 0건)
- 프로파일의 허용 목록 밖 값을 임의로 도입하지 않는다 — 분류 불가 화면은 팀 리더 확인

### 실제 결과 (R)

**enum이 아니다.** `PASS`/`FAIL`/`N/A`/`BLOCK` 을 임의로 채우지 않는다. **신규 작성 시 공란.**

## 검증 단위 — atomic (전 제품 확정)

**검증 항목 1개 = TC 1건.** 여러 동작을 한 TC에 묶지 않는다 (시나리오 금지).

| 지표 | 목표 |
|------|------|
| 절차 평균 단계 수 | **1.0대** — 1단계 원칙, 불가피할 때만 2~3단계 |
| 예상 결과 | 1줄 원칙, 하위 항목 필요 시 `ㄴ` 추가 |
| 사전조건 | **1줄** (줄바꿈 금지) |

실측 참고 — VIOLA에서 단일 화면 하나가 **49건**으로 분해된 사례가 있다
(Breadcrumb / 탭 / 선택기 / 컬럼 구성 / 컬럼별 sort 9건 / 상태 tag 4종 / 일시 형식 / 0건 상태 / 페이지네이션 …).

## 표기 컨벤션 — 공통

### 절차 번호 접두

- **`1. ` 접두 100%** — 숫자 + 마침표 + 공백 1칸. 예외 없음 (전 제품 공통)
- 다단계는 셀 내 줄바꿈 후 `2. `, `3. `
- 종결: **동작 체언** — `~확인`(최다), `~클릭`, `~진입`, `~선택`, `~입력`, `~시도`

### 예상 결과 어조와 `ㄴ`

- **명사형 종결** — `~표출`·`~노출`·`~출력`·`~이동`·`~정렬`·`~불가`·`~처리`
- **「~된다」「~한다」 서술형 종결 금지**
- 하위 항목: 1줄 요약 → 줄바꿈 → **`ㄴ ` (한글 니은 + 공백 1칸)** + 하위 항목
- 번호(`1.`)·불릿(`-`, `•`)은 예상 결과에 **사용하지 않는다**

### UI 라벨 표기 — **프로파일마다 정반대다**

| 제품 | UI 라벨 | 백틱 |
|------|---------|------|
| VIOLA · BootFactory | **백틱** `` `등록` `` | 절차 65% / 예상 결과 52% |
| TROMBONE | **대괄호** `[등록]` | **절차 0.0% (0/3,953)** — 형식 문자열에만 소량 |

**이 하나만 틀려도 케이스 전체가 다른 팀 것처럼 보인다.** 프로파일을 반드시 확인하라.

공통 규칙: **기획서 원문 그대로 인용한다.** 오탈자도 원문대로 쓰고 `[오타 의심]`을 피드백에 남긴다.

### `-` (No data) vs 빈칸 — 가장 자주 틀리는 구분

| 위치 | 표기 |
|------|------|
| **L(`4 Depth`) / M(`5 Depth`)** | **`-`** — 계층 미사용 명시. 빈칸 아님 |
| 예상 결과 본문 | 백틱으로 감싼다 — `` `-` 표출 ``, `` No-data 마커 `-` 노출 `` |
| **D·E·R·S·T·U** (`요구사항 ID`·`기능 ID`·`실제 결과`·`수행자`·`수행일자`·`Jira`) | **빈칸** — `-` 아님 |
| N(`사전조건`) · O(`테스트 데이터`) | 프로파일 참조 (불필요하면 빈칸, `-` 아님) |

### 일시·날짜 형식

- 기본형 **`yyyy-mm-dd hh:mm:ss`** (소문자 시분초)
- 기획서 원문이 대문자면 원문을 인용하고 피드백에 표기 불일치를 기재

### 화면 ID — 공통 원칙

- **기획서 스펙 페이지의 화면 식별자를 원문 그대로 기입한다.** 필드명·패턴은 프로파일
- **구분자·형식을 임의로 통일·변환하지 않는다.** 비정규 값도 기획서 원문이면 그대로
- **유추로 만들지 않는다.** 기획서에서 직접 확인한다
- 예상 결과에서 화면 이동을 서술할 때 목적 화면 ID를 괄호로 인용

### 팝업 처리 — 공통

- 팝업은 **`2 Depth` 에 별도 값으로 분리** (예: `스케줄 삭제 팝업`)
- 화면 ID는 팝업 고유 ID가 있으면 그것을, 없으면 **모(母) 화면 ID 승계**
- 한 화면이 여러 스텝을 가지면 `(1/2)`, `(2/2)` 접미로 `2 Depth` 분리
- 팝업의 `3 Depth` 는 **프로파일** (VIOLA는 `상세` 고정, TROMBONE은 화면 성격에 따름)

> **`2 Depth` 는 페이지 제목을 옮겨 적는 칸이 아니라 케이스를 찾는 색인이다.**
> 한 페이지에 팝업 여러 종이 있으면 페이지 제목 하나로 묶지 말고 팝업별로 나눈다
> (2026-09-01 실측: 팝업 4종 19행이 페이지 제목 하나에 묶여 권한 변경 팝업 12행을 찾을 수 없었다).

## 비고(V) / 피드백(W) — 역할 분리

**두 열의 역할은 명확히 분리된다. 근거 태그를 피드백 열에 쓰면 열 오배치다.**
(2026-08-24 기준선 측정에서 212행 27.8%가 이 오류였다)

| 열 | 이름 | 역할 |
|----|------|------|
| **V** | `비고` | **근거 태그** — 이 케이스가 기획서 어디에서 나왔는가. **실질 필수, 비우지 않는다** |
| **W** | `피드백` | **확인사항 태그** — 기획 확인이 필요한 사항, 불일치. 해당 없으면 공란 |

### 비고 = 근거 태그

| 태그 | 용도 |
|------|------|
| `[DESC N항]` / `[DESC N항-N]` / `[DESC N항-N-a]` | Description **항목 계층** 번호 근거 (최다) |
| `[DESC D{페이지}-{항목}]` | Description **페이지 기반** 번호 근거 — `[DESC D2-5]` = p2의 5번 항목 |
| `[공통 DESC CN]` | 여러 페이지 공통 Description 근거. **C-ID 정의표가 분석서에 있어야 한다** |
| `[UI]` | 화면 mock 근거 (Description에 없는 요소). **페이지 번호 병기** — `[UI] p79 메트릭` |
| `[스티커]` / `[스티커A]` / `[스티커B]` | 기획서 콜아웃 메모 근거 |
| `[강조]` | 기획서 강조 표기(빨간 볼드 등) 근거 |
| `[전 화면 공통]` | 화면 무관 공통 정책 |
| `[확인 불가 기반]` | 확인 불가 항목에서 파생된 케이스 |

- 태그 뒤에 **한 줄 설명을 덧붙인다** — `[DESC 1항] 클릭 시 생성 페이지로 이동`
- 다중 조합 가능 — `[DESC 2항-8-a] [공통 DESC C2] 수정/삭제 작업 정의`

### 피드백 = 확인사항 태그

| 태그 | 용도 |
|------|------|
| `[확인 불가]` | 기획서에 정의가 없어 판정 불가. 대부분 `— 기획 확인 필요` 로 종결 |
| `[기획 확인]` | 기획 확인이 필요한 사항 (TROMBONE 최다 태그) |
| `[UI↔DESC 불일치]` | UI mock과 Description이 상충 |
| `[변경 여부 불확실]` | 변경분인지 기존 UI인지 확정 불가 |
| `[오타 의심]` | 기획서 원문 오타 추정 |
| `[디자인 미반영]` | 디자인 미반영본과 정본 차이 |
| `[판독 주의]` / `[판독 불가]` | 이미지 판독 품질 이슈 (`prd-analyzer` 품질 게이트) |

**서술 패턴:**

- 불일치는 **양쪽 표기를 모두 인용하고 `/` 로 대비** — `UI: … / DESC 2항-3-b: …`
- 종결부에 요구 액션 명시 — `— 기획 확인 필요`, `— 표기 통일 확인 필요`, `— 확정값 확인 필요`
- 기획 미정의 항목은 **예상 결과에도 반영**한다:
  `ㄴ 기획 미정의 항목 — PASS/FAIL 판정 대신 실측 상태를 [실제 결과]에 기재`

> **⚠️ 자기모순 금지.** 예상 결과를 단정해 놓고 피드백에 `[확인 불가]` 를 적으면 **실행자가
> PASS/FAIL을 내려 버린다.** 기획이 정하지 않은 것은 예상 결과에서도 단정하지 않는다.

## 공통 DESC C-ID는 **공유 키**다 — 소진되는 번호가 아니다

`[공통 DESC CN]` 의 목적은 **여러 위치에 걸친 하나의 정의를 잇는 것**이다. TC ID나 `No` 처럼
쓰면 없어지는 순번이 아니다. 실무에서 **양방향으로 다 틀렸던 이력이 있으니** 둘 다 피한다.

| 잘못된 방향 | 무슨 일이 벌어지나 | 실제 사고 |
|------------|-----------------|----------|
| **번호를 나눠 쓴다** — 챕터마다 새 번호 | 같은 변경에 `C1`·`C2` 가 따로 붙어 **같은 것을 두 번 정의**한다. 시트에서 `C1` 로 검색해도 다른 챕터 행이 안 잡혀 연결이 끊긴다 | 2026-08-27: *"`C1` 이 소진됐으니 다음 챕터는 `C2`"* 로 판단 |
| **번호를 겹쳐 쓴다** — 챕터마다 `C1` 부터 재시작 | 서로 **다른** 정의가 한 탭에서 같은 `C1` 을 쓴다. 역추적이 어느 정의인지 가리지 못한다 | 2026-08-25: ch03·ch04가 `C5` 를 각각 다른 뜻으로 사용 (12행 충돌) |

### "하나의 정의"의 판단 기준 — 내용 유사성이 아니라 **기획서의 상호 참조**

| | 하나의 정의 (같은 C-ID) | 병렬 변경 (연결 안 함) |
|---|---|---|
| 판단 근거 | **기획서에 명시적 상호 참조가 있다** (`… > N항 참고`, `… 와 동일하게 제공`) | 각 화면에 **독립한 근거**가 따로 있다 (각각의 스티커, 문구도 다름) |
| 처리 | 양쪽 대표 행에 같은 `[공통 DESC CN]` | 각자 자기 CH-ID로만 관리 |

**기획서가 잇지 않은 것을 이어 붙이면 기획서에 없는 관계를 단정하는 것이다.**
일자·회차·변경 내용이 같아도 상호 참조가 없으면 병렬 변경으로 둔다 — 한쪽 기획 회신이
다른 쪽에 자동 적용된다고 볼 근거가 없다.

**규칙:**

1. **C-ID는 탭 전역에서 정의 단위로 유일하다.** 같은 정의 = 같은 번호, 다른 정의 = 다른 번호
2. **하나의 정의가 여러 챕터·화면에 걸치면 그 전부가 같은 번호를 단다.** 이것이 태그의 본래 용도다
3. **새 번호는 새 정의가 나올 때만 부여한다.** 챕터가 넘어간다고 번호를 올리지 않는다
4. **정의표 없는 C-ID를 시트에 쓰지 않는다** — 역추적이 끊겨 태그가 무의미해진다
5. **여러 챕터를 한 탭에 쓰는 경우 배정은 오케스트레이터가 한다.** 분석 담당은 자기 분석서 안에서
   `C1` 부터 매기고 *"시트 배정은 조정 대상"* 임을 명시한다. 오케스트레이터는 **모든 챕터 분석을
   받은 뒤 한 번에 배정한다** (순차 배정이 2026-08-25 충돌의 직접 원인이었다)

### DESC 번호 두 체계 — 섞지 말고 분석서를 따른다

`[DESC N항-N]`(항목 계층)과 `[DESC DN-N]`(페이지 기반)은 **번호의 축이 다르다.**
`[DESC 2항-5]`의 `2`는 항목 번호이고, `[DESC D2-5]`의 `2`는 **페이지 번호**다.

- **분석서가 쓴 체계를 그대로 따른다.** 기계 변환하면 기획서에 없는 계층을 단정하게 된다
- **한 탭 안에서 두 체계를 섞지 않는다**
- 어느 쪽이든 **태그만 보고 분석서의 해당 항목으로 역추적이 되어야 한다** — 그것이 이 태그의 목적이다

### CH-ID 네임스페이스

챕터별 분석서가 CH-ID를 제각기 매기면 한 탭에서 충돌한다. **`CH{챕터2자리}-N`** 형식으로 통일한다
(`CH01-1`, `CH02-1`). 챕터가 하나뿐이어도 규칙을 지킨다.

## 변경분 모드 태그 (기획서 유형 = `변경` 일 때)

기획서 유형과 예외 항목 규칙은 `testcase-auto` Phase 0 및 `prd-analyzer` PDF-3.5 참조.

### 비고 — 변경분 전용 태그

| 태그 | 용도 |
|------|------|
| `[변경 CH{NN}-N {종류} {회차}-{일자}]` | **CH-ID 필수.** 변경 챕터 ID + 종류 원문 + 회차 + 일자. 예: `[변경 CH01-3 신규추가 v2-26.08.18]` |
| `[DESC 전용]` | Description에만 변경 표기가 있고 **화면에 변경 박스가 없는** 항목 |
| `[스티커 전용]` | `변경사항` 스티커에만 있고 **Description 변경 표기가 없는** 항목 |
| `[ChangeLog]` | 페이지의 `ChangeLog` 패널이 근거. 스티커·DESC에 대응이 없고 **이 패널에만** 있는 항목 |
| `[DESC + 박스 + 스티커]` / `[박스 + 스티커]` / `[DESC + UI 밴드 + 스티커]` | **경로 병기** — 변경 표기가 **둘 이상**의 경로에 있을 때. `[… 전용]` 이 "한쪽에만"을 뜻하는 것과 대비 |

**변경 종류 어휘 (실측):** `신규추가` / `문구수정` / `필드순서변경` / `문구삭제-위치변경` / `문구위치변경` / `디자인변경` / `명칭 변경` / `삭제`

**⚠️ 태그 형식은 종류 원문에 맞춘다.** 종류 원문이 다어절이면 회차와 붙어 읽히지 않도록 띄운다
(`[변경 CH01-1 명칭 변경 v1-26.07.31]`). CH-ID·종류 원문·회차·일자가 모두 남으면 된다.

**미표기 처리 — `-` 를 쓰지 않는다:**

| 상황 | 표기 |
|------|------|
| 날짜를 확인할 수 없음 | **`날짜미표기`** (`-` 금지 — Depth의 No-data 의미와 충돌) |
| 기획서가 **변경 종류를 원문에 적지 않음** | **`종류 원문 미표기`** |

> **표시색으로 변경 종류·회차를 추정해 채우지 않는다.** 색은 종류를 뜻하지 않고, 색↔회차 대응도
> 판본마다 어긋난다 (실측: 한 문서에서 빨강 `26.08.03` / 파랑 `26.08.18` 인데 다른 페이지는 파랑이 `26.08.04`).
> 권위는 **주석 원문**(`v2수정`/`v2추가`/`v2삭제` + 날짜)이다.

### 피드백 — 변경분 전용 태그

| 태그 | 용도 |
|------|------|
| `[변경 표기 불일치]` | 변경 표기 경로(박스 / 스티커 / DESC / `ChangeLog`)가 서로 충돌하거나, 한 경로에 미등재. **판단하지 않고 양쪽을 기록한다** |

**`ChangeLog` 미등재 처리:** 다른 경로에서 찾은 변경분이 `ChangeLog` 에 없으면 이 태그로 기록하되
**미등재를 이유로 변경분을 탈락시키지 않는다.** 이 패널은 작성 시점 스냅샷일 뿐 완전한 목록이 아니다
(실측: 34건 중 15건 미등재, 스티커 최신 일자가 `ChangeLog` 최신 일자보다 뒤인 사례).
**`ChangeLog` 패널이 아예 없는 페이지의 변경분에는 이 태그를 붙이지 않는다** — 패널이 있는데
등재되지 않은 것과, 패널이 없어 대조 대상이 아닌 것은 다르다.

## 탭 구조 / 작성 절차

- 탭 분할 기준 = **기능 챕터 / 모듈 / 변경분 단위** (릴리즈별·작성자별 아님)
- 모든 탭의 1행 헤더는 **A~W 23컬럼 동일**
- `No` 는 탭별 재시작. TC ID 연속 범위는 프로파일

**빈 시트·신규 탭에 작성하는 절차:**

1. `add_tab` 으로 대상 탭 생성
2. **생성 직후 `metadata` 를 호출해 돌아온 `title` 문자열을 복사**해 이후 모든 range 에 쓴다
   — 한글 탭 이름이 NFD 분해형으로 저장되면 조합형으로 타이핑한 같은 문자열이
   HTTP 400 `Unable to parse range` 로 실패한다. 화면상 구분이 되지 않는다
3. `write` — `'{탭명}'!A1:W1` 에 **헤더 원문** 기입 (23개)
4. `append` — 2행부터 케이스 batch 1회 전송
5. `updatedRange` 확인 후 보고
6. 빈 기본 탭(`시트1` 등)은 API로 삭제할 수 없다 → 사람이 수동 정리

> `sheets_api.py` 의 write/append 기본값은 **RAW** 다. `-`·`1. ` 접두·`2026-01-02` 가
> 날짜·수식으로 변환되지 않도록 `--user-entered` 를 쓰지 않는다.
> CLI 하위 명령은 **`metadata`** 다 (`get_metadata` 는 Python 메서드명이며 CLI에 없다).

## 새 케이스 작성 시 암묵 규칙 (공통 요약)

1. **컬럼 23개 순서 고정.** X열 이후 쓰지 않는다
2. **`비고` 를 비우지 않는다.** 근거 태그 필수
3. **`요구사항 ID`·`기능 ID`·`실제 결과`·`수행자`·`수행일자`·`Jira` 는 공란.** `PASS` 등을 임의로 채우지 않는다
4. **`4 Depth`·`5 Depth` 는 `-`**
5. **구분 6종·우선순위 4종을 모두 사용한다.** `P4`·`부수` 누락 금지
6. **atomic 유지** — 절차 1단계, 예상 1~2줄, 사전조건 1줄
7. **화면 ID는 기획서 원문.** 구분자 통일 금지, 유추 금지
8. **기획서 미정의 항목도 케이스로 만든다** — 피드백에 `[확인 불가] … — 기획 확인 필요`
9. **UI↔DESC 불일치는 케이스로 만들고 양쪽을 대비 인용**
10. **팝업은 `2 Depth` 분리 / 화면 ID 모 화면 승계**
11. **예상 결과 종결은 명사형.** 「~된다」 금지
12. **UI 라벨 표기는 프로파일을 확인한다** — 백틱과 대괄호가 제품마다 정반대다
