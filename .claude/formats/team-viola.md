# 팀 양식 사양 — VIOLA 테스트케이스

이 파일은 **테스트 케이스 작성 양식의 기준(사양)** 이다. 매 실행마다 참고 시트를 다시 분석하지 않고
이 사양을 사용한다. 참고 시트는 **사양을 갱신할 때만** 읽는다.

## 메타

| 항목 | 값 |
|------|-----|
| 사양 이름 | `team-viola` |
| 사양 버전 | **1.3** (2026-08-25 **관리대상 컬럼(C) 신설 — 23→24컬럼**) |
| 측정일 | 2026-08-21 |
| 측정 대상 | VIOLA V4.0 테스트케이스 (탭 2개) |

**갱신 시 `CLAUDE.md` 변경 이력에 날짜·대상·사유를 기록한다.** 양식 변경은 케이스 품질 변경이다.

## 권위 규칙 — 사양과 대상 시트가 충돌할 때

케이스를 쓰기 전 `sheet-analyst`가 **대상 시트의 헤더 1행 + 마지막 20~50행**을 읽어 이 사양과 대조한다.
충돌 시 무엇이 이기는지는 항목별로 다르다.

| 항목 | 권위 | 근거 |
|------|------|------|
| 컬럼 구조·순서·이름 | **대상 시트** | 어긋나면 값이 엉뚱한 칸에 들어간다. 사후 복구가 가장 비싸다 → **불일치 시 작성 중단 + 사용자 확인** |
| TC ID 마지막 번호 | **대상 시트** | 계속 자라는 값. 사양에 고정값을 두지 않는다 |
| enum 허용값 | **사양 기준** | 단 시트에 사양 외 값이 있으면 **보고 후 진행 여부 확인** (오타일 수도, 신규 enum일 수도) |
| 문체·검증 단위·미사용 컬럼 정책 | **사양** | 실행마다 흔들리면 안 되는 값 |

### 이 사양이 낡았는지 알아내는 능력의 한계

드리프트 검증(`sheet-analyst` 모드 A)은 **대상 시트 헤더 1행 + 마지막 20~50행**만 읽는다.
그래서 잡히는 변화와 잡히지 않는 변화가 나뉜다. **잡히지 않는 쪽을 알고 있어야 한다.**

| 팀 시트의 변화 | 드리프트 검증이 잡는가 |
|----------------|---------------------|
| 컬럼 추가·삭제·이름 변경·순서 변경 | **잡는다** (헤더 대조, Critical) |
| TC ID가 늘어남 | **잡는다** (꼬리에서 실측) |
| 사양에 없는 enum 값 등장 | **잡는다** (꼬리 표본에 나타나면, Major) |
| **문체 전환** — 예상 결과 명사형 → 서술형(「~된다」), 절차 `N. ` 접두 폐지, `ㄴ` 대신 불릿 사용 | **잡지 못한다** |
| **검증 단위 전환** — atomic → scenario (절차 4단계 이상, 예상 결과 다항목) | **잡지 못한다** |
| **미사용 컬럼 사용 시작** — `요구사항 ID`·`테스트 데이터` 등을 팀이 채우기 시작 | **잡지 못한다** |
| 표기 규칙 변경 — `-` 사용 위치, 백틱 사용 관행 | **잡지 못한다** |

**왜 못 잡는가:** 이 값들은 헤더에 나타나지 않는다. 꼬리 표본(가장 최근 행)에 단서가 보일 수는
있으나, **모드 A의 판정 항목이 헤더·enum·마지막 ID 세 가지로 한정되어 있어 점검하지 않는다.**
데이터는 손에 있고 규칙이 없는 상태다 — 의도적 범위 제한이며, 여기가 이 사양의 사각지대다.

**그래서 다음 신호가 보이면 사양을 갱신한다** (`"참고 시트로 양식 사양 갱신해줘"` + 참고 시트 URL):

- 리뷰에서 **문체·검증 단위 관련 위반이 반복 지적**된다 (사양이 맞고 시트가 바뀐 경우일 수 있다)
- 팀원이 양식·작성 방식을 바꿨다고 말한다
- 위 메타의 **측정일이 오래됐다** — 그 사이 팀 시트가 얼마나 자랐는지 확인해 볼 가치가 있다
- 생성된 케이스가 기존 행과 나란히 놓였을 때 이질적으로 보인다

갱신 전이라도, 리뷰에서 문체 위반이 반복되면 **사양과 시트 중 어느 쪽이 최신인지 사람이 판단해야
한다.** 사양을 무조건 정답으로 두고 시트를 고치라고 하지 않는다.

## enum

### 관리대상 (C) — 3종

`K8S` / `CI·CD` / `BF(공통)`. 상세는 위 "관리대상 컬럼" 절. **팀 실측 근거가 없는 신설 enum이다** (2026-08-25).

### 우선순위 (H) — 4종, 신규 없음

`P1` / `P2` / `P3` / `P4`. 측정 분포: P3 74.9% · P2 13.0% · P4 6.9% · P1 5.1%.
`P0`/`P5`/`High`·`Low` 등장 0건.

### 구분 (I) — 6종, 신규 없음

`표시` / `엣지` / `인터랙션` / `부수` / `정상` / `비정상`.
측정 분포: 표시 55.9% · 엣지 14.5% · 인터랙션 11.2% · 부수 6.9% · 정상 6.3% · 비정상 5.1%.

> `표시`가 과반(56%)인 것이 이 양식의 지배적 특징이다. **`표시`가 적으면 커버리지 부족 신호.**

**생성 분포 기준:** 위 실측 분포가 케이스 생성 시의 목표다 (`testcase-generator` 1-0).
지배 구분은 **`표시`** 이며, UI 표출을 요소 단위로 잘게 쪼개는 것이 이 양식의 정상 상태다.
±15%p 이상 벗어나면 사유를 기재한다.

### 구분 × 우선순위 결합 규칙 (실측 근거)

| 구분 | 우선순위 | 강도 |
|------|---------|------|
| `부수` | **항상 `P4`** | 23/23, 예외 0건 |
| `정상` | `P1` 또는 `P2` | `P3`/`P4` 사례 **0건** |
| `비정상` | `P2` 기본 | P2(13) / P3(4) |
| `표시` / `인터랙션` / `엣지` | `P3` 기본 | `표시`에 `P1` 부여 사례 **0건** |

`P1`은 `정상`·`인터랙션`에만 등장한다. 기준은 비즈니스 임팩트가 아니라
**"이 검증이 깨지면 다음 화면으로 갈 수 없는가"** 다.

### 3 Depth (L) — 4종, 단순 분류

`목록` / `생성` / `수정` / `상세` 중 택일.

- 팝업·모달·다이얼로그 → `상세`
- `X > Y > Z` 세분화 표기 **금지** (사례 0건)
- `등록`/`검색`/`-` 는 사용 사례 0건 → 신규 도입 금지 (분류 불가 화면은 팀 리더 확인)

## TC ID 체계

- 형식: `TC_VIO_{3자리 zero-padded}` — 예외 0건
- **탭 경계를 무시하고 전역 연속.** 결번·중복 0건
- `No`(A열)는 **탭별 1부터 재시작** (TC ID와 다르게 동작)
- **화면(2 Depth) 단위로 연속 블록 부여** — 화면별로 모아서 번호를 매긴다
- **마지막 번호는 사양에 고정하지 않는다.** 대상 시트 실측값 + 1 부터 시작

## 화면 ID (G열) 표기

측정 시점에 **두 가지 구분자 패턴이 혼재**했다 — 정규화되어 있지 않다.

| 패턴 | 예 |
|------|-----|
| `VIOE-NN_NN_NN_NN` (언더스코어 3) | `VIOE-03_01_04_13` |
| `VIOE-NN_NN_NN-NN` (언더스코어 2 + 하이픈) | `VIOE-02_01_01-11` |

- **규칙: 기획서 스펙 페이지 우측 상단의 화면 식별자를 원문 그대로 기입한다.**
  필드명 우선순위는 `Page ID` → `Screen ID` → 기타. 구분자를 임의로 통일·변환하지 않는다.
- 패턴 차이는 기획서 원문 표기 차이가 반영된 결과다. 한 시트에 섞여도 정상.
- **화면 ID를 유추로 만들지 않는다.** 기획서에서 직접 확인한다.
- 예상 결과에서 화면 이동을 서술할 때 목적 화면 ID를 괄호로 인용:
  `HPA 스케줄 생성 화면(VIOE-03_01_04_14)으로 이동`

### 팝업 처리 컨벤션

- 팝업은 **2 Depth에 별도 값으로 분리** (예: `스케줄 삭제 팝업`)
- 팝업의 **화면 ID는 모(母) 화면 ID를 그대로 승계**
- 팝업의 3 Depth는 `상세`
- 한 화면이 여러 스텝을 가지면 `(1/2)`, `(2/2)` 접미로 2 Depth를 분리

## 관리대상 컬럼 (C) — `K8S` / `CI·CD` / `BF(공통)`

VIOLA는 **관리대상이 갈린다.** 같은 화면·같은 기능이라도 어느 관리대상에 속하는지가 검증 조건
(권한 범위·리소스 종류·집계 대상)을 바꾼다. **2026-08-25부터 C열 전용 컬럼에 쓴다.**

### enum — 3종

| 값 | 대상 | 판정 신호 |
|----|------|----------|
| **`K8S`** | 쿠버네티스 관리 영역 | Breadcrumb `Kubernetes Engine` / 리소스 어휘 `파드`·`디플로이먼트`·`데몬셋`·`네임스페이스`·`클러스터` / `클러스터 관리` 권한 |
| **`CI·CD`** | 빌드·배포 관리 영역 | Breadcrumb CI/CD 계열 / 리소스 어휘 `파이프라인`·`빌드`·`배포 이력`·`아티팩트` |
| **`BF(공통)`** | BootFactory 플랫폼 공통 — 관리대상과 무관하게 동작하는 영역 | 기획서에 **`BootFactory` 정책 참조가 명시**된 화면·기능. 로그인·솔루션 진입·테넌트 선택 등 플랫폼 레벨 |

**신규 값을 임의로 만들지 않는다.** 세 값으로 분류되지 않는 화면이 나오면 팀 리더에게 확인한다.

### 판정 단위는 **화면이 아니라 케이스**다

이 컬럼은 행 단위 값이다. **한 화면 안에서도 케이스마다 관리대상이 갈릴 수 있다.**

전형적인 예가 클러스터 선택 팝업이다 — 팝업의 **호출 맥락**(로그인 직후 진입, 솔루션 간 이동)은
BootFactory 정책이지만, 팝업이 **다루는 대상**(클러스터 목록, `클러스터 관리` 권한, 멀티 클러스터
대시보드 이동)은 K8s다. 화면 하나를 통째로 한 값에 몰아넣으면 둘 중 하나가 틀린다.

**판정 질문:** *"이 케이스가 검증하는 대상이 무엇인가"* — 화면이 어디 있는지가 아니다.

| 케이스가 검증하는 것 | 값 |
|--------------------|-----|
| 화면 진입 조건, 플랫폼 정책, 로그인·테넌트 흐름, 관리대상 무관 공통 컴포넌트 | `BF(공통)` |
| K8s 리소스·권한·목록·필터 | `K8S` |
| 빌드·배포 리소스·권한·이력 | `CI·CD` |

### 판정 근거와 그 강도

관리대상은 **기획서에서 근거를 찾아 판정한다. 제품 지식으로 추론해 채우지 않는다.**

| 근거 | 강도 | 처리 |
|------|------|------|
| Breadcrumb 최상위 / 관리대상 명시 문구 / `BootFactory 정책에 따름` 류 명시 참조 | **강** | 확정 |
| 관리대상 고유 리소스 어휘만 존재 | 중 | 확정하되 근거 어휘를 분석서에 남긴다 |
| 어휘 계열 추정만 가능 (Breadcrumb 없는 팝업·공통 정의 페이지) | **약** | 값은 채우되 **피드백 열에 `[관리대상 범위 확인]`** 으로 확인을 요구한다 (기재 범위는 아래) |
| 근거 전무 | — | 사용자에게 관리대상을 확인한다. **빈칸으로 두지 않는다** (C는 필수) |

**강도 `약` 태그의 기재 범위** — 해당 화면의 전 행에 같은 문구를 반복하지 않는다. **판정 결과가
관리대상 범위에 실제로 종속되는 행**(권한 개수·권한 범위·집계 대상이 판정 기준인 행, CH별 대표
표출 행)에만 기재한다. 전 행에 도배하면 실제 확인 요구가 노이즈에 묻힌다 — 관리대상 컨텍스트
자체는 C열에 전 행 있으므로 추적성은 유지된다. (2026-08-25 명문화)

**근거 없는 관리대상 케이스를 만들지 않는다.** 기획서에 한쪽 관리대상만 나오면 그 한쪽만 작성하고,
다른 쪽 적용 여부는 피드백 열에 `[관리대상 범위 확인]` 으로 남긴다. 실행자가 판정할 수 없는
케이스를 늘리는 것보다, 확인 요구를 정확히 남기는 것이 낫다.

### 다른 컬럼에 중복해 쓰지 않는다

C열이 생기기 전에는 `1 Depth`·사전조건·비고에 관리대상을 녹여 썼다. **이제 하지 않는다.**

| 열 | 규칙 |
|----|------|
| **B `솔루션`** | `VIOLA` 고정. `VIOLA_K8S`·`VIOLA_CICD` 접미사 분리는 실측 0건 |
| **O `사전조건`** | `` 관리대상 `K8S` `` 접두를 **붙이지 않는다.** C열과 중복이고 1줄 제약을 잡아먹는다 |
| **W `비고`** | `[관리대상 K8S]` 태그를 **붙이지 않는다.** 근거 태그만 쓴다 |
| **K `2 Depth`** | 화면명 = 기획서 페이지 제목. `[K8S]` 접두를 붙이지 않는다 |

**`J 1 Depth` 는 예외** — Breadcrumb 최상위 원문(`Kubernetes Engine` 등)을 그대로 유지한다.
C열과 값이 겹쳐 보여도 **의미가 다르다**: C는 *관리대상 분류*, `1 Depth`는 *기획서 메뉴 계층 원문*.
(2026-08-25 사용자 판단)

### 관리대상 컬럼과 구 양식 탭 (드리프트 검증 시)

**팀 원본 시트는 여전히 23컬럼(관리대상 없음)이다.** 대상 탭이 구 양식이면 헤더 대조에서
차이가 나는데, 이것은 **컬럼이 밀린 오류가 아니라 양식 세대 차이**다. Critical로 중단하지 말고
아래처럼 판정한다.

| 대상 탭 상태 | 판정 | 처리 |
|-------------|------|------|
| 헤더 24개, C가 `관리대상` | 신 양식 | 그대로 작성 |
| 빈 탭 / 신규 탭 | — | **신 양식(24컬럼) 헤더를 생성** |
| 헤더 23개, 나머지가 사양과 일치 | **구 양식 탭** | **사용자에게 묻는다** — ① C열 삽입 후 진행 ② 23컬럼으로 작성(관리대상 생략) |
| 헤더가 위 어디에도 안 맞음 | 진짜 불일치 | **Critical — 작성 중단 + 사용자 확인** |

구 양식 탭에 24컬럼 행을 그냥 append하면 **모든 값이 한 칸씩 밀린다.** 반드시 먼저 판정한다.

| 지표 | 측정값 |

## 표기 컨벤션

### 절차(Q) 번호 접두

- **`1. ` 접두 100%** — 숫자 + 마침표 + 공백 1칸. 예외 없음
- 2단계면 셀 내 줄바꿈 후 `2. `
- 종결: 동작 체언 — `~확인`(최다), `~클릭`, `~진입`, `~선택`, `~호버`, `~시도`
- 평균 24자

### 예상 결과(R) 어조와 `ㄴ`

- **명사형 종결 100%** — `~표출`(압도적), `~이동`, `~정렬`, `~삭제`, `~전환`, `~불가`, `~처리`.
  「~된다」「~한다」 서술형 종결 **0건**
- 하위 항목: 1줄 요약 → 줄바꿈 → **`ㄴ ` (한글 니은 + 공백 1칸)** + 하위 항목. **최대 1개**
- 용도: ① 부가 조건 ② 열거 ③ 선택 상태
- 번호(`1.`)·불릿(`-`, `•`)은 예상 결과에 사용하지 않는다

### 백틱 코드 표기

- 사용률: 예상 결과 52%, 절차 65%
- 감싸는 대상: UI 레이블·버튼명·컬럼명·상태 enum·메시지 원문·형식 문자열
- **기획서 원문 그대로 인용한다.** 오탈자도 원문대로 쓰고 `[오타 의심]`을 피드백에 남긴다

### `-` (No data) 사용 위치

| 위치 | 표기 |
|------|------|
| M(4 Depth) / N(5 Depth) | **`-`** — 계층 미사용 명시. 빈칸 아님 |
| 예상 결과 본문 | 백틱으로 감싼다 — `` `-` 표출 ``, `` `No data (-)`로 표출 `` |
| E/F/P/S/T/U/V | **빈칸** — `-` 아님 |
| C(관리대상) | **`-` 금지.** 필수 enum 3종 중 하나 |

### 일시·날짜 형식

- 기본형 **`YYYY-MM-DD hh:mm:ss`** (소문자 시분초)
- 기획서 원문이 대문자면 원문을 인용하고 피드백에 표기 불일치를 기재
- 리소스명 규칙에 `yymmdd-hhmmss` 사례 있음

## 비고(W) / 피드백(X) 태그 컨벤션

두 열의 역할이 명확히 분리되어 있다.

### W열 = 비고 (근거 태그) — 실질 필수

| 태그 | 용도 |
|------|------|
| `[DESC N항]` / `[DESC N항-N]` / `[DESC N항-N-a]` | 기획서 Description **항목 계층** 번호 근거 (최다) |
| `[DESC D{페이지}-{항목}]` | 기획서 Description **페이지 기반** 번호 근거 — `[DESC D2-5]` = p2의 5번 항목. 분석서가 페이지 단위로 항목을 번호화한 경우 사용 |
| `[공통 DESC CN]` | 여러 페이지 공통 Description 근거. **C-ID(C1·C2 …)가 무엇을 가리키는지 분석서에 정의표가 있어야 한다** — 없으면 시트에서 역추적이 끊긴다 |
| `[UI]` | 화면 mock 근거 (Description에 없는 요소). **페이지 번호 병기** — `[UI] p79 메트릭` |
| `[스티커]` / `[스티커A]` / `[스티커B]` | 기획서 콜아웃 메모 근거 |
| `[강조]` | 기획서 강조 표기(빨간 볼드 등) 근거 |
| `[변경 CH-N {유형} vN추가-YY.MM.DD]` | **변경분 전용** — 변경 챕터 ID + 유형 + 릴리스 일자 |
| `[전 화면 공통]` | 화면 무관 공통 정책 |
| `[확인 불가 기반]` | 확인 불가 항목에서 파생된 케이스 |

### DESC 번호 두 체계 — 섞지 말고 분석서를 따른다

`[DESC N항-N]`(항목 계층)과 `[DESC DN-N]`(페이지 기반)은 **번호의 축이 다르다.**
`[DESC 2항-5]`의 `2`는 Description 항목 번호이고, `[DESC D2-5]`의 `2`는 **페이지 번호**다.

- **분석서가 쓴 체계를 그대로 따른다.** 한쪽을 다른 쪽으로 기계 변환하면 기획서에 없는 계층을
  단정하게 된다 (2026-08-24 리뷰에서 확인된 결론).
- 한 탭 안에서 두 체계를 섞지 않는다. 분석서가 페이지 기반이면 그 탭은 전부 `[DESC DN-N]`.
- 어느 쪽이든 **태그만 보고 분석서의 해당 항목으로 역추적이 되어야 한다.** 그것이 이 태그의 목적이다.

- 태그 뒤에 **한 줄 설명을 덧붙인다** — `[DESC 1항] 클릭 시 생성 페이지로 이동`
- 다중 조합 가능 — `[DESC 2항-8-a] [공통 DESC C2] 수정/삭제 작업 정의`
- 변경 유형 어휘(실측): `신규추가` / `문구수정` / `필드순서변경` / `문구삭제-위치변경` / `문구위치변경` / `디자인변경`
- 날짜 미확인 시 `날짜미표기` (`-` 금지 — Depth의 No-data 의미와 충돌)

### X열 = 피드백 (확인사항 태그)

| 태그 | 용도 |
|------|------|
| `[확인 불가]` | 기획서에 정의가 없어 판정 불가. 대부분 `— 기획 확인 필요`로 종결 (최다) |
| `[UI↔DESC 불일치]` | UI mock과 Description이 상충 |
| `[변경 여부 불확실]` | 변경분인지 기존 UI인지 확정 불가 |
| `[오타 의심]` | 기획서 원문 오타 추정 |
| `[디자인 미반영]` | 디자인 미반영본과 정본 차이 |
| `[관리대상 범위 확인]` | C열 판정 근거가 약하거나, 다른 관리대상에도 동일 적용되는지 기획서 미기재 |

**서술 패턴:**
- 항목 식별자를 접두로 붙인다 — `U{n}` / `M-{n}` / `N-{n}` / `T-{n}` / `D-{n}`
- 불일치는 **양쪽 표기를 모두 인용하고 `/`로 대비** — `UI: … / DESC 2항-3-b: …`
- 종결부에 요구 액션 명시 — `— 기획 확인 필요`, `— 표기 통일 확인 필요`, `— 확정값 확인 필요`
- 기획 미정의 항목은 예상 결과에도 반영:
  `ㄴ 기획 미정의 항목 — PASS/FAIL 판정 대신 실측 상태를 [실제 결과]에 기재`

## 탭 구조 / 작성 절차

- 탭 분할 기준 = **기능 챕터 / 변경분 단위** (릴리즈별·작성자별 아님)
- 탭명은 `NN_챕터명` 형태 권장. 변경분 탭은 `{챕터명} 변경분`
- 모든 탭의 1행 헤더는 A~X 24컬럼 동일 (구 양식 탭은 23컬럼 — 위 "구 양식 탭" 절)
- TC ID는 탭 간 연속, `No`는 탭별 재시작

**빈 시트·신규 탭에 작성하는 절차:**

1. `add_tab` 으로 대상 탭 생성
2. `write` — `'{탭명}'!A1:X1` 에 위 **헤더 원문** 기입 (24개)
3. `append` — 2행부터 케이스 batch 1회 전송
4. `updatedRange` 확인 후 보고
5. 빈 기본 탭(`시트1` 등)은 자동 정리되지 않는다 → 사람이 수동 삭제

## 새 케이스 작성 시 암묵 규칙 (요약)

1. **컬럼 24개 순서 고정.** Y열 이후 쓰지 않는다
2. **비고(W)를 비우지 않는다.** 근거 태그 필수
3. **S·T·U·V·E·F·P는 공란.** `PASS` 등을 임의로 채우지 않는다
4. **4·5 Depth(M·N)는 `-`**
5. **`부수` → 항상 `P4`.** `정상`에 `P3`/`P4`를 주지 않는다
6. **`표시` 케이스를 요소 단위로 빠짐없이 쪼갠다** (과반이 정상)
7. **구분 6종·우선순위 4종을 모두 사용한다.** `P4`·`부수` 누락 금지
8. **atomic 유지** — 절차 1단계, 예상 1~2줄, 사전조건 1줄
9. **화면 ID는 기획서 원문.** 구분자 통일 금지, 유추 금지
10. **솔루션은 `VIOLA` 고정.** 관리대상은 **C열 전용 컬럼**에 쓰고 사전조건·비고에 중복하지 않는다. **판정 단위는 케이스**이며, 기획서 근거 없는 쪽은 만들지 않는다
11. **UI 레이블·상태값·메시지는 백틱 + 기획서 원문 인용**
12. **기획서 미정의 항목도 케이스로 만든다** — `[확인 불가] … — 기획 확인 필요`
13. **UI↔DESC 불일치는 케이스로 만들고 양쪽을 대비 인용**
14. **팝업은 2 Depth 분리 / 화면 ID 모 화면 승계 / 3 Depth `상세`**
15. **TC ID는 화면 단위 연속 블록**
16. **예상 결과 종결은 명사형.** 「~된다」 금지
