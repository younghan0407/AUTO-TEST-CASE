# Testcase Auto Orchestrator

기획서(PRD) → 팀 양식 분석 → **챕터(간지) 단위 순차 처리** → 테스트 케이스 생성/작성/리뷰까지 전체 파이프라인을 4명의 전문 에이전트 팀으로 자동 수행한다.

## 트리거 키워드

- "테스트 케이스 자동 생성/작성"
- "기획서에서 TC 뽑아줘", "기획서로 케이스 만들어줘"
- "테스트 시트에 케이스 자동으로 추가해줘"
- "다시 실행", "재실행", "특정 기능만 다시", "결과 보완", "이전 결과 기반으로"

## 실행 모드

**에이전트 팀 (기본)** — 4명의 에이전트가 협업한다.

| 에이전트 | 역할 | 사용 스킬 |
|---------|------|----------|
| `prd-analyst` | 챕터별 이미지 순차 분석 | `prd-analyzer` |
| `sheet-analyst` | 기존 시트 양식 분석 | `sheet-operator` |
| `testcase-writer` | 챕터별 케이스 생성 및 시트 작성 | `testcase-generator`, `sheet-operator` |
| `testcase-reviewer` | 챕터별 결과 리뷰 (QA) | `testcase-reviewer`, `sheet-operator` |

## 워크플로우

### Phase 0: 기본 정보 수집 + 컨텍스트 확인

#### 0-1. 환경변수 검증

- `FIGMA_ACCESS_TOKEN` 이 설정됐는가 (Figma 입력일 때만 필수)
- `GOOGLE_APPLICATION_CREDENTIALS` 가 유효한 경로를 가리키는가
- 누락 시 사용자에게 안내 후 중단

#### 0-2. 기본 정보 수집 — **필수 게이트**

**분석·생성에 착수하기 전에 아래 5개 항목을 사용자에게 물어 확정한다.**
사용자가 첫 요청에 이미 적어 준 항목은 다시 묻지 말고 **확인만** 한다.
`AskUserQuestion` 으로 선택지를 제시하면 왕복이 줄어든다.

**추정 금지.** 답이 없으면 진행하지 않는다 — 잘못 추정한 항목 하나가 전 행에 박힌다.

##### (1) 제품 유형 — 선택 필수

| 값 | 프로파일 | 비고 |
|----|---------|------|
| `VIOLA K8s` | `profile-viola` | 쿠버네티스 관리 영역 |
| `VIOLA CI/CD` | `profile-viola` | 빌드·배포 관리 영역 |
| `TROMBONE` | `profile-trombone` | **문체가 VIOLA와 정반대** (대괄호/백틱) |
| `BootFactory` | `profile-bootfactory` | **실측 없는 VIOLA 파생 프로파일** — 사용자에게 그 사실을 알린다 |

- **양식은 `.claude/formats/common.md` + 해당 프로파일 두 개를 함께 읽는다.**
- `VIOLA K8s` 와 `VIOLA CI/CD` 는 **같은 프로파일**을 쓴다. 둘의 차이는 시트 컬럼이 아니라
  **분석 컨텍스트**(어느 영역 기획서인지)와 `1 Depth`(Breadcrumb 최상위 원문)로 표현된다
- **관리대상 컬럼은 2026-09-02에 폐지됐다.** 제품 유형을 행마다 판정하지 않는다
- 대상 시트에 이미 데이터가 있으면 **솔루션 컬럼 실측값과 대조**해 어긋나면 보고한다

##### (2) 기획서 유형 — 선택 필수

| 값 | 의미 | 연동되는 파이프라인 |
|----|------|-------------------|
| **`신규`** | 문서 전체가 신규 기획 → **전수 케이스화** | 전체 분석 경로 |
| **`변경`** | 개정판 → **변경 표기가 있는 항목만** 케이스화 | `prd-analyzer` PDF-3.5 → `testcase-generator` 0-H → `testcase-reviewer` 5-2 |

**한 단계라도 반대 기준으로 동작하면 리뷰가 오판한다** — 각 에이전트 프롬프트에 반드시 명시할 것.

##### (2-1) / (2-2) 예외 항목 — **문서 기본 정책과 반대인 화면 목록**

기획서 유형을 고른 뒤 **반대 정책을 적용할 화면 식별자**를 입력받는다. 없으면 "없음".

| 기획서 유형 | 묻는 것 | 예외 화면에 적용할 정책 |
|------------|--------|----------------------|
| **`신규`** | 문서 안에 **일부 변경건**이 있는가 → 그 화면 ID | **변경 정책** |
| **`변경`** | 문서 안에 **일부 신규건**이 있는가 → 그 화면 ID | **신규 정책** |

**식별자 형식은 제품 프로파일의 화면 ID 체계를 따른다** (`Screen ID` 또는 `Page ID` 원문).
예: `BOOT-03_01_08`, `VIOE-02_01_01-11`, `ADM-GEN-0101-01`

**두 정책의 실제 차이:**

| | 변경 정책 | 신규 정책 |
|---|---|---|
| 케이스화 범위 | **변경 표기(색/취소선/스티커/`ChangeLog`)가 있는 항목만** | **화면 전수** |
| 비고 태그 | `[변경 CH{NN}-N …]` + 경로 태그 (`[DESC 전용]` 등) | 일반 근거 태그 (`[DESC N항]`·`[UI]`·`[스티커]`) |
| 삭제 검증 | 취소선 항목에 "더는 노출되지 않음" 검증 **필수** | 해당 없음 |

- **예외 목록은 화면 ID 단위다.** 그 화면 하나가 통째로 반대 정책이 된다
- 예외 화면의 케이스에는 **피드백에 `[정책 예외] 문서 기본={신규|변경} / 이 화면={변경|신규}`** 를
  남긴다 — 나중에 왜 이 화면만 다르게 작성됐는지 역추적할 수 있어야 한다
- **예외 목록에 없는 화면은 문서 기본 정책을 따른다.** 애매하면 사용자에게 확인한다
- 분석 중 예외 목록에 없는 화면에서 반대 성격이 뚜렷하게 보이면 **보고하되 임의로 정책을 뒤집지 않는다**

##### (3) 기획서 경로 — 필수

Figma URL / PDF 파일 경로 / **이미지(PNG 등) 파일·디렉터리 경로** 중 하나.

- PDF인 경우 `pymupdf` 설치 여부 확인
- **이미지인 경우 변환 단계 없이 바로 이미지 분석 경로로 진행한다** (`pillow`, `numpy` 필요).
  PDF를 요구하지 않는다
- 이미지 + 동일 내용 PDF가 함께 있으면 **PDF를 원천으로 사용** (원본 이미지는 해상도가 과도해
  판독 비효율일 수 있음)

##### (4) 테스트 케이스 경로 — 필수

**대상 구글 시트 URL** (공유 링크). 케이스를 작성할 시트다.

##### (5) 시트(탭) — 선택 필수

| 값 | 추가로 묻는 것 | 처리 |
|----|--------------|------|
| **`신규`** | **생성할 탭명** | `add_tab` → 헤더 23컬럼 기입 → 2행부터 작성 |
| **`기존`** | **기존 탭명** | 헤더 대조 후 마지막 행 다음부터 append |

- **탭명은 `metadata` 가 돌려주는 `title` 문자열을 그대로 쓴다** — 한글 탭 이름이 NFD 분해형으로
  저장되면 조합형으로 타이핑한 같은 문자열이 HTTP 400 `Unable to parse range` 로 실패한다.
  화면상 구분이 되지 않으므로 "탭이 없다"고 오판하거나 중복 탭을 만들 위험이 있다
- **`기존` 인데 그 탭이 없으면** 오타인지 신규인지 사용자에게 확인한다. 임의로 만들지 않는다
- **`기존` 인데 헤더가 23컬럼이 아니면** 그냥 append하지 않는다 — 전 값이 밀린다.
  `common.md` 권위 규칙에 따라 **작성 중단 + 사용자 확인**
- 유사한 이름의 탭이 이미 있으면(구분자만 다른 경우 등) 보고하고 확인받는다

#### 0-3. 그 외 확인 항목

기본 정보 5개 외에 아래를 확인한다. **기본값이 있는 항목은 묻지 않고 적용 후 보고**해도 된다.

| 항목 | 기본값 | 언제 묻는가 |
|------|-------|------------|
| **생성 모드** (atomic / scenario) | **atomic** | 사용자가 시나리오 단위를 명시 요청할 때만 |
| **취소선 = 삭제 표기 여부** | — | **기획서 유형이 `변경` 이면 묻는다.** 기획서마다 컨벤션이 다르고, 취소선은 색 검출에 잡히지 않아 알려주지 않으면 삭제 변경분이 통째로 누락된다 |
| **분석 범위** (특정 챕터만) | 전체 | 사용자가 부분 처리를 요청할 때 |
| **양식 사양 갱신** | 하지 않음 | 사용자가 `"양식 사양 갱신해줘"` 라고 할 때만 (참고 시트 URL 요청) |

**묻지 말아야 할 것 — 변경 표시색.** 색은 사용자 진술보다 스크립트 실측이 정확하다.
1-A-3에서 `--color=both --no-crops` 로 훑어 확정한다.
(2026-09-01 실측: 사용자가 "빨강·파랑"이라고 알려줬으나 파랑 후보 21건이 **전부 오탐**이었다)

#### 0-4. 수집 결과 요약 보고

수집이 끝나면 **확정된 값을 표로 보여주고 진행한다.** 사용자가 오타나 오해를 잡을 마지막 지점이다.

다음 조건으로 진행합니다.

#### 0-5. 기존 산출물 확인 → 실행 모드 결정

### Phase 1: 사전 준비

#### 1-A. 분석 이미지 준비

`sheet-analyst`(1-D)는 이 단계와 **병렬로 동시에 시작**한다.

**PDF 입력인 경우 — 이미지 변환:**

```bash
# 전체 페이지 150 DPI
python scripts/pdf_to_images.py <pdf_path> --dpi=150 --output-dir=_workspace/pdf_images/<name>

# Description 패널 크롭 200 DPI
python scripts/pdf_to_images.py <pdf_path> --crop-desc --dpi=200 --output-dir=_workspace/pdf_images/<name>_desc
```

**이미지 입력인 경우 — 변환 없음, 바로 분석 준비:**

PDF도 Figma도 없이 기획서가 이미지로 전달된 경우 **변환 단계를 찾지 말고 그 이미지를 원천으로 곧바로 진행한다.**

```bash
# 페이지 순서 확인 (파일명 정렬 = 페이지 순서)
ls -1 <이미지 디렉터리>
```

- 파일명 정렬이 페이지 순서와 다르면(`1.png, 10.png, 2.png`) **사용자에게 순서를 확인한다.** 추정 금지
- 흩어진 이미지는 `_workspace/prd_images/<name>/`에 정렬 가능한 이름으로 모은다 (**원본은 수정·삭제하지 않는다**)
- Description 크롭은 만들지 않는다 (`--crop-desc`는 PDF 전용). 원본 이미지 한 장에서 Description을 먼저 판독한 뒤 UI를 본다

#### 1-A-2. 이미지 판독 품질 게이트 (이미지 입력 시 필수)

```bash
python scripts/check_image_quality.py <이미지 디렉터리|파일> --json=_workspace/00_image_quality.json
```

`불가` 판정이 있으면 종료 코드 `2`다. 판정별 처리:

| 판정 | 오케스트레이터 처리 |
|------|------------------|
| `OK` | 그대로 진행 |
| `주의` | **사용자에게 알리고** 진행. 각 챕터 에이전트 프롬프트에 해당 페이지 목록과 사유를 전달 |
| `불가` | **사용자에게 알리고 원본 재전달을 요청**한다. 사용자가 "그대로 진행"을 택하면, 해당 페이지는 추측 케이스 없이 판독 불가 케이스로 남긴다 |

**사용자 통보는 의무다.** 판독이 안 되는 페이지를 조용히 스킵하는 것은 누락이다:

```
⚠️ 이미지 판독 이슈 2건 (총 14장)
- page_012.png : 해상도 부족 (짧은 변 640px) → 판독 주의, 텍스트 오독 가능
- page_015.png : 파일 훼손(중간 끊김) → 판독 불가

판독 불가 페이지는 추측하지 않고 [판독 불가] 표시로 케이스에 남깁니다.
원본을 다시 전달해 주시면 해당 페이지만 재분석합니다. 그대로 진행할까요?
```

PDF 입력에서도 변환 결과가 흐리거나 텍스트가 작으면 이 게이트를 실행한다. `주의`가 다수면 DPI를 200으로 올려 재변환한다.

#### 1-A-3. 변경 표시 영역 검출 (기획서 유형이 `변경` 이거나, 예외 항목에 변경 정책 화면이 있는 경우)

**먼저 이 기획서가 어떤 색을 쓰는지 실측한다.** 표시색은 기획서마다 다르다 — 빨강 단독인 판본도 있고
**빨강+파랑을 함께 쓰는 판본**도 있다. 한 색만 검출하면 나머지 색의 변경분이 그대로 누락된다.

```bash
# 0단계 — 쓰인 색 확인 (크롭 없이 후보 수만 비교)
python scripts/detect_red_regions.py <입력> --color=both --no-crops
```

```bash
# PDF 입력
python scripts/detect_red_regions.py <pdf_path> --pages=START-END --output-dir=_workspace/red_regions/ch{N}

# 이미지 입력 (디렉터리·단일 파일 모두 가능. DPI 옵션 무시, 원본 해상도 사용)
python scripts/detect_red_regions.py <이미지 디렉터리|파일> --output-dir=_workspace/red_regions/ch{N}

# 빨강 + 파랑을 함께 쓰는 기획서
python scripts/detect_red_regions.py <입력> --color=both --output-dir=_workspace/red_regions/ch{N}
```

- 출력은 **후보**다. 오탐(필수 `*`, 원형 번호 배지, 에러 아이콘, 실패 badge, 삭제 버튼, 차트 색, **페이지 외곽 아트보드 프레임**, 파랑의 경우 링크·기본 버튼·선택 탭·간지 배경)이 섞여 있으므로 각 챕터의 `prd-analyst`가 육안으로 확정한다.
- 검출 결과 경로 **+ 실측한 표시색 + 확정된 오탐 목록**을 챕터 에이전트 프롬프트에 함께 전달한다.
- **색으로 변경 종류·회차를 단정하지 않도록 지시한다.** 종류·회차는 주석 텍스트(`v2수정`/`v2추가`/`v2삭제` + 날짜)가 권위다. 색↔날짜 대응은 페이지마다 어긋날 수 있다.
- 기획서 유형이 `신규` 이고 **예외 항목도 없으면** 실행하지 않는다.
- 기획서 유형이 `신규` 인데 **예외 항목(변경 정책 화면)이 있으면 그 화면 페이지에만** 실행한다.

#### 1-B. 간지 감지 + 챕터 목록 생성

경량 스캔 에이전트가 전체 이미지를 순서대로 읽어 **간지(챕터 구분 슬라이드) 페이지**를 식별한다.

**간지 페이지 특징:**
- 어두운 단색(진회색·검정) 배경 전체를 채움
- UI 화면이나 Description 패널 없음
- 좌측 또는 중앙에 대분류 제목 텍스트 (예: `빌드배포`)
- 우측 하단에 챕터 번호 + 소제목 (예: `01. 파이프라인 관리`)

**챕터 목록 생성 형식:**

```
챕터 1: 페이지 3        "빌드배포 > 01. 파이프라인 관리"  (p3 ~ p15)
챕터 2: 페이지 16       "빌드배포 > 02. 배포 이력"       (p16 ~ p27)
챕터 3: 페이지 28       "모니터링 > 01. 대시보드"        (p28 ~ p41)
...
마지막 챕터의 끝 페이지: 총 페이지 수
```

간지로 판단하기 애매한 페이지는 후보로 표시하고 1-C에서 사용자 판단을 받는다.

**이미지 입력 특이사항:** 페이지 번호는 파일명 기준으로 부여하고 챕터 목록에 파일명을 함께 표기한다 (예: `챕터 1: page_003.png ~ page_015.png`). 이미지가 이미 챕터별 디렉터리로 나뉘어 전달됐다면 그 구분을 그대로 챕터 목록으로 쓰고 1-C에서 확인받는다.

#### 1-C. 사용자 확인 게이트 (필수)

챕터 목록을 사용자에게 보여주고 확인받는다:

...

수정이 필요하면 알려주세요. (예: "챕터 2 시작을 p18로 바꿔줘", "챕터 3과 4를 합쳐줘")

- 확정된 챕터 목록은 `_workspace/00_chapters.md`에 저장

#### 1-D. 양식 확정 — sheet-analyst 실행 (1-A와 병렬)

1-A와 동시에 시작. **양식 지식은 커밋된 사양 파일에서 오고, 대상 시트에서는 변화만 확인한다.**

| 모드 | 조건 | 동작 |
|------|------|------|
| **A. 드리프트 검증** (기본) | `.claude/formats/` 에 사양이 있음 | 사양 로드 + **대상 시트 헤더 1행 + 마지막 20~50행** 실측 |
| **B. 사양 갱신** | 사양이 없거나 사용자가 `"양식 사양 갱신"` 을 요청 | 참고 시트 **전수 스캔** → 사양 파일 갱신 |

산출물은 두 모드 모두 `_workspace/02_sheet_format.md` 이며, 최상단에 **어느 모드였는지 명시**한다.

**모드 A에서 확인하는 것:**

| 항목 | 처리 |
|------|------|
| 헤더가 사양과 일치 | 통과 |
| **헤더 불일치** (컬럼 추가·삭제·이름·순서 변경) | **Critical — 작성 중단 + 사용자 확인.** 사양 갱신(모드 B) 여부를 묻는다 |
| 사양 외 enum 값 발견 | Major — 보고 후 진행 여부 확인 (오타일 수도, 신규 enum일 수도) |
| 마지막 TC ID | 다음 시작 번호 = 실측값 + 1 |
| 대상 탭이 비어 있음/미존재 | 정상. 사양의 **헤더 원문으로 헤더 행 생성** (Phase 3) |

**참고 시트는 모드 B에서만 필요하다.** 평상시 사용자에게 참고 시트 URL을 요구하지 않는다.

**프로파일 선택은 Phase 0 (1) 제품 유형에서 이미 확정됐다.** 여기서는 대상 시트에 데이터가
있으면 솔루션 컬럼 실측값과 **대조만** 하고, 어긋나면 보고한다 (`"제품 유형은 TROMBONE인데 시트
솔루션 컬럼은 VIOLA입니다"`). 양식은 **`common.md` + 해당 프로파일 두 개를 함께** 로드한다.
상세 규칙은 `sheet-analyst` A-1 참조.

**모드 결정 보정:** Phase 0에서 사용자가 생성 모드(atomic/scenario)를 명시하지 않은 경우,
사양의 검증 단위 판정을 사용자에게 보고하고 진행 확인을 받는다.

### Phase 2~4: 챕터 루프

1-C에서 확정된 챕터 목록을 **순서대로** 처리한다. 각 챕터는 분석 → TC 생성/작성 → 리뷰가 완료된 후 다음 챕터로 넘어간다.

```
for 챕터 N in 확정된 챕터 목록:
    Phase 2: 챕터 분석
    Phase 3: TC 생성 + 시트 작성
    Phase 4: 챕터 리뷰
```

#### Phase 2: 챕터 분석

`prd-analyst` 1개 에이전트가 해당 챕터의 페이지 이미지를 **순차적**으로 읽어 분석한다.

- 입력: 챕터 페이지 범위 (예: `p3~p15` 또는 `page_003.png ~ page_015.png`), 전체 이미지 (+ PDF 입력 시 Description 크롭 이미지), 판독 이슈 페이지 목록(1-A-2), (기획서 유형이 `변경` 인 경우) 변경 표시 검출 결과 경로·실측 표시색·확정 오탐 목록(1-A-3)
- 상세 분석 절차: `prd-analyzer` 스킬 참조
- 출력: `_workspace/01_prd_analysis_ch{N}.md`

분석 중 모호한 항목은 "확인 불가"로 명시하고 진행 (추측 금지).

**에이전트 프롬프트에 반드시 포함할 것 — Phase 0에서 확정한 값을 그대로 넘긴다:**

| 항목 | 왜 넘겨야 하는가 |
|------|----------------|
| **제품 유형** (`VIOLA K8s` / `VIOLA CI/CD` / `TROMBONE` / `BootFactory`) | 분석 컨텍스트. **관리대상 판정을 시키지 않는다** — 그 절차는 2026-09-02에 폐지됐다 |
| **기획서 유형** (`신규` / `변경`) | 문서 전체 기본 분석 정책. `변경` 이면 `prd-analyzer` PDF-3.5 경로 |
| **예외 항목** (화면 ID 목록) | 그 화면만 **반대 정책으로 분석**한다. 케이스 생성 단계에서 거르는 것이 아니다 — 기본이 `변경` 인데 예외 화면을 변경분만 뽑아 두면 전수 분석 근거가 분석서에 아예 없고 후속 단계가 복구할 방법이 없다 |
| **취소선 = 삭제 표기 여부** | 취소선은 색 검출에 잡히지 않는다. 알려주지 않으면 삭제 변경분이 통째로 누락된다 |

- `## 이미지 판독 이슈` 섹션 산출 의무 (이슈가 없으면 "판독 이슈 없음" 명시)
- 판독 `불가` 페이지는 추측으로 채우지 않고 `[판독 불가]`로 남길 것
- 예외 화면 항목에는 **`[정책 예외]`** 표시를 남길 것

#### Phase 3: TC 생성 + 시트 작성

`testcase-writer`에게 작업 할당:

- 입력: `_workspace/01_prd_analysis_ch{N}.md` + `_workspace/02_sheet_format.md` + 대상 시트 URL·탭명 + **Phase 0 확정값 전부**(제품 유형 / 기획서 유형 / 예외 항목 / 생성 모드)
- **양식은 `.claude/formats/common.md` + 해당 프로파일 두 개를 함께 읽도록 지시한다.** 한쪽만 읽으면 규칙의 절반이 없다
- **예외 화면 케이스의 피드백에 `[정책 예외] 문서 기본=… / 이 화면=…` 을 남기도록 지시한다**
- 작업:
  1. 케이스 도출 (`testcase-generator` 스킬) — 판독 이슈 페이지 처리 규칙 적용 (0-J)
  2. `_workspace/03_testcases_ch{N}.md` 작성
     - 분포 표는 **실제 작성된 케이스로 카운트한 정확한 값** 사용 (추정 금지)
  3. **검토 게이트** (첫 번째 챕터만):
     - 03_testcases_ch01.md 요약을 사용자에게 보여주고 진행 확인
     - 이후 챕터는 자동 진행
  4. 사용자 OK (또는 자동 진행) → `sheet-operator`로 시트에 작성
     - 대상 탭이 없으면 `add_tab` → **생성 직후 `metadata` 의 `title` 을 복사** → `common.md` 의 **헤더 원문**을 `A1:W1` (23컬럼)에 기입 → 2행부터 batch append
     - 기존 탭이면 batch append (헤더 대조는 1-D에서 이미 완료)
  5. 작성된 행 범위 보고

#### Phase 4: 챕터 리뷰

`testcase-reviewer`에게 작업 할당:

- 입력: 해당 챕터의 01, 02, 03 파일 + 실제 시트의 작성된 범위 + **Phase 0 확정값 3개**(제품 유형 / 기획서 유형 / 예외 항목)
- 작업: 세 경계면 교차 비교 (기획 ↔ 케이스, 양식 ↔ 케이스, 로컬 ↔ 시트)
- 출력: `_workspace/04_review_report_ch{N}.md`

**리뷰어 프롬프트에 반드시 넣을 오판 방지 항목:**

- **제품 유형 → 프로파일**을 명시한다. 프로파일마다 **정반대인 규칙**이 있다 (UI 라벨 백틱 ↔ 대괄호, 지배 구분 `표시` ↔ `정상`, `정상`의 우선순위 P1·P2만 ↔ P1~P4 전부). 한쪽 기준으로 다른 쪽을 지적하는 것이 대표적 오판이다
- **기획서 유형이 `변경` 이면 비변경분 미작성은 정상**이다 — 누락으로 지적하지 않는다
- **예외 화면이 문서 기본 정책과 다르게 작성된 것은 정상**이다 — 그게 예외의 정의다. 대신 ① 예외 화면이 실제로 반대 정책으로 작성됐는가 ② `[정책 예외]` 표시가 있는가 ③ 예외 목록에 없는 화면이 반대 정책으로 작성되지 않았는가(범위 초과)를 점검한다
- **관리대상 컬럼은 폐지됐다** — 부재를 결함으로 지적하지 않는다
- **작성자 자기 점검표를 인용하지 말고 독립 실측하라**

**Critical 이슈 발생 시:**
- 리뷰어가 `testcase-writer`에게 재작성 요청
- writer가 수정 → reviewer가 재리뷰 (최대 1회 루프)
- 두 번째 리뷰에도 Critical이 남으면 사용자에게 결정 위임 후 다음 챕터 진행

> **첫 번째 챕터 리뷰 후 패턴 이슈 발견 시:** Critical이 특정 패턴(예: 표시 형식 케이스 누락, enum 오류)에서 반복된다면 남은 챕터 진행 전 사용자에게 보고하고 방향 조정 여부를 확인받는다.

### Phase 6: 피드백 및 진화 (선택)

사용자에게 묻는다:
- "결과에서 개선할 부분이 있나요?"
- "에이전트 역할이나 워크플로우에 바꾸고 싶은 점이 있나요?"

피드백 유형별 진화 경로는 `harness` 메타 스킬(외부 플러그인)의 Phase 7을 참조한다. 이 저장소에는 포함되지 않으므로 필요할 때 설치한다 — `/plugin marketplace add revfactory/harness`. **설치 여부와 무관하게, 하네스를 변경하면 `CLAUDE.md`의 변경 이력 테이블에 날짜·대상·사유를 기록한다.**

## 에러 핸들링

| 에러 유형 | 대응 |
|----------|------|
| Figma 토큰 누락/만료 | 즉시 중단 + 토큰 재발급 안내 |
| Figma API 403/404 | 파일 권한·URL 재확인 요청 |
| 시트 권한 없음 (403) | 서비스 계정 이메일 공유 안내 + 사용자 확인 후 재시도 |
| 시트 ID 잘못됨 (404) | URL 재확인 요청 |
| API rate limit (429) | 60초 대기 후 1회 재시도, 실패 시 부분 결과 보고 |
| 시트 쓰기 부분 실패 | 어디까지 작성됐는지 명시 + 미작성 케이스 ID 목록 보고 |
| 간지 감지 불가 (이미지 없음 등) | 사용자에게 페이지 범위 직접 입력 요청 |
| 챕터 분석 결과 0건 | 사용자에게 해당 챕터 범위 재확인 요청 후 재시도 또는 스킵 |
| 대상 시트 헤더가 사양과 불일치 | **작성 중단** + 사용자 확인. 사양 갱신(모드 B) 또는 대상 탭 교체 |
| Phase 0 기본 정보 5개 중 하나라도 미확정 | **진행 중단** — 사용자에게 묻는다. 추정 금지 |
| 제품 유형에 해당하는 프로파일 파일이 없음 | 새 제품 가능성 → 참고 시트로 프로파일 신규 작성(모드 B) 제안 |
| 제품 유형 ↔ 대상 시트 솔루션값 불일치 | **보고 후 확인** — 어느 쪽이 맞는지 사용자가 판단 |
| 한 탭에 두 제품 솔루션값이 섞여 있음 | 최다값 사용 + 사용자에게 보고 (프로파일은 제품 단위) |
| `기존` 탭 지정인데 그 탭이 없음 | 오타인지 신규인지 확인. **임의로 생성하지 않는다** |
| `기존` 탭 헤더가 23컬럼이 아님 | **작성 중단** — 그냥 append하면 전 값이 밀린다 |
| 예외 항목 화면 ID가 기획서에 없음 | 보고 후 확인 (오타 가능성). 임의로 무시하지 않는다 |
| 이미지 판독 품질 `주의` | 사용자 통보 + 진행. 해당 페이지 케이스 피드백에 `[판독 주의]` 기재 |
| 이미지 판독 품질 `불가` (해상도 심각 부족·훼손·백지) | 사용자 통보 + 원본 재전달 요청. 재전달 전 진행 시 해당 페이지는 판독 불가 케이스로만 남김 (추측 금지) |
| 이미지 파일이 열리지 않음 (손상) | 파일명·사유 명시해 보고. "분석 완료"로 처리하지 않음 |
| 이미지 파일명 정렬 ≠ 페이지 순서 | 사용자에게 순서 확인 요청 (추정 금지) |
| `pillow`/`numpy` 미설치 (이미지 입력) | `pip install pillow numpy` 안내 후 중단 |

**원칙:** 1회 재시도 후 재실패 시 해당 챕터 결과 없이 다음 챕터로 진행하고 보고서에 누락 명시.

## 팀 크기 및 조율

- 팀 크기: 4명 (소규모 ~ 중규모)
- 팀원당 작업 수: 1~2개
- Phase 1만 일부 병렬 (1-A + 1-D), 챕터 루프는 순차
- 조율 오버헤드 최소화: 챕터 루프 내에서는 분석→생성→리뷰 순차 처리

## 테스트 시나리오

### 정상 흐름

1. 사용자: PDF 기획서 + **대상** 구글 시트 URL 제공 (참고 시트 불필요 — 사양 재사용)
2. Phase 0: 환경변수·기존 산출물 확인 → 초기 실행
3. Phase 1-A: 이미지 준비 (PDF는 변환 / 이미지 입력은 변환 없음) → 1-A-2 판독 품질 게이트 (1-D sheet-analyst 병렬 진행)
4. Phase 1-B: 간지 감지 → 챕터 목록 생성
5. Phase 1-C: 사용자에게 챕터 목록 확인 → OK
6. 챕터 루프 시작:
   - ch01: prd-analyst 분석 → testcase-writer 케이스 생성 → 사용자 첫 검토 → 시트 작성 → reviewer 리뷰
   - ch02: 자동 진행 → ... → 리뷰
   - ... (반복)
7. Phase 5: 합본 + 종합 보고
8. Phase 6: 피드백 수집

### 챕터 목록 수정 흐름

1. Phase 1-C에서 "챕터 3 시작을 p30으로 바꿔줘" 요청
2. 오케스트레이터: 챕터 목록 수정 후 재표시
3. 사용자 OK → 확정

### 특정 챕터 재실행 흐름

1. 사용자: "챕터 2 케이스 다시 만들어줘"
2. `_workspace/00_chapters.md` 확인 → ch02 범위 특정
3. prd-analyst·sheet-analyst 호출 없음 (기존 산출물 재사용)
4. testcase-writer만 호출, ch02 케이스 재생성
5. reviewer가 새 케이스만 검토

### 첫 챕터 패턴 이슈 발견 흐름

1. ch01 리뷰: "표시 형식 검증 케이스가 전혀 없음" Critical 발견
2. writer 재작성 → reviewer 재리뷰 → Critical 해결
3. 오케스트레이터: "ch01에서 표시 형식 자동 도출 누락 패턴 발견. 남은 챕터 진행 전 확인합니다."
4. 사용자 확인 → 이후 챕터 진행
