# Testcase Auto Orchestrator

기획서(PRD) → 팀 양식 분석 → **화면 ID(`Screen ID` / `Page ID`) 단위 순차 처리** → 테스트 케이스 생성/작성/리뷰까지 전체 파이프라인을 4명의 전문 에이전트 팀으로 자동 수행한다.

## 트리거 키워드

- "테스트 케이스 자동 생성/작성"
- "기획서에서 TC 뽑아줘", "기획서로 케이스 만들어줘"
- "테스트 시트에 케이스 자동으로 추가해줘"
- "다시 실행", "재실행", "특정 기능만 다시", "결과 보완", "이전 결과 기반으로"

## 실행 모드

**에이전트 팀 (기본)** — 4명의 에이전트가 협업한다.

| 에이전트 | 역할 | 사용 스킬 |
|---------|------|----------|
| `prd-analyst` | 화면별 이미지 순차 분석 | `prd-analyzer` |
| `sheet-analyst` | 기존 시트 양식 분석 | `sheet-operator` |
| `testcase-writer` | 화면별 케이스 생성 및 시트 작성 | `testcase-generator`, `sheet-operator` |
| `testcase-reviewer` | 화면별 리뷰 + 전체 집계 리뷰 (QA) | `testcase-reviewer`, `sheet-operator` |

## 워크플로우

### Phase 0: 기본 정보 수집 + 컨텍스트 확인

#### 0-1. 환경변수 검증

- `FIGMA_ACCESS_TOKEN` 이 설정됐는가 (Figma 입력일 때만 필수)
- `GOOGLE_APPLICATION_CREDENTIALS` 가 유효한 경로를 가리키는가
- 누락 시 사용자에게 안내 후 중단

#### 0-2. 기본 정보 수집 — **필수 게이트**

**분석·생성에 착수하기 전에 아래 5개 항목을 사용자에게 물어 확정한다.**
사용자가 첫 요청에 이미 적어 준 항목은 다시 묻지 말고 **확인만** 한다.
`AskUserQuestion` 으로 선택지를 제시하면 왕복이 줄어든다.

**추정 금지.** 답이 없으면 진행하지 않는다 — 잘못 추정한 항목 하나가 전 행에 박힌다.

##### (1) 제품 유형 — 선택 필수

| 값 | 프로파일 | 비고 |
|----|---------|------|
| `VIOLA K8s` | `profile-viola` | 쿠버네티스 관리 영역 |
| `VIOLA CI/CD` | `profile-viola` | 빌드·배포 관리 영역 |
| `TROMBONE` | `profile-trombone` | **문체가 VIOLA와 정반대** (대괄호/백틱) |
| `BootFactory` | `profile-bootfactory` | **실측 없는 VIOLA 파생 프로파일** — 사용자에게 그 사실을 알린다 |

- **양식은 `.claude/formats/common.md` + 해당 프로파일 두 개를 함께 읽는다.**
- `VIOLA K8s` 와 `VIOLA CI/CD` 는 **같은 프로파일**을 쓴다. 둘의 차이는 시트 컬럼이 아니라
  **분석 컨텍스트**(어느 영역 기획서인지)와 `1 Depth`(Breadcrumb 최상위 원문)로 표현된다
- **관리대상 컬럼은 2026-09-02에 폐지됐다.** 제품 유형을 행마다 판정하지 않는다
- 대상 시트에 이미 데이터가 있으면 **솔루션 컬럼 실측값과 대조**해 어긋나면 보고한다

##### (2) 기획서 유형 — 선택 필수

| 값 | 의미 | 연동되는 파이프라인 |
|----|------|-------------------|
| **`신규`** | 문서 전체가 신규 기획 → **전수 케이스화** | 전체 분석 경로 |
| **`변경`** | 개정판 → **변경 표기가 있는 항목만** 케이스화 | `prd-analyzer` PDF-3.5 → `testcase-generator` 0-H → `testcase-reviewer` 5-2 |

**한 단계라도 반대 기준으로 동작하면 리뷰가 오판한다** — 각 에이전트 프롬프트에 반드시 명시할 것.

##### (2-1) / (2-2) 예외 항목 — **문서 기본 정책과 반대인 화면 목록**

기획서 유형을 고른 뒤 **반대 정책을 적용할 화면 식별자**를 입력받는다. 없으면 "없음".

| 기획서 유형 | 묻는 것 | 예외 화면에 적용할 정책 |
|------------|--------|----------------------|
| **`신규`** | 문서 안에 **일부 변경건**이 있는가 → 그 화면 ID | **변경 정책** |
| **`변경`** | 문서 안에 **일부 신규건**이 있는가 → 그 화면 ID | **신규 정책** |

**식별자 형식은 제품 프로파일의 화면 ID 체계를 따른다** (`Screen ID` 또는 `Page ID` 원문).
예: `BOOT-03_01_08`, `VIOE-02_01_01-11`, `ADM-GEN-0101-01`

**두 정책의 실제 차이:**

| | 변경 정책 | 신규 정책 |
|---|---|---|
| 케이스화 범위 | **변경 표기(색/취소선/스티커/`ChangeLog`)가 있는 항목만** | **화면 전수** |
| 비고 태그 | `[변경 CH{NN}-N …]` + 경로 태그 (`[DESC 전용]` 등) | 일반 근거 태그 (`[DESC N항]`·`[UI]`·`[스티커]`) |
| 삭제 검증 | 취소선 항목에 "더는 노출되지 않음" 검증 **필수** | 해당 없음 |

- **예외 목록은 화면 ID 단위다.** 그 화면 하나가 통째로 반대 정책이 된다
- 예외 화면의 케이스에는 **피드백에 `[정책 예외] 문서 기본={신규|변경} / 이 화면={변경|신규}`** 를
  남긴다 — 나중에 왜 이 화면만 다르게 작성됐는지 역추적할 수 있어야 한다
- **예외 목록에 없는 화면은 문서 기본 정책을 따른다.** 애매하면 사용자에게 확인한다
- 분석 중 예외 목록에 없는 화면에서 반대 성격이 뚜렷하게 보이면 **보고하되 임의로 정책을 뒤집지 않는다**

##### (3) 기획서 경로 — 필수

Figma URL / PDF 파일 경로 / **이미지(PNG 등) 파일·디렉터리 경로** 중 하나.

- PDF인 경우 `pymupdf` 설치 여부 확인
- **이미지인 경우 변환 단계 없이 바로 이미지 분석 경로로 진행한다** (`pillow`, `numpy` 필요).
  PDF를 요구하지 않는다
- 이미지 + 동일 내용 PDF가 함께 있으면 **PDF를 원천으로 사용** (원본 이미지는 해상도가 과도해
  판독 비효율일 수 있음)

##### (4) 테스트 케이스 경로 — 필수

**대상 구글 시트 URL** (공유 링크). 케이스를 작성할 시트다.

##### (5) 시트(탭) — 선택 필수

| 값 | 추가로 묻는 것 | 처리 |
|----|--------------|------|
| **`신규`** | **생성할 탭명** | `add_tab` → 헤더 23컬럼 기입 → 2행부터 작성 |
| **`기존`** | **기존 탭명** | 헤더 대조 후 마지막 행 다음부터 append |

- **탭명은 `metadata` 가 돌려주는 `title` 문자열을 그대로 쓴다** — 한글 탭 이름이 NFD 분해형으로
  저장되면 조합형으로 타이핑한 같은 문자열이 HTTP 400 `Unable to parse range` 로 실패한다.
  화면상 구분이 되지 않으므로 "탭이 없다"고 오판하거나 중복 탭을 만들 위험이 있다
- **`기존` 인데 그 탭이 없으면** 오타인지 신규인지 사용자에게 확인한다. 임의로 만들지 않는다
- **`기존` 인데 헤더가 23컬럼이 아니면** 그냥 append하지 않는다 — 전 값이 밀린다.
  `common.md` 권위 규칙에 따라 **작성 중단 + 사용자 확인**
- 유사한 이름의 탭이 이미 있으면(구분자만 다른 경우 등) 보고하고 확인받는다

#### 0-3. 그 외 확인 항목

기본 정보 5개 외에 아래를 확인한다. **기본값이 있는 항목은 묻지 않고 적용 후 보고**해도 된다.

| 항목 | 기본값 | 언제 묻는가 |
|------|-------|------------|
| **생성 모드** (atomic / scenario) | **atomic** | 사용자가 시나리오 단위를 명시 요청할 때만 |
| **취소선 = 삭제 표기 여부** | — | **기획서 유형이 `변경` 이면 묻는다.** 기획서마다 컨벤션이 다르고, 취소선은 색 검출에 잡히지 않아 알려주지 않으면 삭제 변경분이 통째로 누락된다 |
| **분석 범위** (특정 화면만) | 전체 | 사용자가 부분 처리를 요청할 때 |
| **양식 사양 갱신** | 하지 않음 | 사용자가 `"양식 사양 갱신해줘"` 라고 할 때만 (참고 시트 URL 요청) |

**묻지 말아야 할 것 — 변경 표시색.** 색은 사용자 진술보다 스크립트 실측이 정확하다.
1-A-3에서 `--color=both --no-crops` 로 훑어 확정한다.
(2026-09-01 실측: 사용자가 "빨강·파랑"이라고 알려줬으나 파랑 후보 21건이 **전부 오탐**이었다)

#### 0-5. 기존 산출물 확인 → 실행 모드 결정

- `_workspace/` 가 없음 → **초기 실행** (Phase 1부터 전체 진행)
- `_workspace/` 가 있고 사용자가 "다시" / "재실행" 요청 → 기존을 `_workspace_prev_{설명}_{날짜}/` 로 이동, **새 실행**

### Phase 1: 사전 준비

#### 1-A. 분석 이미지 준비

`sheet-analyst`(1-D)는 이 단계와 **병렬로 동시에 시작**한다.

**PDF 입력인 경우 — 이미지 변환:**

```bash
# 전체 페이지 150 DPI
python scripts/pdf_to_images.py <pdf_path> --dpi=150 --output-dir=_workspace/pdf_images/<name>

# Description 패널 크롭 200 DPI + 판독용 분할 (--tile=auto 필수)
python scripts/pdf_to_images.py <pdf_path> --crop-desc --dpi=200 --tile=auto --output-dir=_workspace/pdf_images/<name>_desc
```

**`--tile=auto` 를 빼면 안 된다.** 이미지는 모델 전달 시 긴 변 1568px로 축소되므로
**올린 DPI가 상한에서 버려진다** — 실측으로 DESC 크롭 200 DPI는 한글 본문 1자가 **9.9px** 로
도착해 판독이 안 되고, 에이전트가 영역을 다시 잘라 재판독하는 왕복이 발생한다
(화면 34개 실행에서 애드혹 재크롭 21장). `--tile=auto` 는 조각을 상한 안에 넣어 **17.8px** 로
올리고 **토큰도 페이지당 ~11.5K → ~6.5K 로 줄인다.**

- 변환 직후 stderr의 **유효배율·한글 예상 px** 을 확인하고, 경고가 있으면 사용자에게 알린다
- 조각 파일명은 `page_NNN_desc_t1.png` ~ `_tN.png` (위→아래 순서, 경계 겹침 포함).
  **화면 에이전트 프롬프트에 조각 파일 목록을 순서대로 넘긴다**

**이미지 입력인 경우 — 변환 없음, 바로 분석 준비:**

PDF도 Figma도 없이 기획서가 이미지로 전달된 경우 **변환 단계를 찾지 말고 그 이미지를 원천으로 곧바로 진행한다.**

```bash
# 페이지 순서 확인 (파일명 정렬 = 페이지 순서)
ls -1 <이미지 디렉터리>
```

- 파일명 정렬이 페이지 순서와 다르면(`1.png, 10.png, 2.png`) **사용자에게 순서를 확인한다.** 추정 금지
- 흩어진 이미지는 `_workspace/prd_images/<name>/`에 정렬 가능한 이름으로 모은다 (**원본은 수정·삭제하지 않는다**)
- Description 크롭은 만들지 않는다 (`--crop-desc`는 PDF 전용). 원본 이미지 한 장에서 Description을 먼저 판독한 뒤 UI를 본다

#### 1-A-2. 이미지 판독 품질 게이트 (이미지 입력 시 필수)

```bash
python scripts/check_image_quality.py <이미지 디렉터리|파일> --json=_workspace/00_image_quality.json
```

`불가` 판정이 있으면 종료 코드 `2`다. 판정별 처리:

| 판정 | 오케스트레이터 처리 |
|------|------------------|
| `OK` | 그대로 진행 |
| `주의` | **사용자에게 알리고** 진행. 각 화면 에이전트 프롬프트에 해당 페이지 목록과 사유를 전달 |
| `불가` | **사용자에게 알리고 원본 재전달을 요청**한다. 사용자가 "그대로 진행"을 택하면, 해당 페이지는 추측 케이스 없이 판독 불가 케이스로 남긴다 |

**사용자 통보는 의무다.** 판독이 안 되는 페이지를 조용히 스킵하는 것은 누락이다:

```
⚠️ 이미지 판독 이슈 2건 (총 14장)
- page_012.png : 해상도 부족 (짧은 변 640px) → 판독 주의, 텍스트 오독 가능
- page_015.png : 파일 훼손(중간 끊김) → 판독 불가

판독 불가 페이지는 추측하지 않고 [판독 불가] 표시로 케이스에 남깁니다.
```

#### 1-A-3. 변경 표시 영역 검출 (기획서 유형이 `변경` 이거나, 예외 항목에 변경 정책 화면이 있는 경우)

**먼저 이 기획서가 어떤 색을 쓰는지 실측한다.** 표시색은 기획서마다 다르다 — 빨강 단독인 판본도 있고
**빨강+파랑을 함께 쓰는 판본**도 있다. 한 색만 검출하면 나머지 색의 변경분이 그대로 누락된다.

```bash
# 0단계 — 쓰인 색 확인 (크롭 없이 후보 수만 비교)
python scripts/detect_red_regions.py <입력> --color=both --no-crops
```

```bash
# PDF 입력 — 전 페이지 1회 실행
python scripts/detect_red_regions.py <pdf_path> --output-dir=_workspace/red_regions

# 이미지 입력 (디렉터리·단일 파일 모두 가능. DPI 옵션 무시, 원본 해상도 사용)
python scripts/detect_red_regions.py <이미지 디렉터리|파일> --output-dir=_workspace/red_regions

# 빨강 + 파랑을 함께 쓰는 기획서
python scripts/detect_red_regions.py <입력> --color=both --output-dir=_workspace/red_regions
```

- 출력은 **후보**다. 오탐(필수 `*`, 원형 번호 배지, 에러 아이콘, 실패 badge, 삭제 버튼, 차트 색, **페이지 외곽 아트보드 프레임**, 파랑의 경우 링크·기본 버튼·선택 탭·간지 배경)이 섞여 있으므로 각 화면의 `prd-analyst`가 육안으로 확정한다.
- **검출은 전 페이지에 1회만 실행한다.** 오케스트레이터가 화면 인덱스의 페이지 범위로 결과를 잘라 각 화면 에이전트에게 넘긴다 — 화면마다 스크립트를 다시 돌리지 않는다.
- 검출 결과 경로(해당 화면 페이지 분) **+ 실측한 표시색 + 확정된 오탐 목록**을 화면 에이전트 프롬프트에 함께 전달한다.
- **색으로 변경 종류·회차를 단정하지 않도록 지시한다.** 종류·회차는 주석 텍스트(`v2수정`/`v2추가`/`v2삭제` + 날짜)가 권위다. 색↔날짜 대응은 페이지마다 어긋날 수 있다.
- 기획서 유형이 `신규` 이고 **예외 항목도 없으면** 실행하지 않는다.
- 기획서 유형이 `신규` 인데 **예외 항목(변경 정책 화면)이 있으면 그 화면 페이지에만** 실행한다.

#### 1-B. 화면 인덱스 사전 스캔

경량 스캔 에이전트 1개가 전체 이미지를 순서대로 **얕게** 훑어 처리 단위 목록을 만든다.

**판독 깊이를 얕게 유지한다** — 화면 식별자 / 페이지 경계 / Description 항목 **제목** / 상호 참조
원문(`… 참고`) 까지만 본다. **본 판독은 Phase 2가 한다.** 여기서 깊이 읽으면 분석을 두 번 하는 것이다.

**산출물 3개:**

| 산출물 | 내용 |
|--------|------|
| `_workspace/00_screen_index.md` | 처리 단위 목록 + 진행 상태 |
| `_workspace/00_cid_register.md` | 공통 DESC 후보 + C-ID 선배정 |
| (보고) 화면 식별자 출처 필드명 | `Screen ID` / `Page ID` / 기타 — **제품 프로파일의 화면 ID 체계와 대조**하고 어긋나면 보고 |

**화면 식별자 추출은 `prd-analyzer` 의 「화면 식별자 추출 규칙」을 따른다** (프로파일의 우선순위대로
탐색하고 **원문 표기를 그대로** 쓴다. 형식 정규화 금지).

**인덱스 형식:**

```
# 화면 인덱스

- 기획서: PDF/VIOLA_V4.0/03_파드.pdf
- 화면 식별자 출처: Screen ID
- 문서 기본 정책: 변경
- 예외 항목: VIOE-03_01_04_13 (신규 정책)
- 기존 탭 CH-ID 최대: CH04 (sheet-analyst 실측) → 화면 CH-ID는 CH05부터

| 순번 | 화면 ID(원문) | CH-ID 접두 | 페이지 | 소속 간지 | 정책 | 배치 | 상태 | 시트 행 |
|------|--------------|-----------|--------|----------|------|------|------|--------|
| 01 | VIOE-02_01_01-11 | CH05 | p5~p7 | 통합 모니터링 | 변경 | B01 | 대기 | - |
| 02 | VIOE-02_01_02 | CH06 | p8 | 통합 모니터링 | 변경 | B02 | 대기 | - |
| 03 | VIOE-03_01_04_13 | CH07 | p9 | 파드 | 신규(예외) | B03 | 대기 | - |
| 04 | NOID-01 | CH08 | p10 | 파드 | 변경 | B02 | 대기 | - |
```

- 상태 enum: `대기` / `분석중` / `작성중` / `완료` / `실패`
- **`배치`** 는 한 에이전트 호출로 함께 처리할 묶음 ID다 (1-B-1). **상태·시트 행은 배치가 아니라
  화면마다 개별로 기록한다** — 배치 하나가 실패해도 어느 화면이 실패했는지 남아야 한다
- `시트 행` 은 append 직후 오케스트레이터가 기록한다. 미작성은 `-`
- `CH-ID 접두` 는 **1-D `sheet-analyst` 가 실측한 기존 최대값 다음부터** 배정한다
  (`common.md` 「CH-ID 충돌 방지」). 인덱스 순번과 어긋날 수 있으며 이 컬럼이 단일 출처다
- **소속 간지**는 처리 단위가 아니라 **그룹 라벨**이다. 분석 컨텍스트로 화면 에이전트에게 넘긴다

**단위 확정 규칙 (경계 케이스):**

| 상황 | 처리 |
|------|------|
| 한 화면 ID가 여러 페이지에 걸침 | 묶어서 **한 단위** |
| 한 페이지에 여러 화면 ID (팝업 등) | 페이지 중복 등재 허용 — 단위 기준은 화면 |
| 같은 화면 ID가 문서 앞뒤로 떨어져 등장 | 한 단위로 병합하고 페이지 목록에 둘 다 기재 |
| 화면 ID 판독 불가 | `[판독 불가]` 로 등재 + 1-C에서 사용자 확인. **추정 금지** |
| 간지 · 목차 | **인덱스 제외** — UI·Description이 없어 케이스 원천이 없다 |
| 공통 정책 · 플로우 페이지 | `NOID-{일련번호}` 로 **독립 단위** 등재 |

**`NOID` 단위의 표기:**

- 일련번호는 인덱스 순번과 **별개인 자체 연번**이다 (`NOID-01`, `NOID-02`)
- 시트의 `화면 ID` 컬럼에 **`NOID-01` 을 쓰지 않는다.** 기획서에 없는 문자열이므로 사양의
  No-data 규칙대로 표기한다. `NOID` 는 하네스 내부 단위 식별자다
- 그 케이스의 `비고` 에 근거 페이지를 남긴다 (예: `[DESC p10-2항]`)
- **직전 화면에 병합하지 않는다** — 여러 화면에 걸치는 공통 정책을 한 화면에만 귀속시키면
  나머지 화면에서 근거가 사라진다

**C-ID 레지스터 형식** (`_workspace/00_cid_register.md`):

```
# 공통 DESC C-ID 레지스터

※ 배정 권한은 오케스트레이터에 있다. 분석 담당은 로컬 번호를 매기지 않는다.

| C-ID | 정의 내용 | 근거 화면 ID·DESC 항목 | 적용 화면 순번 | 연결 근거(상호 참조 원문) |
|------|----------|---------------------|--------------|------------------------|
| C1 | '터미널 실행' 버튼 동작 | VIOE-03_01_01-01 > 2항 | 01, 04 | `상세 동작은 목록 > '작업' 버튼 정의와 동일하게 제공 (VIOE-03_01_01-01 > 2항 참고)` |
```

- **「연결 근거」가 빈 항목은 레지스터에 올리지 않는다.** 연결 판정 근거는 **기획서의 상호 참조**
  뿐이다 — 일자·회차·내용이 같아도 상호 참조가 없으면 병렬 변경으로 두고 연결하지 않는다
  (`common.md` 「하나의 정의 판단 기준」)
- 사전 스캔이 놓친 정의는 루프 중 분석 담당의 **발급 요청**으로 추가한다 (Phase 2)

**이미지 입력 특이사항:** 페이지 번호는 파일명 기준으로 부여하고 인덱스의 `페이지` 칸에 파일명을
함께 표기한다 (예: `page_005.png ~ page_007.png`).

**화면 식별자를 어느 페이지에서도 찾지 못하면** 인덱스를 만들 수 없다. 사용자에게 식별자
필드명·위치를 확인한다. **간지 단위로 임의 폴백하지 않는다.**

#### 1-B-1. 배치 계획 — 소형 화면을 묶는다

고정 문서(브리핑·SKILL·에이전트 정의)는 **호출당** 붙는다. 화면 단위 처리에서는 그 비용이
화면마다 반복되므로(실측 화면당 531KB), **작은 화면을 묶으면 고정분을 나눠 부담한다.**

**묶는 조건 — 넷을 모두 만족할 때만:**

| 조건 | 이유 |
|------|------|
| **같은 소속 간지** | 분석 컨텍스트가 같다. 다른 간지를 섞으면 Breadcrumb·`1 Depth` 판정이 흐려진다 |
| **같은 정책** (`신규`/`변경`) | 정책이 다르면 케이스화 범위가 반대다. 한 프롬프트에 두 기준을 넣으면 오적용 위험이 크다 |
| **예상 규모가 작다** — 페이지 합 3장 이하 | 큰 화면을 묶으면 컨텍스트 한도·판독 누락 위험이 생긴다 |
| **정책 예외 화면이 아니다** | 예외 화면은 단독 처리한다 — 반대 정책이 섞이는 위험을 감수할 이유가 없다 |

- **한 배치는 최대 3화면.** 그 이상은 묶지 않는다
- **첫 배치(`B01`)는 반드시 화면 1개다.** 첫 화면 검토 게이트(Phase 3)의 목적이
  문체·태그·enum 오류를 **전 행에 번지기 전에** 잡는 것이므로, 첫 호출에 여러 화면을 넣으면
  게이트를 통과할 때 이미 여러 화면 분량이 잘못 쓰여 있다
- 묶지 못하는 화면은 **자기 혼자 배치**가 된다 (`B0N` 에 화면 1개). 정상이다

**산출물은 화면별로 분리 저장한다 — 묶는 것은 호출뿐이다:**

- `01_prd_analysis_s{NN}.md` · `03_testcases_s{NN}.md` · `03_rows_s{NN}.tsv` ·
  `04_review_report_s{NN}.md` 는 **화면마다 하나씩** 만든다
- 시트 append도 **화면 단위로 나눠** 하고 인덱스의 `시트 행` 을 화면마다 기록한다
- 이유는 **부분 재실행 정밀도**다. 배치로 합쳐 저장하면 화면 하나만 다시 만들 수 없어
  2026-09-02 화면 단위 재편의 이득이 사라진다
- **한 화면이 실패하면 그 화면만 상태 `실패`** 로 남기고 배치의 나머지는 계속 진행한다

**사이클 수 계산이 바뀐다** — 화면 N개·배치 M개면 `3M + 1` 회다(배치마다 분석·생성·리뷰 3회
+ Phase 5 집계 리뷰 1회). 1-C 게이트에서 **배치 계획과 함께** 이 값을 보여준다.

#### 1-C. 사용자 확인 게이트 (필수)

화면 인덱스를 사용자에게 보여주고 확인받는다. **화면 수·배치 수·예상 에이전트 사이클을 함께
알린다** — 배치 M개면 `3M + 1` 회다(배치마다 분석·생성·리뷰 3회 + Phase 5 집계 리뷰 1회).
사용자가 규모를 알고 시작해야 하고, **배치 묶음이 맞는지도 이 게이트에서 확인받는다.**

```
다음 화면 단위로 처리합니다. 맞는지 확인해 주세요.
화면 8개 → 배치 5개 → 에이전트 사이클 16회 (배치로 묶지 않으면 25회)

| 순번 | 화면 ID | 페이지 | 소속 간지 | 정책 | 배치 |

| 02 | VIOE-02_01_02 | p8 | 통합 모니터링 | 변경 | B02 |
| 04 | NOID-01 (공통 정책 페이지) | p10 | 통합 모니터링 | 변경 | B02 |

...

배치 기준: 같은 간지 + 같은 정책 + 페이지 합 3장 이하 + 예외 화면 아님 (최대 3화면)
산출물·시트 행은 배치와 무관하게 **화면별로** 분리 기록됩니다 (부분 재실행 정밀도 유지).

제외한 페이지: p1~p4 (간지·목차)
판독 불가: 없음

수정이 필요하면 알려주세요.
(예: "p8도 01번 화면에 포함시켜줘", "04번은 제외해줘", "02·04는 따로 돌려줘")
OK면 그대로 진행합니다.
```

- 사용자 OK → 확정된 인덱스로 루프 진입
- 사용자 수정 → 인덱스 수정 후 다시 보여주고 재확인 (OK까지 반복)
- 확정된 인덱스는 `_workspace/00_screen_index.md` 에 저장
- **제외한 페이지와 판독 불가 항목을 반드시 함께 보여준다** — 조용히 빠진 페이지가 누락의 원천이다
- 화면 수가 많으면(예: 50개 초과) 사이클 수를 알리고 **범위 축소 여부를 확인한다**

#### 1-D. 양식 확정 — sheet-analyst 실행 (1-A와 병렬)

1-A와 동시에 시작. **양식 지식은 커밋된 사양 파일에서 오고, 대상 시트에서는 변화만 확인한다.**

| 모드 | 조건 | 동작 |
|------|------|------|
| **A. 드리프트 검증** (기본) | `.claude/formats/` 에 사양이 있음 | 사양 로드 + **대상 시트 헤더 1행 + 마지막 20~50행** 실측 |
| **B. 사양 갱신** | 사양이 없거나 사용자가 `"양식 사양 갱신"` 을 요청 | 참고 시트 **전수 스캔** → 사양 파일 갱신 |

산출물은 두 모드 모두 `_workspace/02_sheet_format.md` 이며, 최상단에 **어느 모드였는지 명시**한다.

**모드 A에서 확인하는 것:**

| 항목 | 처리 |
|------|------|
| 헤더가 사양과 일치 | 통과 |
| **헤더 불일치** (컬럼 추가·삭제·이름·순서 변경) | **Critical — 작성 중단 + 사용자 확인.** 사양 갱신(모드 B) 여부를 묻는다 |
| 사양 외 enum 값 발견 | Major — 보고 후 진행 여부 확인 (오타일 수도, 신규 enum일 수도) |
| 마지막 TC ID | 다음 시작 번호 = 실측값 + 1 |
| 대상 탭이 비어 있음/미존재 | 정상. 사양의 **헤더 원문으로 헤더 행 생성** (Phase 3) |

**참고 시트는 모드 B에서만 필요하다.** 평상시 사용자에게 참고 시트 URL을 요구하지 않는다.

**프로파일 선택은 Phase 0 (1) 제품 유형에서 이미 확정됐다.** 여기서는 대상 시트에 데이터가
있으면 솔루션 컬럼 실측값과 **대조만** 하고, 어긋나면 보고한다 (`"제품 유형은 TROMBONE인데 시트
솔루션 컬럼은 VIOLA입니다"`). 양식은 **`common.md` + 해당 프로파일 두 개를 함께** 로드한다.
상세 규칙은 `sheet-analyst` A-1 참조.

**모드 결정 보정:** Phase 0에서 사용자가 생성 모드(atomic/scenario)를 명시하지 않은 경우,
사양의 검증 단위 판정을 사용자에게 보고하고 진행 확인을 받는다.

#### 1-E. 역할별 브리핑 생성 (루프 진입 전 1회)

에이전트 호출마다 사양·인덱스 전문이 다시 올라간다. 비용은 **컨텍스트 크기 × 턴 수** 이므로
(실측: 고정 문서가 화면당 531KB · 34화면 17.6MB 재전송) 역할에 필요한 절만 남긴 브리핑을
**루프 진입 전 1회** 만들고, 화면 에이전트에게는 **브리핑만** 준다.

```bash
# Phase 0 확정값 표를 파일로 먼저 저장 (0-4에서 사용자에게 보여준 그 표)
#   → _workspace/00_phase0.md

for R in analyst writer reviewer; do
  python scripts/build_brief.py --role=$R \
      --profile={viola|trombone|bootfactory} --doc-type={신규|변경} \
      --phase0=_workspace/00_phase0.md \
      --index=_workspace/00_screen_index.md \
      --out=_workspace/00_brief_$R.md
done
# 문서 기본이 `신규` 인데 변경 정책 예외 화면이 있으면 --has-change-exception 를 함께 준다
```

- **요약이 아니라 사양 절 원문 발췌다.** 문장을 줄이지 않으므로 규칙이 빠지지 않는다.
  요약본을 만들면 빠진 규칙이 전 행에 번지므로 그 방식은 쓰지 않는다
- `--doc-type=신규` + 예외 없음이면 **변경분 모드 절이 제외**된다 (쓰지 않는 규칙을 싣지 않는다)
- 화면 인덱스 슬림판은 **`analyst` 브리핑에만** 들어간다 — writer·reviewer는 담당 화면
  분석서 하나로 작업하므로 인덱스가 필요 없다
- **사양을 고친 뒤에는 `--coverage-check` 를 돌린다.** 새 절이 어느 역할에도 배정되지
  않으면 **어느 브리핑에도 들어가지 않아 조용히 사라진다.** 그래서 미배정을 실패로 만들었다

```bash
python scripts/build_brief.py --coverage-check    # 사양 수정 후 필수
```

- 브리핑에 없는 규칙이 필요하다고 판단되면 에이전트가 **원천 사양을 직접 열어도 된다** —
  브리핑은 기본 로드를 줄이는 장치이고 원천 접근을 막는 장치가 아니다

### Phase 2~4: 화면 루프

1-C에서 확정된 화면 인덱스를 **순번대로** 처리한다. 각 화면은 분석 → TC 생성/작성 → 리뷰가
완료된 후 다음 화면으로 넘어간다. **화면 하나가 시트에 쓰이고 나서 다음 화면이 시작된다** —
진행 중에도 사용자가 시트에서 지금까지 작성된 분량을 확인할 수 있다.

```
for 배치 in 배치 목록 (B01, B02, … 순):          # 1-B-1. 대개 화면 1~3개
    배치 소속 화면 전부 → 상태 분석중
    Phase 2: 배치 분석  → 화면별 01_prd_analysis_s{NN}.md      (에이전트 1회)
    배치 소속 화면 전부 → 상태 작성중
    Phase 3: TC 생성    → 화면별 03_testcases_s{NN}.md + 03_rows_s{NN}.tsv
             시트 append 는 **화면 단위로 나눠** 하고 화면별 시트 행 기록  (에이전트 1회)
    Phase 4: 배치 리뷰  → 화면별 04_review_report_s{NN}.md      (에이전트 1회)
    화면별로 상태 → 완료 (그 화면이 실패했으면 그 화면만 실패)
```

**`{NN}` 은 인덱스 순번이다** (CH-ID 접두가 아니다 — 둘은 어긋날 수 있다).
**배치는 호출 단위이고 산출물·상태·시트 행은 화면 단위다.** 배치로 합쳐 저장하면 화면 하나만
다시 만들 수 없어 화면 단위 재편의 이득이 사라진다.
**인덱스 상태는 매 단계 후 갱신한다.** 이 파일이 진행 상태의 단일 출처이므로, 갱신하지 않으면
중단 후 이어 실행이 어디서 끊겼는지 알 수 없다.

#### Phase 2: 화면 분석

`prd-analyst` 1개 에이전트가 그 화면의 페이지 이미지를 **순차적**으로 읽어 분석한다.

- 입력: **화면 ID 원문 · 페이지 범위 · CH-ID 접두 · 소속 간지 · 그 화면의 정책**, 전체 이미지
  (+ PDF 입력 시 Description 크롭 이미지), 판독 이슈 페이지 목록(1-A-2),
  (변경 정책인 경우) **그 화면 페이지 분의** 변경 표시 검출 결과·실측 표시색·확정 오탐 목록(1-A-3),
  `_workspace/00_cid_register.md` 경로, **`_workspace/00_brief_analyst.md`**
  (Phase 0 확정값 + 사양 발췌 원문 + 화면 인덱스 슬림판이 이 한 파일에 있다)
- 상세 분석 절차: `prd-analyzer` 스킬 참조
- 출력: `_workspace/01_prd_analysis_s{NN}.md`

분석 중 모호한 항목은 "확인 불가"로 명시하고 진행 (추측 금지).

**인덱스(슬림판)를 넘기는 이유** — 목록↔상세처럼 화면 간 연결이 있는 기획서에서 자기 화면만
보면 맥락이 끊긴다. 다른 화면의 존재와 ID를 알아야 상호 참조를 판독할 수 있다. 다만 진행
관리용 컬럼(`색tl`·`케이스 수`·`상태`·`시트 행`)은 분석에 쓰이지 않으므로 슬림판에서 제외된다.

**에이전트 프롬프트에 반드시 포함할 것 — Phase 0에서 확정한 값을 그대로 넘긴다:**

| 항목 | 왜 넘겨야 하는가 |
|------|----------------|
| **제품 유형** (`VIOLA K8s` / `VIOLA CI/CD` / `TROMBONE` / `BootFactory`) | 분석 컨텍스트. **관리대상 판정을 시키지 않는다** — 그 절차는 2026-09-02에 폐지됐다 |
| **기획서 유형** (`신규` / `변경`) | 문서 전체 기본 분석 정책. `변경` 이면 `prd-analyzer` PDF-3.5 경로 |
| **예외 항목** (화면 ID 목록) | 그 화면만 **반대 정책으로 분석**한다. 케이스 생성 단계에서 거르는 것이 아니다 — 기본이 `변경` 인데 예외 화면을 변경분만 뽑아 두면 전수 분석 근거가 분석서에 아예 없고 후속 단계가 복구할 방법이 없다 |
| **취소선 = 삭제 표기 여부** | 취소선은 색 검출에 잡히지 않는다. 알려주지 않으면 삭제 변경분이 통째로 누락된다 |
| **CH-ID 접두** (`CH05` 등) | 변경분 CH-ID를 `CH{접두}-N` 으로 매긴다. 인덱스 순번과 다를 수 있으므로 인덱스 값을 그대로 넘긴다 |
| **C-ID 레지스터 경로** | 공통 DESC 번호는 레지스터에서 **읽어 쓴다.** 로컬 번호를 매기지 않는다 — 없는 정의를 발견하면 발급을 요청한다 |

- `## 이미지 판독 이슈` 섹션 산출 의무 (이슈가 없으면 "판독 이슈 없음" 명시)
- 판독 `불가` 페이지는 추측으로 채우지 않고 `[판독 불가]`로 남길 것
- 예외 화면 항목에는 **`[정책 예외]`** 표시를 남길 것

#### Phase 3: TC 생성 + 시트 작성

`testcase-writer`에게 작업 할당:

- 입력: `_workspace/01_prd_analysis_s{NN}.md` + `_workspace/02_sheet_format.md` + 대상 시트 URL·탭명
  + **`_workspace/00_brief_writer.md`**(Phase 0 확정값 + 양식 발췌 원문) + **CH-ID 접두**
  + `_workspace/00_cid_register.md`
- **양식은 브리핑에 발췌 원문으로 들어 있다.** 브리핑에 없는 절이 필요하면 `.claude/formats/common.md`
  + 해당 프로파일을 직접 열어도 된다 — 다만 기본 로드는 브리핑으로 한다
- **예외 화면 케이스의 피드백에 `[정책 예외] 문서 기본=… / 이 화면=…` 을 남기도록 지시한다**
- 작업:
  1. 케이스 도출 (`testcase-generator` 스킬) — 판독 이슈 페이지 처리 규칙 적용 (0-J)
  2. `_workspace/03_testcases_s{NN}.md`(메타·요약·근거 매핑) + `_workspace/03_rows_s{NN}.tsv`
     (시트에 보낼 23컬럼 원본, 스크립트 전용) 작성 — **케이스 본문을 `.md` 에 중복 저장하지 않는다.**
     실측에서 `.md` 의 65%가 시트와 같은 케이스 전문이었고 리뷰어가 같은 텍스트를 두 번 읽었다.
     `.tsv` 는 append 부분 실패 시 복구 경로이며 사람도 모델도 읽지 않으므로 컨텍스트 비용이 0이다
     - 케이스 수는 **실제 작성분을 센 정확한 값** 사용 (추정 금지)
     - **프로파일 분포 대조는 여기서 하지 않는다.** 화면 1개 표본으로는 편차가 의미를 갖지
       못한다 — Phase 5 전체 집계에서 1회 측정한다
  3. **검토 게이트** (**첫 화면만**):
     - `03_testcases_s01.md` 요약을 사용자에게 보여주고 진행 확인
     - 이후 화면은 자동 진행
     - **첫 화면에서 문체·태그·enum을 잡아야 나머지 전 행에 번지지 않는다**
  4. 사용자 OK (또는 자동 진행) → `sheet-operator`로 시트에 작성
     - 대상 탭이 없으면 `add_tab` → **생성 직후 `metadata` 의 `title` 을 복사** → `common.md` 의 **헤더 원문**을 `A1:W1` (23컬럼)에 기입 → 2행부터 batch append
     - 기존 탭이면 batch append (헤더 대조는 1-D에서 이미 완료)
  5. 작성된 행 범위 보고 → **오케스트레이터가 인덱스의 `시트 행` 칸에 기록**

#### Phase 4: 화면 리뷰

`testcase-reviewer`에게 작업 할당:

- 입력: 그 화면의 01·03 파일 + `02_sheet_format.md` + 실제 시트의 작성된 행 범위
  + **`_workspace/00_brief_reviewer.md`**(Phase 0 확정값 + 양식 발췌 원문)
- 작업: 세 경계면 교차 비교 (기획 ↔ 케이스, 양식 ↔ 케이스, 로컬 ↔ 시트)
- 출력: `_workspace/04_review_report_s{NN}.md`

**화면 리뷰에서 제외하는 점검 — 전역 지표이므로 Phase 5로 이관됐다:**

| 제외 항목 | 이유 |
|----------|------|
| **분포 편차 점검 (`testcase-reviewer` 3-1)** | 화면 1개 표본은 5~20건이다. 이 표본으로 프로파일 실측 분포와 대조하면 **지배 구분 역전이 상시 Critical로 뜬다** |
| **TC ID 연속성** | 시작 번호·중복·결번은 탭 전역 지표다 |

**리뷰어 프롬프트에 반드시 넣을 오판 방지 항목:**

- **제품 유형 → 프로파일**을 명시한다. 프로파일마다 **정반대인 규칙**이 있다 (UI 라벨 백틱 ↔ 대괄호, 지배 구분 `표시` ↔ `정상`, `정상`의 우선순위 P1·P2만 ↔ P1~P4 전부). 한쪽 기준으로 다른 쪽을 지적하는 것이 대표적 오판이다
- **기획서 유형이 `변경` 이면 비변경분 미작성은 정상**이다 — 누락으로 지적하지 않는다
- **예외 화면이 문서 기본 정책과 다르게 작성된 것은 정상**이다 — 그게 예외의 정의다. 대신 ① 예외 화면이 실제로 반대 정책으로 작성됐는가 ② `[정책 예외]` 표시가 있는가 ③ 예외 목록에 없는 화면이 반대 정책으로 작성되지 않았는가(범위 초과)를 점검한다
- **관리대상 컬럼은 폐지됐다** — 부재를 결함으로 지적하지 않는다
- **분포 편차와 TC ID 연속성은 이 단계에서 지적하지 않는다** — 표본이 한 화면뿐이다
- **작성자 자기 점검표를 인용하지 말고 독립 실측하라**

**Critical 이슈 발생 시:**
- 리뷰어가 `testcase-writer`에게 재작성 요청
- writer가 수정 → reviewer가 재리뷰 (최대 1회 루프)
- 두 번째 리뷰에도 Critical이 남으면 사용자에게 결정 위임 후 다음 화면 진행

> **첫 화면 리뷰 후 패턴 이슈 발견 시:** Critical이 특정 패턴(예: 표시 형식 케이스 누락, enum 오류)에서 나왔다면 남은 화면 진행 전 사용자에게 보고하고 방향 조정 여부를 확인받는다. **화면 단위는 반복 횟수가 많아 패턴 오류의 번짐이 더 크다.**

산출물은 **파일**이고, 리턴은 **파일을 가리키는 영수증**이다. 리턴에 케이스 표·분석 전문·
위반 목록 전문을 담으면 그 텍스트가 오케스트레이터 컨텍스트에 쌓이고, 이후 **모든 턴에서
다시 읽힌다.**

| 리턴에 담을 것 | 담지 않을 것 |
|--------------|-------------|
| 산출물 파일 경로 | 케이스 표·분석 전문·리뷰 위반 목록 전문 |
| 건수 (케이스 수·위반 수·Critical/Major/Minor) | 개별 케이스 본문·근거 태그 나열 |
| 시트 작성 행 범위 | 컬럼별 판정 근거 서술 |
| 다음 단계에 필요한 값 (CH-ID 소진분·C-ID 발급 요청) | 자기 점검표 |
| 사용자 결정이 필요한 항목 1~3개 | 이미 파일에 쓴 내용의 재서술 |

> **실측 근거:** 화면 34개 실행에서 오케스트레이터 컨텍스트가 **평균 40만 토큰**까지 자랐고,
> 877턴 동안 계속 재사용돼 **전체 비용의 25.5%** 를 오케스트레이터 혼자 썼다.
> 오케스트레이터가 상세를 알아야 할 때는 **그때 파일을 열면 된다** — 상시 보유할 이유가 없다.

## 에러 핸들링

| 에러 유형 | 대응 |
|----------|------|
| Figma 토큰 누락/만료 | 즉시 중단 + 토큰 재발급 안내 |
| Figma API 403/404 | 파일 권한·URL 재확인 요청 |
| 시트 권한 없음 (403) | 서비스 계정 이메일 공유 안내 + 사용자 확인 후 재시도 |
| 시트 ID 잘못됨 (404) | URL 재확인 요청 |
| API rate limit (429) | 60초 대기 후 1회 재시도, 실패 시 부분 결과 보고 |
| 시트 쓰기 부분 실패 | 어디까지 작성됐는지 명시 + 미작성 케이스 ID 목록 보고 |
| 화면 식별자를 어느 페이지에서도 찾지 못함 | 인덱스 생성 불가 → 사용자에게 식별자 필드명·위치 확인 요청. **간지 단위로 임의 폴백하지 않는다** |
| 특정 페이지의 화면 ID 판독 불가 | 인덱스에 `[판독 불가]` 로 등재 + 1-C에서 사용자 확인. 추정 금지 |
| 인덱스에 없는 화면 ID가 분석 중 발견 | 보고 후 인덱스에 추가. **임의로 진행하지 않는다** — 인덱스가 진행 상태의 단일 출처이므로 우회하면 상태가 깨진다 |
| 기존 탭에 챕터 의미의 CH-ID가 존재 | `sheet-analyst` 실측 최대 `NN` 다음부터 배정. 실측 불가 시 사용자 확인 (`common.md` 「CH-ID 충돌 방지」) |
| 화면 분석 결과 0건 | 사용자에게 그 화면의 페이지 범위 재확인 요청 후 재시도 또는 스킵 |
| 화면 하나 처리 실패 | 인덱스 상태 `실패` 기록 후 다음 화면 진행. Phase 5 보고서에 누락 명시 |
| **배치 중 일부 화면만 실패** | 그 화면만 `실패` 로 남기고 **배치의 나머지는 계속 진행**한다. 배치 전체를 실패로 처리하지 않는다 |
| **배치가 컨텍스트 한도에 근접** | 그 배치를 화면 단위로 쪼개 재실행한다. 묶음 조건(페이지 합 3장 이하)을 넘겼는지 확인 |
| **배치에 정책이 섞여 있음** | 1-B-1 조건 위반이다. 배치를 정책별로 분리한 뒤 재실행 (섞인 채 진행하면 절반이 반대 기준으로 작성된다) |
| 화면 수 과다 (예: 50개 초과) | 1-C 게이트에서 사이클 수(`3N+1`)를 알리고 범위 축소 여부 확인 |
| 대상 시트 헤더가 사양과 불일치 | **작성 중단** + 사용자 확인. 사양 갱신(모드 B) 또는 대상 탭 교체 |
| Phase 0 기본 정보 5개 중 하나라도 미확정 | **진행 중단** — 사용자에게 묻는다. 추정 금지 |
| 제품 유형에 해당하는 프로파일 파일이 없음 | 새 제품 가능성 → 참고 시트로 프로파일 신규 작성(모드 B) 제안 |
| 제품 유형 ↔ 대상 시트 솔루션값 불일치 | **보고 후 확인** — 어느 쪽이 맞는지 사용자가 판단 |
| 한 탭에 두 제품 솔루션값이 섞여 있음 | 최다값 사용 + 사용자에게 보고 (프로파일은 제품 단위) |
| `기존` 탭 지정인데 그 탭이 없음 | 오타인지 신규인지 확인. **임의로 생성하지 않는다** |
| `기존` 탭 헤더가 23컬럼이 아님 | **작성 중단** — 그냥 append하면 전 값이 밀린다 |
| 예외 항목 화면 ID가 기획서에 없음 | 보고 후 확인 (오타 가능성). 임의로 무시하지 않는다 |
| 이미지 판독 품질 `주의` | 사용자 통보 + 진행. 해당 페이지 케이스 피드백에 `[판독 주의]` 기재 |
| 이미지 판독 품질 `불가` (해상도 심각 부족·훼손·백지) | 사용자 통보 + 원본 재전달 요청. 재전달 전 진행 시 해당 페이지는 판독 불가 케이스로만 남김 (추측 금지) |
| 이미지 파일이 열리지 않음 (손상) | 파일명·사유 명시해 보고. "분석 완료"로 처리하지 않음 |
| 이미지 파일명 정렬 ≠ 페이지 순서 | 사용자에게 순서 확인 요청 (추정 금지) |
| `pillow`/`numpy` 미설치 (이미지 입력) | `pip install pillow numpy` 안내 후 중단 |

**원칙:** 1회 재시도 후 재실패 시 해당 화면 결과 없이 다음 화면으로 진행하고, 인덱스 상태를 `실패` 로 남기고 보고서에 누락을 명시한다.
