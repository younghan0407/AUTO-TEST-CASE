# Testcase Reviewer

`testcase-writer`가 작성한 케이스를 세 가지 경계면에서 교차 검증한다.

## 트리거 키워드

- "테스트 케이스 리뷰", "TC 검토", "케이스 품질 점검"
- "빠진 케이스 있나 확인", "양식 위반 검사"
- "작성된 시트 검증"

## 핵심 원칙 — 경계면 교차 비교

QA의 핵심은 "케이스가 N개 작성되었다" 같은 **존재 확인**이 아니다. 다음 세 경계면을 비교한다:

| 경계면 | 비교 대상 | 검증 질문 |
|--------|----------|----------|
| **기획 ↔ 케이스** | `01_prd_analysis.md` ↔ `03_testcases.md` | 모든 기능 단위가 커버됐는가? 추측에 기반한 케이스는 표시됐는가? |
| **양식 ↔ 케이스** | `02_sheet_format.md` ↔ `03_testcases.md` | 컬럼 순서·enum 값·ID 체계가 일치하는가? |
| **로컬 ↔ 시트** | `03_testcases.md` ↔ 실제 시트 내용 | 작성된 행과 로컬 산출물이 동일한가? 빠진 행은 없는가? |

세 경계면 중 하나라도 빠뜨리면 QA의 의미가 없다.

## 작업 흐름

### 1. 입력 자료 로드

다음 4개를 모두 읽는다:
1. `_workspace/01_prd_analysis.md` — **`## 이미지 판독 이슈` 섹션을 반드시 함께 읽는다** (5-3 검증 기준)
2. `_workspace/02_sheet_format.md` — **최상단의 모드(A 드리프트 검증 / B 전수 스캔 갱신)를 먼저 확인한다.** 여기에 헤더 대조 결과와 다음 TC ID가 기록되어 있다. 양식 원문은 `.claude/formats/{사양}.md` 를 함께 읽는다
3. `_workspace/03_testcases.md`
4. 실제 시트 내용 (sheet-operator로 작성된 범위 읽기)

하나라도 없으면 어느 단계가 실패했는지 보고하고 검토 중단.

### 2. 기능 커버리지 매트릭스 생성

| 기능 단위 | 작성 케이스 수 | 정상 | 비정상 | 엣지 | 충분성 평가 |
|----------|--------------|------|--------|------|-----------|

평가 기준:
- **부족 (Critical):** 정상 흐름이 0개거나, 핵심 기능에 비정상이 없음
- **보완 권장 (Major):** 엣지 케이스가 전혀 없는 핵심 기능
- **충분 (OK):** 정상·비정상이 균형 있게 존재

### 3. 양식 준수 점검

**기준은 양식 사양(`.claude/formats/{사양}.md`)이다.** 시트를 보고 양식을 역추론하지 않는다 — 역추론하면
잘못 쓰인 행이 기준이 되어 위반을 정상으로 판정한다.

각 케이스 행에 대해:
- 컬럼 수·순서가 사양과 일치하는가 (사양은 A~W 23컬럼, X열 이후 사용 금지)
- enum 컬럼 값이 사양의 허용 enum 안에 있는가 (사양 외 값은 1-D에서 보고됐어야 한다)
- ID가 사양 규칙을 따르는가 + **시작 번호가 `02_sheet_format.md`의 실측 마지막 ID + 1 인가**
- 미사용 컬럼(사양에 `미사용`으로 표시된 열)이 공란인가 — 채워져 있으면 위반
- Depth 계열은 `-`, 미사용·실행 컬럼은 빈칸인가 (혼용은 위반)
- 필수 컬럼에 누락된 셀이 있는가 (비고(V)는 실질 필수)
- 문체가 사양과 맞는가 — 절차 `N. ` 접두, 예상 결과 명사형 종결, 사전조건 1줄

**사양과 시트가 충돌할 때의 권위**는 사양 파일의 "권위 규칙" 표를 따른다. 컬럼 구조·마지막 ID는
대상 시트가, 문체·검증 단위·미사용 컬럼 정책은 사양이 이긴다.

**⚠️ 제품별 사양을 확인하고 그 기준으로만 판정한다.** `02_sheet_format.md` 최상단의 사용 사양
이름을 먼저 본다. 제품마다 정반대인 항목이 있어 **다른 제품 기준으로 지적하면 잘못된 리뷰**가 된다:

| 항목 | 제품별 차이 예 |
|------|--------------|
| UI 라벨 | 한쪽은 백틱, 다른 쪽은 대괄호 — **대괄호를 "백틱 누락"으로 지적하면 오판** |
| 지배 구분 | `표시` 과반 vs `정상` 과반 — **`표시`가 적은 것이 정상인 제품이 있다** |
| `정상`의 우선순위 | P1/P2 한정 vs P1~P4 전부 — **`정상`+P3를 위반으로 지적하면 오판** |
| 사전조건 | 100% 필수 vs 공란 허용 — **공란을 누락으로 지적하면 오판** |
| 팝업 3 Depth | `상세` 고정 vs 화면 성격에 따름 |
| TC ID | 제품 전역 연속 vs 모듈별 연속 |

**⚠️ 오판 주의:** `02_sheet_format.md`가 **모드 A(사양 재사용)** 인 경우, 참고 시트 전수 분석 결과가
없는 것이 **정상**이다. "양식 분석이 부실하다"고 지적하면 잘못된 리뷰다.

위반 발견 시 표 형태로 구체적으로 지적:

```markdown
| TC-ID | 위반 컬럼 | 발견 값 | 양식 기준 | 권고 |
| TC-LOGIN-013 | 우선순위 | Critical | High/Medium/Low | "High"로 수정 |
```

### 4. 시트-로컬 일치성 점검

`sheet-operator`로 작성된 행 범위를 읽어 `03_testcases.md`와 비교:
- 행 수 일치 여부
- 샘플 5개 행의 셀 내용 일치 여부
- 헤더 위치 적정성

불일치 발견 시 어느 쪽이 정답인지(보통 시트가 최종) 명시.

### 5. 공통 Description 항목 누락 점검

`01_prd_analysis.md`에서 `[공통 DESC]` 태그가 붙은 항목을 추출하고, 해당 항목이 태그에 명시된 **모든 페이지(화면 ID)** 에 대해 TC가 작성됐는지 확인한다.

| 공통 DESC 항목 | 대상 화면 ID | TC 작성 여부 |
|--------------|------------|------------|

누락 발견 시 Critical로 분류하고 `testcase-writer`에게 해당 페이지의 TC 추가 요청.

### 5-1. UI ↔ Description 불일치 반영 점검

`01_prd_analysis.md`에서 `[UI↔DESC 불일치]` 태그가 붙은 항목을 추출하고, `03_testcases.md`와 실제 시트에서 해당 내용이 TC 비고(확인사항) 컬럼에 기재됐는지 확인한다.

| 불일치 항목 | 관련 TC-ID | 비고 컬럼 기재 여부 |
|-----------|----------|-----------------|

누락 발견 시 Major로 분류. 기획 확인이 필요한 사항이므로 즉시 수정보다 사용자 인지가 우선.

### 5-2. 변경분 한정 모드 검증

분석 결과 메타정보에 `분석 방식: 변경분(빨강 표시) 한정 분석`이 있으면 **검증 기준을 전환한다.**

**⚠️ 오판 주의:** 이 모드에서는 비변경분에 케이스가 없는 것이 **정상**이다.
전체 분석 기준으로 "Description 항목 누락"을 지적하면 잘못된 리뷰다. 반드시 모드를 먼저 확인할 것.

점검 항목:

| # | 점검 내용 | 위반 시 |
|---|----------|--------|
| 1 | 변경분 목록의 **모든 항목**이 최소 1건 TC로 커버되는가 | Critical |
| 2 | 삭제 유형 변경분에 "더는 노출되지 않음" 검증 TC가 있는가 | Critical |
| 3 | `[맥락 — 비변경분]` 항목으로 만든 TC가 섞여 있지 않은가 (범위 초과) | Major |
| 4 | 각 TC 비고에 `[변경 {CH-ID} {유형} {버전-일자}]` 근거가 기재됐는가 (**CH-ID 누락은 역추적 불가**) | Major |
| 4-1 | **절차·예상 결과가 비고가 선언한 변경분을 실제로 검증하는가** (변경 전에도 성립하는 케이스는 실질적 범위 초과) | Major |
| 4-2 | 기획 미정의 항목의 예상 결과가 단정되어 있지 않은가 (예상 결과 단정 + 피드백 `[확인 불가]`는 자기모순 → 실행자가 오판) | Major |
| 4-3 | 현재 기획서에 근거 없는 값을 다른 챕터·참고 시트에서 가져와 단정하지 않았는가 | Major |
| 5 | 구분(H) enum에 `변경` 등 신규 값을 만들지 않았는가 | Major |
| 6 | `[스티커 전용]` / `[DESC 전용]` / `[변경 표기 불일치]` 항목이 케이스화되고 확인 필요로 기재됐는가 | Major |
| 7 | 위치·순서 변경 / 디자인 변경 항목이 `표시` 구분으로 검증되는가 | Minor |
| 8 | `03_testcases_ch{N}.md`에 `생성 범위: 변경분 한정`이 명시됐는가 | Minor |

**변경분 커버리지 매트릭스**를 보고서에 포함한다 (변경분 목록 항목 ↔ 커버 TC ID). 커버리지 100% 미달 시 미커버 항목을 전부 나열한다.

### 5-3. 이미지 판독 이슈 반영 검증

`01_prd_analysis*.md`의 `## 이미지 판독 이슈` 섹션과 시트를 대조한다.

| # | 점검 내용 | 위반 시 |
|---|----------|--------|
| 1 | `## 이미지 판독 이슈` 섹션이 존재하는가 (이슈 없으면 "판독 이슈 없음" 명시) | Major |
| 2 | `주의` 페이지 근거 케이스의 피드백 컬럼에 `[판독 주의]`가 기재됐는가 | Major |
| 3 | `불가` 페이지에 판독 불가 케이스가 1건 존재하는가 (조용한 스킵은 누락) | Critical |
| 4 | `불가` 페이지의 예상 결과가 단정되지 않았는가 (`ㄴ … PASS/FAIL 판정 대신 …` 패턴) | Major |
| 5 | 판독 이슈가 사용자에게 보고됐는가 (오케스트레이터 로그·보고서에 기록) | Major |

**⚠️ 오판 주의:** 판독 `불가` 페이지에 상세 케이스가 없는 것은 **정상**이다. 이를 "Description 누락"으로 지적하면 잘못된 리뷰다. 먼저 판독 이슈 섹션을 확인할 것.

### 6. 케이스 품질 점검

각 케이스 본문 자체의 품질:

| 안티 패턴 | 예시 | 조치 |
|----------|------|------|
| **검증 목표 다중** | 한 케이스에 3개 이상 검증 | 분리 권고 |
| **측정 불가** | "잘 동작해야 한다" | 구체적 결과 명시 권고 |
| **단계 모호** | "여러 번 클릭한다" | 횟수 명시 |
| **사전조건 누락** | 로그인 필요한데 조건에 없음 | 추가 |

### 7. 추측 기반 케이스 표시

`03_testcases.md`의 "기획 확인 필요 항목" 섹션을 그대로 가져와 리뷰 보고서에 인용. 이 항목들이 시트에 실제 작성됐다면 비고 컬럼에 표시가 있는지 점검.

### 8. 보고서 작성

`_workspace/04_review_report_ch{N}.md`에 결과 저장. 형식은 `testcase-reviewer` 에이전트 정의의 출력 프로토콜 참조.

## 권고 분류

리뷰 결과를 다음 3단계로 분류:

| 권고 | 의미 | 후속 조치 |
|------|------|----------|
| **Critical (즉시 수정)** | 양식 위반, 핵심 기능 누락, 시트-로컬 불일치 | `testcase-writer` 재호출하여 수정 |
| **Major (확인 권장)** | 엣지 케이스 부족, 추측 기반 케이스 다수 | 사용자에게 결정 위임 |
| **Minor (참고)** | 표현 개선, 우선순위 재조정 제안 | 정보 제공만 |

## 작업 원칙

1. **임의로 수정하지 않는다.** 리뷰어가 케이스를 직접 고치면 작성자의 의도가 묻힌다. 발견된 문제를 보고하고 `testcase-writer`가 수정한다.

2. **구체적으로 지적한다.** "양식이 맞지 않음" 같은 추상적 표현 금지. TC-ID, 컬럼명, 발견값, 기준값을 명시.

3. **점진적 검토 가능.** 케이스가 많으면 기능 단위로 묶어 검토하고 부분 보고서 작성도 허용.

4. **재검토 시 개선 평가.** `_workspace/04_review_report.md`가 이미 있으면 이전 보고서와 비교하여 어떤 이슈가 해결됐고 어떤 게 남았는지 명시.
