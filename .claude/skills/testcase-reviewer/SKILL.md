# Testcase Reviewer

`testcase-writer`가 작성한 케이스를 세 가지 경계면에서 교차 검증한다.

## 트리거 키워드

- "테스트 케이스 리뷰", "TC 검토", "케이스 품질 점검"
- "빠진 케이스 있나 확인", "양식 위반 검사"
- "작성된 시트 검증"

## 핵심 원칙 — 경계면 교차 비교

QA의 핵심은 "케이스가 N개 작성되었다" 같은 **존재 확인**이 아니다. 다음 세 경계면을 비교한다:

| 경계면 | 비교 대상 | 검증 질문 |
|--------|----------|----------|
| **기획 ↔ 케이스** | `01_prd_analysis.md` ↔ `03_testcases.md` | 모든 기능 단위가 커버됐는가? 추측에 기반한 케이스는 표시됐는가? |
| **양식 ↔ 케이스** | `common.md` + `profile-{제품}.md` (+ `02_sheet_format.md` 실측) ↔ `03_testcases.md` | 컬럼 순서·enum 값·ID 체계·문체가 일치하는가? |
| **로컬 ↔ 시트** | `03_testcases.md` ↔ 실제 시트 내용 | 작성된 행과 로컬 산출물이 동일한가? 빠진 행은 없는가? |

세 경계면 중 하나라도 빠뜨리면 QA의 의미가 없다.

## 작업 흐름

### 0. 리뷰 전제 확인 — 프롬프트로 받는 3개

오케스트레이터가 `testcase-auto` **Phase 0 기본 정보 수집**에서 확정한 값을 리뷰어에게 전달한다.
**이 3개를 모르면 리뷰 기준 자체가 성립하지 않는다** — 받지 못했으면 추정하지 말고 오케스트레이터에게 묻는다.

| # | 받는 값 | 리뷰에서 쓰는 곳 |
|---|--------|----------------|
| 1 | **제품 유형** (`VIOLA K8s` / `VIOLA CI/CD` / `TROMBONE` / `BootFactory`) | 어느 프로파일로 판정할지 (3절) |
| 2 | **기획서 유형** (`신규` / `변경`) — **문서 전체 기본 정책** | 케이스화 범위·비고 태그 기준 (5-2) |
| 3 | **예외 항목** — 기본 정책과 **반대 정책**을 적용할 화면 ID 목록 (없으면 "없음") | 정책 예외 점검 (3-3) |

**⚠️ 기획서 유형은 문서 전체 기본값이지 전 화면 고정값이 아니다.** 예외 목록에 오른 화면은
반대 정책으로 작성된 것이 **정상**이다. 이를 결함으로 지적하는 것이 이 리뷰의 새로운 대표 오판이다 (3-3).

### 1. 입력 자료 로드

다음 5개를 모두 읽는다:
1. `_workspace/01_prd_analysis.md` — **`## 이미지 판독 이슈` 섹션을 반드시 함께 읽는다** (5-3 검증 기준)
2. **양식 사양 — `.claude/formats/common.md` + `.claude/formats/profile-{제품}.md` 두 개를 함께 읽는다.**
   **한쪽만 읽으면 판정 기준이 성립하지 않는다** — 컬럼 골격·태그 체계·`-` vs 빈칸은 `common.md` 에,
   문체·분포·enum 범위·TC ID 규칙은 프로파일에 있다. 제품 ↔ 프로파일 대응:

   | 제품 유형 | 프로파일 |
   |----------|---------|
   | `VIOLA K8s` · `VIOLA CI/CD` | `profile-viola` (둘은 **같은 프로파일**) |
   | `TROMBONE` | `profile-trombone` |
   | `BootFactory` | `profile-bootfactory` (**실측 없는 VIOLA 파생** — 편차 지적 시 이 사실을 함께 적는다) |

3. `_workspace/02_sheet_format.md` — **최상단의 모드(A 드리프트 검증 / B 전수 스캔 갱신)를 먼저 확인한다.** 여기에 헤더 대조 결과와 다음 TC ID가 기록되어 있다
4. `_workspace/03_testcases.md`
5. 실제 시트 내용 (sheet-operator로 작성된 범위 읽기)

하나라도 없으면 어느 단계가 실패했는지 보고하고 검토 중단.

### 2. 기능 커버리지 매트릭스 생성

| 기능 단위 | 작성 케이스 수 | 정상 | 비정상 | 엣지 | 충분성 평가 |
|----------|--------------|------|--------|------|-----------|

평가 기준:
- **부족 (Critical):** 정상 흐름이 0개거나, 핵심 기능에 비정상이 없음
- **보완 권장 (Major):** 엣지 케이스가 전혀 없는 핵심 기능
- **충분 (OK):** 정상·비정상이 균형 있게 존재

### 3. 양식 준수 점검

**기준은 양식 사양 두 개(`common.md` + 해당 프로파일)다.** 시트를 보고 양식을 역추론하지 않는다 —
역추론하면 잘못 쓰인 행이 기준이 되어 위반을 정상으로 판정한다.

각 케이스 행에 대해:
- 컬럼 수·순서가 **`common.md` 의 컬럼 구조 표**와 일치하는가
  - **전 제품 공통 23컬럼**이다. 마지막 컬럼은 `피드백` 이며 **그 뒤 열은 쓰지 않는다**
  - **2026-09-02에 VIOLA 전용 `관리대상` 컬럼이 폐지됐다.** 예전 문서의 24컬럼 표기를 기준으로
    삼지 말 것. 컬럼 수·순서 판정은 반드시 **`common.md` 의 표를 열어 대조**한다
- enum 컬럼 값이 사양의 허용 enum 안에 있는가 (사양 외 값은 1-D에서 보고됐어야 한다)
  - 우선순위 4종·구분 6종은 `common.md`, **3 Depth 범위와 결합 규칙은 프로파일**이다
- ID가 사양 규칙을 따르는가 + **시작 번호가 `02_sheet_format.md`의 실측 마지막 ID + 1 인가**
- 미사용 컬럼(사양에 `미사용`으로 표시된 열)이 공란인가 — 채워져 있으면 위반
- Depth 계열은 `-`, 미사용·실행 컬럼은 빈칸인가 (혼용은 위반)
- 필수 컬럼에 누락된 셀이 있는가 (`비고`는 실질 필수)
- 문체가 사양과 맞는가 — 절차 `N. ` 접두, 예상 결과 명사형 종결, 사전조건 1줄

**사양과 시트가 충돌할 때의 권위**는 `common.md` 의 "권위 규칙" 표를 따른다. 컬럼 구조·마지막 ID는
대상 시트가, 문체·검증 단위·미사용 컬럼 정책은 사양이 이긴다.

**⚠️ 프로파일마다 정반대인 항목이 있다 — 한쪽 규칙으로 다른 쪽을 지적하는 것이 이 리뷰의
대표적 오판이다.** 판정 전에 **제품 유형(Phase 0)과 `02_sheet_format.md` 최상단의 프로파일 이름**을
먼저 확인한다. 아래는 절충값이 존재하지 않는 항목들이다 — "중간쯤"으로 판정할 수 없다:

| 항목 | VIOLA · BootFactory | TROMBONE | 오판 예 |
|------|--------------------|----------|--------|
| **UI 라벨** | **백틱** `` `등록` `` (절차 65%) | **대괄호** `[등록]` (절차 백틱 **0.0% — 0/3,953행**) | TROMBONE 행의 대괄호를 "백틱 누락"으로 지적 |
| **지배 구분** | **`표시` 55.9%** (과반이 정상 상태) | **`정상` 65.1%** / `표시` 2.4% | TROMBONE에서 "`표시`가 적다 = 커버리지 부족"으로 지적 |
| **`정상`의 우선순위** | **`P1`·`P2` 만** (P3/P4 사례 0건) | **P1~P4 전부** (P3가 60%, P4도 193건) | TROMBONE의 `정상`+`P3`를 결합 규칙 위반으로 지적 |
| **사전조건** | **100% 필수** (공란 불가) | **92.1% — 공란 허용** | TROMBONE 표시 검증 행의 사전조건 공란을 누락으로 지적 |
| 팝업 `3 Depth` | **`상세` 고정** | 화면 성격에 따름 (`생성`/`목록`/`상세`/`-`) | |
| `3 Depth` 범위 | **4종 고정** (`목록`/`생성`/`수정`/`상세`) | 7종이되 **탭별 실사용 범위**가 다름 (대부분 3종) | 전역 허용 목록으로 판정 |
| TC ID | **제품 전역 연속** `TC_VIO_{3}` / `TC_BF_{3}` | **모듈(탭) 단위 연속** `TC_{모듈}_{3}` | |
| DESC 태그 표기 | `[DESC N항]` / `[DESC DN-N]` | **원문자** `[DESC ❶-N]` | 원문자를 형식 위반으로 지적 |

**`BootFactory` 프로파일은 실측이 아니라 VIOLA 파생이다.** 분포·문체 편차를 지적할 때는
**"프로파일 자체가 미검증"** 이라는 사실을 함께 적고, 반복되면 사양 갱신을 제안한다 (작성자 책임으로 몰지 않는다).

**⚠️ 오판 주의:** `02_sheet_format.md`가 **모드 A(사양 재사용)** 인 경우, 참고 시트 전수 분석 결과가
없는 것이 **정상**이다. "양식 분석이 부실하다"고 지적하면 잘못된 리뷰다.

위반 발견 시 표 형태로 구체적으로 지적:

```markdown
| TC-ID | 위반 컬럼 | 발견 값 | 양식 기준 | 권고 |
| TC-LOGIN-013 | 우선순위 | Critical | High/Medium/Low | "High"로 수정 |
```

### 3-1. 분포 편차 점검 (프로파일 실측 대비)

**해당 프로파일의** "구분 분포" 실측값과 작성된 케이스 분포를 대조한다. `common.md` 에는 분포가 없다.

| 구분 | 프로파일% | 작성% | 편차 | 판정 |
|------|----------|------|------|------|

- **±15%p 이상 편차 + 사유 없음 → Major.** 양식 이탈 신호다
- 특히 **지배 구분이 뒤바뀐 경우 → Critical** (예: 프로파일은 `정상` 65%인데 작성은 `표시`가 최다)
- 편차 사유가 `03_testcases_ch{N}.md`에 기재돼 있으면 그 타당성만 평가하고 위반으로 세지 않는다

**⚠️ 오판 주의:** 어느 구분이 지배적인지는 **프로파일마다 정반대**다 (VIOLA `표시` 55.9% ↔
TROMBONE `정상` 65.1%). 다른 프로파일 기준으로 지적하지 않는다.

실측 근거: `일반 v2` 탭에서 `정상` -44.9%p / `표시` +29.4%p 편차가 발생했고, 원인은
생성 정책이 제품 중립이 아니라 VIOLA 분포를 하드코딩한 것이었다 (`docs/baselines/trombone-general-v2.md`).

### 3-2. 컬럼 기재 규율 점검

| # | 점검 내용 | 위반 시 |
|---|----------|--------|
| 1 | 근거 태그(`[DESC …]` `[공통 DESC]`)가 **`비고`에만** 있는가 — `피드백`으로 새지 않았는가 | **Critical** (열 오배치. 실측 212행 사례) |
| 2 | 확인사항(`[확인 불가]` `[기획 확인]` `[UI↔DESC 불일치]`)이 **`피드백`에만** 있는가 | Major |
| 3 | 사양이 `실질 필수`로 표시한 컬럼에 공란이 없는가 | Critical |
| 4 | 사양이 `미사용`으로 표시한 컬럼이 공란인가 | Major (실측 69행 사례) |
| 5 | 구분 × 우선순위 결합 규칙(예외 0건 항목) 위반이 없는가 | Major |
| 6 | 3 Depth가 해당 모듈의 **실사용 범위** 안인가 (전역 허용 목록이 아니라) | Minor |

### 3-3. 정책 예외 점검 (예외 항목)

Phase 0에서 받은 **기획서 유형(문서 기본 정책)** 과 **예외 항목 화면 ID 목록**이 기준이다.
예외 목록이 "없음"이면 이 절은 "예외 없음 — 전 화면 기본 정책"만 확인하고 넘어간다.

**두 정책의 차이 (판정 기준):**

| | 변경 정책 | 신규 정책 |
|---|---|---|
| 케이스화 범위 | **변경 표기(색/취소선/스티커/`ChangeLog`)가 있는 항목만** | **화면 전수** |
| 비고 태그 | `[변경 CH{NN}-N …]` + 경로 태그 (`[DESC 전용]`·`[박스 + 스티커]` 등) | 일반 근거 태그 (`[DESC N항]`·`[UI]`·`[스티커]`) |
| 삭제 검증 | 취소선 항목에 "더는 노출되지 않음" 검증 **필수** + **삭제 내용의 정상 동작 케이스 금지** (양방향, 5-2-1) | 해당 없음 |

**점검 항목:**

| # | 점검 내용 | 위반 시 |
|---|----------|--------|
| 1 | **예외 화면의 케이스가 실제로 반대 정책으로 작성됐는가** — 기본이 `변경` 인데 예외 화면이 변경분만 다뤘거나, 기본이 `신규` 인데 예외 화면을 전수 케이스화했으면 정책 미적용 | **Critical** |
| 2 | 예외 화면 케이스의 **비고 태그 체계가 그 화면의 정책과 맞는가** — 신규 정책 화면에 `[변경 CH…]` 가, 변경 정책 화면에 변경 근거 없는 일반 태그만 있으면 위반 | Major |
| 3 | 예외 화면 케이스의 **피드백에 `[정책 예외] 문서 기본={신규\|변경} / 이 화면={변경\|신규}`** 가 있는가 — 없으면 왜 이 화면만 다른지 역추적 불가 | Major |
| 4 | **예외 목록에 없는 화면이 반대 정책으로 작성되지 않았는가** (범위 초과) — 기본이 `변경` 인데 목록에 없는 화면을 전수 케이스화했으면 범위 초과, 기본이 `신규` 인데 목록에 없는 화면을 변경분만 다뤘으면 누락 | **Critical** |
| 5 | 예외 화면이 **변경 정책**인 경우, 그 화면에 한해 **5-2 + 5-2-1 + 5-2-2 의 변경분 점검 전체를 적용**했는가 (삭제 양방향 검증·변경 범위 초과·CH-ID·커버리지 매트릭스) | Major |
| 6 | 예외 목록의 화면 ID가 **실제로 시트·분석서에 존재하는가** — 없으면 오타 가능성. 임의로 무시하지 말고 보고 | Major |

**⚠️ 역방향 오판 금지 — 이 절의 핵심.**
**예외 화면이 문서 기본 정책과 다르게 작성된 것을 결함으로 지적하지 마라. 그게 예외의 정의다.**

구체적으로 다음은 **전부 정상**이며, 지적하면 잘못된 리뷰다:

- 문서 기본이 `변경` 인데 **예외 화면에만 비변경 항목 케이스가 잔뜩 있는 것** → 그 화면은 신규 정책이다.
  "범위 초과(비변경분 케이스화)"로 세지 마라
- 문서 기본이 `신규` 인데 **예외 화면의 케이스 수가 유독 적은 것** → 그 화면은 변경 정책이라
  변경 표기 항목만 뽑았다. "Description 항목 누락"으로 세지 마라
- 예외 화면과 다른 화면 사이에 **비고 태그 체계가 다른 것** → 정책이 다르므로 태그도 다르다.
  "태그 일관성 위반"으로 세지 마라

**지적 전에 반드시 예외 목록을 먼저 펴 보고, 해당 화면 ID가 목록에 있는지 확인한다.**
화면 ID 대조는 **원문 표기 그대로** 한다 — 구분자를 정규화해서 맞춰 보지 않는다(`VIOE-02_01_01-11` ≠ `VIOE-02_01_01_11` 로 취급하지 말고, 애매하면 보고).

- 샘플 5개 행의 셀 내용 일치 여부
- 헤더 위치 적정성

### 5-2. 변경분 한정 모드 검증

**적용 대상은 두 가지다:**

1. **기획서 유형(문서 기본 정책)이 `변경`** — 예외 목록에 오른 화면을 **뺀** 전체
2. 문서 기본이 `신규` 라도 **예외 목록에 오른 화면**(그 화면만 변경 정책)

분석 결과 메타정보의 `분석 방식: 변경분 한정 분석`(옛 표기 `변경분(빨강 표시) 한정 분석`) 기재와
Phase 0의 기획서 유형이 **어긋나면 먼저 그것을 보고한다** — 한 단계가 반대 기준으로 돌면 리뷰 전체가 오판한다.

**⚠️ 오판 주의:** 이 모드에서는 비변경분에 케이스가 없는 것이 **정상**이다.
전체 분석 기준으로 "Description 항목 누락"을 지적하면 잘못된 리뷰다. 반드시 모드를 먼저 확인할 것.

**⚠️ 예외 화면에 이 절을 그대로 적용하지 마라.** 문서 기본이 `변경` 이어도 **예외 목록의 화면은
신규 정책**이므로 아래 점검 항목(특히 3번 범위 초과, 4번 `[변경 CH…]` 태그)을 적용하면 전부 오탐이 된다.
행마다 **그 화면 ID가 예외 목록에 있는지 먼저 본다** (3-3).

**⚠️ 표시색 오판 주의:** 기획서의 변경 표시색은 판본마다 다르다 — 빨강 단독인 것도 있고
**빨강+파랑을 함께 쓰는 것**도 있다. 분석서 메타정보의 `표시색` 기재를 먼저 확인하라.
- 분석서가 두 색을 다뤘는데 한 색만 기준으로 "이 색은 변경분이 아니다"라고 지적하면 **오판**이다
- 반대로 분석서가 한 색만 다뤘다면 **나머지 색의 변경분이 누락됐을 수 있다** — 기획서 원본을 직접
  열어 다른 색 변경 표기가 있는지 확인하고, 있으면 **Critical(변경분 누락)** 로 보고한다
- **색으로 변경 종류·회차를 판정하지 마라.** 권위는 주석 원문(`v2수정`/`v2추가`/`v2삭제` + 날짜)이다.
  색↔날짜 대응은 페이지마다 어긋날 수 있다 (실측 사례 있음)
- 다음은 변경분이 아니다 — 이것들을 케이스화했다면 범위 초과(Major): **페이지 외곽 아트보드 프레임**
  (전 페이지 동일), 색 원형 번호 배지(❶·`3-1`), **목록 번호만 색이 번진 항목**, `*필수`, 상태 badge,
  차트 색, 링크·기본 버튼·선택 탭의 파랑
- **삭제 유형 변경분을 색 검출 기준으로 "없다"고 판정하지 마라.** 삭제는 **취소선**으로만 표기되는 경우가
  많고 취소선은 색 검출·텍스트 레이어 어느 쪽에도 걸리지 않는다. 분석서에 삭제 항목이 0건이면
  **`scripts/detect_strikethrough.py --color-only` 로 후보를 뽑고 DESC 전문을 육안 판독해** 취소선 항목이
  실재하는지 확인하라 (그 스크립트는 양성 대조를 거쳐야 "0건"이 의미를 갖는다). 있는데 분석서가
  놓쳤다면 **Critical(변경분 누락)** 이다
- **양성 대조를 거친 "0건"도 근거가 못 된다.** 대조는 *그 길이대의* 취소선을 잡는다는 것만 증명한다.
  **부분 취소선(단어·글자 몇 개)은 임계값 아래로 떨어져 검출되지 않는다** (실측: 610px 런으로 대조한
  `--min-len=110` 설정이 같은 문서의 2글자 ~80px 취소선을 놓쳤다). 분석서가 검출 결과만 근거로
  "삭제 없음"을 주장하면 **DESC 육안 재판독 여부를 확인**하고, 안 했으면 직접 훑어라

점검 항목:

| # | 점검 내용 | 위반 시 |
|---|----------|--------|

### 5-2-1. 삭제 항목 양방향 점검 (취소선)

기준 문서는 `common.md` 의 「취소선 = 삭제 — 정상 동작 케이스를 만들지 않는다」 절이다.

**삭제는 두 방향으로 틀릴 수 있는데, 그동안 한 방향만 봤다.**

| 방향 | 점검 | 위반 시 |
|------|------|--------|
| **정방향** | 삭제 항목에 **"더는 노출·동작하지 않음"** 검증 TC가 있는가 | Critical |
| **역방향** | **삭제된 내용으로 정상 동작·표출 케이스를 만들지 않았는가** | **Critical** |

**역방향이 Critical인 이유 — 케이스 자체가 잘못된 결함을 만들어낸다.**
삭제된 기능을 테스트하라고 지시하면 **실행자가 반드시 FAIL을 낸다.** 기획대로 사라진 것을
"안 된다"고 결함 보고하게 되므로, 누락(있어야 할 검증이 없음)보다 해롭다 — 없는 결함을 생산한다.

**판정 방법:**

1. `01_prd_analysis.md` 에서 **취소선 항목 목록**을 뽑는다 (CH-ID + 삭제된 내용 원문)
2. 각 항목에 대해 시트에서 그 내용을 다루는 행을 **전부** 찾는다
3. 그 행들이 **미표출·미호출·미잔존·미동작** 형태로만 검증하는지 확인한다
4. 그 항목의 **표출·동작·입력을 긍정형으로 검증하는 행이 하나라도 있으면 위반**이다

**취소선 형태별 정상 케이스 구성:**

| 취소선 형태 | 정상 | 위반 |
|------------|------|------|
| 항목 전체 취소선 | 그 항목이 **미표출·미동작** | 그 항목의 표출·동작·입력 검증 |
| 하위 트리 전체 취소선 | 트리 **전부**가 미표출 | 하위 항목의 개별 동작 검증 (상위만 지우고 하위를 살림) |
| **부분 취소선** (`솔루션 `~~`멤버`~~` 관리자`) | ① **삭제 토큰 미잔존** ② **새 토큰 표출** — **두 개만** | **삭제된 토큰을 포함한 기능 검증** |

**⚠️ 경계 — 오판하지 말 것.** 삭제 자리의 **대체 동작**은 **기획서에 대체가 명시돼 있으면 정당하다.**
대체 케이스가 있다는 이유만으로 "삭제 항목을 동작 케이스화했다"고 지적하면 오판이다.

- 먼저 **기획서에 대체 규정이 있는지** 확인한다. 있으면 그 케이스 자체는 정상
- 다만 근거는 **삭제 항목의 CH-ID가 아니라 대체를 규정한 항목의 CH-ID**여야 한다.
  삭제 CH-ID로 대체 동작을 검증하면 **비고 ↔ 절차 불일치(Major)** 다 (5-2 4-1항과 같은 종류)
- 기획서에 대체 명시가 없으면 **미노출 검증까지만**이 정상이고, 대체 여부는 피드백 `[확인 불가]` 다

### 5-2-2. 변경 범위 초과 점검 — 박스는 범위를 확정하지 않는다

기준 문서는 `common.md` 의 「변경 표기 경로의 위계 — 박스는 범위를 확정하지 않는다」 절이다.
**색 테두리 박스는 범위 후보(scope hint)일 뿐 확정력이 없다.** 항목을 확정하는 것은
DESC 색 텍스트 · 취소선 · `변경사항` 스티커 · `ChangeLog` 네 경로다.

| # | 점검 내용 | 위반 시 |
|---|----------|--------|
| A | **색 박스만 근거인 항목이 화면·팝업 전체로 케이스화되지 않았는가** — 박스 안의 항목 근거가 가리키는 범위를 넘어섰으면 범위 초과 | **Major** |
| B | 분석서에 **「박스 ↔ 확정 항목 대조표」** 가 있으면, 케이스 범위가 **그 대조표의 확정 항목과 일치하는가** | **Major** |
| C | 박스 안에 항목 근거가 **0건**인데 케이스가 만들어졌으면 **`[변경 범위 불명]`** 이 피드백에 있는가 | Minor |

**판정 기준:**

- 박스가 화면 전면을 감싸고 있어도, 그 안의 **스티커·DESC 색 텍스트·취소선이 가리키는 항목만** 대상이다.
  **박스의 크기는 변경 범위가 아니다**
- 박스 안에 스티커가 N개 있으면 **그 N개가 범위**다. 스티커가 개별 변경을 구체적으로 가리키는데도
  화면 전체 기능(타이틀·구성 요소·확인/취소 버튼 등)이 케이스화됐으면 **A 위반**
- 예외는 **화면·팝업 자체가 신규인 경우**뿐이며, 그때도 판정 근거는 **박스가 아니라
  스티커·`ChangeLog` 원문**(`… 팝업 추가`, `… 화면 신규`)이어야 한다

**⚠️ 반대 방향 오판 금지 — 지적 전에 반드시 확인하라.**
**화면·팝업 자체가 신규라 전수 케이스화된 것을 "범위 초과"로 지적하면 오판이다.**
A 위반을 올리기 전에 **그 화면의 스티커·`ChangeLog` 원문에 `추가`·`신규` 어휘가 있는지 먼저 확인**한다.
있으면 전수가 정상이며, 이 경우 지적할 수 있는 것은 존재·기본 구성을 넘어선 세부 동작에
개별 항목 근거가 없는 경우뿐이다.

> **실측 근거.** Boot Factory `멤버 관리 > 사용자` 6페이지 실행에서 **전면 색 박스가 있는 두 화면이
> 전체 케이스의 69%(87/127건)** 를 차지했다. 권한 설정 팝업은 **스티커 9개가 개별 변경을 구체적으로
> 가리키고 있었는데도** 전면 박스를 근거로 팝업 전체 기능이 케이스화돼 **58건**이 됐다.
> 원인은 박스에 범위 확정력을 준 것이다.

### 5-3. 이미지 판독 이슈 반영 검증

| # | 점검 내용 | 위반 시 |
|---|----------|--------|
| 1 | `## 이미지 판독 이슈` 섹션이 존재하는가 (이슈 없으면 "판독 이슈 없음" 명시) | Major |
| 2 | `주의` 페이지 근거 케이스의 피드백 컬럼에 `[판독 주의]`가 기재됐는가 | Major |
| 3 | `불가` 페이지에 판독 불가 케이스가 1건 존재하는가 (조용한 스킵은 누락) | Critical |
| 4 | `불가` 페이지의 예상 결과가 단정되지 않았는가 (`ㄴ … PASS/FAIL 판정 대신 …` 패턴) | Major |
| 5 | 판독 이슈가 사용자에게 보고됐는가 (오케스트레이터 로그·보고서에 기록) | Major |

### 7. 추측 기반 케이스 표시

`03_testcases.md`의 "기획 확인 필요 항목" 섹션을 리뷰 보고서에 인용하되, **인용으로 점검을 대신하지 않는다.**
이 항목들이 시트에 실제 작성됐는지, `비고`·`피드백` 컬럼에 표시가 있는지 **시트를 직접 읽어 확인**한다.

> **⚠️ 작성자 자기 점검표를 인용하지 말고 독립 실측하라.** `03_testcases_ch{N}.md` 의 분포 표·
> 커버리지 표·"자기 점검 완료" 서술은 **작성자의 주장이지 측정 결과가 아니다.** 리뷰어가 그것을
> 옮겨 적으면 QA가 아니라 전사(轉寫)가 된다. 분포·행 수·커버리지·태그 기재율은 **시트에서 직접 센다.**
> 작성자 표와 실측이 다르면 **그 불일치 자체를 이슈로 보고**한다 (실측 근거: 분포 표가 실제 작성과
> 어긋나는 회귀가 있었다).

### 8. 보고서 작성

`_workspace/04_review_report_ch{N}.md`에 결과 저장. 형식은 `testcase-reviewer` 에이전트 정의의 출력 프로토콜 참조.

## 권고 분류

리뷰 결과를 다음 3단계로 분류:

| 권고 | 의미 | 후속 조치 |
|------|------|----------|
| **Critical (즉시 수정)** | 양식 위반, 핵심 기능 누락, 시트-로컬 불일치 | `testcase-writer` 재호출하여 수정 |
| **Major (확인 권장)** | 엣지 케이스 부족, 추측 기반 케이스 다수 | 사용자에게 결정 위임 |
| **Minor (참고)** | 표현 개선, 우선순위 재조정 제안 | 정보 제공만 |

## 작업 원칙

1. **임의로 수정하지 않는다.** 리뷰어가 케이스를 직접 고치면 작성자의 의도가 묻힌다. 발견된 문제를 보고하고 `testcase-writer`가 수정한다.

2. **구체적으로 지적한다.** "양식이 맞지 않음" 같은 추상적 표현 금지. TC-ID, 컬럼명, 발견값, 기준값을 명시.

3. **점진적 검토 가능.** 케이스가 많으면 기능 단위로 묶어 검토하고 부분 보고서 작성도 허용.

4. **재검토 시 개선 평가.** `_workspace/04_review_report.md`가 이미 있으면 이전 보고서와 비교하여 어떤 이슈가 해결됐고 어떤 게 남았는지 명시.

5. **독립 실측한다.** 작성자의 자기 점검표·분포 표를 근거로 삼지 않는다. 수치는 시트에서 직접 센다 (7절).

6. **정책을 화면 단위로 판정한다.** 문서 기본 정책 하나로 전 행을 재단하지 않는다. 지적하기 전에
   **그 행의 화면 ID가 예외 목록에 있는지** 확인한다 (3-3).
