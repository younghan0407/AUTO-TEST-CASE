# 변경분 전용 생성 모드 (0-H)

> `testcase-generator` SKILL의 분리된 참조 문서다. **기획서 유형이 `변경` 이거나 이 화면이 변경 정책일 때에만 읽는다.**
> 절 번호는 원래 SKILL의 것을 유지하므로 다른 문서의 상호 참조가 그대로 유효하다.

#### 0-H. 변경분 전용 생성 모드 (기획서 유형 = `변경`)

**Phase 0의 기획서 유형이 `변경`이면 문서 전체가 이 모드다.** 분석 결과 메타정보의
`분석 방식: 변경분 한정 분석`(옛 표기 `변경분(빨강 표시) 한정 분석`)도 같은 신호다.
개정판 기획서의 **변경된 부분만** 케이스화하는 모드다.

**단, 예외 목록에 오른 화면은 이 모드에서 빠진다** — 0-I를 먼저 확인하라.

**표시색은 케이스에 쓰지 않는다.** 기획서는 빨강 단독 또는 빨강+파랑으로 변경분을 표기하지만,
색은 변경 종류를 뜻하지 않는다. 비고의 `{변경유형}`·`{버전-일자}` 는 **분석서가 인용한 주석 원문**
(`v2수정` / `v2추가` / `v2삭제` + 날짜)에서 가져온다. `[변경 CH01-1 파란박스]` 처럼 색을 종류 자리에
넣지 마라 — 실행자가 무엇이 어떻게 바뀌었는지 알 수 없다.
**색↔회차 대응도 판본마다 어긋난다** (실측: 한 문서에서 빨강 `26.08.03` / 파랑 `26.08.18` 인데
다른 페이지는 파랑이 `26.08.04`).

**생성 대상:**
- 분석 결과의 **변경분 목록에 있는 항목만** 케이스화한다.
- `[맥락 — 비변경분]`으로 표시된 항목은 **케이스를 만들지 않는다.** 변경분 케이스의 **사전조건·절차**에만 활용한다.
  - 예: 변경된 필드가 팝업 안에 있다면 → 팝업 호출 경로는 사전조건에 쓰되, 팝업 호출 자체를 별도 TC로 만들지 않는다.

**케이스화 범위 확정 — 색 박스는 범위를 확정하지 않는다:**

분석서의 변경분 목록을 그대로 받아 케이스화하기 전에 **항목마다 근거가 무엇인지 확인한다.**
변경 표기 경로는 대등하지 않다 — **어디를 볼지 알려주는 것(색 박스)** 과 **무엇이 어떻게 바뀌었는지
정하는 것(DESC 색 텍스트·취소선·`변경사항` 스티커·`ChangeLog`)** 은 역할이 다르다. 위계 원문은
`common.md` 「변경 표기 경로의 위계 — 박스는 범위를 확정하지 않는다」에 있다.

| 분석서 항목의 근거 | 케이스화 범위 |
|------------------|-------------|
| 박스 + 항목 근거(DESC·취소선·스티커·`ChangeLog`) | **항목 근거가 가리키는 항목만.** 박스가 화면 전면을 감싸고 있어도 범위를 넓히지 않는다 |
| **박스뿐 (항목 근거 0건)** | **화면 전체를 케이스화하지 않는다.** 피드백에 `[변경 범위 불명]`을 남기고 확인을 요구한다. 임의 전수화 금지 |
| 화면·팝업 **자체가 신규** (판정 근거는 박스가 아니라 스티커·`ChangeLog` 원문 — `… 팝업 추가`, `… 화면 신규`) | 전수 대상이지만 **존재·기본 구성 수준으로 묶는다.** 세부 동작까지 쪼개려면 그 동작 **각각에** 항목 근거(DESC·스티커·`ChangeLog`)가 있어야 한다 |

- 분석서에 **「박스 ↔ 확정 항목 대조표」**(`prd-analyzer` PDF-3.5 산출물)가 있으면 **그것을 케이스 범위의 기준으로 삼는다.** 대조표에서 항목 근거 0건으로 표시된 박스는 위 두 번째 행 처리를 따른다.
- **신규 화면 판정 근거를 박스에서 찾지 않는다.** 박스는 "화면 전체가 신규"와 "화면 안 일부가 수정"을 구분하지 못한다.

> **실측 — 박스에 확정력을 주면 케이스가 부풀어 오른다.** Boot Factory `멤버 관리 > 사용자`
> 6페이지 실행에서 **전면 박스가 있는 두 화면이 전체 케이스의 69%(87/127건)** 를 차지했다.
> 특히 권한 설정 팝업은 **스티커 9개가 개별 변경을 구체적으로 가리키고 있었는데도** 전면 박스를
> 근거로 팝업 전체 기능(타이틀·구성 요소·확인·취소 버튼)이 케이스화돼 58건이 됐다.

**변경분 커버리지 (Description 100% 커버리지의 변경분 모드 대응):**
- 변경분 목록의 **모든 항목이 최소 1건 이상의 케이스로 커버**되어야 한다.
- 변경 유형별 최소 검증:

  | 변경 유형 | 필수 케이스 |
  |----------|-----------|
  | 추가 | 신규 항목의 표출 + 동작 + (해당 시) 입력 검증 |
  | 수정 | 변경된 동작·문구·조건의 신규 기대값 검증 |
  | 삭제 | 삭제된 항목이 **더는 노출되지 않음** 검증 (누락 빈발 — 반드시 작성) |
  | 위치·순서 변경 | 변경된 순서·위치대로 표출되는지 검증 (`표시` 구분) |
  | 디자인 변경 | 변경된 표기 형태 검증 (`표시` 구분) |

> **삭제 유형은 조용히 누락되기 쉽다.** 기획서가 삭제를 **취소선**으로만 표기하는 경우가 있는데
> 색 검출 스크립트는 선 몇 픽셀을 잡지 못한다. 분석서에 취소선 항목이 있으면 **하나도 빠짐없이**
> "더는 노출되지 않음" 검증 케이스를 만든다.

**취소선(삭제) 항목 — 금지 규칙:**

> **취소선 그어진 내용으로 정상 동작·표출 케이스를 만들지 않는다.**
> 그 내용에 허용되는 유일한 케이스는 **"더는 노출·동작하지 않음" 검증**이다.

**이유 — 삭제된 기능을 동작 케이스로 만들면 실행자가 반드시 FAIL을 낸다.** 기획대로 사라진 것을
"안 된다"고 보고하게 되므로, **케이스가 잘못된 결함을 만들어내는 셈**이다. 위 유형별 표의 "필수 케이스"는
**만들어야 할 것**을 규정하고, 이 절은 **만들면 안 되는 것**을 규정한다. 의무만 지키고 금지를 어기면
같은 항목에 "더는 안 보인다"와 "정상 동작한다"는 **상반된 두 케이스**가 함께 남는다.

| 취소선 형태 | 만들 케이스 | 만들지 않을 케이스 |
|------------|-----------|------------------|
| **항목 전체 취소선** | 그 항목이 **미표출·미호출·미동작** | 그 항목의 표출·동작·입력 검증 |
| **하위 트리 전체 취소선** | 트리 **전부**가 미표출 (상위만 보고 하위를 살리지 않는다) | 하위 항목의 개별 동작 |
| **부분 취소선** (`솔루션 `~~`멤버`~~` 관리자`) | ① 삭제 토큰 **미잔존** ② 새 토큰 **표출** — 두 개만 | 삭제된 토큰을 포함한 기능 검증 |

**경계 — "삭제 자리의 대체 동작":**

- 삭제된 기능 자리에 무엇이 대신 오는지는 **기획서에 대체가 명시된 경우에만** 케이스화한다.
  명시가 없으면 **미노출 검증까지만** 만들고, 대체 여부는 피드백에 `[확인 불가]`로 남긴다.
  대체를 추정해 케이스를 만들면 기획서에 없는 동작을 단정하는 것이다.
- 대체를 케이스화할 때는 **삭제 항목의 CH-ID가 아니라 대체를 규정한 항목의 CH-ID**를 근거로 단다.
  삭제 근거로 대체 동작을 검증하면 **비고가 선언한 변경분을 절차가 건드리지 않는다** (아래
  "절차가 검증 대상을 실제로 포함하는지 확인"과 같은 종류의 위반이다).

**비고 컬럼 기재 의무:**

형식: **`[변경 CH{NN}-N {종류 원문} {회차}-{일자}] {변경 내역} [{근거}] {상세}`**

```
[변경 CH01-1 신규추가 v1-26.05.26] '엔진 버전' 영역 추가 [스티커A] p71 2영역 빨간 박스
[변경 CH01-8 신규추가 v1-26.05.26] 업그레이드 버전 [DESC 2항-3-a] 현재 버전의 다음 마이너 버전 제공
[변경 CH03-2 명칭 변경 v1-26.07.31] 메뉴명 변경 [DESC 1항] [박스 + 스티커]
[변경 CH03-5 신규추가 날짜미표기] 부여 권한에 따른 메뉴·기능 제한 [DESC D2-8] [DESC 전용]
```

- **`CH-ID`를 반드시 포함한다.** 이것이 없으면 시트 행 → 분석서 변경분 역추적이 불가해져 리뷰·보완 실행에서 근거를 찾을 수 없다. 실무에서 실제로 누락됐던 항목이다.
- **CH-ID는 `CH{NN}-N` 네임스페이스를 지킨다.** `NN` 은 **오케스트레이터가 넘긴 CH-ID 접두**이며 화면 인덱스의 값이다 (`CH05-1`, `CH06-3`). **인덱스 순번과 다를 수 있으므로 직접 계산하지 않고 넘겨받은 값을 쓴다** — 기존 탭에 챕터 의미의 CH-ID가 있으면 그 최대값 다음부터 배정된다 (`common.md` 「CH-ID 충돌 방지」). 화면이 하나뿐이어도 지킨다 — 제각기 매기면 한 탭에서 충돌한다 (2026-08-25 실제 사고).
- 변경 종류 어휘는 `신규추가` / `문구수정` / `삭제` / `필드순서변경` / `문구삭제-위치변경` / `문구위치변경` / `디자인변경` / `명칭 변경` 등 **팀 시트 실측 어휘**를 따른다.
- **종류 원문이 다어절이면 회차와 붙어 읽히지 않도록 띄운다** — `[변경 CH01-1 명칭 변경 v1-26.07.31]`. CH-ID·종류 원문·회차·일자가 모두 남으면 형식은 만족한다.
- 회차-일자는 기획서 원 표기에 맞춘다 (`v1-26.05.26`, `v2-26.08.18`).
- **변경 일자가 기획서에 없으면 `날짜미표기`로 적는다. `-`를 쓰지 않는다** — 이 양식에서 `-`는 4/5 Depth의 No-data 의미로 고정되어 있어 의미가 충돌한다.
- **기획서가 변경 종류를 원문에 적지 않았으면 `종류 원문 미표기`로 적는다.** 빈칸으로 두면 근거가 사라지고, **색으로 종류·회차를 추정하면 기획서에 없는 종류를 단정하게 된다.** 실측 근거: ch01 변경 8건 중 `(v2…)` 주석을 동반한 항목이 1건뿐이었다.
- 근거 태그(`[DESC ...]`, `[스티커A]`, `[UI]`)와 경로 태그(`[DESC 전용]` / `[스티커 전용]` / `[ChangeLog]` / `[DESC + 박스 + 스티커]` 등)를 함께 남긴다. `[변경 표기 불일치]`는 **피드백**에 쓴다 (C-1).
- **`구분` enum에 `변경` 같은 신규 값을 만들지 않는다.** 팀 양식의 기존 enum을 유지하고, 변경 사실은 비고로만 표현한다.

**기획 미정의 항목의 예상 결과:**

변경분이라도 기대 결과가 기획서에 정의되지 않은 경우가 있다. 이때 예상 결과를 단정하면서 피드백 열에 `[확인 불가]`를 적는 것은 **자기모순**이며, 실행자가 잘못된 FAIL을 기록하게 만든다. 다음 형태로 통일한다:

```
{관측 대상 서술}
ㄴ 기획 미정의 항목 — PASS/FAIL 판정 대신 실측 상태를 [실제 결과]에 기재
```

특히 주의: 참고 시트의 다른 탭·화면에서 쓰인 값(`No data (-)` 등)을 **현재 기획서에 근거가 없는데 가져와 단정하지 않는다.**

**절차가 검증 대상을 실제로 포함하는지 확인:**

비고가 "신규 항목 X와 Y의 연동 확인"이라고 선언했는데 절차에 X가 없으면, 그 케이스는 변경 전에도 성립하는 비변경분 검증이다. 각 케이스의 **절차·예상 결과가 비고에 적은 변경분을 실제로 건드리는지** 작성 후 대조하라.

**변경 표기 불일치 처리:**
- 분석 결과에 `[스티커 전용]` / `[DESC 전용]` / `[변경 표기 불일치]`로 표시된 항목도 **케이스화 대상에 포함**한다.
- 경로 표시는 **비고**에, 불일치 사실은 **피드백**에 남긴다 (C-1의 열 분리를 지킨다).
- `ChangeLog` 패널에 없다는 이유로 다른 경로에서 찾은 변경분을 **탈락시키지 않는다.** 그 패널은 작성 시점 스냅샷일 뿐 완전한 목록이 아니다. 단, **패널이 아예 없는 페이지의 변경분에는 `[변경 표기 불일치]`를 붙이지 않는다** — 대조 대상이 없는 것과 등재 누락은 다르다.

**보고 의무:**
- `03_testcases_s{NN}.md` 메타정보에 `생성 범위: 변경분 한정`을 명시한다.
- 변경분 목록 항목 수 대비 커버된 항목 수를 표로 보고한다 (커버리지 100%가 목표).
