# Testcase Generator

기획서 분석(`_workspace/01_prd_analysis.md`)과 팀 양식 사양(`.claude/formats/common.md` + `profile-{제품}.md` + `_workspace/02_sheet_format.md`)을 입력으로, 팀이 그대로 사용할 수 있는 테스트 케이스 행 집합을 생성한다.

> **양식은 항상 두 파일을 함께 읽는다.** `common.md`(공통 골격 — 컬럼 23개·`-` vs 빈칸·태그 체계·
> C-ID/CH-ID·변경분 모드) + 해당 제품 프로파일(`profile-viola.md` / `profile-trombone.md` /
> `profile-bootfactory.md` — 분포·enum 범위·문체·TC ID 체계). **어느 한쪽만 읽으면 케이스가 틀린다.**

## 트리거 키워드

- "테스트 케이스 생성", "TC 만들어줘", "기획서 기반 케이스 도출"
- "정상 흐름/비정상 흐름 케이스 작성"
- "엣지 케이스 추가", "케이스 보완"

## 사전 조건

1. `_workspace/01_prd_analysis.md` 존재 — 없으면 `prd-analyst`를 먼저 실행하라고 보고
2. **양식 기준 확보** — 참고 시트 전수 분석은 필수가 아니다.
   - **`.claude/formats/common.md` + 제품 프로파일** (권장·기본) — 커밋된 양식 사양. 참고 시트 없이 시작 가능
   - `_workspace/02_sheet_format.md` — `sheet-analyst`가 위 두 파일을 로드해 대상 시트와 대조한 결과
   - 사양 파일을 못 찾으면 `sheet-analyst`를 먼저 실행하라고 보고 (임의로 양식을 추정하지 않는다)
3. 대상 구글 시트의 **마지막 케이스 ID** (충돌 방지용) — 사양에는 없다. 대상 시트 실측값을 쓴다
4. **생성 모드** 결정 — 아래 "0. 생성 모드 선택" 참고
5. **Phase 0 기본 정보** 수령 — 오케스트레이터(`testcase-auto` Phase 0)가 프롬프트로 전달한다. **추정 금지, 없으면 요청한다.**

| 항목 | 값 | 이 스킬에서의 쓰임 |
|------|-----|------------------|
| **제품 유형** | `VIOLA K8s` / `VIOLA CI/CD` / `TROMBONE` / `BootFactory` | 읽을 **프로파일**을 정한다 |
| **기획서 유형** | `신규` / `변경` | **문서 전체의 기본 정책.** `변경`이면 0-H 변경분 모드로 동작 |
| **예외 항목** | 반대 정책을 적용할 **화면 ID 목록** (없으면 "없음") | 0-I 정책 예외 처리 |

- `VIOLA K8s`와 `VIOLA CI/CD`는 **같은 프로파일(`profile-viola`)** 을 쓴다. 둘의 차이는 시트 컬럼이 아니라 **탭 분리 + `1 Depth`(Breadcrumb 최상위 원문)** 로 표현된다. `1 Depth` 값을 제품 유형에서 만들어내지 말고 기획서 Breadcrumb 원문을 쓴다
- **행마다 관리 영역을 판정해 기입하는 컬럼은 없다.** 2026-08-25에 VIOLA 전용으로 신설했던 전용 컬럼은 **2026-09-02에 폐지**되어 전 제품 **23컬럼 A~W**로 통일됐다. 제품 유형은 분석 컨텍스트일 뿐 컬럼 값의 출처가 아니다
- `BootFactory` 프로파일은 **실측 없는 VIOLA 파생**이다. 편차가 반복 지적되면 사양이 틀린 것일 수 있으므로 보고한다

### 양식 기준이 충돌할 때 (사양 vs 대상 시트)

`02_sheet_format.md`에 헤더 대조 결과가 함께 기록된다. 충돌 시 무엇을 따르는지는 항목별로 다르다.

| 항목 | 따를 것 | 이유 |
|------|--------|------|
| 컬럼 구조·순서·이름 | **대상 시트** | 어긋나면 값이 엉뚱한 칸에 들어간다. 불일치가 보고됐으면 **작성하지 말고 중단** |
| TC ID 마지막 번호 | **대상 시트** | 계속 자라는 값. 사양의 값은 신뢰하지 않는다 |
| enum 허용값 | **사양** | 시트에 사양 외 값이 있으면 보고된 상태다. 승인 없이 그 값을 쓰지 않는다 |
| 문체·검증 단위·미사용 컬럼 정책 | **사양** | 실행마다 흔들리면 안 되는 값 |

**사양을 요약해서 쓰지 않는다.** 컬럼 순서·enum·표기 규칙은 사양 원문을 그대로 참조한다.

**⚠️ 제품 프로파일을 혼용하지 않는다.** `.claude/formats/` 에 프로파일이 여러 개 있다.
컬럼 골격은 `common.md` 하나로 공통이지만 아래는 프로파일마다 다르다 — 잘못된 프로파일을 쓰면
**컬럼은 맞고 내용이 팀 컨벤션에서 통째로 벗어난다.**

| 항목 | 프로파일별로 다름 |
|------|-----------------|
| UI 라벨 표기 | 백틱(`` `등록` ``, VIOLA·BootFactory) vs 대괄호(`[등록]`, TROMBONE) |
| TC ID | 제품 전역 연속 vs 모듈별 연속 |
| 구분 × 우선순위 결합 | `정상`에 P3·P4 허용 여부가 정반대 |
| 지배 구분 | `표시` 과반 vs `정상` 과반 |
| 사전조건 | 100% 필수 vs 공란 허용 |
| 3 Depth enum 범위 | 4종 고정 vs 탭별 3~7종 |

> 실측: 절차의 **백틱 사용률이 VIOLA 65% 대 TROMBONE 0.0%(0/3,953행)** 다. 절충값이 없는 항목이다.

`02_sheet_format.md` 최상단의 **사용 프로파일 이름을 먼저 확인**하고, `common.md` + 그 프로파일 원문만 참조한다.

## 0. 생성 모드 선택 (atomic vs scenario)

오케스트레이터에서 사용자가 선택한 모드를 따른다. 모드별 케이스 도출 단위와 우선순위 정책이 다르다.

| 모드 | 한 케이스 단위 | 적합한 상황 | 케이스 수 (4화면 기준) |
|------|--------------|----------|---------------------|
| **atomic** (팀 협업 권장) | 화면 내 단일 검증 (컬럼 1개, 클릭 1회, 표시 1건) | 회귀 추적, 팀 공동 작성, 실패 원인 정확 파악 | 80~120개 |
| **scenario** (초안 작성 권장) | 사용자 행동 시나리오 (다단계 → 다중 검증) | 기획 초기 검토, 케이스 수 압축, 신규 화면 빠른 커버 | 30~50개 |

**모드 선택이 누락된 경우 기본값은 `atomic`** — 팀 협업 협업 친화적이고 양식 컨벤션과 더 잘 맞기 때문.

### atomic 모드 핵심 규칙

1. 한 케이스 = **하나의 단일 검증**. 화면 진입 시 보이는 모든 영역을 한 케이스에 묶지 않는다.
2. 절차는 **1~2 단계** 이내. 더 많으면 분해.
3. 예상 결과도 **1~3 줄**. 다항목 검증이면 케이스 분리.
4. 화면 진입 후 컬럼별 표시는 **각 컬럼당 1개 케이스**로 분해.
5. 호버·툴팁·정렬·페이지네이션 같은 인터랙션도 **각 동작당 별도 케이스**.

### scenario 모드 핵심 규칙

1. 한 케이스 = **한 사용자 행동 시나리오** (등록·수정·삭제 등 단위).
2. 절차에 사전 조건·다단계 행동 포함 가능.
3. 예상 결과에 여러 영역 검증을 `ㄴ` sub-bullet으로 묶을 수 있음.

> 비교 분석으로 발견된 사실: **팀이 정착시킨 양식은 atomic이다.** 우리 자동 생성이 scenario로 가면 협업이 어려워진다. 사용자가 명시적으로 scenario를 원하지 않는 한 atomic을 기본 사용.

## 읽을 참조 문서 결정 (먼저 이것부터)

| 조건 | 읽을 파일 |
|------|----------|
| **항상** | 이 SKILL 본문 |
| 기획서 유형이 **`변경`** 또는 이 화면이 **변경 정책**(정책 예외) | `references/change-mode.md` (0-H) |
| **추가 작업 = `예외 사항`** (`testcase-augment`) | `references/exception-catalog.md` — 예외 유형 12종·적용 판정·중복 판정·양식 매핑 |
| **추가 작업 = `권한`** (`testcase-augment`) | `references/permission-mode.md` — 셀→검증 지점 전개·기능 매핑·양식 매핑·상충 처리 |

조건에 맞지 않으면 열지 않는다. 그 화면의 정책은 오케스트레이터가 프롬프트로 준다.

## 케이스 도출 원칙

### 0. 분석 소스 우선순위 및 품질 규칙

케이스를 도출하기 전 반드시 이 규칙을 확인한다.

#### 0-A. Description 100% 커버리지 (최우선)

`01_prd_analysis.md`에 기록된 Description 항목은 **전부** 케이스화한다. 누락 금지.

- Description 항목 번호(❶-1-a 등) → 케이스 비고에 `[DESC ❶-1-a]` 형태로 출처 표시
- `[강조]` 태그 항목 → 특히 빠짐없이 케이스화 (기획자가 강조 표시한 항목)
- Description에 있는 내용을 UI 화면 이미지에서 안 보인다는 이유로 생략하지 않는다

**Description 커버리지 체크**: 케이스 생성 후 Description 항목 수와 케이스 출처 커버 수를 대조한다.

#### 0-B. 화면 ID 컬럼 = 기획서 화면 식별자 (Page ID 또는 Screen ID)

화면 ID 컬럼에는 기획서 스펙 페이지 우측 상단 헤더의 **화면 식별자** 값을 기입한다.
**헤더 필드명은 기획서마다 다르다. 필드명 우선순위와 값 패턴은 프로파일의 "화면 ID" 절을 따른다**
(VIOLA·BootFactory는 `Screen ID` → `Page ID` → 기타).

| 우선순위 | 헤더 필드명 | 값 형식 예 |
|---------|-----------|----------|
| 1 | 프로파일이 지정한 1순위 필드 | `VIOE-00_00_05`, `VIOE-02_01_01-11`, `BOOT-03_01_01` |
| 2 | 프로파일이 지정한 2순위 필드 | `ADM-TCK-0100-02` |
| 3 | 그 외 화면 식별자 성격의 필드 | 기획서 표기 그대로 |

- **1순위 필드가 없으면 다음 순위 값을 그대로 기입한다.** 값 형식을 다른 꼴로 변환·정규화하지 않는다. **기획서 원문 표기 그대로** 쓴다.
- 한 시트에 **구분자 패턴이 섞여도 정상**이다 (VIOLA 실측: 언더스코어 3개 형과 언더스코어 2개 + 하이픈 형 혼재). 임의로 통일하지 않는다.
- `01_prd_analysis.md`의 각 기능 단위에 화면 식별자와 그 출처 필드명이 기록되어 있다. 분석 결과에 기록된 값을 그대로 사용한다.
- 식별자가 없는 화면(표지, 팝업 전용 페이지 등)은 상위 기능의 식별자를 사용한다.
- 동일 시트 내에서 화면 ID 표기 체계가 섞이는 것은 정상이다 (기획서마다 체계가 다름). 임의로 통일하지 않는다.

#### 0-C. 사전조건 명시 의무

동일 화면에서 상황에 따라 다른 UI/동작이 제공될 때, 케이스마다 사전조건을 명확히 구분한다.

나쁜 예: 사전조건 없이 "상세 검색 펼침 상태 확인"
좋은 예: 사전조건 = "상세 검색 입력 영역이 펼쳐진 상태" → 케이스 작성

특히 아래 상황은 사전조건 필수:
- 특정 버튼 클릭 후 나타나는 UI 상태
- 특정 데이터가 존재/부재인 상태
- 권한·역할에 따라 다른 화면

#### 0-D. 공통 Description 항목 독립 TC 의무화

`01_prd_analysis.md`에 `[공통 DESC]` 태그가 붙은 항목은 **여러 페이지에 동일하게 등장하는 Description 항목**이다.

- **공통 항목이라도 해당 페이지(화면 ID)마다 독립적으로 TC를 작성한다.** "이미 다른 페이지에서 작성됨"을 이유로 생략 금지.
- 각 화면의 맥락(사전조건, UI 상태)이 다를 수 있으므로 동일 Description이라도 독립 케이스로 다룬다.
- 공통 항목 TC의 케이스 제목에는 해당 화면 ID를 명시하여 구분한다.

**공통 항목 커버리지 체크**: 케이스 생성 후 `[공통 DESC]` 항목의 페이지 목록과 실제 작성된 TC 화면 ID를 대조한다. 누락된 페이지가 있으면 추가 작성.

#### 0-E. UI ↔ Description 불일치 항목 확인사항 자동 추가

`01_prd_analysis.md`에 `[UI↔DESC 불일치]` 태그가 붙은 항목은 UI 화면과 Description 내용이 서로 다른 항목이다.

- 해당 기능의 TC 비고(확인사항) 컬럼에 불일치 내용을 반드시 기재한다.
- 형식: `[기획 확인] UI: {UI 내용} / DESC: {Description 내용} — 어느 쪽이 맞는지 확인 필요`
- 예: `[기획 확인] UI: 아이디·비밀번호 입력 / DESC: 아이디·비밀번호·OTP 입력 — 어느 쪽이 맞는지 확인 필요`
- 불일치 항목이 있는 기능은 "기획 확인 필요 항목" 섹션에도 별도 기재한다.

#### 0-G. 오탈자 검수 (케이스 작성 후 필수)

케이스 전체 작성 후 아래 항목을 반드시 검수한다:
1. 기획서 용어와 케이스 용어 일치 여부 (예: "삭제된 티켓 포함" ≠ "상세 티켓 포함")
2. 상태 enum 값 정확성 (기획서에 없는 상태값 사용 금지)
3. 숫자·단위 정확성 (글자수, 최댓값 등은 Description 기준 우선)
4. 메시지 코드 정확성 (CMN001, TCK057 등 기획서 코드 그대로)

#### 0-H. 변경분 전용 생성 모드 → **`references/change-mode.md`**

기획서 유형이 `변경` 이거나 이 화면이 변경 정책(정책 예외)일 때 **그 파일을 읽고 그대로 따른다.**
`신규` 정책 화면만 다루는 실행에서는 읽지 않는다 — 변경 표기 위계·취소선 금지 규칙·CH-ID 태그
규율이 담긴 이 절이 스킬 본문의 23%였고, 쓰지 않는 실행에서도 매 호출마다 올라가고 있었다.

#### 0-I. 예외 항목 (정책 예외) — 화면 단위로 반대 정책 적용

Phase 0에서 받은 **예외 항목 목록**은 *문서 기본 정책과 반대로 작성할 화면 ID 목록*이다.
**기획서 유형은 문서 전체의 기본값일 뿐, 예외 목록에 오른 화면만 반대 정책으로 쓴다.**

| | 변경 정책 | 신규 정책 |
|---|---|---|
| 케이스화 범위 | 변경 표기(색/취소선/스티커/`ChangeLog`)가 있는 항목만 | **화면 전수** |
| 비고 태그 | `[변경 CH{NN}-N …]` + 경로 태그(`[DESC 전용]` 등) | 일반 근거 태그(`[DESC N항]`·`[UI]`·`[스티커]`) |
| 삭제 검증 | 취소선 항목에 "더는 노출되지 않음" 검증 **필수** | 해당 없음 |

**적용 규칙:**

1. **판정 단위는 화면 ID다.** 예외 목록에 오른 화면은 **그 화면의 케이스 전부**가 반대 정책을 따른다. 항목별로 갈라 쓰지 않는다.
2. **예외 목록에 없는 화면은 문서 기본 정책을 따른다.** 애매하면 오케스트레이터에 확인한다.
3. 예외 화면의 **모든** 케이스 피드백에 다음을 남긴다:

   ```
   [정책 예외] 문서 기본=변경 / 이 화면=신규
   [정책 예외] 문서 기본=신규 / 이 화면=변경
   ```

   이 표시가 없으면 나중에 **왜 이 화면만 다르게 작성됐는지 역추적할 수 없고**, 리뷰가 정상 작성분을 "정책 위반"으로 오판한다.
4. **정책을 임의로 뒤집지 않는다.** 예외 목록에 없는 화면에서 반대 성격이 뚜렷하게 보이면 `03_testcases_s{NN}.md`에 **보고만** 하고 기본 정책대로 작성한다.
5. 피드백에 다른 확인사항(`[확인 불가]` 등)이 함께 있으면 **둘 다** 남긴다. `[정책 예외]`가 다른 태그를 밀어내지 않는다.

**보고 의무:** `03_testcases_s{NN}.md` 메타정보에 `기획서 유형` / `예외 항목` / 예외 화면별 케이스 수를 표로 남긴다.

#### 0-J. 판독 이슈 페이지 처리 (해상도 부족·훼손 등)

`01_prd_analysis_s{NN}.md`의 `## 이미지 판독 이슈` 섹션에 기록된 페이지는 **케이스에 그 사실을 남긴다.** 조용히 넘어가면 실행자가 "검증 완료"로 오해한다.

| 판정 | 케이스 처리 |
|------|-----------|
| `주의` | 해당 페이지 근거 케이스를 **정상적으로 작성**하고, 피드백 컬럼에 `[판독 주의] {사유} — 기획서 원문 재확인 필요`를 기재한다 |
| `불가` | 추측으로 케이스를 만들지 않는다. 해당 화면에 대해 **판독 불가 사실을 남기는 케이스 1건**을 작성한다 (아래 형식) |

**판독 불가 케이스 형식:**

```
사전조건 : {판독 가능한 범위의 화면 진입 조건, 불명이면 '기획서 판독 불가'}
절차     : 1. {화면}의 해당 영역 확인
예상 결과 : 기획서 판독 불가 항목
           ㄴ 기획서 이미지 판독 불가({사유}) — PASS/FAIL 판정 대신 실측 상태를 [실제 결과]에 기재
비고     : [판독 불가 {페이지}] {파일명} {사유}
피드백   : [판독 불가] 기획서 원본 재전달 필요 — 재전달 후 케이스 보완 예정
```

- 예상 결과를 단정하지 않는다 (0-H의 "기획 미정의 항목" 패턴과 동일한 이유 — 실행자가 잘못된 FAIL을 기록한다).
- `03_testcases_s{NN}.md`의 "기획 확인 필요 항목" 섹션에 판독 이슈 페이지 목록을 그대로 옮긴다.

### 1. 기능 단위마다 분류별 케이스 작성

`01_prd_analysis.md`의 각 기능 단위에 대해 구분(분류)별로 케이스를 도출한다.

#### 1-0. 분포 기준은 **제품 프로파일의 실측 분포**다 (하드코딩 금지)

**제품 프로파일(`.claude/formats/profile-{제품}.md`)의 "구분 분포" 절이 목표값이다.
스킬 본문에서 분포를 읽지 말고 항상 프로파일에서 읽는다.**

프로파일마다 분포가 정반대다 — 어느 쪽인지는 **반드시 파일에서 확인하고**, 여기 적힌 수치를
기억으로 대신 쓰지 않는다 (아래는 왜 확인이 필요한지 보여주는 예시일 뿐이다).

| 구분 | VIOLA | TROMBONE |
|------|-------|----------|
| `정상` | 6.3% | **65.1%** |
| `표시` | **55.9%** | 2.4% |
| `인터랙션` | 11.2% | 0.6% |
| `부수` | 6.9% | 0.2% |

- **프로파일의 지배 구분을 확인하고 그 비중을 맞춘다.** VIOLA는 `표시`를 요소 단위로 잘게 쪼개는 것이 정상이고, TROMBONE은 `정상`이 과반인 것이 정상이다
- **화면 단위에서는 프로파일 분포와 대조하지 않는다.** 화면 1개 표본은 5~20건이라 편차가 의미를 갖지 못하고, 억지로 맞추면 그 화면에 없는 케이스를 만들게 된다. 분포 대조는 **오케스트레이터 Phase 5 전체 집계 리뷰**에서 탭 전체를 대상으로 1회 한다
- `03_testcases_s{NN}.md` 에는 **그 화면의 실제 분류별 케이스 수만** 센 값으로 적는다 (추정 금지)
- 편차가 큰 구분(±15%p 이상)은 그 사유를 함께 적는다. 기획서 특성상 불가피할 수 있으나, **사유 없이 벗어나면 양식 이탈이다**
- `profile-bootfactory`의 분포는 **VIOLA 실측을 이식한 값**이다. 편차가 반복되면 케이스가 아니라 프로파일이 틀렸을 수 있으므로 그 가능성도 함께 보고한다

> **실측 근거:** `일반 v2` 탭(하네스 출력 763행)을 TROMBONE 사양으로 채점한 결과
> `정상` **-44.9%p** / `표시` **+29.4%p** / `인터랙션` **+16.7%p** 편차가 났다.
> 원인은 아래 폴백 표가 스킬 본문에 하드코딩되어 제품 무관하게 적용된 것이었다.
> 상세: `docs/baselines/trombone-general-v2.md`

#### 1-1. 폴백 — **프로파일이 없을 때만** 쓰는 권장 개수

**적용 조건: `.claude/formats/` 에 해당 제품의 프로파일이 존재하지 않을 때에 한한다.**
프로파일이 하나라도 잡히면(`profile-viola` / `profile-trombone` / `profile-bootfactory`)
**이 표를 쓰지 않고 그 프로파일의 실측 분포를 쓴다.** 아직 프로파일이 없는 신규 제품의 출발점이다.

이 값은 VIOLA 양식에서 도출된 것이므로 **다른 제품에 그대로 적용하면 분포가 어긋난다.**
폴백을 실제로 쓴 경우 `03_testcases_s{NN}.md`에 **"프로파일 부재 — 폴백 표 사용"을 명시**한다.

| 분류 | 목적 | atomic 모드 (화면당) | scenario 모드 (기능당) |
|------|------|------------------|--------------------|
| **표시 형식 검증 (UI 표출)** | 컬럼별 노출, enum, 빈 값 표시, 일시 형식 | 8~15개 | 0~2개 (시나리오에 통합) |
| **인터랙션 검증** | 버튼 클릭→이동, 호버, 정렬, 페이지네이션 | 5~10개 | 1~3개 |
| **정상 흐름 (Happy Path)** | 정상 입력으로 의도한 결과 | 2~4개 | 1~2개 |
| **비정상 흐름 (Negative)** | 잘못된 입력, 오류 처리, 권한 문제 | 3~6개 | 2~4개 |
| **엣지 케이스 (Edge)** | 경계값, 조건부 분기, 자동 처리 | 2~4개 | 1~3개 |
| **부수적 (Cancel/비활성)** | 취소 동작, 비활성화 상태, 권한 없음 | 3~5개 | 0~1개 |

### 1-A. 표시 형식 검증 자동 도출 (atomic 모드 필수)

기획서에 컬럼·필드·일시·상태값이 등장하면 다음 검증 케이스를 **자동 추가**한다.

**단, 개수는 프로파일의 `표시` 비중에 맞춘다.** 프로파일에서 `표시`가 소수인 제품(예: TROMBONE 2.4%)이면
표시 검증을 요소 단위로 무한히 쪼개지 않고, 팀이 실제로 쓰는 수준으로 묶는다 (1-0 참조).

| 표시 항목 | 자동 도출 케이스 |
|----------|--------------|
| 테이블 컬럼 | 1. 컬럼 순서·이름 확인 / 2. 정렬 가능 컬럼별 sort 동작 / 3. 빈 값(`-`) 표시 |
| 상태값 enum | 1. 각 상태 노출 형식 / 2. 호버 시 enum 툴팁 (열거된 모든 값 명시) |
| 일시 표시 | 1. `yyyy-mm-dd hh:mm:ss` 형식 확인 / 2. 값 없을 때 `No data (-)` |
| 표기 형식 (`{A}/{B}`) | 1. 형식 정확성 / 2. 일부 값 누락 시 동작 |
| 액션 버튼 (생성/실행/수정/삭제) | 1. 클릭 → 이동/동작 / 2. 모달 표출 / 3. 모달 취소(P4) / 4. 모달 진행 |

**상태값 enum이 외부 정의 시트로 위임된 경우** (예: "리소스 상태값 정의 시트 참고"): 비고에 "기획 확인 필요: enum 정의" 표시하고 호버 케이스만 작성.

### 2. 한 케이스 = 한 검증 목표

여러 검증을 한 케이스에 묶지 않는다. 실패했을 때 어떤 검증이 실패했는지 명확해야 한다.

**나쁜 예:** "로그인 폼에 이메일/비밀번호 입력하고 약관 동의 체크하고 로그인 버튼 클릭하면 메인 화면으로 이동하며 토스트 메시지가 표시된다"

**좋은 예:**
- TC-001: "유효한 이메일/비밀번호로 로그인 → 메인 화면 이동"
- TC-002: "로그인 성공 시 환영 토스트 메시지 표시"
- TC-003: "약관 미동의 상태에서 로그인 버튼 비활성화"

### 3. 사전 조건 / 단계 / 예상 결과의 구체성

- **사전 조건**: 케이스 실행 전 충족돼야 하는 상태. 예: "테스트 계정으로 로그인 안 된 상태"
- **단계 (Steps)**: 사용자가 실제로 수행하는 행동. 번호 매김. 한 단계 = 한 행동.
- **예상 결과**: 각 단계 또는 마지막 단계의 기대 결과. 측정 가능해야 한다.

### 4. 기획서에 없는 정보 처리

`prd-analyst`가 "확인 불가"로 표시한 항목:
- **옵션 A**: 일반 베스트 프랙티스로 작성 + 비고에 "기획 확인 필요" 표시
- **옵션 B**: 케이스 생성 보류 + 별도 목록으로 보고

기본값은 옵션 A. 사용자가 엄격함을 원하면 옵션 B 적용.

### 5. ID 부여

`sheet-analyst`가 추출한 ID 체계와 마지막 사용 ID를 따라 새 ID를 부여한다. 예:
- 마지막 ID: `TC-LOGIN-012`
- 새 ID: `TC-LOGIN-013`, `TC-LOGIN-014`, ...

기능이 바뀌면 prefix도 바뀐다. 예: 회원가입 케이스는 `TC-SIGNUP-001`부터.

## 컬럼 기재 규율 (실측 위반이 있었던 항목)

`일반 v2` 준수도 측정에서 실제로 벗어난 항목이다 (`docs/baselines/trombone-general-v2.md`).
케이스 내용이 아니라 **어느 칸에 무엇을 쓰는가**의 문제이므로 작성 후 반드시 대조한다.

### C-1. 근거 태그는 `비고` 전용 — `피드백`에 쓰지 않는다

| 열 | 넣는 것 | 넣지 않는 것 |
|----|--------|-------------|
| **`비고`** | 근거 태그 — `[DESC 2항-1]` `[공통 DESC]` `[UI] p79` `[스티커]` `[강조]` `[변경 CH-N …]` | 확인사항 |
| **`피드백`** | 확인사항 — `[확인 불가]` `[기획 확인]` `[UI↔DESC 불일치]` `[오타 의심]` `[판독 주의]` | **근거 태그** |

- **`common.md`가 `실질 필수`로 표시한 컬럼(`비고`)은 전 행 채운다.** 비우면 시트 행 → 분석서 역추적이 끊긴다
- 근거를 `피드백`에 쓰고 `비고`를 비우는 것은 **누락이 아니라 열 오배치**다. 실측에서 **212행(27.8%)** 이 이렇게 비었다
- 한 케이스에 근거와 확인사항이 모두 있으면 **`비고`와 `피드백`에 각각** 쓴다. 한쪽에 몰지 않는다

### C-2. `미사용`으로 표시된 컬럼은 공란 유지

- 컬럼이 존재한다는 이유로 채우지 않는다. 팀이 의도적으로 비워 둔 칸이다
- 실측 위반 **69행(9.0%)** — 요구사항 ID·기능 ID·테스트 데이터를 채웠다
- 실행 단계 컬럼(실제 결과·수행자·수행일자·Jira)도 공란이다. `PASS` 등을 미리 채우지 않는다
- **`-` 와 빈칸을 구분한다.** `common.md`의 "`-` (No data) vs 빈칸" 절을 따른다 (`4 Depth`·`5 Depth`는 `-`, 미사용·실행 컬럼은 빈칸)
- `테스트 데이터`·`사전조건`의 사용 여부는 **프로파일**에 있다 (VIOLA는 `사전조건` 100% 필수·`테스트 데이터` 미사용)

### C-3. 구분 × 우선순위 결합 규칙을 지킨다

**프로파일**의 "구분 × 우선순위 결합 규칙" 표에 **예외 0건인 규칙**이 있다. 이건 지침이 아니라 제약이다.

- 예: 세 프로파일 모두 `부수` → **항상 `P4`**. TROMBONE은 `표시` → **항상 `P3`**
- 반대로 **제품마다 다른 규칙을 옮겨 적용하지 않는다** — VIOLA는 `정상`에 P3·P4를 준 사례가 0건이지만 TROMBONE `정상`은 P3가 60%다
- 작성 후 결합 규칙 위반 건수를 세어 0인지 확인한다

### C-4. 솔루션 컬럼은 단일값 고정 — 모듈 접미사를 만들지 않는다

- 값은 **프로파일**에서 읽는다 (VIOLA `VIOLA` / BootFactory `BOOTFACTORY` 등). 제품 전역 단일값이다
- **`VIOLA_K8S`·`VIOLA_CICD` 같은 모듈별 접미사 분리는 실측 0건이므로 만들지 않는다.** 대상 시트에 접미사가 실제로 보이면 사양 외 enum(Major)으로 **보고**한다
- 관리 영역(K8s / CI·CD)은 **탭 분리 + `1 Depth`(Breadcrumb 최상위 원문)** 로 표현된다. 솔루션 컬럼에도, 별도 컬럼에도 넣지 않는다 — 2026-08-25에 신설했던 전용 컬럼은 **2026-09-02에 폐지**됐다
- `1 Depth`는 기획서 Breadcrumb 최상위 **원문**을 그대로 쓴다. 제품 유형 이름을 옮겨 적는 칸이 아니다

## 양식 매핑

`common.md`의 **23컬럼 A~W** 구조 그대로 출력한다 (대상 시트 실측 헤더가 다르면 `02_sheet_format.md`의
대조 결과가 우선이며, 불일치가 보고됐으면 **작성하지 말고 중단**한다).
임의로 컬럼을 추가/제거하지 않는다. **23컬럼을 넘겨 쓰지 않는다.**

개념 → 컬럼 매핑 (실제 컬럼명·순서는 `common.md`가 유일한 기준. 대상 시트 실측과 다르면 `sheet-analyst` 결과 우선):

| 우리가 생성한 항목 | 시트 컬럼 매핑 예시 |
|-------------------|-------------------|
| ID | TC ID / 케이스 번호 |
| 기능 분류 | Module / 기능 |
| 케이스 제목 | Title / 시나리오명 |
| 사전 조건 | Pre-condition |
| 단계 (개행 구분 번호) | Steps / 절차 |
| 예상 결과 | Expected Result |
| 우선순위 | Priority (양식 enum에서 선택) |
| 분류 | Type (Normal/Negative/Edge) |
| 비고 | Note / Remarks |

양식 기준에 정의된 enum 값(P1~P4, High/Medium/Low 등)만 사용한다. 사양에 없는 값을 새로 만들지 않는다.

## 우선순위 결정 기준

양식 기준의 enum이 무엇이냐에 따라 다음 정책을 적용한다.

### A. P1/P2/P3 + P4 enum이 정의된 팀 양식 (atomic 모드 권장 정책)

| 우선순위 | 적용 케이스 | 예시 |
|---------|-----------|------|
| **P1** | 핵심 액션 버튼 클릭 → 다음 화면 이동 / 기능 동작 트리거 (라우팅 중심) | "생성" 클릭, "실행" 클릭, "실행 번호 클릭 → 로그 모달" |
| **P2** | 다이얼로그 진행, 시나리오 흐름 완료, 비즈니스 임팩트 큰 비정상 | "수정" 다이얼로그 진행, 도메인 규칙 위반 |
| **P3** | UI 표시 검증, 컬럼별 노출, enum 표출, 일시 형식 | "컬럼 순서 확인", "상태 호버 enum", "일시 형식" |
| **P4** | 취소 동작, 비활성화 상태, 권한 없음 닫기, 부수 모달 | "취소" 클릭 → 모달 닫힘, "권한 없음" 팝업 닫기 |

> **중요**: 팀이 정착시킨 정책에서 P1은 매우 보수적이다. 단순 정상 흐름이라도 라우팅·핵심 동작이 아니면 P3로 분류한다. 비즈니스 임팩트가 아니라 **"이 검증이 깨지면 다음 화면으로 갈 수 없는가?"** 기준.

### B. P1/P2/P3만 정의된 양식 (구식 / 일반)

| 우선순위 | 적용 케이스 |
|---------|-----------|
| **P1** | 핵심 기능의 정상 흐름, 결제·인증 등 비즈니스 임팩트가 큰 흐름 |
| **P2** | 부수 기능, 일반적인 비정상 흐름, 흔한 엣지 케이스 |
| **P3** | UI 디테일, 드물게 발생하는 엣지 케이스 |

양식 기준의 enum을 그대로 따른다. P4가 있으면 A 정책, 없으면 B 정책.

## 출력 형식

산출물은 **두 개**다. **케이스 본문은 시트가 단일 출처이고, `.md` 는 그것을 가리키는 요약이다.**

| 파일 | 내용 | 읽는 주체 |
|------|------|----------|
| `_workspace/03_testcases_s{NN}.md` | 메타 + 요약 + **근거 매핑 표** (케이스 본문 없음) | 사용자·리뷰어 |
| `_workspace/03_rows_s{NN}.tsv` | 시트에 쓴 23컬럼 **원본 그대로** (탭 구분, 헤더 없음) | 스크립트 전용 |

### 왜 케이스 본문을 `.md` 에 중복 저장하지 않는가

실측에서 `03_*.md` 34개 1,099KB 중 **케이스 전문이 714KB(65%)** 였고 그 내용은 **시트에 이미
있는 것과 같았다.** 리뷰어는 `.md` 와 시트 read-back을 **둘 다** 읽어 같은 텍스트를 두 번 봤다.
작성 출력(5배 단가) + 리뷰 입력이 이중으로 든다.

**복구 경로는 `.tsv` 가 담당한다.** 시트 append가 부분 실패해도 `.tsv` 가 있으면 재작성할 수
있고, 이 파일은 사람도 모델도 읽지 않으므로 컨텍스트 비용이 0이다.

### `03_testcases_s{NN}.md` 구조

```markdown
# 생성된 테스트 케이스 — 순번 {NN} / `{화면 ID}`

## 메타정보
- 대상 시트 / 탭 / **작성 행 범위**
- 제품 유형 / 프로파일 · 기획서 유형 · 이 화면의 정책 · 생성 모드
- 생성 케이스 수 (**실측 카운트**) · TC ID 범위 · `No` 범위 · CH-ID 접두 · 사용 C-ID
- 로컬 원본: `_workspace/03_rows_s{NN}.tsv`

## 케이스 요약 (구분별 — 실측 카운트)
| 구분 | 개수 |

## 근거 매핑 (역추적용 — 이 표가 이 파일의 본체다)
| TC ID | 근거 (비고에 쓴 태그) | 대상 |
|-------|--------------------|------|
| TC_VIO_603 | `[DESC 2항-1]` | 기본 정보 섹션 표시 |
| TC_VIO_604 | `[공통 DESC C9]` | 터미널 실행 버튼 |

## 기획 확인 필요 항목
| TC ID | 추측 기반 작성 부분 | 확인 요청 사항 |
```

### 쓰지 않는 것 — 자기점검 서술

**아래를 `.md` 에 적지 않는다.** 기계 검사는 `verify_sheet_rows.py` 가 전수로 하고,
리뷰어는 **작성자 자기 점검표를 인용하는 것이 금지**돼 있다 — 즉 **아무도 읽지 않는 출력을
출력 단가로 생산하는 것**이다 (실측: `.md` 의 35%, 한 파일은 55%가 메타·자기점검이었다).

| 쓰지 않는다 | 대신 |
|-----------|------|
| 「표기 규약 (이 파일 한정)」 | — (`common.md` 규칙을 재서술할 이유가 없다) |
| 「오케스트레이터 확정값 적용 결과」 표 | 메타정보 한 줄 |
| 「R7 통과 — 대괄호 0건 (기계 검사)」 류 | `verify_sheet_rows.py` 결과 (리뷰어가 직접 실행) |
| 「분포 대조 (프로파일 실측 vs 생성)」 | **Phase 5 전체 집계 리뷰** — 화면 1개 표본은 의미 없다 |
| 「정책 예외 반영 현황」 표 | 케이스 `피드백` 의 `[정책 예외]` 태그 (시트에 이미 있다) |
| 「판독 이슈 반영 현황」 표 | 케이스 `피드백` 의 `[판독 주의]` 태그 |

**메타정보에 남길 자기 점검은 한 줄이다:**
`기계 검사: verify_sheet_rows.py 위반 0건 (exit 0)` — 실행하지 않았으면 `미실행` 이라 적는다.
**"통과"라고 적으려면 실제로 돌렸어야 한다.**

`.tsv` 는 시트에 보낸 값과 **동일한 문자열**이어야 한다 (셀 내 개행은 `\n` 이스케이프 없이
그대로 두지 말고, `.tsv` 에서는 개행을 `\\n` 리터럴로 치환해 한 행 = 한 줄을 유지한다).

이 파일은 시트 작성 **후** 갱신한다 (작성 행 범위를 메타에 적기 때문). 첫 화면만 사용자 검토를
거치고, 검토 시점에는 `.tsv` 와 요약을 보여준다.

- [ ] `불가` 페이지는 추측 케이스 없이 판독 불가 케이스 1건으로 남고, 예상 결과가 단정되지 않음

기획서 유형이 `변경`인 경우 추가 (0-H):
- [ ] 메타정보에 `생성 범위: 변경분 한정` 명시됨
- [ ] 변경분 목록의 모든 항목이 최소 1건 이상 커버됨 (커버리지 표로 보고)
- [ ] `[맥락 — 비변경분]` 항목으로 TC를 만들지 않았음 (사전조건·절차에만 활용)
- [ ] **삭제 유형 변경분에 "더는 노출되지 않음" 검증 케이스가 있음** (취소선 항목 전수 확인)
- [ ] **취소선 항목으로 정상 동작·표출 케이스를 만들지 않았음** — 허용되는 유일한 케이스는 "더는 노출·동작하지 않음" 검증 (만들면 실행자가 반드시 잘못된 FAIL을 낸다)
- [ ] **하위 트리 전체 취소선** 항목에 하위 개별 동작 케이스가 없음 (트리 전부 미표출로 묶임)
- [ ] **부분 취소선** 항목이 ① 삭제 토큰 미잔존 ② 새 토큰 표출 **두 건으로만** 작성됨 (삭제 토큰을 포함한 기능 검증 0건)
- [ ] "삭제 자리의 대체 동작"은 기획서에 대체가 **명시된 경우에만** 케이스화됨 (명시 없으면 미노출 검증까지 + 피드백 `[확인 불가]`)
- [ ] 대체 동작 케이스의 비고 CH-ID가 **삭제 항목이 아니라 대체를 규정한 항목**의 것임
- [ ] **근거가 색 박스뿐인 항목을 화면 전수로 케이스화하지 않았음** (피드백에 `[변경 범위 불명]` 기재 + 확인 요구)
- [ ] 박스 + 항목 근거가 함께 있는 항목이 **항목 근거가 가리키는 범위**로만 케이스화됨 (전면 박스로 범위를 넓히지 않음)
- [ ] 신규 화면·팝업이 **존재·기본 구성 수준**으로 묶임 (세부 동작 분해는 그 동작 각각에 항목 근거가 있을 때만)
- [ ] 분석서에 「박스 ↔ 확정 항목 대조표」가 있으면 **그것을 케이스 범위 기준으로 삼았음**
- [ ] 각 케이스 비고에 `[변경 CH{NN}-N {종류 원문} {회차}-{일자}]` 근거가 기재됨 (**CH-ID 필수** — 없으면 역추적 불가)
- [ ] CH-ID가 `CH{NN}-N` 네임스페이스를 지킴 — **오케스트레이터가 넘긴 CH-ID 접두를 그대로 사용**했고 직접 계산하지 않았음 (충돌 0건)
- [ ] **다어절 종류 원문이 회차와 붙지 않고 띄어져 있음** (`[변경 CH01-1 명칭 변경 v1-26.07.31]`)
- [ ] 날짜 미표기 항목이 `-`가 아니라 `날짜미표기`로 기재됨 (`-`는 No-data 의미와 충돌)
- [ ] 종류 원문이 없는 항목이 `종류 원문 미표기`로 기재됨 (**색으로 종류·회차를 추정하지 않음**)
- [ ] 각 케이스의 절차·예상 결과가 비고에 적은 변경분을 실제로 건드림 (선언만 하고 비변경분을 검증하는 케이스 없음)
- [ ] 기획 미정의 항목의 예상 결과가 `ㄴ 기획 미정의 항목 — PASS/FAIL 판정 대신…` 패턴으로 통일됨 (단정 + `[확인 불가]` 자기모순 없음)
- [ ] `구분` enum에 신규 값을 만들지 않았음 (팀 양식 enum 유지)

예외 항목(정책 예외)이 있는 경우 추가 (0-I):
- [ ] 예외 화면의 **모든** 케이스 피드백에 `[정책 예외] 문서 기본={신규|변경} / 이 화면={변경|신규}` 기재됨
- [ ] 예외 화면이 반대 정책의 **케이스화 범위**로 작성됨 (신규 정책 → 화면 전수 / 변경 정책 → 변경 표기 항목만)
- [ ] 예외 화면의 **비고 태그 체계**가 그 정책에 맞음 (신규 정책 화면에 `[변경 CH…]` 태그를 쓰지 않았음)
- [ ] 예외 목록에 없는 화면은 문서 기본 정책대로 작성됨 (임의 정책 전환 0건 — 의심 사례는 보고만)
- [ ] `[정책 예외]`가 다른 피드백 태그를 밀어내지 않았음 (둘 다 기재)
