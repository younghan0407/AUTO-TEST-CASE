# PRD Analyzer

Figma REST API / PDF 변환 이미지 / 직접 전달된 이미지 파일을 읽어 기획서(PRD)를 분석하고, "테스트 케이스 작성에 활용 가능한 기능 단위"로 변환한다.

## 트리거 키워드

- Figma URL 언급, "기획서 분석", "화면 인벤토리"
- "이 디자인에서 테스트 케이스 뽑아줘"
- "Figma 다시 읽어줘", "특정 프레임만 다시 분석"
- PDF 파일 경로 언급, "PDF로 분석해줘"
- 이미지 파일·디렉터리 경로 언급(`.png`, `.jpg` 등), "이미지로 된 기획서", "캡처로 분석해줘"

## 사전 조건

- **Figma 입력 시**: `FIGMA_ACCESS_TOKEN` 환경변수 설정 (`.claude/settings.json`의 env), 파일에 view 권한 이상
- **PDF 입력 시**: `pymupdf` 패키지 설치 (`pip install pymupdf`)
- **이미지 입력 시**: `pillow`, `numpy` 패키지 설치 (`pip install pillow numpy`). `pymupdf`는 필요 없다

## 입력 유형 판별

입력을 받으면 가장 먼저 유형을 판별하여 해당 경로로 분기한다:

| 입력 형태 | 판별 기준 | 실행 경로 |
|-----------|----------|----------|
| Figma URL | `figma.com` 도메인 포함 | [Figma API 경로](#figma-api-경로) |
| PDF 파일 | `.pdf` 확장자 또는 사용자가 "PDF"라고 명시 | [PDF 경로](#pdf-경로) |
| **이미지 파일·디렉터리** | `.png` `.jpg` `.jpeg` `.webp` `.bmp` `.tif` 확장자, 또는 이미지가 담긴 디렉터리 경로 | [이미지 경로](#이미지-경로) |

**PDF도 Figma도 없이 기획서가 이미지로만 전달된 경우 — 변환 단계를 찾지 말고 즉시 이미지 분석에 들어간다.**
PDF를 요구하거나 되돌려 받으려 하지 않는다. 이미지가 곧 분석 원천이다.

| 상황 | 처리 |
|------|------|
| 이미지만 있음 | **바로 [이미지 경로](#이미지-경로)로 분석 시작** (변환 없음) |
| 이미지 + 동일 내용 PDF가 함께 있음 | PDF를 원천으로 표준 변환 경로 사용 (원본 이미지는 해상도가 과도해 판독 비효율일 수 있음) |
| 이미지 + 다른 내용 PDF | 각각 별도 입력으로 취급하고 사용자에게 처리 범위를 확인 |

## 공통: 이미지 판독 품질 게이트 (분석 착수 전 필수)

분석 대상 이미지를 읽기 **전에** 판독 품질을 진단한다. 이미지 입력에서는 필수이고, PDF 변환 결과에도 그대로 쓸 수 있다.

```bash
python scripts/check_image_quality.py <이미지 디렉터리|파일> --json=_workspace/00_image_quality_ch{N}.json
```

지표: 짧은 변 픽셀(해상도) / 라플라시안 분산(선명도) / 그레이스케일 표준편차(대비) / 파일 끊김(훼손).
종료 코드는 `불가` 판정이 하나라도 있으면 `2`다 (파이프라인 게이트로 사용 가능).

| 판정 | 처리 |
|------|------|
| `OK` | 그대로 분석 진행 |
| `주의` | ① 사용자에게 알린다 ② 분석 결과에 `[판독 주의]` 기록 ③ 해당 페이지 케이스의 피드백 컬럼에 판독 이슈 기재 후 진행 |
| `불가` | ① 사용자에게 알리고 **원본 재전달을 요청**한다 ② 분석 결과에 `[판독 불가]` 기록 ③ 추측으로 케이스화하지 않고, 판독 불가 사실을 남기는 케이스를 작성한다 |

**사용자 통보는 의무다.** 판독이 안 되는 페이지를 조용히 스킵하는 것은 누락과 같다. 다음 형식으로 즉시 보고한다:

```
⚠️ 이미지 판독 이슈 2건 (총 14장)
- page_012.png : 해상도 부족 (짧은 변 640px) → 판독 주의, 텍스트 오독 가능
- page_015.png : 파일 훼손(중간 끊김) → 판독 불가

판독 불가 페이지는 추측하지 않고 [판독 불가] 표시로 케이스에 남깁니다.
해당 페이지 원본을 다시 전달해 주시면 재분석합니다.
```

**스크립트 판정보다 실제 판독 결과가 우선이다.** 지표가 `OK`인데 육안으로 글자가 뭉개져 읽히지 않으면 그 페이지는 `주의`/`불가`로 취급한다. 반대로 지표가 `주의`인데 텍스트가 온전히 읽히면 그대로 진행하고 그 사실을 기록한다.

**분석 결과 기록 형식** (`01_prd_analysis_ch{N}.md`에 섹션 필수. 이슈가 없으면 "판독 이슈 없음"으로 명시):

```markdown
## 이미지 판독 이슈
| 페이지 | 파일 | 판정 | 사유 | 영향 (판독 못한 항목) |
|--------|------|------|------|---------------------|
| p012 | page_012.png | 주의 | 해상도 부족(640px) | Description 3항 일부 숫자 오독 가능 |
| p015 | page_015.png | 불가 | 파일 훼손 | 페이지 전체 |
```

## 공통: 분석 컨텍스트 — 오케스트레이터에게 받는 것 (스스로 판정하지 않는다)

분석 착수 전 오케스트레이터가 `testcase-auto` **Phase 0 기본 정보 수집**에서 사용자에게
확정받은 값을 프롬프트로 넘긴다. **분석 담당이 추정하거나 뒤집지 않는다.**

| 항목 | 값 | 분석에서 쓰는 방식 |
|------|-----|------------------|
| **제품 유형** | `VIOLA K8s` / `VIOLA CI/CD` / `TROMBONE` / `BootFactory` | **분석 컨텍스트** — 어느 관리 영역의 기획서인지. 양식 프로파일 선택의 근거이기도 하다 |
| **기획서 유형** | `신규` / `변경` | 문서 **전체의 기본 분석 정책**. `변경` 이면 [PDF-3.5](#pdf-35-변경분-한정-분석-모드) |
| **예외 항목** | 화면 ID 목록 (없으면 "없음") | 그 화면만 **반대 정책**으로 분석 |
| 기획서 경로 / 대상 시트·탭 | — | 분석 대상 범위 |

**양식 사양은 `.claude/formats/common.md`(공통 골격) + 해당 `profile-{제품}.md`(제품별 델타)
두 개를 함께 읽는다.** 한쪽만 읽으면 규칙의 절반이 없다.
(구 `team-viola.md`·`team-trombone.md` 는 2026-09-02에 이 구조로 재편되며 삭제됐다.)

### 제품 유형은 컬럼 값이 아니라 컨텍스트다

2026-08-25에 VIOLA 전용으로 신설했던 **`관리대상` 컬럼(`K8S`/`CI·CD`/`BF(공통)`)은
2026-09-02에 폐지됐다.** 전 제품이 23컬럼 A~W로 통일됐고,
**화면·케이스마다 관리대상을 판정하던 절차도 함께 삭제됐다 — 그 판정을 하지 마라.**

- 관리 영역(`K8s` / `CI·CD`)은 **Phase 0에서 제품 유형으로 이미 확정**돼 프롬프트로 온다
- 시트에서 그 구분은 **탭 분리 + `1 Depth`** 로 표현된다
- **`1 Depth` 에 쓸 값은 여전히 분석서가 원천이다** — Breadcrumb 최상위 **원문 그대로**
  (번역·변형·구분자 통일 금지). **제품 유형 문자열에서 만들어내지 마라.** 제품 유형이
  `VIOLA K8s` 라고 `1 Depth` 를 `K8s` 로 적는 것은 기획서에 없는 값이다

### 예외 항목 — 문서 기본 정책과 반대인 화면

기획서 유형이 **문서 전체의 기본 정책**이고, 예외 목록에 오른 **화면 ID만 반대 정책**을 적용한다.

| 문서 기본 | 예외 화면에 적용 | 그 화면의 분석 범위 |
|-----------|----------------|-------------------|
| `신규` | **변경 정책** | 항목 근거(스티커 / DESC 색 텍스트 / 취소선 / `ChangeLog`)가 있는 항목만. **색 박스는 범위 후보일 뿐 항목을 확정하지 않는다** ([PDF-3.5](#pdf-35-변경분-한정-분석-모드)) |
| `변경` | **신규 정책** | **변경 표기 유무와 무관하게 화면 전수** |

**예외 화면은 분석 단계에서부터 반대 정책으로 분석한다.** 케이스 생성 단계에서 걸러 내는 것이
아니다 — 기본이 `변경` 인데 예외 화면을 변경분만 뽑아 두면 그 화면의 전수 분석 근거가
분석서에 아예 없고, 후속 단계가 복구할 방법이 없다.

분석서 산출 의무:

- **메타정보에 문서 기본 정책과 예외 화면 목록을 명시**한다
  (예: `분석 정책: 기본=변경 / 예외=VIOE-03_01_04_13 (이 화면만 신규 정책)`)
- 예외 화면에서 나온 항목에는 **`[정책 예외]`** 표시를 남긴다. 나중에 왜 이 화면만
  다르게 분석됐는지 역추적할 수 있어야 한다
- **예외 목록에 없는 화면에서 반대 성격이 뚜렷하게 보여도 임의로 정책을 뒤집지 않는다.**
  사실만 적어 보고하고(예: *"p12는 화면 전체가 신규로 보이는데 예외 목록에 없음"*)
  오케스트레이터의 판단을 받는다

**추론으로 채우지 않는다.** 제품 지식으로 "VIOLA니까 CI·CD 화면도 있을 것"이라고 쓰는 것은
근거가 아니다. 기획서에 없으면 없다고 쓰고 확인을 요구한다.

## PDF 경로

### PDF-1. 이미지 변환

PDF 파일을 페이지별 PNG로 변환한다.

```bash
python scripts/pdf_to_images.py <pdf_path> [--dpi=150] [--output-dir=_workspace/pdf_images/<name>] [--pages=START-END]
```

- 기본 DPI: 150 (텍스트 가독성 충분). 텍스트가 작거나 표·다이어그램이 밀집된 경우 200으로 올린다.
- 출력 파일: `_workspace/pdf_images/<pdf_basename>/page_001.png`, `page_002.png`, ...
- `pymupdf` 미설치 시 설치 안내 메시지가 출력되고 중단됨.
- `--pages=START-END`: 변환할 페이지 범위 지정 (1-indexed, 양 끝 포함). 생략 시 전체 변환.

### PDF-1.5. 챕터 단위 순차 분석 전략

PDF 분석은 **챕터(간지) 단위로 순차 처리**한다. 1개의 prd-analyst 에이전트가 담당 챕터의 페이지 이미지를 처음부터 끝까지 순서대로 읽어 분석한다.

**에이전트당 안전 이미지 한도: 12~13페이지** (전체 + 크롭 이미지 합산 ~26장)

챕터 내 페이지 수가 이 한도를 초과하더라도 **단일 에이전트가 순차적으로 처리**한다. Claude는 이미지를 순서대로 읽으므로, 앞 페이지의 맥락을 유지하면서 다음 페이지를 분석할 수 있다. 한도를 초과하는 경우 다음과 같이 처리한다:

- 한 번의 Read 호출에 최대 13페이지씩 나누어 순차 분석
- 각 구간 분석 결과를 메모리에 유지하면서 다음 구간 분석 시 이전 맥락을 참고
- 모든 구간 완료 후 하나의 챕터 분석 파일로 통합

**파일 명명 규칙:**

| 단계 | 파일명 패턴 | 생성자 |
|------|-----------|--------|
| 챕터 분석 결과 | `_workspace/01_prd_analysis_ch{N}.md` | prd-analyst |
| 전체 합본 | `_workspace/01_prd_analysis.md` | 오케스트레이터 (Phase 5) |

챕터 번호 `{N}`은 `_workspace/00_chapters.md`의 순서를 따른다 (예: ch01, ch02, ...).

### PDF-2. 이미지 변환 전략 (DPI 선택)

기획서 스펙 페이지는 **좌측 UI 화면 + 우측 Description 패널** 구조다. 두 영역을 별도 전략으로 변환한다:

| 변환 대상 | DPI | 명령 | 용도 |
|----------|-----|------|------|
| 전체 페이지 | 150 | `python scripts/pdf_to_images.py <pdf> --dpi=150` | UI 화면 파악, 화면 인벤토리, 플로우 추론 |
| Description 패널 크롭 | 200 | `python scripts/pdf_to_images.py <pdf> --crop-desc --dpi=200` | Description 텍스트 정밀 판독 (최우선 분석 소스) |

스펙 페이지(Description 패널이 있는 페이지)는 반드시 크롭 이미지를 먼저 읽어 Description을 추출한 뒤, 전체 이미지로 UI를 보완한다.

### PDF-3. 이미지 시각 분석

**분석 우선순위: Description 패널 > UI 화면**

Description 패널(`page_NNN_desc.png`)을 먼저 읽어 모든 항목을 추출한다. Description에 명시된 내용은 100% 케이스화 대상이다. UI 화면(`page_NNN.png`)은 Description에 없는 항목을 보완하는 용도로만 사용한다.

**스펙 페이지 분석 절차:**
1. 크롭 이미지(`page_NNN_desc.png`) 읽기 → Description 항목 전수 추출
   - 번호/알파벳 계층 구조 (❶, 1, 1.a, 1.b 등) 그대로 기록
   - 빨간색(강조) 텍스트 별도 표시 (`[강조]` 태그)
   - 화면 식별자 (우측 상단 헤더) 반드시 추출 — 필드명이 `Page ID`가 아닐 수 있다. 아래 **화면 식별자 추출 규칙** 참조
2. 전체 이미지(`page_NNN.png`) 읽기 → UI 요소 중 Description 미포함 항목 보완
3. **UI ↔ Description 비교** — 동일 항목에 대해 UI와 Description 내용이 다른 경우 `[UI↔DESC 불일치]` 태그로 명시
   - 불일치 형식: `[UI↔DESC 불일치] UI: {UI에서 확인된 내용} / DESC: {Description 내용}`
   - 예: `[UI↔DESC 불일치] UI: 아이디·비밀번호 입력 / DESC: 아이디·비밀번호·OTP 입력`
   - 어느 쪽이 맞는지 판단하지 않는다. 사실 그대로 기록.

**챕터 내 공통 Description 감지 (페이지 전체 분석 후):**

챕터 내 모든 페이지 분석이 끝난 뒤, Description 항목을 페이지 간 비교한다.
- 2개 이상의 페이지에서 동일하거나 매우 유사한 Description 항목이 발견되면 `[공통 DESC]` 태그를 붙이고 해당 페이지 목록을 기록한다.
- 형식: `[공통 DESC: ADM-TCK-0100-01, ADM-TCK-0100-02] {항목 내용}`
- **공통 항목이라도 각 페이지의 분석 결과에 모두 포함한다. 생략 금지.**

**공통 DESC C-ID 배정 절차 (분석 담당이 할 일 / 하지 말 일):**

시트 비고에 들어가는 `[공통 DESC CN]` 의 번호는 **탭 전역에서 정의 단위로 유일**해야 한다.
그런데 챕터 분석 담당은 **다른 챕터가 어떤 번호를 썼는지 알 수 없다.** 그래서 역할을 나눈다.

| 단계 | 담당 | 하는 일 |
|------|------|--------|
| 1 | **분석 담당(나)** | 자기 분석서 안에서 **`C1` 부터** 매기고 **정의표**를 싣는다 |
| 2 | **오케스트레이터** | **모든 챕터 분석을 받은 뒤 한 번에** 시트용 번호를 배정한다 |

1. **번호는 자기 분석서 기준 `C1` 부터 시작한다.** 앞 챕터가 `C1`~`C4` 를 썼을 것 같다는 이유로
   `C5` 부터 매기지 않는다. 그 추측이 틀리면 그대로 충돌이다
2. **정의표에 조정 대상임을 반드시 적는다.** 이 문구가 없으면 다음 사람이 분석서 번호를 그대로
   시트에 옮긴다. 정의표 머리에 다음 한 줄을 넣는다:
   > `※ 이 C-ID는 본 분석서 내 로컬 번호다. 시트 배정은 오케스트레이터가 전 챕터를 모아 조정한다.`
3. **정의표 없는 C-ID를 쓰지 않는다.** 정의가 없으면 시트 행에서 기획서 근거로 역추적이 끊겨
   태그 자체가 무의미해진다. 형식:

   | C-ID (로컬) | 정의 내용 | 근거 화면 ID·DESC 항목 | 적용 페이지 | 연결 근거(상호 참조 원문) |
   |------------|----------|---------------------|-----------|------------------------|

   **「연결 근거」 칸이 비어 있으면 연결하면 안 되는 항목이다.** 아래 판단 기준을 보라.

**⚠️ "하나의 정의"인지는 내용 유사성이 아니라 기획서의 상호 참조로 판단한다.**
이건 분석 담당이 내리는 판정이므로 특히 조심할 것.

| | 하나의 정의 (같은 C-ID) | 병렬 변경 (연결하지 않음) |
|---|---|---|
| 판단 근거 | 기획서에 **명시적 상호 참조**가 있다 — `… > N항 참고`, `… 와 동일하게 제공` | 각 화면에 **독립한 근거**가 따로 있다 (각각의 스티커, 문구도 서로 다름) |
| 처리 | 두 위치에 같은 C-ID를 달고 정의표에 적용 페이지를 모두 적는다 | 연결하지 않고 각자 CH-ID로만 관리한다 |

**일자·회차·변경 내용이 완전히 같아도 상호 참조가 없으면 연결하지 않는다.**
기획서가 잇지 않은 것을 이어 붙이면 기획서에 없는 관계를 단정하는 것이고, 한쪽 기획 회신이
다른 쪽에 자동 적용된다고 볼 근거가 없다.
(실측 판정 2건 — 상세 화면 DESC가 `목록 > '작업' 버튼 정의와 동일하게 제공 (VIOE-03_01_01-01 > 2항 참고)`
로 목록 화면을 직접 가리킨 건은 **하나의 정의**. 반면 두 화면의 `상태 표기 형태 변경` 은
일자 `26.03.19`·회차 `v1`·내용 `icon+text → tag` 가 전부 같았지만 각 화면에 **독립한 스티커**가
있고 문구도 달라 **병렬 변경**으로 두었다.)

> 이 규칙은 **양방향으로 다 틀린 이력**에서 나왔다. 2026-08-25에는 ch03·ch04가 `C5` 를 각각
> 다른 뜻으로 써서 12행이 충돌했고(순차 배정이 원인), 2026-08-27에는 *"`C1` 이 소진됐으니
> 다음 챕터는 `C2`"* 로 판단해 **같은 변경 하나를 두 번 정의**할 뻔했다.
> **C-ID는 소진되는 순번이 아니라 정의를 잇는 공유 키다.**

**화면 식별자 추출 규칙 (화면 ID 컬럼의 원천):**

스펙 페이지 우측 상단 헤더에서 화면 식별자를 추출한다. **필드명은 기획서마다 다르므로 다음 우선순위로 탐색한다.**

| 우선순위 | 헤더 필드명 | 값 형식 예 |
|---------|-----------|----------|
| 1 | `Page ID` | `ADM-TCK-0100-02` |
| 2 | `Screen ID` | `VIOE-00_00_05`, `VIOE-02_01_01-11` |
| 3 | 그 외 화면 식별자 성격의 필드 (`화면 ID`, `Screen No`, `Page No` 등) | 기획서 표기 그대로 |

- **`Page ID`가 없으면 `Screen ID` 값을 그대로 화면 ID 컬럼에 사용한다.** 값 형식을 `ADM-XXX-NNNN-NN` 꼴로 변환·정규화하지 말고 **기획서 원문 표기를 그대로** 쓴다.
- 어떤 필드명에서 가져왔는지 분석 결과 메타정보에 명시한다 (예: `화면 식별자 출처: Screen ID`).
- 우선순위 1~3 모두 없으면 `[확인 불가]`로 명시하고, 상위 기능/직전 페이지의 식별자를 임시 사용하되 그 사실을 함께 기록한다.
- 동일 식별자가 여러 페이지에 반복되거나 번호가 역순으로 배치된 경우, 판단하지 말고 사실만 기록한다.

**분석 항목:**
1. **화면 식별자 추출** — 위 규칙에 따라 `Page ID` → `Screen ID` → 기타 순으로 탐색. 이 값이 화면 ID 컬럼에 기입된다
2. **화면 식별** — 각 페이지가 독립 화면인지, 스펙 페이지인지 판단
3. **Description 전수 추출** — 번호·알파벳 계층 구조의 모든 항목, 강조(빨간색) 항목 포함
4. **UI 요소 추출** — Description 미포함 버튼, 입력 필드, 테이블, 모달, 토스트, 탭
5. **UI ↔ Description 불일치 목록** — 두 소스 간 내용이 다른 항목 (`[UI↔DESC 불일치]` 태그)
6. **플로우 추론** — 화면 간 번호/화살표/주석, 불명확하면 "추론" 표시
7. **비즈니스 규칙** — 필수/선택 표시, 입력 제약, 권한 분기, 상태 조건
8. **`1 Depth` 원천 추출** — Breadcrumb 최상위 **원문 그대로** (번역·변형·구분자 통일 금지). 제품 유형 문자열에서 만들어내지 않는다 (위 "공통: 분석 컨텍스트" 절)
9. **정책 예외 화면 여부** — 그 페이지의 화면 ID가 예외 목록에 있으면 반대 정책으로 분석하고 항목에 `[정책 예외]` 표시

분석 불가 항목은 추측하지 않고 "이미지에서 확인 불가"로 명시한다.

### PDF-3.5. 변경분 한정 분석 모드

**Phase 0에서 확정된 기획서 유형이 `변경`** 이면 이 모드로 동작한다
(사용자가 **"변경된 이력만"**, **"변경분만"**, **"변경사항 위주로"** 라고 직접 요청한 경우도 같다).
개정판 기획서(v1, v2 …)는 변경된 부분만 색으로 표시하는 것이 팀 컨벤션이다.

**정책 예외 화면은 이 모드에서 제외된다.** 기획서 유형이 `변경` 이어도 예외 목록에 오른 화면은
**신규 정책 — 화면 전수 분석**이다 (위 "공통: 분석 컨텍스트 > 예외 항목" 절). 반대로 기획서
유형이 `신규` 여도 예외 목록에 오른 화면에는 **이 절을 그 화면에만 적용**한다.

**변경 표시 컨벤션 — 경로를 모두 교차 확인하되, 경로가 대등하지 않다는 것을 먼저 알아라.**

**어디를 볼지 알려주는 것**과 **무엇이 바뀌었는지 정하는 것**은 다른 역할이다. 섞으면 변경 범위가 부풀어 오른다.
(`.claude/formats/common.md` 「변경 표기 경로의 위계」 절과 같은 규칙이다.)

| # | 경로 | 위치 | 역할 | 확정력 |
|---|------|------|------|--------|
| 1 | **색 테두리 박스** | 화면 와이어프레임 | **범위 후보(scope hint)** — "이 영역 안에 변경이 있다"까지만 | **없음** |
| 2 | **색 `변경사항` 스티커** | 화면 여백 | **항목 확정** — 변경 내역을 문장으로 명시 (날짜·`vN` 배지 포함) | 있음 |
| 3 | **DESC 색 텍스트** | Description 패널 | **항목 확정** — 무엇이 어떻게 바뀌었는지 서술. `(v1추가 - YYMMDD)`, `(v2수정_현행화 - YYMMDD)`, `(v2삭제_탭 통합 - YYMMDD)` 를 동반하는 경우가 많다 | 있음 |
| 4 | **취소선** | Description·화면 라벨 | **항목 확정** — 그 내용의 **삭제** (아래 [취소선 = 삭제](#취소선--삭제-변경-종류-판정-규칙) 절) | 있음 |
| 5 | **`ChangeLog` 패널** | 페이지 우측 하단 (Description 패널 아래) | **항목 확정** — 그 페이지 변경 내역을 **목록으로 정리한 별도 패널**. 있으면 **체크리스트로 쓴다** | 있음 |

**박스 처리 규칙 (분석 절차에 그대로 적용한다):**

1. **박스를 발견하면 그 안에서 항목 근거를 찾아 그것만 변경분으로 확정한다.** 박스의 크기는 변경 범위가 아니다
2. **박스 + 항목 근거가 함께 있으면 항목 근거가 범위다.** 박스가 화면 전면을 감싸고 있어도,
   그 안의 **스티커·DESC 색 텍스트·취소선·`ChangeLog`** 가 가리키는 **항목만** 변경분이다
3. **박스만 있고 항목 근거가 0건이면 화면 전체를 변경분으로 잡지 않는다.**
   `[변경 범위 불명]` 으로 보고하고 사용자 확인을 요구한다. **임의 전수화 금지**
4. **예외 — 화면·팝업 자체가 신규인 경우만 전수 대상이다.** 단 그 판정 근거는 **박스가 아니라
   스티커·`ChangeLog` 원문**(`… 팝업 추가`, `… 화면 신규`)이어야 한다. 이 경우에도
   **존재·기본 구성 수준으로 묶고**, 세부 동작은 각각의 항목 근거를 요구한다

> **왜 이 위계가 필요한가 (실측).** Boot Factory `멤버 관리 > 사용자` 6페이지 실행에서
> **전면 박스가 있는 두 화면이 전체 케이스의 69%(87/127건)** 를 차지했다. 특히 권한 설정 팝업은
> **스티커 9개가 개별 변경을 구체적으로 가리키고 있었는데도** 전면 박스를 근거로
> `권한 설정 팝업 추가` 하나가 잡히면서 **팝업 전체 기능**(타이틀·구성 요소·확인·취소 버튼)이
> 케이스화돼 58건이 됐다. 박스에 확정력을 준 것이 원인이다.

**산출 의무 — 「박스 ↔ 확정 항목 대조표」**

색 박스를 하나라도 발견하면 분석서에 다음 표를 싣는다. **항목 근거가 0건인 박스도 행으로 남기고
그 사실을 명시한다** — 표에서 빠지면 "확인했는데 없었다"와 "안 봤다"를 구분할 수 없다.

| 박스 위치·크기 | 그 안의 항목 근거 (DESC·스티커·취소선·`ChangeLog`) | 확정된 변경분 CH-ID | 비고 |
|---------------|------------------------------------------------|-------------------|------|
| p5 권한 설정 팝업 전면 (1180×760) | 스티커 9건 | CH01-4 ~ CH01-12 | 박스 전면이지만 범위는 스티커 9항목 |
| p3 상단 검색 영역 (420×64) | **0건** | — | `[변경 범위 불명]` — 확인 요청 |

**⚠️ `ChangeLog` 는 완전한 목록이 아니다 — 체크리스트로 쓰되 권위로 믿지 마라.**

실측(VIOLA V4.0 `03 파드` p4)에서 이 패널의 한계가 그대로 드러났다:

- **항목 수는 스티커와 일치했다** — 분홍 스티커 2개가 각 2항목씩 담아 총 4항목, `ChangeLog` 도 4항목.
  "스티커보다 항목이 많다"가 일반 규칙은 아니다 (스티커 *개수* 와 *항목 수* 를 혼동하지 말 것)
- **그런데 회차가 통째로 빠져 있었다** — `ChangeLog` 배지는 `26.07.22 v1` 하나뿐이고,
  같은 페이지의 **v2(`26.08.18`) 변경 9건이 전부 미등재**였다. 파란 스티커·파란 DESC에는 있다

즉 `ChangeLog` 는 **작성 시점 회차까지만 반영된 스냅샷**일 수 있다.
그래서 두 방향으로 쓴다:

1. **정방향** — `ChangeLog` 원문을 전사하고 각 항목이 CH-ID로 커버되는지 대조표를 산출물에 싣는다.
   커버리지 자기 점검에 값싸고 확실하다
2. **역방향** — 다른 경로(박스·스티커·DESC)에서 찾은 변경분이 `ChangeLog` 에 **없는지** 확인한다.
   없으면 `[변경 표기 불일치]` 로 양쪽을 기록한다 (판단하지 말 것). **`ChangeLog` 에 없다는 이유로
   변경분을 탈락시키지 마라** — 위 실측에서 그렇게 했다면 v2 변경 9건이 전부 사라진다

`ChangeLog` 에만 있는 항목은 변경분으로 포함하고 근거를 `[ChangeLog]` 로 남긴다.

#### 취소선 = 삭제 (변경 종류 판정 규칙)

**기획서의 취소선은 그 내용이 삭제됐다는 뜻이다.** 이것은 검출 난이도 이전에 **변경 종류 판정 규칙**이다
— *어떻게 찾는가*(아래 스크립트 절)와 별개로, *찾으면 무슨 뜻인가*가 먼저 확정돼 있어야 한다.
(`.claude/formats/common.md` 「취소선 = 삭제」 절과 같은 규칙이다.)

1. **취소선이 있으면 변경 종류는 `삭제` 로 확정한다.** 주석 원문(`v2삭제_탭 통합` 등)이 함께 있으면
   그것을 **인용**하고, **없어도 취소선만으로 삭제로 판정한다.** 이때는 `종류 원문 미표기` 가 아니다
   — 종류는 취소선으로 확정됐고, **모르는 것은 일자뿐이므로 `날짜미표기`** 로 적는다
2. **하위 트리 전체 취소선은 트리 전부가 삭제다.** 상위 항목만 삭제로 보고 하위 항목을 살려 두지 않는다
   (실측: `~~상세 정보~~ (v2삭제_탭 통합 - 26.08.18)` — 하위 트리 전체에 취소선)
3. **부분 취소선은 삭제된 토큰과 남은 토큰을 갈라 적는다.** 분석서에 어느 토큰이 지워지고 어느 토큰이
   남는지 **명시적으로 분리**해 기록한다 — 후속 단계가 ① **삭제 토큰 미잔존** ② **새 토큰 표출**
   두 케이스를 만들 수 있어야 한다. (실측 형태: `솔루션 `~~`멤버`~~` 관리자`)
4. **삭제 자리의 대체 동작은 기획서에 명시된 경우에만 기록한다.** 명시가 있으면 **삭제 항목과 다른
   CH-ID**를 부여한다(대체를 규정한 항목이 근거이지, 삭제 항목이 근거가 아니다).
   **명시가 없으면 대체를 추정하지 말고 `[확인 불가]`** 로 남긴다

> 후속 단계가 이 판정에 의존한다. 삭제된 내용으로 정상 동작·표출 케이스를 만들면
> **실행자가 반드시 FAIL을 낸다** — 기획대로 사라진 것을 "안 된다"고 보고하게 된다.
> 그래서 분석서는 **삭제 항목을 삭제로 못 박아** 넘겨야 한다.

**표시색은 기획서마다 다르다 — 시작 전에 실측으로 확정하라.**

빨강만 쓰는 판본도 있고 **빨강과 파랑을 함께 쓰는 판본**도 있다 (VIOLA V4.0 `02-1 통합 모니터링` 실측).
색이 곧 변경 종류(추가/수정/삭제)를 뜻한다고 단정하지 마라 — **종류와 회차는 주석 텍스트 자체**에
`v2수정` / `v2추가` / `v2삭제` + 날짜로 적혀 있고, 그것이 권위 있는 근거다.

색↔회차 대응도 일정하지 않을 수 있다. 위 실측 기획서는 한 페이지에서 빨강이 `26.08.03`,
파랑이 `26.08.18` 이었으나 다른 페이지에서는 파랑이 `26.08.04` 였다. **색으로 회차를 추론하지 말고
주석 원문을 인용하라.**

먼저 어떤 색이 쓰였는지 픽셀 수로 확인하고, `--color` 를 그에 맞춰 지정한다:

```bash
# 어떤 색이 쓰였는지 훑기 — 두 색 모두 검출해 후보 수를 비교
python scripts/detect_red_regions.py <입력> --color=both --no-crops
```

**⚠️ 검출 스크립트로 잡히지 않는 변경 표기 — 육안 판독만이 근거인 것들**

색 검출은 "색이 칠해진 영역"만 찾는다. 다음 네 가지는 스크립트로도, 텍스트 레이어로도
잡히지 않으므로 **반드시 렌더 이미지를 직접 읽어야** 한다. 놓치면 그대로 누락이다.

| 표기 | 실측 예 | 왜 안 잡히나 |
|------|---------|------------|
| **취소선 = 삭제 표기** (판정은 위 [취소선 = 삭제](#취소선--삭제-변경-종류-판정-규칙) 절) | `~~상세 정보~~ (v2삭제_탭 통합 - 26.08.18)`, `~~패킷 드롭 현황 테이블~~ (v2삭제_현행화 - 26.8.03)` — 하위 트리 전체에 취소선 | 취소선은 **선 몇 픽셀**이라 색 영역으로 검출되지 않고, 텍스트 레이어에도 서식 정보가 없다. **삭제 변경분은 거의 전부 이 방식으로만 식별된다** |
| **부분 토큰만 색칠** | `… VIOE-04_04_02 > `**`2항`**`과 동일하게 제공 `**`(v2수정_현행화 - 26.08.03)`** — 나머지는 검정 | 줄 단위로 보면 검정이 대세라 변경분이 아닌 줄로 오판한다. **토큰 단위로 색을 확인**할 것 |
| **한 줄에 두 색 혼용** | `- `**`y축 단위 :`**`(빨강) `**`회 (v2수정_현행화 - 26.08.03)`**`(파랑)` | 색으로 종류·회차를 추정하면 안 되는 직접 증거다. 같은 항목이 두 색으로 갈린다 |
| **목록 번호 색 번짐** | 빨간 항목 뒤 검정 항목의 **번호만** 빨강 (`2.` `3.`) | 번호가 색이라고 그 항목을 변경분으로 세면 **오탐**이다. 라벨·본문 색을 기준으로 판정할 것 |

취소선 때문에 **삭제 유형은 색 검출 후보 목록에 아예 안 나타날 수 있다.** 삭제 검증 누락은
`testcase-generator` 0-H가 필수로 요구하는 항목이므로, 다음 두 경로를 **둘 다** 거친다.

```bash
# 취소선 후보 검출 — 글자를 가로지르는 얇은 수평선을 기하학적으로 찾는다
python scripts/detect_strikethrough.py <이미지|디렉터리> --color-only

# 변경 표기를 반드시 색으로 하는 기획서면 --color-only 로 무채색 글자획·괘선을 걸러낸다
```

**이 스크립트를 쓸 때 반드시 지킬 것 두 가지:**

1. **`--min-len` 을 문서의 글자 폭으로 실측해 정하라.** 한글 가로획(`ㅗ` `ㅍ` `ㅌ` `ㅡ`)은 그 자체가
   짧은 수평선이라, 임계값이 글자 폭보다 작으면 글자획이 통째로 후보가 된다.
   (실측: VIOLA V4.0 150 DPI 렌더에서 DESC 본문 한글 1자 폭 **40~42px** → 기본값 70px 적정)
2. **양성 대조를 먼저 하라.** 취소선이 실재하는 페이지에 돌려 검출되는지 확인한 뒤 나머지에 적용한다.
   대조군 없이 나온 "0건"은 *"취소선이 없다"* 가 아니라 *"임계값이 안 맞는다"* 일 수 있다.
3. **⚠️ 양성 대조를 통과해도 "0건"을 *취소선 없음* 의 근거로 쓰지 마라.** 대조가 증명하는 것은
   **그 길이대의 취소선을 잡는다**는 것뿐이다. 대조 대상이 문장 전체를 긋는 긴 런이면
   **부분 취소선(단어·글자 몇 개)은 임계값 아래로 떨어져 그대로 누락된다.**
   (실측: Boot Factory 멤버관리 150 DPI — p5 1항 **610px** 런으로 대조해 `--min-len=110` 을 세웠으나,
   같은 문서 p3의 `` ~~멤버~~ `` **2글자 ~80px** 취소선은 검출 0건이었다. DESC 전문 육안 재판독으로만 찾았다)
   **부분 취소선은 수정 변경에 동반되므로 삭제만큼 흔하다.** 검출 결과가 0건인 페이지도 육안으로 훑어라.

그리고 **스크립트 결과와 무관하게 DESC 전문을 육안으로 재판독**한다. 출력은 후보일 뿐이며
밑줄·표 괘선·스티커 구분선·아이콘이 섞인다. 최종 근거는 항상 육안 판독이다.

**절차:**

1. **변경 표시 픽셀 검출로 후보 영역 추출** (보조 수단)

   ```bash
   # 빨강만 쓰는 기획서 (기본값)
   python scripts/detect_red_regions.py <pdf_path> --pages=START-END --output-dir=_workspace/red_regions/ch{N}

   # 빨강 + 파랑을 함께 쓰는 기획서
   python scripts/detect_red_regions.py <pdf_path> --pages=START-END --color=both --output-dir=_workspace/red_regions/ch{N}
   ```

   출력: 색별 크롭 이미지(`pNNN_redMM.png` / `pNNN_blueMM.png`) + 영역 좌표·크기 목록.
   메타데이터는 빨강 단독이면 `red_regions.json`, 파랑을 포함하면 `change_regions.json` 이다.

2. **⚠️ 검출 결과는 반드시 육안 판독으로 확정한다** — 스크립트는 원래부터 그 색인 UI 요소도 잡는다:
   - 필수 입력 표시 `*`, 빨간 원형 번호 배지(❶ ❷ ❸, `3-1` 등 주석 마커)
   - 에러·경고 아이콘, 실패 상태 tag/badge
   - 삭제 버튼, 위험 액션 버튼
   - 차트·그래프의 빨강·파랑 계열 색상
   - **페이지 외곽을 감싸는 색 테두리(아트보드 프레임)** — 전 페이지에 동일하게 있으면 변경 표시가 아니다.
     한 페이지에 하나씩 나오는 페이지 전면적 `box` 후보가 이것인지 먼저 확인할 것
   - **파랑 특유의 오탐** — 링크, 기본(primary) 버튼, 선택된 탭·메뉴, 토글 ON, 간지(표지) 페이지의 배경.
     파랑은 평상시 UI에도 흔한 색이라 빨강보다 오탐 비율이 높다

   → 이들은 **변경분이 아니다.** 전체 이미지·크롭 이미지를 직접 읽어 "변경 표기인지" 확정할 것.

3. **경로 교차 확정 — 항목 근거로 확정하고, 박스는 어디를 볼지에만 쓴다.**
   스티커가 열거한 변경 내역, Description의 색 텍스트, 취소선, (있으면) `ChangeLog` 패널 목록으로
   변경분 목록을 확정하고, 색 박스는 **그 항목 근거를 찾을 영역을 좁히는 데** 쓴다.
   - **박스 안에서 항목 근거를 찾아 그것만 확정한다.** 박스가 화면 전면이어도 범위는 항목 근거다
   - **박스만 있고 항목 근거 0건** → 화면 전체를 케이스화하지 말고 `[변경 범위 불명]` 으로 보고·확인 요청
   - 스티커에는 있는데 Description 색 텍스트가 없는 항목 → 변경분으로 포함하고 `[스티커 전용]` 표시
   - Description은 색인데 화면에 색 박스가 없는 항목 → 변경분으로 포함하고 `[DESC 전용]` 표시
   - `ChangeLog` 에만 있는 항목 → 변경분으로 포함하고 `[ChangeLog]` 표시
   - 둘 이상에 근거가 있으면 경로를 병기 (`[DESC + 박스 + 스티커]`)
   - 경로가 충돌하면 `[변경 표기 불일치]`로 양쪽 기록 (판단하지 않음)
   - **색 박스가 있으면 「박스 ↔ 확정 항목 대조표」를 산출한다** (항목 근거 0건인 박스도 행으로 남긴다)
   - **`ChangeLog` 가 있으면 마지막에 「`ChangeLog` ↔ CH-ID 대조표」로 커버리지를 자기 점검한다**

4. **변경분 목록을 별도 섹션으로 산출** — 각 항목에 다음을 기록:
   - 변경 유형: `추가` / `수정` / `삭제` / `위치·순서 변경` / `디자인 변경`.
     **취소선이 있으면 `삭제` 로 확정한다** (위 [취소선 = 삭제](#취소선--삭제-변경-종류-판정-규칙) 절)
   - 근거 경로: 색 박스 / `변경사항` 스티커 / DESC 색 텍스트 / `ChangeLog` 패널 / 취소선 (복수 가능).
     **색 박스 단독은 근거가 되지 못한다** — 박스만 있으면 `[변경 범위 불명]` 이다
   - 변경 일자 (`(v1추가 - 26.05.26)` 등 표기에서 추출). **확인 불가면 `날짜미표기`** — `-` 를 쓰지 않는다 (`4`·`5 Depth` 의 No-data 의미와 충돌한다)
   - 변경 종류 원문. 기획서가 종류를 적지 않았으면 **`종류 원문 미표기`** — 색으로 추정해 채우지 않는다.
     **단 취소선 항목은 예외다** — 종류는 `삭제` 로 확정된 것이므로 `종류 원문 미표기` 가 아니라
     주석 원문이 없다는 사실만 남기고 일자를 `날짜미표기` 로 적는다
   - **삭제 항목이면**: 삭제 범위(항목 전체 / 하위 트리 전체 / 부분 토큰)를 명시하고,
     부분 취소선은 **삭제된 토큰과 남은 토큰을 갈라 적는다**.
     대체 동작은 **기획서에 명시된 경우에만** 별도 항목으로(다른 CH-ID) 기록하고, 없으면 `[확인 불가]`
   - 관련 Description 항목 ID
   - 화면 식별자

5. **비변경분 처리** — 변경분의 **사전조건·검증에 필요한 맥락**은 분석 결과에 함께 기록한다(예: 변경된 필드가 속한 팝업의 호출 경로). 단, 변경분 목록과는 명확히 구분하여 `[맥락 — 비변경분]`으로 표시한다. 케이스 생성 대상은 변경분뿐이다 — **정책 예외 화면은 예외로, 그 화면은 전수가 대상이다.**

6. **변경 표기가 전혀 없는 페이지** — 해당 페이지는 케이스 생성 대상에서 제외하고, 그 사실을 분석 결과에 명시한다 (누락이 아니라 의도적 제외임을 남긴다).
   **단 그 페이지의 화면 ID가 예외 목록에 있으면 제외하지 않는다** — 신규 정책이므로 변경 표기가 없어도 전수 분석하고 `[정책 예외]` 를 붙인다.

**모드 명시 의무:** 변경분 한정 모드로 분석한 경우 `01_prd_analysis_ch{N}.md` 메타정보 최상단에 다음 세 줄을 반드시 기재한다. 전체 분석과 산출물을 구분하지 못하면 후속 리뷰가 "누락"으로 오판한다.

```
분석 방식: 변경분 한정 분석 (기획서 유형=변경)
표시색: {실측값 — 예: 빨강 + 파랑}
분석 정책: 기본=변경 / 예외={화면 ID 목록 또는 없음}
```

### PDF-4. 결과 저장

## 이미지 경로

기획서가 PDF/Figma 없이 **이미지로 전달된 경우의 경로**다. 변환 단계가 없으므로 **바로 분석에 들어간다.**

### IMG-1. 대상 이미지 수집

```bash
ls -1 <이미지 디렉터리>            # 파일명 정렬 순서가 페이지 순서다
```

- 파일명이 페이지 순서를 보장하지 않으면(`1.png, 10.png, 2.png` 등) 사용자에게 순서를 확인한다. 임의로 추정하지 않는다.
- 이미지가 흩어져 있으면 한 디렉터리(`_workspace/prd_images/<name>/`)로 모아 정렬 가능한 이름으로 복사한다. **원본은 수정·삭제하지 않는다.**
- Description 패널 크롭이 별도로 제공되면 `<name>_desc/`에 같은 규칙으로 둔다. 없으면 원본 이미지 하나로 UI와 Description을 모두 판독한다 (`pdf_to_images.py --crop-desc`는 PDF 전용이므로 쓰지 않는다).

### IMG-2. 판독 품질 게이트 (필수)

[공통: 이미지 판독 품질 게이트](#공통-이미지-판독-품질-게이트-분석-착수-전-필수)를 그대로 실행한다. **이미지 입력에서는 생략 불가** — 원본 품질을 통제할 수 없는 입력이기 때문이다.

### IMG-3. 시각 분석

분석 절차·우선순위·화면 식별자 추출 규칙은 [PDF-3](#pdf-3-이미지-시각-분석)과 **완전히 동일**하다. Description 패널이 별도 크롭으로 없더라도 **Description 우선 원칙은 그대로 유지**한다 (같은 이미지 안에서 Description 영역을 먼저 판독한 뒤 UI를 본다).

이미지 입력 특이사항:

| 항목 | 처리 |
|------|------|
| 페이지 번호 | 파일명 기준으로 부여하고 분석 결과에 파일명을 함께 기록한다 (`p003 (page_003.png)`) |
| 챕터(간지) 구분 | 이미지 순서대로 스캔하여 동일하게 감지한다. 이미지가 챕터 단위로 이미 나뉘어 전달됐다면 그 구분을 그대로 사용하고 사용자에게 확인받는다 |
| 확대 판독 | 텍스트가 작아 읽기 어려우면 해당 영역만 크롭해 다시 읽는다 (`_workspace/prd_images/crops/`). 원본을 업스케일해도 정보는 늘지 않으므로 판독 불가는 판독 불가로 기록한다 |

### IMG-4. 변경분 한정 분석 (해당 시)

기획서 유형이 `변경` 인 경우에만(또는 정책 예외로 변경 정책이 적용되는 화면에만) [PDF-3.5](#pdf-35-변경분-한정-분석-모드)를 그대로 적용한다. `detect_red_regions.py`는 이미지 디렉터리·단일 파일도 입력으로 받으므로 이미지 입력에서도 동일하게 사용할 수 있다 (`--dpi`는 적용되지 않고 원본 해상도를 쓴다).

```bash
python scripts/detect_red_regions.py <이미지 디렉터리|파일> --output-dir=_workspace/red_regions/ch{N}

# 빨강 + 파랑을 함께 쓰는 기획서
python scripts/detect_red_regions.py <이미지 디렉터리|파일> --color=both --output-dir=_workspace/red_regions/ch{N}
```

`_workspace/01_prd_analysis_ch{N}.md`에 PDF 경로와 동일 형식으로 저장한다.
메타정보에 입력 유형(`이미지`), 이미지 디렉터리 경로, 파일 수, 페이지↔파일명 매핑, 챕터 제목, 담당 범위를 기재한다.

## Figma API 경로

### 1. 파일 키 추출 및 메타정보 확인

Figma URL에서 파일 키를 추출하고 작은 요청으로 접근 가능 여부를 먼저 확인한다. 큰 파일을 전체 가져오기 전에 `depth=1`로 최상위 페이지 구조만 본다.

```bash
python scripts/figma_api.py file <FIGMA_URL> 1
```

### 2. 분석 범위 결정

`depth=1` 응답에서 페이지(`CANVAS`) 목록을 본다. 큰 파일은 모든 페이지를 깊게 가져오면 응답이 수십 MB가 될 수 있다. 다음 전략 중 선택:

- **소규모 파일** (페이지 ≤ 3, 프레임 ≤ 20): `get_file` 전체 가져오기
- **중대형 파일**: 페이지별로 `depth=3~4` 또는 주요 프레임 ID만 `get_file_nodes`로 추출
- **사용자가 특정 노드만 지정한 경우**: 해당 노드 ID로 `get_file_nodes` 호출

URL 쿼리에 `?node-id=...`가 있으면 사용자가 특정 프레임을 가리킨 것이므로 그 노드 중심으로 분석한다.

### 3. 기능 단위 추출

노드 트리를 그대로 옮기지 않는다. 다음 규칙으로 추상화:

1. **프레임 분류**
   - 화면 단위 프레임: `type=FRAME`이면서 카드보드 크기(보통 width 320~1440)
   - 컴포넌트 정의: `type=COMPONENT` / `COMPONENT_SET`
   - 작업 영역(아트보드 외부, 메모 등): 분석 제외

2. **기능 단위 묶기**
   - 같은 사용자 행동을 다루는 화면들을 묶는다 (예: 로그인 화면 + 비밀번호 입력 + 2FA → "로그인" 기능)
   - 화면 이름의 prefix·suffix로 묶기 (예: "로그인-1", "로그인-2", "로그인-에러")

3. **UI 요소 추출 (화면별)**
   - 입력 필드: `INPUT` 컴포넌트, placeholder 텍스트
   - 버튼: `BUTTON` 컴포넌트, 라벨 텍스트
   - 상태 변형: 같은 컴포넌트의 hover/disabled/error 변형
   - 모달/토스트: 별도 프레임으로 존재하는 피드백 UI

4. **플로우 추론**
   - Figma의 prototype 연결 정보(`flowStartingPoints`, `transitionNodeID` 등)가 있으면 사용
   - 없으면 화면 이름 순서로 추정하고 "추론" 표시

### 4. 비주얼 확인이 필요할 때만 이미지 export

텍스트로 충분한 화면은 이미지를 가져오지 않는다. 다음 경우에만 export:
- 복잡한 레이아웃 검증이 필요한 화면
- 사용자가 명시적으로 시각적 확인을 요청한 경우

```bash
python scripts/figma_api.py images <FILE_KEY> <NODE_IDS> --format=png --scale=1
```

응답의 이미지 URL은 일시적(약 30일)이므로 분석 시점에만 사용한다.

### 5. 결과 저장

`_workspace/01_prd_analysis.md`에 저장. 형식은 `prd-analyst` 에이전트 정의 참조.

## Figma API 응답 핵심 필드

| 필드 | 의미 | 활용 |
|------|------|------|
| `document.children[]` | 페이지 목록 | 페이지 분류 |
| `node.type` | 노드 종류 | FRAME(화면), TEXT(라벨), COMPONENT(컴포넌트) |
| `node.name` | 디자이너가 붙인 이름 | 기능 분류 기준 |
| `node.characters` | TEXT 노드의 실제 문자열 | 라벨, 안내 문구 추출 |
| `node.componentId` | INSTANCE가 가리키는 원본 | 재사용 컴포넌트 식별 |
| `node.absoluteBoundingBox` | 화면상 위치/크기 | 모바일/데스크탑 추정 |

## 한계 및 주의사항

1. **Figma 무료 플랜**: 파일 수 제한은 있지만 API 접근은 무료 플랜에서도 모두 동작.
2. **권한 부족**: 다른 사람 소유 파일은 토큰 소유자에게 view 권한이 명시적으로 부여돼야 한다.
3. **이미지 URL 만료**: export된 이미지 URL은 영구적이지 않으므로 즉시 다운로드해서 사용해야 한다.
4. **대용량 파일**: `get_file`은 전체 트리를 반환하므로 큰 파일은 페이지 단위 노드 가져오기로 쪼개야 한다.

## 번들된 스크립트

원본은 `.claude/skills/prd-analyzer/scripts/`에 있고, 프로젝트 루트 `scripts/`에 심볼릭 링크가 걸려 있다. **이 문서의 모든 명령은 프로젝트 루트에서 `scripts/...` 경로로 실행한다.**

- `scripts/check_image_quality.py` — 이미지 판독 품질 진단(해상도·선명도·대비·훼손) + `OK`/`주의`/`불가` 판정. `불가`가 있으면 종료 코드 `2`
