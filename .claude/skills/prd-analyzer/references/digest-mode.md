# 기획서 분석 모드 (`prd-digest`) — 판독 절 (D-1 ~ D-7)

> 경로의 `{WS}`·`{SHARED}` 는 오케스트레이터가 **실제 경로로 치환해 프롬프트에 적어** 준다. 스스로 치환하지 않는다.

> `prd-analyzer` SKILL의 분리된 참조 문서다. **작업 유형이 기획서 분석(`prd-digest`) 일 때에만 읽는다.**
> 이 절차는 테스트 케이스를 만들지 않으므로, 케이스 생성 쪽 절(`testcase-generator` 0-H 등)은
> 여기서 쓰이지 않는다. 변경 표기를 **읽는 규칙**은 `references/change-mode.md` 를 함께 쓰되,
> 그 파일이 요구하는 **산출물·CH-ID·대조표·페이지 제외**는 이 모드에 적용되지 않는다 (D-7).

### D-1. 이 모드가 만드는 것

화면마다 파일 **두 개**를 낸다. 하나는 사람이 읽고 하나는 스크립트가 읽는다.

| 산출물 | 읽는 쪽 | 내용 |
|--------|---------|------|
| `{WS}/02_screen_s{NN}.md` | 사람 | 그 화면의 기능 요약·판정 근거·판독 메모 |
| `{WS}/02_features_s{NN}.tsv` | 기계 | **7열 탭 구분 · 헤더 행 없음** |

열 순서는 고정이다 — `render_digest.py` 와 `verify_digest.py` 가 **이름이 아니라 위치로** 읽는다.

```
화면ID <TAB> 기능명 <TAB> 설명 <TAB> 분류 <TAB> 근거 <TAB> 페이지 <TAB> 메뉴경로_폴백
```

- **셀에 탭과 개행을 넣지 않는다.** 하나만 들어가도 그 행의 열 수가 어긋나 `verify_digest.py` 가
  `TSV_COLS` **Critical** 로 멈춘다. 설명이 길면 줄을 바꾸지 말고 짧게 쓴다 (D-2)
- 파이프(`|`)는 렌더러가 escape 하므로 치명적이지 않으나, 표로 읽기 어려워지므로 쓰지 않는다
- `페이지` 는 `p043` 형식으로 적는다 — 점검이 `pNNN` 을 세어 **어느 화면에도 귀속되지 않은 페이지**를
  `PAGE_GAP` 으로 보고한다. 형식이 다르면 그 페이지는 안 읽은 것으로 집계된다

**이 모드는 테스트 케이스를 만들지 않는다. 구글 시트를 쓰지 않는다.**
TC ID·`구분`·우선순위·사전조건·예상 결과·`솔루션`·양식 프로파일은 **이 절차에 없는 개념**이다.
그것이 필요해 보이면 요청이 `prd-digest` 가 아니라 `testcase-auto` 로 갔어야 하는 것이므로,
스스로 만들지 말고 오케스트레이터에 보고한다.

사람이 읽을 두 문서(`{WS}/03_기능_전체.md` · `{WS}/04_신규변경.md`)는 **쓰지 않는다.**
`render_digest.py` 가 이 TSV 한 벌에서 두 축으로 배열해 만든다 — 같은 사실을 두 번 배열하는 일을
모델에게 시키면 **두 문서가 어긋난다.** 화면 담당은 TSV 한 벌만 정확히 내면 된다.

### D-2. 설명 깊이 — 기능 단위 요약

화면마다 **기능 3~10개**로 끊고, 각 설명은 **1~2줄**이다.

**Description 전수 전사를 하지 않는다.** 전사하면 산출물 분량이 기획서와 맞먹고 비용이
테스트 케이스 생성과 같아지는데(직전 케이스 실행 136 사이클), 그러면 *읽기 위한 문서* 라는
이 절차의 목적을 잃는다. 전수 전사가 필요한 절차는 `testcase-auto` 쪽이다.

- 기능이 **3개 미만**이면 화면을 덜 읽은 것인지 먼저 의심한다. 그래도 적으면 그대로 내고
  `{WS}/02_screen_s{NN}.md` 에 *화면 자체가 단순하다* 는 사실을 남긴다
- **10개를 넘으면 쪼개지 말고 의미 단위로 묶는다** — 버튼 하나하나는 기능이 아니다.
  같은 목적을 이루는 조작은 한 기능으로 묶고, 갈라지는 것은 *결과가 다른* 지점뿐이다
- 설명은 **무엇을 하는 기능인가** 까지다. 조작 절차·예상 결과·검증 방법을 쓰지 않는다
- 기획서가 적지 않은 동작을 채워 넣지 않는다. 비어 있으면 비어 있는 채로 둔다

### D-3. 분류 5종 — `신규` · `변경` · `삭제` · `확인 필요` · `미변경`

`분류` 열은 이 **다섯 값만** 받는다. 다른 표기(`신설`·`수정`·`미정` 등)는 `verify_digest.py` 가
`CLASS_ENUM` **Critical** 로 잡는다. 값에 공백·괄호·설명을 덧붙이지 않는다.

| 근거 | 분류 | 언제 쓰나 |
|------|------|----------|
| `v1추가` · Menu Structure 신규 메뉴 | `신규` | 이번 회차에 **생긴** 기능 |
| `v1수정` | `변경` | 이번 회차에 **고쳐진** 기능 |
| `v1삭제` · 취소선 · 반투명 오버레이 + `v1삭제` 배지 | `삭제` | 이번 회차에 **없어진** 기능 |
| 종류 원문 없음 · 박스만 있고 항목 근거 0건 | **`확인 필요`** | 변경 표기는 있는데 **종류를 확정하지 못한** 기능 |
| 변경 표기가 **아예 없음** | **`미변경`** | 기획서에 실려 있으나 이번 회차에 **손대지 않은** 기능 |

**권위는 주석 원문이다.** `v1추가`·`v1수정`·`v1삭제` 와 날짜가 적힌 텍스트 자체가 근거이고,
**색은 근거가 아니다.** 같은 문서에서 빨강과 파랑이 회차와 일정하게 대응하지 않았던 실측이 있다
(`change-mode.md` 「표시색은 기획서마다 다르다」 절). 색으로 종류를 추정해 세 분류에 넣지 않는다.

**넷째 버킷을 둔 이유** — 3분류에 억지로 넣으면 **기획서에 없는 종류를 단정**하게 된다.
직전 실행에서 `종류 원문 미표기` 는 드문 일이 아니었다. `확인 필요` 는 판독 실패가 아니라
**정상 산출**이며, 그렇게 쓰라고 만든 값이다. 확신이 없으면 세 분류 중 하나를 고르지 말고 여기에 둔다.

**삭제를 변경에 섞지 않는다.** 섞으면 *사라진 기능* 을 따로 볼 수 없고, 전체 기능 목록에도
사라진 것이 남아 버린다. 그래서 `삭제` 가 독립 분류다.

**`미변경` 은 버리는 값이 아니다 — 이것이 `03_기능_전체.md` 를 완전하게 만든다.**
그 문서는 **기획서에 실린 모든 기능**이고, 모든 행은 다섯 값 중 하나를 달아야 한다.
변경 표기가 없다고 그 기능을 **빼면 안 된다** — 전체 목록이 아니게 되는데,
**한 화면에 행이 하나만 남아도 `SCREEN_MISSING` 은 울리지 않아 손실을 아무도 감지하지 못한다.**
반대로 `확인 필요` 로 몰아서도 안 된다 — 변경 문서의 「확인 필요」 절이 미변경 수백 건으로
뒤덮여 그 문서의 목적이 사라진다(실측 규모: 화면 127개 · 변경 항목 165건, 화면당 기능 3~10개면
**손대지 않은 기능이 수백 건**이다).

`미변경` 행은 **근거가 비어도 된다** (D-5). *바뀌지 않았다* 에 변경 근거를 요구하면 자기모순이다.
렌더러는 이 행을 `03_기능_전체.md` 에 그대로 싣고, `04_신규변경.md` 에서는 **요약 표에만 집계**한다
(전체 중 얼마가 그대로인지는 읽는 사람에게 필요한 맥락이다). **`미변경` 절은 없다.**

**문서 유형에 따라 쓰이는 값이 갈린다:**

| 기획서 유형 | 이렇게 된다 |
|-------------|------------|
| `신규` | **전 기능이 `신규`** 다. `미변경` 은 생기지 않는다 — 비교할 이전 회차가 없다. 렌더 결과의 `변경`·`삭제` 절은 `해당 없음` 이고 그것이 정상이며 누락이 아니다 |
| `변경` | **대다수 기능이 `미변경`** 이고 변경 표기가 붙은 것만 `신규`·`변경`·`삭제`·`확인 필요` 다. 변경분만 뽑고 나머지를 버리지 않는다 — 그것은 `testcase-auto` 의 변경분 한정 모드이고 이 절차가 아니다 (D-7) |

### D-4. 전역 5개 섹션 — `화면ID = 문서 전역`

화면 판독과 **별개로** 문서의 다섯 섹션을 읽는다. 이 다섯은 어느 화면에도 속하지 않는다.

| 섹션 | 여기서 잡는 것 |
|------|--------------|
| **Document History** | 문서 회차·일자 (산출물 머리말의 근거가 된다) |
| **Policy** | 전역 정책의 신설·변경 |
| **Menu Structure** | **신규 메뉴** (실측: K8s p009 에 `v1추가` 표기 **4건** = 신규 메뉴 4개) |
| **기본 모드 공통 정의** | 전 화면에 걸치는 공통 동작 정의 |
| **Wireframe 공통 표출 모달 정의** | 여러 화면이 공유하는 모달 정의 |

여기서 나온 항목은 **같은 TSV 형식**으로 `화면ID` 열에 `문서 전역` 을 적어 낸다.
별도 파일·별도 형식을 만들지 않으므로 집계와 검증이 한 메커니즘으로 끝난다.
렌더러가 이 행을 `04_신규변경.md` 의 「문서 전역」 절로 보내고 `03_기능_전체.md`(기능 목록)에서는
뺀다 — **전역 정책은 화면 기능이 아니다.** 화면 기능 목록에 섞으면 메뉴 트리에 매달 자리가 없다.

**두 축을 모두 읽는다.** 전역만 보면 화면 내부에서 바뀐 항목을 통째로 놓치고, 화면만 보면
**신규 메뉴의 존재가 드러나지 않는다** — Menu Structure 에 `v1추가` 로 표시된 메뉴가 정작 그
화면 페이지에는 아무 표기도 없을 수 있다. 실측에서 그 형태가 신규 메뉴 4개를 모두 만들어 냈다.

### D-5. 근거 태그 — `common.md` 어휘 + 이 모드의 자체 태그

| 태그 | 쓰는 곳 |
|------|--------|
| `[DESC pNNN-N항]` | Description 패널의 항목 |
| `[스티커 pNNN]` | 여백의 `변경사항` 스티커 |
| `[ChangeLog pNNN]` | 페이지 우측 하단 `ChangeLog` 패널 |
| `[취소선 pNNN]` | 취소선 |
| `[Menu Structure pNNN]` | Menu Structure 페이지의 메뉴 항목 |

**위 다섯 중 `[취소선 …]` 과 `[Menu Structure …]` 는 이 모드의 자체 태그다.**
`common.md` 태그표에 있는 것은 `[DESC N항-N]`·`[DESC DN-N]`·`[스티커]`·`[ChangeLog]` 이고,
이 둘은 거기에 없다. 페이지 번호를 붙이는 `pNNN` 형태도 이 모드의 것이다 — 여기서는 CH-ID 가
없어 페이지가 유일한 역추적 좌표이기 때문이다. **`common.md` 태그표로 이 태그들을 채점하지 않는다.**
어느 스크립트도 태그 어휘를 파싱하지 않으므로 기계적으로 깨지는 것은 없으나, 이 저장소는
「사양에 없는 태그」 왕복으로 리뷰 사이클을 두 번 태운 적이 있어 관계를 여기 못 박는다.

**태그 뒤에 종류·일자 원문을 그대로 인용한다** — `[스티커 p043] v1추가 26.06.19`.
근거가 둘 이상이면 병기한다 — `[DESC p043-2항] [스티커 p043] v1수정 26.08.03`.
일자를 알 수 없으면 `날짜미표기`, 종류 원문이 아예 없으면 `종류 원문 미표기` 로 적는다.
**`-` 를 쓰지 않는다** — 다른 산출물에서 `-` 는 No-data 표기라 뜻이 충돌한다.

**`신규`·`변경`·`삭제` 행은 근거가 필수다.** 비어 있으면 `verify_digest.py` 가 `NO_EVIDENCE`
**Critical** 로 잡는다. 근거 없이 종류를 단정한 행은 역추적이 끊겨 뒤에서 되짚을 방법이 없다.

**`확인 필요` 와 `미변경` 행은 근거가 비어도 된다.** 두 분류 모두 *제시할 변경 근거가 없다* 는
것이 그 값의 뜻이므로 근거를 요구하면 자기모순이다 — 점검(`EVIDENCE_REQUIRED`)도 이 두 행에는
근거를 묻지 않는다. 근거 열을 억지로 채우지 말고 **빈 칸으로 둔다.**

다만 `확인 필요` 는 **무엇을 보고 확정하지 못했는지를 `{WS}/02_screen_s{NN}.md` 에 반드시 남긴다.**
남기지 않으면 "확인했는데 못 정했다"와 "안 봤다"를 구분할 수 없다. `미변경` 에는 그 의무가 없다
— 화면 전체에 변경 표기가 없었다는 사실을 화면 MD 에 한 줄로 적으면 족하다.

### D-6. 메뉴 경로·화면명을 적지 않는다

`메뉴경로_폴백` 열은 **메뉴 IA 에 없는 화면에만** 채운다. 그 외에는 **빈 칸**이다.

렌더러가 `{WS}/00_menu_tree.json` 에서 화면 ID 로 **경로와 화면명을 조회한다.** 옮겨 적으면
IA 가 갱신될 때 산출물만 낡아 어긋난다 — 같은 사실을 두 곳에 두지 않는다.

**어느 화면이 IA 에 없는지는 스스로 알아내지 않는다.** 메뉴 트리는 오케스트레이터가 가진
`parse_menu_ia.py` 산출물이고 화면 담당에게는 없다. **오케스트레이터가 프롬프트에 「IA 에 없는
화면」 목록을 적어 준다** — 그 목록에 있는 화면만 폴백을 채우고 나머지는 빈 칸으로 둔다.
목록이 프롬프트에 없으면 추측하지 말고 **오케스트레이터에 요청한다.**

**전 화면에 채우면 그룹핑이 깨진다.** IA 에 있으면서 경로 레벨이 전부 `-` 인 화면(`VIOE-00_00_*`
같은 공통 정의)은 경로가 **빈 문자열**로 조회되는데, 이때 폴백이 차 있으면 렌더러가 그 값을 쓴다.
그러면 그 화면이 「공통 정의 (메뉴 경로 없음)」 절이 아니라 **엉뚱한 경로 절 아래로 떨어진다.**

- **화면명 열은 TSV 에 없다.** 필요하면 렌더러가 IA 또는 `00_screen_index.md` 의 `Page Title` 에서 가져온다
- IA 에 없는 화면은 그 화면의 **Breadcrumb 원문을 그대로** 적는다 (`모니터링 > 외부 알람 설정`).
  만들어 내지 않는다 — Breadcrumb 이 없으면 빈 칸으로 두고 `02_screen_s{NN}.md` 에 그 사실을 남긴다
- **`화면ID` 는 `{WS}/00_screen_index.md` 의 표기와 글자 그대로 같아야 한다.** 점검이 두 집합을
  **정확 비교**하므로 공백·접미사를 다듬으면 그 화면이 통째로 `SCREEN_MISSING` **Critical** 이 된다.
  실측 인덱스에는 `VIOE-02_01_01-10` 과 `VIOE-02_01_01-10 (flow)` 처럼 **공백으로만 갈리는 쌍**이
  있다 — 정규화하면 두 화면이 한 화면으로 뭉개진다. 인덱스 문자열을 **복사해 쓴다**
- **IA 에 없다는 사실을 `신규` 의 근거로 쓰지 않는다.** IA 부재는 신규의 *신호* 이지 근거가 아니다.
  실측 반례가 양쪽에 있다 — `VIOE-03_02_05-*` **19개는 신규인데 IA 에 이미 실려 있고**,
  CI/CD 는 IA(`260731`)가 기획서(`260819` v2)보다 **낡았다.** 신규 판정의 근거는 D-3 의 주석 원문이다
- IA ↔ 기획서 차이는 렌더러가 「IA ↔ 기획서 대조」 절로 **보고만** 한다. 판정이 아니다

### D-7. 변경 표기 판독은 `change-mode.md` 를 읽는다 — 여기에 복제하지 않는다

기획서 유형이 **`변경`** 이면 `references/change-mode.md` 를 **함께 읽는다.**
이 문서는 그 규칙을 복제하지 않고 가리킨다. 다만 **그 파일을 통째로 따르지는 않는다** —
그쪽은 테스트 케이스 생성 절차용이라 이 모드에 없는 산출물과 개념을 요구한다. 아래 두 표가
**무엇을 가져오고 무엇을 버리는지**를 가른다.

거기에 있는 것 — 표기 경로 5종의 **위계**(색 박스는 범위 후보일 뿐 확정력이 없다) ·
**취소선 = 삭제** 판정 규칙 · 검출 스크립트로 잡히지 않는 표기 4종(취소선 · 부분 토큰만 색칠 ·
한 줄에 두 색 혼용 · 목록 번호 색 번짐) · `ChangeLog` 가 완전한 목록이 아니라는 것 ·
**검출 0건이 「없음」을 뜻하지 않는다**는 것 · 표시색 실측 절차.

**복제하지 않는 이유 — 복제본은 반드시 낡는다.** 이 저장소는 2026-09-15 에 같은 이유로
`HARNESS_SUMMARY.md` 를 폐지했다(현재 동작과 갈라져 폐기된 처리 단위를 서술하고 있었다).
위 규칙들은 **실제 누락을 치르고 얻은 것**이라, 사본이 갈라지면 갈라진 쪽을 읽은 실행이
그 값을 다시 치른다 — 2글자 ~80px 취소선이 검출 0건으로 나온 실측이 그 예다.

**가져오는 것 — 판정 결과를 이 모드의 분류 5종으로 옮겨 적는다:**

| `change-mode.md` 의 판정 | 여기서는 |
|--------------------------|----------|
| 박스만 있고 항목 근거 0건 → `[변경 범위 불명]` | 화면을 전수화하지 말고 그 항목을 **`확인 필요`**, 근거는 빈 칸. 무엇을 보고 확정하지 못했는지는 화면 MD 에 남긴다 |
| 취소선 → `삭제` 확정 | 분류 **`삭제`**. 주석 원문이 없어도 취소선만으로 확정하고, 종류는 확정됐으므로 `종류 원문 미표기` 가 아니라 모르는 **일자만 `날짜미표기`** 로 적는다 |
| `[DESC 전용]`·`[스티커 전용]`·`[ChangeLog]`·`[변경 표기 불일치]` 같은 경로 표시 | 근거 열에 D-5 태그와 **함께 적는다**. 분류를 바꾸지 않는다 |

**따르지 않는 것 — `change-mode.md` 가 요구하지만 이 모드에 없는 것:**

| `change-mode.md` 가 요구하는 것 | 여기서 하지 않는 이유 |
|--------------------------------|----------------------|
| 산출물 `01_prd_analysis_s{NN}.md` 와 **3줄 메타 블록**(`분석 방식`/`표시색`/`분석 정책`) | 이 모드의 산출물은 `02_screen_s{NN}.md` + `02_features_s{NN}.tsv` **둘뿐**이다 (D-1). 있지도 않은 파일을 만들지 않는다. 같은 이유로 **`prd-analyzer` SKILL 본문의 산출물 체크리스트도 이 모드에는 적용되지 않는다** — 그 체크리스트는 케이스 생성 경로의 것이다 |
| **CH-ID 부여**와 `[변경 CH-N …]` 태그 | 이 모드에는 CH-ID 열이 없다. 역추적 좌표는 **페이지 번호**다 (D-5) |
| 「박스 ↔ 확정 항목 대조표」·「`ChangeLog` ↔ CH-ID 대조표」 산출 | CH-ID 가 없어 표의 한 축이 성립하지 않는다. 박스를 보고 확정하지 못한 사실은 **`확인 필요` 행 자체**와 화면 MD 의 메모로 남는다 |
| **절차 5항** — 변경분만 케이스 대상, 비변경분은 `[맥락 — 비변경분]` | 이 모드는 **모든 기능을 싣는다.** 변경 표기가 없는 기능은 버리지 않고 **`미변경`** 으로 적는다 (D-3) |
| **절차 6항** — 변경 표기가 없는 페이지는 대상에서 제외 | **페이지를 건너뛰지 않는다.** 표기가 없어도 그 화면의 기능을 요약한다. 건너뛰면 `03_기능_전체.md` 가 전체 목록이 아니게 되고, 점검은 페이지 누락을 `PAGE_GAP`(Major) 으로만 알린다 |
| 「정책 예외 화면」 분기 | `prd-digest` 에는 정책 예외 개념이 없다. 한 실행은 문서 전체를 같은 방식으로 읽는다 |

**요약하면 — `change-mode.md` 에서 가져오는 것은 「무엇이 바뀌었는가」를 읽는 눈이고,
「무엇을 산출하는가」는 전부 이 문서(D-1 ~ D-6)가 정한다.**
