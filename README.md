# OKE-AUTO-TEST-CASE

기획서(PRD)를 분석해 **팀 양식에 맞는 테스트 케이스를 자동 생성하고 구글 시트에 작성·리뷰**하는 Claude Code 하네스.

## 무엇을 하나

```
[기본 정보 7가지를 먼저 묻는다]
기획서(PDF / 이미지 / Figma) ─┐
                              ├─→ 화면 ID 단위 순차 처리 ─→ 구글 시트 작성 ─→ QA 리뷰
양식 사양 (커밋된 파일) ──────┘     (분석 → 케이스 생성 → 리뷰)
```

**요청하면 하네스가 먼저 7가지를 물어봅니다** — ① 제품 유형 ② 기획서 유형(`신규`/`변경`)과 예외 항목
③ 기획서 경로 ④ 대상 시트 URL ⑤ 탭(신규/기존) ⑥ 작업 디렉터리명(`{제품}_{제품버전}_{문서회차}`)
⑦ 이미 변환된 이미지 경로(선택 — 있으면 변환을 건너뜁니다). 프롬프트에 미리 적어 보내면 확인만 하고 넘어갑니다.
**추정하지 않습니다** — 잘못 추정한 항목 하나가 수백 행에 그대로 박히기 때문입니다.

팀 양식은 `.claude/formats/` 에 **공통 골격 1개 + 제품 프로파일 3개로 커밋**되어 있습니다
(`common.md` + `profile-viola` / `profile-trombone` / `profile-bootfactory`).
**양식은 공통 골격과 해당 프로파일 두 개를 함께 읽어야 성립합니다.**
그래서 실행할 때 참고 시트 URL이 필요하지 않고, 대상 시트에서는 **헤더와 마지막 TC ID만** 확인합니다.
프로파일은 ① 제품 유형으로 정해지고, 시트에 데이터가 있으면 솔루션 컬럼과 대조합니다.

기획서 기반 생성(`testcase-auto`)은 에이전트 4명이 협업합니다.

| 에이전트 | 역할 |
|---------|------|
| `prd-analyst` | 기획서 화면·Description 전수 분석 |
| `sheet-analyst` | 양식 사양 로드 + 대상 시트 드리프트 검증 (헤더·마지막 ID·신규 enum) |
| `testcase-writer` | 케이스 생성 + 시트 작성 |
| `testcase-reviewer` | 기획 ↔ 케이스 ↔ 양식 ↔ 시트 교차 검증 |

## 특징

- **기본 정보를 먼저 확정합니다.** 제품 유형·기획서 유형·예외 항목·기획서·시트·탭·작업 디렉터리명 6가지(+ 선택 1)를 분석 착수 전에 묻고, 확정값을 표로 보여줍니다. **답이 없으면 진행하지 않습니다.**
- **팀 양식을 그대로 따릅니다.** 전수 실측(VIOLA 331행 / TROMBONE 3,953행)으로 만든 양식 사양(컬럼 순서·enum·문체·표기 컨벤션)을 기준으로 생성하므로, 기존 케이스와 섞여도 이질감이 없습니다.
- **양식 사양은 커밋되어 재사용됩니다.** 매 실행 참고 시트를 다시 분석하지 않아 실행 간 판정이 흔들리지 않고, 빈 새 시트에도 헤더를 만들어 쓸 수 있습니다. 대상 시트 헤더가 사양과 다르면 **작성을 멈추고 알립니다.**
- **제품별 프로파일을 지원합니다.** 컬럼은 **전 제품 23컬럼(A~W)으로 통일**되어 있고, 제품마다 실측으로 갈리는 것만 프로파일에 있습니다 — 문체(백틱 vs 대괄호)·ID 체계(전역 vs 모듈별 연속)·지배 구분(`표시` 56% vs `정상` 65%)·우선순위 결합 규칙. 리뷰도 선택된 프로파일 기준으로 판정합니다.
- **관리 영역은 컬럼이 아니라 제품 유형으로 받습니다.** VIOLA의 `K8s` / `CI·CD` 구분은 **탭 분리 + `1 Depth`**(Breadcrumb 최상위 원문)로 표현됩니다. 2026-08-25에 도입했던 `관리대상` 전용 컬럼(VIOLA 24컬럼)은 **2026-09-02에 폐지**됐고, 그 결과 오히려 팀 원본 시트(23컬럼)와 일치하게 됐습니다.
- **⚠️ `profile-bootfactory` 는 실측이 아니라 VIOLA 파생입니다.** 화면 ID 패턴(`BOOT-NN_NN_NN`)만 실측이고, `솔루션` 값 `BOOTFACTORY` 와 TC ID 코드 `BF` 는 **제안값**입니다. 팀 BootFactory 원본 시트가 나오면 전수 스캔으로 교체하는 것이 정공법입니다.
- **atomic 단위 생성.** 한 케이스 = 한 검증. 실패 원인 추적과 팀 공동 작성에 맞춘 단위입니다.
- **Description 100% 커버리지.** 기획서 Description 항목은 전부 케이스화하고, 근거를 비고 컬럼에 태그로 남깁니다.
- **변경분 한정 모드.** 기획서 유형을 `변경` 으로 지정하면 개정판 기획서의 변경 표기(색 박스 / `변경사항` 스티커 / Description 색 텍스트 / `ChangeLog` 패널 / 취소선)가 있는 항목만 케이스화합니다. **문서 안의 일부 신규건은 예외 항목으로 지정**해 그 화면만 전수로 돌릴 수 있습니다.
- **판독 품질 게이트.** 해상도 부족·훼손 이미지를 조용히 넘기지 않고 보고하며, 판독 불가 페이지는 추측하지 않고 그 사실을 케이스로 남깁니다.
- **추측 금지.** 기획서에 없는 내용은 단정하지 않고 "기획 확인 필요"로 분리 보고합니다.

## 시작하기

**[SETUP.md](SETUP.md) 를 따라 세팅한 뒤 `python3 verify_setup.py` 로 검증하세요.** (약 15분)

```bash
git clone https://github.com/sihan-qa/OKE-AUTO-TEST-CASE.git
cd OKE-AUTO-TEST-CASE
python3 -m pip install -r requirements.txt
# 서비스 계정 키를 .credentials/google-service-account.json 에 배치 (SETUP.md 3단계)
python3 verify_setup.py
```

세팅이 끝나면 이 폴더에서 Claude Code를 실행하고 "테스트 케이스 만들어줘"라고 요청하면 됩니다.
**나머지는 하네스가 7가지 질문으로 채웁니다** — 기획서·시트 URL을 미리 적어 보내도 되고, 안 적어도 됩니다.
요청 문구는 [docs/PROMPTS.md](docs/PROMPTS.md) 를 참고하세요 — 7가지 질문의 의미와 품질이 갈리는 지점이 정리되어 있습니다.

### 테스트케이스 추가 작업 (예외 사항 / 권한)

이미 작성된 테스트 케이스를 원천으로 **기획서에 없는 검증**을 파생 생성한다. 기획서를 읽지 않는다.
기획서 기반 생성(`testcase-auto`)과 나란한 두 번째 절차이며 스킬 이름은 `testcase-augment` 다.

프롬프트에 `테스트케이스 추가 작업 진행해줘.` 를 입력하면 아래를 순서대로 묻는다.

| 순서 | 묻는 것 |
|------|--------|
| 1 | 추가 작업 유형 — `예외 사항` / `권한` **중 하나** (둘 다 필요하면 두 번 실행) |
| 2 | 원본 TC 시트 URL + **원본 탭** (탭 목록을 보여주고 고르게 한다) |
| 3 | (`예외 사항` 일 때) **범위** — 원천으로 삼을 `화면 ID` 목록. 전부면 `전수` |
| 4 | (`권한` 일 때) 권한 자료 경로 — 시트 URL / CSV·마크다운 / 이미지·PDF |
| 5 | 작성 대상 시트 URL + 탭 (없으면 생성) |

**범위는 `예외 사항` 전용**입니다 — `권한` 은 매트릭스의 역할 × 기능 전수가 범위를 정합니다.
화면 ID를 모르면 `전수` 로 두시면 되고, 규모 확인 게이트에서 **실제 목록을 보여드린 뒤**
거기서 줄일 수 있습니다. 원본에 없는 화면 ID를 주면 오타로 보고 **멈춥니다**(조용히 0건을
내지 않습니다).

**묻지 않는 것:** 제품 유형(원본 TC의 `솔루션` 컬럼 실측으로 판정), 기획서 경로·유형.

**구글 시트 전용이다.** 엑셀(.xlsx) 경로가 들어오면 미지원을 안내하고 중단한다 —
구글 시트로 옮기거나 CSV로 내보내면 된다.

진행 중 사용자 확인 게이트가 3곳 있다 — **권한 자료 판독 확인** / **규모 확인**(역할 × 기능
전수는 수백 행이 될 수 있다) / **첫 배치 검토**(문체·태그 오류가 전 행에 번지기 전에 잡는다).

### 기획서 분석 (기능 목록 · 신규·변경 판정)

테스트 케이스를 만들기 전에 **기획서에 무엇이 들어 있는지** 먼저 보고 싶을 때 쓴다.
기획서를 화면 단위로 읽어 **사람이 읽는 문서 2개**를 낸다. 스킬 이름은 `prd-digest` 이며
**테스트 케이스를 만들지 않고 구글 시트를 쓰지 않는다.**

| 산출물 | 무엇인가 |
|--------|---------|
| `03_기능_전체.md` | 기획서에 실린 **모든 기능**을 메뉴 구조 순서로 정리한 목록 |
| `04_신규변경.md` | 이번 회차에 **생긴·바뀐·없어진** 기능만 모은 문서 |

프롬프트에 `기획서 분석해줘.` 또는 `이번 회차에 뭐가 바뀌었는지 정리해줘.` 를 입력하면 시작한다.
(`테스트 케이스`·`TC` 같은 말이 함께 있으면 케이스 생성으로 갑니다 — 둘 다 필요하면 따로 요청하세요.)

묻는 것은 7가지다 — 제품 유형 / 기획서 경로 / **메뉴 IA 엑셀 경로**(선택) / 기획서 유형
(`신규`·`변경`) / 취소선이 삭제 표기인지(`변경` 일 때) / 이미 아는 신규 화면 목록(선택) /
이미 변환된 이미지 경로(선택).

- **메뉴 구조는 엑셀에서 스크립트가 읽습니다.** 모델이 트리 그림을 판독하지 않습니다 —
  개정판의 메뉴 구조 페이지는 바뀐 가지 위주로만 그려져 전체 트리가 나오지 않기 때문입니다.
  엑셀이 없으면 기획서에서 폴백으로 뽑고, 그 사실을 산출물 머리말에 남깁니다.
- **IA는 뼈대이지 판정 근거가 아닙니다.** IA에 없는 화면이 곧 신규는 아닙니다(실측 반례가
  양쪽에 있습니다). 신규·변경·삭제의 근거는 기획서의 주석 원문입니다.
- **두 문서는 한 벌의 TSV에서 렌더됩니다.** 그래서 서로 어긋날 수 없고, 기획서를 다시 읽지
  않고 다시 렌더할 수 있습니다. 대신 **두 MD를 손으로 고치면 안 됩니다** — 다음 렌더에서 사라집니다.
- **`TROMBONE` 은 미지원입니다.** 기획서·IA 구조를 실측한 적이 없어, 고르면 사유를 안내하고 멈춥니다.

사용자 확인 게이트는 3곳이다 — **기본 정보 확정** / **화면 인덱스 확정**(화면 수·배치 수·
IA 차이를 보여준다) / **첫 배치 검토**(기능 단위의 굵기와 분류 오류를 전 화면에 번지기 전에 잡는다).


작업 디렉터리는 **제품·제품버전·문서회차마다 따로** 만들어지고, `shared/` 의 이미지는 같은 판본이면
재사용됩니다(재실행으로 되돌려도 `shared/` 는 제자리에 남습니다). 경로 규칙의 단일 출처는
`.claude/skills/testcase-auto/SKILL.md` 의 **0-0** 절입니다.

**오케스트레이터 셋은 원천과 산출물이 다릅니다** — `testcase-auto` 는 기획서를 읽어 시트에 쓰고,
`prd-digest` 는 기획서를 읽되 시트를 쓰지 않으며(산출물은 MD 2개), `testcase-augment` 는 기획서를
읽지 않습니다(이미 작성된 케이스가 원천). 한 스킬에 모드를 얹지 않고 나눈 이유는 Phase 0 질문부터
품질 규칙까지 공유하는 것이 거의 없어, 합치면 세 경로가 함께 무거워지기 때문입니다.
기획서 이미지는 `shared/` 에서 공유하므로 `prd-digest` 를 먼저 돌렸으면 `testcase-auto` 가
변환을 건너뜁니다.
