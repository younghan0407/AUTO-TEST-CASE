# 테스트케이스 추가 작업 — 예외 사항 / 권한 파생 절차

- 날짜: 2026-09-10
- 상태: 설계 확정 (구현 계획 대기)
- 범위: 신설 스킬 1개 · 신설 에이전트 1개 · 신설 스크립트 1개 · 신설 참조 3개 · 양식 사양 1개 · 사용자 문서 4개 · `CLAUDE.md`

## 1. 배경

현행 하네스의 원천은 **기획서 하나**다. `testcase-auto` 는 기획서를 화면 ID 단위로 잘라 케이스를 만들고 시트에 쓴다. 그래서 **기획서에 적히지 않은 검증**은 구조적으로 나오지 않는다.

QA 실무에서 빠지는 것이 두 종류다.

1. **예외 흐름** — 기획서는 정상 흐름을 서술한다. 필수값 미입력, 형식 위반, 중복, 서버 오류, 동시성 충돌, 중단·이탈은 기획서에 항목으로 존재하지 않는 경우가 대부분이다. 하네스는 기획서에 없는 것을 단정하지 않는 규칙을 지키므로 이 영역이 통째로 비어 있다.
2. **권한별 동작** — 역할마다 같은 기능이 다르게 동작하는데, 그 매핑은 기획서가 아니라 **별도 권한 자료**에 있다. 하네스는 그 자료를 읽는 경로가 없다.

두 영역은 기획서 분석으로는 닿지 않고, **이미 작성된 테스트 케이스**를 원천으로 삼으면 닿는다. 기존 케이스에는 이 절차가 필요한 값이 전부 들어 있다 — 기능 단위(`화면 ID`·`1~3 Depth`), 절차, 제품 유형(`솔루션`), 커버리지 현황(`구분`).

## 2. 변경 요지

**기존 테스트 케이스를 원천으로 파생 케이스를 만드는 절차를 신설한다.** 기획서를 읽지 않는다.

| | `testcase-auto` (기존) | `testcase-augment` (신설) |
|---|---|---|
| 원천 | 기획서 (Figma / PDF / 이미지) | **구글 시트의 기존 테스트 케이스** |
| 트리거 | "테스트 케이스 자동 생성" | **`"테스트케이스 추가 작업 진행해줘."`** |
| 제품 유형 | Phase 0에서 **사용자에게 묻는다** | **`솔루션` 컬럼 실측으로 판정** (묻지 않는다) |
| 처리 단위 | 화면 ID 1개 (기획서 페이지 기준) | 화면 ID 1개 (원본 케이스 그룹 기준) |
| 산출 | 기획 근거 케이스 | **예외 사항** 케이스 / **권한** 케이스 |
| 근거 태그 | `[DESC N항]` · `[UI]` · `[스티커]` | **`[예외 파생 …]`** · **`[권한 매트릭스 …]`** |

두 절차는 **같은 양식 사양·같은 검증 스크립트·같은 리뷰어**를 공유한다. 갈리는 것은 원천과 도출 규칙뿐이다.

## 3. 확정된 설계 결정

### 결정 1 — `testcase-auto` 에 모드를 얹지 않고 별도 오케스트레이터로 분리한다

`testcase-auto` SKILL은 이미 55KB다. Phase 0의 질문 5개(제품 유형·기획서 유형·예외 항목·기획서 경로·시트)가 이 절차에서는 **하나도 그대로 쓰이지 않는다** — 제품 유형은 실측으로 판정하고 기획서 유형·예외 항목은 개념 자체가 없다. Phase 1의 이미지 변환·판독 품질 게이트·변경 표시 검출도 전부 무관하다.

한 파일에 넣으면 거의 모든 절에 `if 작업 유형` 분기가 붙어 **두 경로가 함께 무거워진다.** 실제로 2026-09-08에 `prd-analyzer` 를 조건별 `references/` 로 쪼갠 이유가 이것이다 — 한 실행이 쓰지 않는 경로를 싣고 있었다.

**기각한 대안.**
- *`testcase-auto` Phase 0에 작업 유형 분기 추가* — 위 이유.
- *`testcase-generator` 스킬만 확장* — 스킬은 케이스 도출 규칙만 담고 오케스트레이션(게이트·배치·시트 append·상태 관리)을 하지 않는다. 오케스트레이터가 없으면 사용자 게이트를 걸 자리가 없다.

### 결정 2 — 원본 TC 읽기는 **스크립트**가 한다. 에이전트에게 시트를 읽히지 않는다

원본 탭은 수백~수천 행이다. 이를 에이전트가 읽으면 그 텍스트가 컨텍스트에 쌓이고, 오케스트레이터가 요약을 받아 들고 있으면 이후 모든 턴에서 다시 읽힌다. 2026-09-08 실측에서 오케스트레이터가 **평균 40만 토큰**까지 자라 전체 비용의 25.5%를 혼자 쓴 것과 같은 구조다.

인벤토리 집계에는 **판단할 값이 없다** — 컬럼 값을 세고 그룹핑하는 것이 전부다. `verify_sheet_rows.py` 를 도입할 때와 같은 논리로 스크립트가 맡는다.

`read_tc_inventory.py` 가 원본 탭을 읽어 집계 산출물만 남기고, 에이전트는 **자기 배치 분량의 인벤토리 발췌**만 받는다.

### 결정 3 — 파생 케이스는 **분포 편차 점검의 대상이 아니다** (핵심 오판 방지)

예외 추가 작업은 정의상 `비정상`·`엣지` 만 대량 만들고, 권한 추가 작업은 `정상`·`부수` 만 만든다. 프로파일의 실측 분포(VIOLA `표시` 55.9% / TROMBONE `정상` 65.1%)와 대조하면 **어느 프로파일에서도 지배 구분 역전이 반드시 뜬다.**

2026-08-24에 분포 편차의 지배 구분 역전을 **Critical**로 규정한 것은 기획서 전수 케이스화를 전제한 판정이다. 그 판정을 이 절차에 그대로 적용하면 *"그 작업이 만들라고 한 것을 만들지 말라"* 는 지적이 된다.

**따라서 이 절차의 리뷰에서 분포 편차 점검을 제외한다.** 대신 그 자리에 **카탈로그 커버리지**(예외) 와 **매트릭스 셀 커버리지**(권한) 를 넣는다 — 이쪽이 이 절차에서 의미 있는 완전성 지표다.

### 결정 3-1 — 범위(`화면 ID` 목록)는 Phase 0 **필수 입력**이고, 필터는 **스크립트**가 한다 (2026-09-11 추가)

⚠️ **이 항목은 최초 스펙에서 누락됐다.** 브레인스토밍에서 합의했는데 스펙에 적히지 않아, 계획과 구현이 스펙을 충실히 따르면서 끝까지 빠진 상태로 내려갔다. 구현 후 사용자가 발견했다. **교훈: 스펙 대조는 「스펙에 있는 것이 구현됐는가」만이 아니라 「합의한 것이 스펙에 있는가」도 봐야 한다.**

범위 없이 진행하면 1-C 게이트에서 **전체를 늘어놓고 빼는 사후 축소**뿐이다. 대상이 처음부터 정해진 경우(*"이번엔 파드 생성 화면만"*)를 표현할 수단이 없고, 기능 단위가 수십~수백 개면 게이트 표 자체가 읽을 수 없게 커진다.

- **축은 `화면 ID`** — `testcase-auto` 의 처리 단위(2026-09-02)와 정책 예외가 이미 화면 ID 단위여서 하네스 전반의 생각과 일치한다
- **필수로 묻되 `전수` 를 허용한다.** 값 없이 전수로 가정하면 사용자가 화면 3개를 생각했는데 수십 개가 케이스화된다
- 사용자가 화면 ID 를 모르면 `전수` 로 1-A를 돌리고 **1-C 게이트에서 실제 목록을 보여준 뒤 줄이게 한다** (인벤토리를 돌려야 목록이 나온다)

**필터를 에이전트가 아니라 스크립트(`--screen-id`)가 하는 이유** — **범위 밖 행의 `기능테스트 ID` 도 번호 실측에는 세야 한다.** 범위는 *무엇을 뒤집을지*를 정하고, TC ID는 탭 전역에서 유일해야 한다. 빼면 다음 번호가 이미 쓰인 값과 겹친다. 실측 확인: 범위를 화면 1개로 좁혀 원본 1행만 남았는데도 다음 번호가 `TC_VIO_010` 이었다(범위 밖 `TC_VIO_009` 를 셌다). 뺐다면 `TC_VIO_004` 를 발급해 충돌했다.

**오타는 Critical (`SCOPE_NO_MATCH`).** 원본에 없는 화면 ID를 주면 조용히 0건이 나오는데, 그건 *"그 화면엔 만들 게 없다"* 와 구별되지 않는다. 종료 코드 `2` 로 멈춘다.

### 결정 4 — 제품 유형은 `솔루션` 컬럼 실측으로 판정하고 사용자에게 묻지 않는다

Phase 0 「추정 금지」 원칙(2026-09-02)과 충돌하지 않는다. **추정이 아니라 실측**이다 — 원본 탭 전 행의 `솔루션` 값을 세어 최다값으로 프로파일을 정한다.

| 실측값 | 프로파일 |
|--------|---------|
| `VIOLA` | `profile-viola` |
| `TROMBONE` | `profile-trombone` |
| `BOOTFACTORY` | `profile-bootfactory` |

- **한 탭에 두 솔루션값이 섞여 있으면 최다값을 쓰고 사용자에게 보고한다** (프로파일은 제품 단위다 — `testcase-auto` 의 기존 에러 처리와 같은 규칙)
- **프로파일에 없는 솔루션값이면 진행하지 않는다.** 참고 시트로 프로파일 신설(모드 B)을 제안한다
- `VIOLA K8s` / `VIOLA CI/CD` 구분은 **묻지 않는다.** 두 영역이 같은 프로파일을 쓰고, 이 절차는 `1 Depth` 를 원본에서 승계하므로 영역 정보가 필요한 자리가 없다

### 결정 5 — 파생 태그가 붙은 행은 **원본에서 제외**한다 (재실행 안전장치)

원본 탭과 작성 대상 탭이 **같을 수 있다**(사용자 명세가 두 경로를 따로 받으므로 같게 줄 수도 있다). 이때 절차를 두 번 돌리면 1차 파생분이 2차에서 원본으로 읽혀 **파생의 파생**이 생긴다 — `[예외 파생 …]` 케이스에서 또 예외를 뽑는다.

`read_tc_inventory.py` 는 `비고` 에 파생 태그(`[예외 파생 `·`[권한 매트릭스 `)가 있는 행을 **원본 목록에서 제외하고 커버리지 맵에만 넣는다.** 즉 이미 만든 파생분은 "다시 만들지 않을 것"으로만 쓰인다.

### 결정 6 — TC ID 다음 번호는 **관련 스프레드시트의 전 탭 최대값** 기준

VIOLA 프로파일은 **탭 경계를 무시하고 제품 전역 연속**(결번·중복 0건)이다. 대상 탭의 마지막 값만 보면 다른 탭에 더 큰 값이 있을 때 중복이 발생한다.

`read_tc_inventory.py` 는 `metadata` 로 탭 목록을 얻어 **원본·대상 두 스프레드시트의 전 탭에서 `기능테스트 ID` 컬럼만** 읽어 최대값을 실측한다. 컬럼 하나만 읽으므로 비용이 작다.

- TC ID 연속 범위 규칙은 **프로파일에서 읽는다** (TROMBONE은 모듈별 연속이다 — 전역 최대값을 그대로 쓰면 틀린다)
- `No` 는 `common.md` 대로 **탭별 1부터 재시작**이므로 대상 탭만 본다

### 결정 7 — 권한 자료의 「기능」을 원본 TC 기능 단위에 매핑하고, 그 대응표를 사용자에게 확인받는다

권한 자료의 기능명(`파드 삭제`)과 원본 TC의 기능 단위(`2 Depth` = `파드 목록`, `3 Depth` = `목록`)는 **문자열이 일치하지 않는다.** 매핑을 임의 추정하면 셀 하나가 엉뚱한 화면에 붙어 케이스 한 건이 통째로 틀린다.

Phase 1-B 게이트에서 **판독한 매트릭스 + 기능 대응표를 함께** 되보여 준다.

| 상황 | 처리 |
|------|------|
| 자료의 기능 ↔ 원본 TC 기능 단위가 1:1로 잡힘 | 그대로 진행 |
| 자료에만 있고 원본 TC에 대응이 없음 | **케이스를 만들지 않고 보고**한다. 사용자가 화면 ID를 직접 지정하면 포함 |
| 원본 TC에만 있고 자료에 없음 | 권한 미정의로 보고 (그 기능은 권한 케이스 대상이 아니다) |
| 후보가 여럿이라 확정 불가 | 후보를 나열해 사용자에게 확인. **임의 선택 금지** |

**화면 ID를 유추로 만들지 않는다** — `common.md` 「화면 ID 공통 원칙」이 금지한다.

### 결정 8 — 사용자 게이트 3곳을 유지한다

| 게이트 | 없으면 무슨 일이 벌어지나 |
|--------|----------------------|
| **권한 판독 확인** (Phase 1-B, 권한 모드만) | 매트릭스 셀 하나의 오독이 그대로 틀린 케이스 한 건이 된다. 이미지·PDF 판독을 허용하기로 했으므로 필수다 |
| **규모 확인** (Phase 1-C) | 역할 × 기능 전수는 수백 행이 될 수 있다. 사용자가 규모를 모른 채 시트에 박히면 되돌리는 비용이 크다 |
| **첫 배치 검토** (Phase 2) | 문체·태그·enum 오류가 전 행에 번진다. 2026-09-02·09-08에 두 번 확인된 규칙이라 승계한다 |

## 4. 새 파이프라인

### Phase 0 — 기본 정보 수집

**0-1. 환경 검증** — `GOOGLE_APPLICATION_CREDENTIALS` 가 유효한 경로를 가리키는가. 누락 시 안내 후 중단. (Figma 토큰은 이 절차에서 쓰지 않으므로 검사하지 않는다)

**0-2. 추가 작업 유형** — `AskUserQuestion`, **복수 선택 허용**

| 값 | 산출 |
|----|------|
| `예외 사항` | 정상 흐름을 벗어나는 케이스 |
| `권한` | 권한 매핑대로 기능이 동작하는지 확인하는 케이스 |

**하나만 고른다** (2026-09-11 정정 — 최초 스펙은 복수 선택이었다). 한 실행에 한 유형이며, 둘 다 필요하면 도구를 두 번 실행한다. 도출 규칙·근거 태그·`구분` 값·완전성 지표가 전부 달라 한 실행에 섞으면 산출물과 리뷰가 두 기준을 오간다. 사용자가 둘 다 요청하면 **어느 쪽을 먼저 할지 물어 하나로 확정한다.**

**0-3. 유형별 입력**

공통 (두 유형 모두):

| 항목 | 내용 |
|------|------|
| **원본 TC 시트 URL** | 읽을 테스트 케이스가 있는 구글 시트 |
| **원본 탭** | `metadata` 로 탭 목록을 보여주고 고르게 한다. **복수 선택 허용** — 탭마다 인벤토리를 만들고 기능 단위에 출처 탭을 남긴다(탭이 다르면 같은 화면 ID여도 별개 단위로 두지 않고 병합하되, 커버리지 맵은 두 탭을 합산한다) |

`예외 사항` 을 골랐을 때 추가:

| 항목 | 내용 |
|------|------|
| **범위** | 파생의 원천으로 삼을 **`화면 ID` 목록**(`Screen ID` / `Page ID` 원문). 전부 대상이면 `전수` 로 받는다. **빈칸으로 넘기지 않고 반드시 묻는다** |

| 항목 | 내용 |
|------|------|

**범위는 `예외 사항` 전용이다.** `권한` 은 매트릭스의 역할 × 기능 전수가 범위를 정하므로 따로 묻지 않는다 — 물으면 자료와 사용자 진술이 어긋날 때 어느 쪽이 권위인지 알 수 없다.

**엑셀(.xlsx) 경로가 들어오면 미지원을 안내하고 중단한다.** 구글 시트로 옮기거나 CSV로 내보내 달라고 요청한다. (현행 하네스의 시트 I/O는 `sheets_api.py` 하나이며, 엑셀을 넣으면 읽기·쓰기·`verify_sheet_rows.py --diff` 까지 대응 계층이 필요하다 — 이번 범위에서 제외했다)

조회 전용 화면에 「필수값 누락」을 만들면 검증 목표가 없는 행이 된다.

| 원본 기능 단위의 성격 (`3 Depth` · 절차 동사) | 적용 유형 |
|---|---|
| 입력 폼 (`생성` · `수정`) | 1, 2, 3, 4, 5, 10, 12 |
| 목록 조회 (`목록`) | 6, 8, 9, 11, 12 |
| 상세 · 팝업 (`상세`) | 6, 7, 8, 9, 12 |
| 삭제·실행 액션 | 6, 7, 8, 9, 10, 12 |
| **전 성격 공통** | **8, 9, 12** |

- **판정은 원본 케이스의 절차·`3 Depth` 를 근거로 한다.** 화면 성격을 유추하지 않는다
- 적용 유형인데 만들지 않았으면 **사유를 `12_cases_{EX|PM}-B{NN}.md` 에 적는다** (리뷰 Minor 통과 조건)
- 카탈로그에 없는 예외를 발견하면 만들고 **카탈로그 추가를 보고한다**. 카탈로그는 상한이 아니라 하한이다

## 6. 권한 케이스 사양

`.claude/skills/testcase-generator/references/permission-mode.md` 에 둔다.

### 셀 → 검증 지점 전개

케이스 1건 = **검증 지점 1개**. 매트릭스 셀 하나가 여러 지점을 가질 수 있다.

| 셀의 권한값 성격 | 검증 지점 |
|---|---|
| 전체 허용 | 1건 — 기능 정상 수행 |
| 전체 차단 | 1건 — 진입·실행 차단 (메뉴 미노출 / 버튼 비활성 / 접근 거부) |
| **부분 허용** (조회 전용 등) | **2건** — 허용 동작 수행 + 차단 동작 차단 |

규모 게이트(1-C)의 총 행 수는 **셀 수가 아니라 검증 지점 수**로 계산한다.

### 양식 매핑

| 컬럼 | 값 |
|------|-----|
| `구분` | 허용 → `정상` / 차단 → `부수` |
| `우선순위` | **프로파일의 구분 × 우선순위 결합 규칙을 따른다.** 하드코딩하지 않는다 |
| `사전조건` | `{역할} 권한 계정으로 로그인된 상태` (1줄) |
| `화면 ID` · `1~3 Depth` · `2 Depth` | **원본 TC에서 승계** |
| `비고` | `[권한 매트릭스 {역할}×{기능}] {권한값}` |
| `피드백` | 매트릭스와 원본 TC가 상충할 때만 — 양쪽을 `/` 로 대비 인용 |

> **결합 규칙을 스킬에 박지 않는 이유.** VIOLA는 `정상` 에 `P1`·`P2` 만 주고 `P3`·`P4` 사례가 0건인데 TROMBONE `정상` 은 `P1`~`P4` 를 전부 쓴다. `부수` → `P4` 는 두 프로파일 모두 예외 0건이지만, **한쪽 값을 기억으로 옮겨 적으면 2026-08-24 분포 하드코딩 사고(`정상` −44.9%p)를 형태만 바꿔 재현한다.**

### 매트릭스 ↔ 원본 TC 상충 처리

권한 자료는 `불가` 인데 원본 TC에 그 역할의 정상 동작 케이스가 있으면 **판단하지 않고 양쪽을 기록**한다. `피드백` 에 `[기획 확인] 권한 자료: 불가 / 원본 TC_VIO_031: 정상 수행 — 확정값 확인 필요`.

## 7. 케이스 ↔ 양식 매핑 (예외 사항)

| 컬럼 | 값 |
|------|-----|
| `구분` | `비정상` 주력 / 경계값(3·5·11) → `엣지` / 취소·비활성(12) → `부수` |
| `우선순위` | **프로파일 결합 규칙** (VIOLA: `비정상` → `P2` 기본, `엣지` → `P3`, `부수` → `P4` 항상) |
| `화면 ID` · `1~3 Depth` · `2 Depth` | **원본 TC에서 승계.** 유추 금지 |
| `사전조건` | 예외 진입 조건 1줄 (프로파일이 100% 채움을 요구하면 반드시 채운다) |
| `절차` | `N. ` 접두 100%, 1단계 원칙 |
| `예상 결과` | **명사형 종결.** 동작 수준까지만 — 오류 문구를 단정하지 않는다 |
| `비고` | `[예외 파생 {원본 기능테스트 ID}] {예외 유형명}` |
| `피드백` | `[기획 확인] {무엇이 미정의인가} — 확정값 확인 필요` |

### 예상 결과를 어디까지 쓰는가

```
좋은 예: `필수 입력값 누락` 오류 메시지 표출 및 저장 차단
        → 동작(차단)은 단정, 문구는 원문 인용 없이 성격만

나쁜 예: "이름을 입력해 주세요" 토스트 메시지 표출
        → 기획서에 없는 문구를 단정 → 실행자가 잘못된 FAIL을 낸다
```

**문구·코드·지연 시간 같은 확정값은 단정하지 않고 `[기획 확인]` 으로 넘긴다.** `common.md` 의 자기모순 금지 규칙이 그대로 적용된다 — 예상 결과를 단정해 놓고 `[확인 불가]` 를 적으면 실행자가 PASS/FAIL을 내려 버린다.

### 중복 판정 기준

**"같은 검증 목표"가 이미 원본에 있으면 만들지 않는다.** 문자열 일치가 아니라 검증 목표 일치다.

| 상황 | 판정 |
|------|------|
| 원본에 `필수값 미입력 시 저장 차단` 이 있고 같은 것을 만듦 | **중복 — 만들지 않는다** |
| 원본에 `이름 필수값 미입력` 이 있고 `설명 필수값 미입력` 을 만듦 | 필드가 다르면 별개 검증 목표 — 만든다 |
| 원본의 `구분` 이 `비정상` 이지만 내용은 다른 예외 | 만든다 |

중복 후보는 `12_cases_{EX|PM}-B{NN}.md` 의 「중복 제외」 절에 **원본 TC ID와 함께** 적는다.

| 태그 | 용도 |

**왜 사양에 등재하는가.** 스킬이 요구하는 태그가 사양 태그표에 없으면 리뷰가 매번 "사양 미등재 어휘"로 지적하고 시트 분석은 "사양 미등재 태그 병존"으로 올리는 **무한 왕복**이 생긴다. 2026-08-25(`[DESC 전용]` 등 3종)과 2026-08-26(경로 병기 3종)에 **같은 사고가 두 번** 있었고, 두 번 다 태그를 막는 대신 사양을 올리는 방향으로 해소했다.

### 「파생 케이스의 원천」 절 신설

기존 태그가 전부 기획서를 가리킨다는 전제(`[DESC …]`·`[UI]`·`[스티커]`·`[ChangeLog]`)를 명시적으로 확장한다.

- 근거 태그의 원천은 **기획서** 또는 **기존 테스트 케이스 + 권한 자료** 둘 중 하나다
- **한 케이스에 두 원천 태그를 섞지 않는다** — 역추적 대상이 갈린다
- **파생 케이스는 프로파일 분포 대조의 대상이 아니다** (결정 3). 이 사실을 사양에 적어 두지 않으면 리뷰가 반복해서 지적한다

### `build_brief.py` 절 배정

새 절 2개(태그 2종은 기존 표에 행 추가이므로 절 신설 아님)에 역할을 배정하고 `--coverage-check` 를 통과시킨다. 미배정 절은 **어느 브리핑에도 들어가지 않아 조용히 사라진다.**

## 11. 오판 방지 목록 (리뷰어 프롬프트 필수 항목)

이 절차는 기존 리뷰 기준 여러 개가 **정반대로 적용되는** 환경이다.

| 지적하면 오판인 것 | 이유 |
|---|---|
| **`구분` 분포가 프로파일과 다르다** | 결정 3. 예외는 `비정상`·`엣지` 만, 권한은 `정상`·`부수` 만 만드는 것이 이 작업의 정의다 |
| **`표시` 케이스가 없다 / 커버리지 부족** | 표시 검증은 기획서 기반 작업의 영역이다. 이 절차의 산출물이 아니다 |
| **기획서 근거 태그(`[DESC …]`)가 없다** | 원천이 기획서가 아니다. `[예외 파생 …]`·`[권한 매트릭스 …]` 가 정상 근거다 |
| **`예상 결과` 에 오류 문구가 없어 불충분하다** | 문구 단정 금지가 규칙이다 (§7). 문구를 적었다면 그쪽이 위반이다 |
| **`[기획 확인]` 이 너무 많다** | 기획 미정의 영역을 다루므로 대량 발생이 정상이다 |
| **TC ID가 원본과 이어지지 않는다 / 화면 블록이 흩어졌다** | append-only이므로 파생분은 대상 탭 끝에 붙는다. 원본 화면 블록과 떨어지는 것이 정상이다 |
| **미대응 기능이 누락됐다** | 1-C·Phase 4에서 제외를 명시하고 사용자가 확인한 항목이다 |
| **`No` 가 1부터 시작한다** | 신규 탭이면 `common.md` 대로 탭별 1부터 재시작이 맞다 |

**반대 방향도 함께 점검한다** — 위 항목을 근거로 **실제 결함을 통과시키면** 안 된다. 예: "분포 점검 제외"는 `구분` 값 자체가 enum 밖인 것을 통과시키라는 뜻이 아니다.

## 12. 신규 에러 처리

| 에러 | 대응 |
|------|------|
| 엑셀(.xlsx) 경로 입력 | **미지원 안내 후 중단.** 구글 시트 이관 또는 CSV 내보내기 요청 |
| 원본 탭 헤더가 23컬럼과 불일치 | **Critical 중단** — 원본을 잘못 읽으면 전 파생분이 어긋난다 |
| 대상 탭이 존재하는데 헤더가 23컬럼 아님 | **Critical 중단** — append하면 전 값이 밀린다 |
| `솔루션` 값이 프로파일에 없음 | 진행 중단. 참고 시트로 프로파일 신설(모드 B) 제안 |
| `솔루션` 값이 한 탭에 혼재 | 최다값 사용 + 사용자 보고 |
| 원본 탭에 유효 케이스 0건 (전부 파생 태그 행) | 진행 중단 — 뒤집을 원본이 없다. 다른 탭 지정 요청 |
| 권한 자료 판독 실패·품질 `불가` | 사용자 통보 + 재전달 요청. 추측 금지 |
| 권한 자료의 기능 ↔ 원본 TC 매핑 실패 | 그 기능 제외 + 보고. **화면 ID 유추 금지** |
| 권한값 enum을 판별할 수 없음 | 게이트에서 사용자에게 확인. 어휘를 하네스가 정하지 않는다 |
| 두 작업 유형이 한 배치에 섞임 | 배치 분리 후 재실행 (도출 규칙·태그가 다르다) |
| 배치 중 일부 기능 단위만 실패 | 그 항목만 `실패` 로 남기고 나머지 진행 |
| `--diff` 대조 불일치 | **Critical** — 로컬 `.tsv` 로 해당 행 재작성 |
| 규모가 과다 (예: 500행 초과) | 1-C 게이트에서 알리고 범위 축소 여부 확인 |
| 원본·대상 탭이 같고 재실행 | 결정 5로 파생 태그 행이 제외되므로 정상 진행. 제외 건수를 인벤토리에 명시 |

## 15. 유지되는 것 (회귀 방지 목록)

이 절차를 넣으면서 **깨뜨리면 안 되는** 기존 규칙.

1. **양식은 `common.md` + 제품 프로파일 두 파일을 함께 읽는다.** 한쪽만 읽으면 규칙의 절반이 없다
2. **컬럼 23개 A~W 고정.** 열 문자는 사양 파일에만 두고 스킬·에이전트는 컬럼명으로 지칭한다
3. **`비고` 를 비우지 않는다.** 근거 태그 필수
4. **`4 Depth`·`5 Depth` 는 `-`, 미사용·실행 컬럼은 빈칸**
5. **atomic** — 검증 항목 1개 = TC 1건. 절차 1단계 원칙
6. **분포·결합 규칙·문체·enum·TC ID 체계는 프로파일에서 읽는다.** 하드코딩 금지
7. **탭명은 `metadata` 의 `title` 문자열을 그대로 쓴다** (NFD/NFC 함정)
8. **`sheets_api.py` write/append 는 RAW.** `--user-entered` 를 쓰지 않는다
9. **서브에이전트 리턴은 20줄 이내**, 산출물은 파일
10. **케이스 본문의 단일 출처는 시트.** `.md` 에 중복 저장하지 않고 `.tsv` 가 복구 경로
11. **첫 배치 검토 게이트**로 문체·태그·enum 오류의 전파를 막는다
12. **사용자에게 제외 항목을 반드시 보여준다.** 조용히 빠진 것이 누락의 원천이다
