# 기획서 분석 절차 신설 (`prd-digest`) — 설계

- 날짜: 2026-09-19
- 상태: 설계 확정 (구현 전)
- **선행 스펙**: `2026-09-19-workspace-layout-design.md` — 그 스펙이 **먼저 적용된다**.
  이 절차는 처음부터 `{WS}` = `_workspace/{디렉터리명}/digest`,
  `{SHARED}` = `…/shared` 위에서 태어난다

## 1. 문제

하네스의 산출물은 **테스트 케이스 행 하나뿐**이다. 기획서를 받았을 때
*이 문서에 무엇이 들어 있고, 이번에 무엇이 새로 생기고 무엇이 바뀌었나* 를
알려면 현재는 **작성된 케이스를 역산하는 수밖에 없다**(직전 실행: 733행).
케이스는 검증 단위로 잘려 있어 기능 목록으로 읽히지 않는다.

또 **트리거가 이미 충돌한다.** `CLAUDE.md` 가 *"테스트 케이스 자동 생성·기획서
분석·시트 작성 관련 요청 시 `testcase-auto`"* 라고 적고 있어, `"기획서 분석해줘"`
는 지금 그대로면 **테스트 케이스 생성이 시작된다.**

### 1-1. 기획서가 이미 가진 것 — 실측

두 VIOLA 기획서의 앞부분이 판정 근거 5종과 그대로 대응한다.

| 섹션 | K8s (181p) | CI/CD (89p, v2) |
|------|-----------|-----------------|
| Document History | p003 (`v1 / 2026.07.28`) | p003 (`v2 / 2026.08.19`, `v1`) |
| Policy | p005~006 | p005 |
| Menu Structure | p009 | p007 |
| 기본 모드 공통 정의 | p087·p088 | p009 (`CICD-00_00_01`) |
| Wireframe 공통 표출 모달 정의 | (`공통 정의` p015·p016) | p011 (`CICD-00_00_11`) |

### 1-2. 메뉴 IA 엑셀 — 기계 판독 가능한 메뉴 트리

`PDF/VIOLA_V4.0/(4.0) VIOLA_메뉴IA구조도_v1.0_260727.xlsx` 의 `1. 메뉴구조도` 시트:

| 열 | 내용 |
|----|------|
| D~G | `LEVEL 1` ~ `LEVEL 4 (Tab)` |
| H · I | **`화면ID` · `화면명`** |
| J~L | 역할별 화면 접근 권한 (`솔루션관리자`·`클러스터 관리자`·`네임스페이스 관리자`) |

실측 대조 결과:

| | 값 |
|---|-----|
| IA 화면 ID | **292** |
| K8s 기획서 화면 ID | **124** |
| 일치 | **114** |
| 기획서에만 있음 | **10** (`VIOE-03_01_04_13`~`_16` 등) |
| IA에만 있음 | 180 (개정판이라 정상 — 이번에 안 바뀐 화면) |

예: `VIOE-03_02_05-01` → `워크플로우 > 네트워크 > 게이트웨이 API > HTTP라우트`.
**메뉴 경로를 판독으로 알아낼 필요가 없다.**

## 2. 설계 결정

### 결정 1 — 독립 스킬로 신설한다 (`testcase-auto` 에 얹지 않는다)

`testcase-auto`·`testcase-augment` 와 나란한 **세 번째 절차**다.

| | `testcase-auto` | `testcase-augment` | **`prd-digest`** |
|---|---|---|---|
| 원천 | 기획서 | 구글 시트의 기존 케이스 | **기획서 + 메뉴 IA** |
| 산출 | 시트 행 | 시트 행 | **MD 2개** (시트 안 씀) |

근거는 2026-09-10 `testcase-augment` 를 분리한 것과 같다 — 시트·TC ID·양식
프로파일·분포·정책 예외가 **하나도 쓰이지 않아**, 한 스킬에 넣으면 거의 모든 절에
`if 작업 유형` 분기가 붙어 **두 경로가 함께 무거워진다**(`testcase-auto` SKILL 은
이미 836줄이다).

**판독 규칙은 재사용한다** — `prd-analyzer` SKILL 본문과 `pdf_to_images.py --tile=auto` ·
`detect_red_regions.py` · `detect_strikethrough.py` · `check_image_quality.py`.
변경 표기 판독 규칙을 새로 쓰지 않는다. 불투명도 4단계·마커 색 번짐·스티커만이
근거인 화면 같은, 값을 치르고 얻은 규칙이 거기 있다.

### 결정 2 — 트리거 분기

| 요청에 있는 말 | 가는 곳 |
|---|---|
| `테스트 케이스` · `TC` · `케이스 생성` | `testcase-auto` |
| **`기획서 분석` · `기능 정리` · `신규·변경 기능 파악`** (케이스 어휘 없음) | **`prd-digest`** |
| 둘 다 있거나 애매 | **묻는다** — 추정하지 않는다 |

`CLAUDE.md` 트리거 절에서 "기획서 분석"을 `testcase-auto` 에서 떼어낸다.

### 결정 3 — 산출물은 MD 2개, 실행 단위는 제품 1개

한 실행에 제품 하나(`VIOLA K8s` 또는 `VIOLA CI/CD`)를 지정한다. 두 문서는 메뉴 트리
뿌리를 공유하지 않아 섞으면 읽기 어렵고, 한 실행이 270p를 읽게 된다.

| 산출물 | 정리 축 |
|--------|--------|
| `{WS}/03_기능_전체.md` | **메뉴 구조** — 기획서에 실린 모든 기능 |
| `{WS}/04_신규변경.md` | **화면 ID** — 신규 / 변경 / 삭제 |

### 결정 4 — 판정 축은 둘이다

| 축 | 근거 | 잡는 것 |
|----|------|--------|
| **문서 전역** | Document History · Policy · Menu Structure · 기본 모드 공통 정의 · 공통 표출 모달 정의 | 신규 메뉴·전역 정책 변경 (실측: Menu Structure p009 에 `v1추가` 빨강 **4건** = 신규 메뉴 4개) |
| **화면** | 그 화면의 변경 표기 (빨강 · 스티커 · 취소선 · `ChangeLog`) | 기존 화면 안에서 바뀐 항목 |

**둘 다 읽는다.** 전역만 보면 화면 내부 변경을 놓치고(직전 실행에서 확정된 CH-ID
165개 중 대부분이 여기서 나왔다), 화면만 보면 신규 메뉴의 존재가 드러나지 않는다.

### 결정 5 — 설명 깊이는 기능 단위 요약

화면마다 기능을 3~10개로 끊어 각 **1~2줄**로 쓰고 메뉴 트리에 매단다.
Description 전수 전사는 하지 않는다 — 산출물 분량이 기획서와 맞먹고 비용이
케이스 생성과 같아지는데(직전 실행 136 사이클), 그러면 *읽기 위한 문서* 라는
목적을 잃는다.

### 결정 6 — 3분류 + 「분류 확인 필요」 넷째 버킷

`분류` enum은 **`신규` · `변경` · `삭제` · `확인 필요`** 4종.

| 근거 | 분류 |
|------|------|
| `v1추가` · Menu Structure 신규 메뉴 | `신규` |
| `v1수정` | `변경` |
| `v1삭제` · 취소선 · 반투명 오버레이 + `v1삭제` 배지 | `삭제` |
| 종류 원문 없음 · 박스만 있고 항목 근거 0건 | **`확인 필요`** |

**권위는 주석 원문이다**(`common.md` 변경 종류 판정 규칙 그대로). 색으로 종류를
추정하지 않는다.

**넷째 버킷을 둔 이유** — 3분류에 억지로 넣으면 **기획서에 없는 종류를 단정**하게
된다. 직전 실행에서 `종류 원문 미표기` 는 드문 일이 아니었다. 삭제를 별도 분류로
세운 것도 같은 맥락이다 — 삭제를 변경에 섞으면 *사라진 기능* 을 따로 볼 수 없고,
전체 기능 목록에도 사라진 것이 남아 버린다.

### 결정 7 — IA 엑셀은 뼈대이되 **권위가 아니다**

- 메뉴 트리·화면 경로는 **`parse_menu_ia.py` 가 결정적으로 파싱**한다.
  판단할 값이 없는 일을 모델에게 시키지 않는다(`verify_sheet_rows.py`·
  `read_tc_inventory.py` 와 같은 논리)
- **IA 부재를 신규 판정 근거로 쓰지 않는다.** 반례가 실측에 있다 —
  `VIOE-03_02_05-*` **19개는 신규인데 IA에 이미 실려 있다.** 또 CI/CD는 IA가
  `260731` 인데 기획서가 `260819` v2 라 **IA가 더 낡았다**
- IA ↔ 기획서 차이는 **「대조」 절로 보고**만 한다
- **IA가 없으면** Menu Structure 페이지 + 각 화면 Breadcrumb 으로 폴백한다.
  폴백했다는 사실을 산출물 머리말에 남긴다

### 결정 8 — 두 MD는 **한 TSV에서 렌더**한다

화면 에이전트는 사람이 읽을 `02_screen_s{NN}.md` 와 기계용
**`02_features_s{NN}.tsv`** 를 함께 낸다.

```
화면ID <TAB> 기능명 <TAB> 설명 <TAB> 분류 <TAB> 근거 <TAB> 페이지 <TAB> 메뉴경로_폴백
```

`render_digest.py` 가 이 TSV를 읽어 **메뉴 트리 순서**와 **화면 ID 순서**로 두 번
배열한다. TSV에 없는 두 값은 **렌더러가 조회해 채운다** — 에이전트가 옮겨 적게
하면 IA와 어긋날 수 있다.

| 값 | 1순위 | 폴백 | 둘 다 없으면 |
|----|------|------|------------|
| 메뉴 경로 | IA (`LEVEL 1~4`) | TSV의 `메뉴경로_폴백` | `(경로 없음)` |
| 화면명 | IA (`화면명` 열) | `00_screen_index.md` 의 `Page Title` | `(이름 없음)` |

**모델이 같은 사실을 두 번 옮겨 적지 않으므로 두 MD가 어긋날 수 없다.**
기획서를 다시 읽지 않고 재렌더할 수도 있다. `03_rows_s{NN}.tsv` 와 같은 구조다.

### 결정 9 — TROMBONE 은 안내 후 중단

Phase 0에서 `TROMBONE` 을 고르면 **진행하지 않고 안내한다.** 기획서가 6개 파일로
쪼개져 있고 IA도 따로 있으며, Screen ID 체계·변경 표기 컨벤션을 **실측한 적이
없다.** VIOLA 규칙을 그대로 적용하면 전 항목이 틀린다 —
`profile-bootfactory` 를 실측 없이 파생으로 만들어 두고 계속 경고를 달아야 했던
것과 같은 함정이다. 실측 근거가 생기면 그때 넣는다.

### 결정 10 — `.claude/formats/` 와 `build_brief.py` 는 건드리지 않는다

이 절차엔 23컬럼도, 구분 분포도, 문체 규칙도 없다. 프로파일에서는 **화면 ID
체계만** 읽는다. `build_brief.py --coverage-check` 에 새 역할을 넣지 않는다 —
넣으면 양식 사양의 모든 절이 이 절차에도 배정돼야 하는데 대부분 무관하다.

## 4. 산출물 형식

**`03_기능_전체.md`**

```markdown
# VIOLA K8s 기능 정리 — 메뉴 구조 기준
- 기획서: … (181p) · Document History `v1 / 2026.07.28`
- 메뉴 IA: … (292 화면)   ← 폴백이면 그 사실을 여기 적는다
- 수록 범위: 기획서에 실린 124 화면 — IA 일치 114 + 기획서 단독 10

## 공통 정의            ← 메뉴 경로가 없는 VIOE-00_00_* (IA의 LEVEL 1~4 가 전부 `-`)
## 모니터링 > 외부 알람 설정
### VIOE-04_06_01 외부 알람 목록  〈p043〉
| 기능 | 설명 | 분류 |
```

**`04_신규변경.md`**

```markdown
## 요약            분류별 기능 수 · 화면 수
## 문서 전역       ← 5개 섹션에서 나온 것
## 신규  ## 변경  ## 삭제
### VIOE-04_06_01 외부 알람 목록 〈모니터링 > 외부 알람 설정〉 p043
| 기능 | 설명 | 근거 |
| 알람 목록 조회 | … | `[스티커 p043] v1추가 26.06.19` |

## 분류 확인 필요   ← 결정 6
## IA ↔ 기획서 대조 ← 결정 7. 판정 아님
```

근거 태그 어휘는 `common.md` 를 따른다 — `[DESC pNNN-N항]` · `[스티커 pNNN]` ·
`[ChangeLog pNNN]` · `[취소선 pNNN]` · `[Menu Structure pNNN]` + 종류·일자 원문.

`기획서 유형 = 신규` 면 전 기능이 `신규` 이고 변경·삭제 절은 `해당 없음` 으로 남긴다.

## 5. 품질 장치

**`verify_digest.py` — 결정적 점검**

| 점검 | 등급 |
|------|------|
| 인덱스의 모든 화면이 두 MD에 등장 | Critical |
| `분류` enum 4종 외 값 | Critical |
| `신규`·`변경`·`삭제` 행의 **근거 태그 공란** | Critical |
| TSV ↔ 렌더된 두 MD 대조 | Critical |
| 기획서 전 페이지가 화면에 귀속되거나 제외 목록에 있음 | Major |

`--selftest` 를 함께 만든다. **통과만 확인하면 파서가 빈 규칙을 돌려줘도
「위반 0건」이 나온다**(2026-09-08 `verify_sheet_rows.py` 에서 겪은 것).

**리뷰 — `testcase-reviewer` + 신설 참조 `digest-mode.md`, 집계 1회**

역방향 오판 금지를 함께 박는다. 이것이 없으면 리뷰가 매 실행 재작업 루프를 만든다
(같은 방어를 이미 6번 신설했다).

- 「분류 확인 필요」가 있는 것을 결함으로 지적 금지 — **그것이 설계다**

## 8. 하지 않는 것

- **시트 작성** — 이 절차의 산출물은 MD뿐이다
- **케이스 생성으로 이어가기** — 분석만 하고 끝낸다. 케이스가 필요하면 `testcase-auto`
- **TROMBONE·BootFactory** (결정 9)
- **`.claude/formats/`·`build_brief.py` 수정** (결정 10)
- **IA의 역할별 접근 권한(J~L) 활용** — `testcase-augment` 권한 모드의 원천이 될
  수 있으나 이 절차의 산출물이 아니다. 별건

  정보일 수 있다. 1-E 구현 시 실측으로 정한다
