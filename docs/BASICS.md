## 1. 한 줄로

**기획서를 읽고 테스트 케이스를 써서 구글 시트에 넣어 주는 도구다.**

사람이 하던 일을 그대로 한다 — 기획서를 한 화면씩 보면서 "이건 이렇게 동작해야 하니 이런 케이스가
필요하다"를 적고, 팀 시트 양식에 맞춰 행으로 채워 넣는 일. 다만 **혼자 다 하지 않는다.** 분석하는
쪽, 케이스를 쓰는 쪽, 검사하는 쪽이 나뉘어 있고 **중간에 세 번 사람에게 물어본다.**

## 2. 무엇을 넣고 무엇이 나오나

### 넣는 것 셋

| 넣는 것 | 형태 | 비고 |
|---------|------|------|
| **기획서** | PDF · 이미지(PNG 등) · Figma URL | 이미지는 변환 없이 경로만 주면 된다 |
| **대상 시트** | 구글 시트 URL + 탭 이름 | 서비스 계정에 **편집자 공유**가 되어 있어야 한다 |
| **제품 유형** | `VIOLA K8s` / `VIOLA CI/CD` / `TROMBONE` / `BootFactory` | 이 값으로 문체·ID 체계가 정해진다 |

**팀 양식 시트(참고용)는 넣지 않는다.** 양식은 이미 저장소 안에 사양 파일로 들어 있다.

### 나오는 것 하나

**구글 시트의 행들.** 그 외는 전부 중간 산출물이고 **작업 디렉터리**에 남는다(커밋되지 않는다).
작업 디렉터리는 제품·제품버전·문서회차마다 따로 생기며, 이름은 게이트 1에서 정한다 —
예를 들어 `_workspace/VIOLA-K8s_4.0_v1/` 이고 그 아래 `shared/`(이미지·검출 결과)와
`testcase/`(케이스 산출물)로 나뉜다.

### 케이스 말고 **기능 목록**이 나오는 절차도 있다

이 문서가 설명하는 것은 케이스를 만드는 절차다. 같은 기획서로 **케이스 대신 읽는 문서**를
받고 싶으면 **기획서 분석**(별도 절차)을 쓴다. 나오는 것은 시트 행이 아니라 파일 2개다.

| 나오는 것 | 무엇인가 |
|---|---|
| `_workspace/VIOLA-K8s_4.0_v1/digest/03_기능_전체.md` | 기획서에 실린 **모든 기능**을 메뉴 구조 순서로 정리한 목록 |
| `_workspace/VIOLA-K8s_4.0_v1/digest/04_신규변경.md` | 이번 회차에 **생긴·바뀐·없어진** 기능만 모은 문서 |

기능마다 위 **분류** 5종 중 하나가 붙는다(용어 4절). 요청할 때 `테스트 케이스` 라는 말을
쓰지 않는 것이 중요하다 — 그 말이 있으면 케이스 생성으로 간다. 요청 문구는
[docs/PROMPTS.md](PROMPTS.md) 11절에 있다.

**시트를 쓰지 않으므로 대상 시트도 서비스 계정 공유도 필요 없다.** 넣는 것은 기획서와
제품 유형, 그리고 **메뉴 IA 엑셀**(선택 — 메뉴 구조를 여기서 읽는다)이다.

## 3. 테스트 케이스 한 줄은 이렇게 생겼다

시트는 **23개 컬럼(A~W)** 인데, 새 케이스를 쓸 때 **실제로 채우는 것은 13개**다. 나머지는 미사용이거나
실행 단계에서 채운다.

VIOLA 기획서의 클러스터 목록 화면에서 나온 한 줄을 예로 들면:

| 열 | 컬럼 | 값 | 무슨 뜻인가 |
|----|------|-----|------------|
| A | `No` | `1` | 탭 안에서 1부터 세는 번호 |
| B | `솔루션` | `VIOLA` | 제품 이름. 한 탭 안에서 항상 같은 값 |
| C | `기능테스트 ID` | `TC_VIO_001` | 케이스 고유 번호 |
| F | `화면 ID` | `VIOE-03_01_01` | **기획서에 적힌 화면 식별자를 그대로** 옮긴다 |
| G | `우선순위` | `P1` | `P1`~`P4` |
| H | `구분` | `표시` | 6종 중 하나 (아래 용어 참조) |
| I | `1 Depth` | `클러스터 관리` | 대분류 — 기획서 breadcrumb 최상위 |
| J | `2 Depth` | `클러스터 목록` | 화면 이름 |
| K | `3 Depth` | `목록` | `목록`/`생성`/`수정`/`상세` |
| N | `사전조건` | `클러스터가 1개 이상 등록된 상태` | 한 줄로 |
| P | `절차` | `1. 좌측 메뉴에서 '클러스터 관리' 클릭` | **`1. ` 접두를 반드시 붙인다** |
| Q | `예상 결과` | `클러스터 목록 테이블 표출` | **명사형으로 끝낸다** ("표출된다" ✕) |
| V | `비고` | `[DESC 2항-1]` | **이 케이스가 기획서 어디서 나왔는지** |

나머지 열 — `L`·`M`(4·5 Depth)은 전 행 `-`, `D`·`E`·`R`·`S`·`T`·`U`는 **빈칸**으로 둔다.

> **`-` 와 빈칸은 다르다.** `-` 는 "해당 없음"을 적은 것이고, 빈칸은 "아직 안 채운 칸"이다.
> 이 구분은 하네스가 자동으로 맞춘다.

### 가장 중요한 칸은 `비고` 다

`[DESC 2항-1]` 은 **"기획서 2항의 1번 항목을 보고 만든 케이스"** 라는 뜻이다. 이게 있어야 나중에
"이 케이스 왜 만들었지?"를 기획서로 되짚을 수 있다. 하네스는 **비고를 비우지 않는다.**

## 4. 용어 15개

처음 읽을 때 막히는 단어만 모았다.

| 용어 | 뜻 |
|------|-----|
| **하네스** | 이 도구 전체. 스킬·에이전트·스크립트를 묶어 부르는 말 |
| **화면 ID** | 기획서 페이지에 적힌 화면 식별자(`VIOE-03_01_01` · `BOOT-03_01_01` 같은 것). **하네스가 일을 자르는 단위** — 화면 하나를 끝내고 다음 화면으로 간다 |
| **케이스 / TC** | 테스트 케이스. 시트의 한 행 = 한 케이스 |
| **atomic** | **한 케이스는 한 가지만 검증한다**는 원칙. "로그인하고 목록 보고 삭제한다"를 한 줄에 넣지 않는다. 실패했을 때 어디가 문제인지 알 수 있어야 하기 때문 |
| **구분** | 그 케이스의 성격. `정상`(제대로 될 때) / `비정상`(잘못된 입력) / `표시`(화면에 뭐가 보이나) / `엣지`(경계 상황) / `인터랙션`(조작 반응) / `부수`(취소·비활성 등) |
| **양식 사양 / 프로파일** | 팀 시트를 **전수로 세어 만든 규칙 파일.** 컬럼 순서·허용값·문체가 적혀 있다. 제품마다 문체가 달라(VIOLA는 백틱, TROMBONE은 대괄호) 제품별 프로파일이 따로 있다 |
| **게이트** | 하네스가 멈추고 사람에게 물어보는 지점. **3곳이고 우회할 수 없다** |
| **에이전트** | 일을 나눠 맡은 실행 주체. 분석·작성·검사가 각각 다른 에이전트다 |
| **변경분 한정** | 개정판 기획서에서 **바뀐 부분만** 케이스로 만드는 모드. 기획서 유형을 `변경` 이라고 답하면 이 모드로 돈다 |
| **정책 예외** | 위 모드의 예외. "이 문서는 개정판인데 이 화면만은 신규니까 전부 뽑아줘" 할 때 쓰는 **화면 ID 목록** |
| **드리프트** | 저장소의 양식 사양과 **실제 시트가 달라진 것.** 컬럼이 추가됐다거나. 하네스가 매번 헤더를 대조해서 잡는다 |
| **추가 작업** | 기획서가 아니라 **이미 쓴 케이스**를 원천으로 예외 사항·권한 케이스를 파생하는 별도 절차 |
| **기획서 분석** | 기획서를 읽어 **기능 목록과 신규·변경 판정**만 내는 별도 절차. **케이스를 만들지 않고 시트를 쓰지 않는다.** 결과물은 읽는 문서 2개다 |
| **분류** | 기획서 분석에서 기능마다 붙는 값. **5종**이다 — `신규` / `변경` / `삭제` / `확인 필요`(변경 표기는 있는데 종류가 안 적혀 있다) / `미변경`(이번에 손대지 않았다). 케이스의 `구분` 과는 다른 것이다 |
| **작업 디렉터리** | 중간 산출물이 쌓이는 자리. `_workspace/{제품}_{제품버전}_{문서회차}/`(예 `_workspace/VIOLA-K8s_4.0_v1/`)이고 이름은 게이트 1에서 정한다. 그 아래 `shared/`(이미지·검출 결과 — 절차끼리 공용) · `testcase/`(케이스 산출물) · `digest/`(기획서 분석 산출물)로 나뉜다 |

## 5. 한 번 돌리면 이런 일이 일어난다

사용자 입장에서 시간순으로.

**① 요청한다.** `테스트 케이스 자동 생성해줘.` 한 줄이면 된다.

**② 하네스가 일곱 가지를 물어본다.** ← **게이트 1**

> 제품 유형 / 기획서 유형(신규·변경) / 정책 예외 / 기획서 경로 / 시트와 탭 /
> 작업 디렉터리명 / 이미 변환해 둔 이미지가 있는지(선택)

미리 적어 보냈으면 확인만 하고 넘어간다. **답하지 않으면 진행하지 않는다** — 하나를 잘못 추측하면
수백 행에 그대로 박히기 때문이다.

**③ 준비 작업을 한다.** PDF를 읽을 수 있는 이미지로 바꾸고(같은 기획서를 전에 돌렸다면 그 이미지를 그대로 쓴다), 기획서에 칠해진 색과 취소선을 스크립트로
훑고, 대상 시트의 헤더를 사양과 대조한다. 몇 분 걸린다.

**④ 화면 목록을 보여준다.** ← **게이트 2**

> 화면 12개 · 예상 케이스 약 150건 · 이렇게 자르면 될까요?

**여기가 범위를 줄일 수 있는 자리다.** 150건이 부담스러우면 "앞의 3개만" 이라고 말하면 된다.

**⑤ 첫 화면을 작업해서 보여준다.** ← **게이트 3**

첫 화면의 케이스를 만들어 시트에 쓴 다음 멈춘다. **여기서 본 것이 나머지 전체에 적용된다** —
문체가 이상하거나 사전조건이 부실하면 지금 말해야 한다.

**⑥ 나머지를 자동으로 돈다.** 화면 하나씩 분석 → 작성 → 검사를 반복한다. **시트에 실시간으로 쌓이므로
진행 중에도 결과를 볼 수 있다.**

**⑦ 전체 결과를 보고한다.** 만든 케이스 수, 시트 행 범위, 검사에서 나온 문제, 기획 확인이 필요한 항목.

## 6. 내가 해야 하는 일 — 게이트 3곳

하네스가 멈추는 세 곳에서 **무엇을 보고 무엇을 말할지**만 알면 된다. 나머지는 자동이다.

### 게이트 1 — 기본 정보

**볼 것:** 하네스가 되보여 주는 확정값 표.

**주의할 것:** 탭 이름이 기존 탭과 **구분자만 다른 경우**(`01 목록` vs `01_목록`). 실제로 되물은
사례가 있다. 그리고 **기획서 유형** — 개정판인데 `신규` 라고 답하면 바뀌지 않은 부분까지 전부
케이스가 된다. **작업 디렉터리명**은 같은 기획서를 다시 돌릴 때 지난번과 똑같이 답한다 —
이름이 다르면 이미 만들어 둔 이미지를 못 찾아 처음부터 다시 변환한다(181페이지에 약 10분).

### 게이트 2 — 화면 목록과 규모

**볼 것:** 화면 개수, 예상 케이스 수, 제외된 페이지.

**말할 것:**
- 규모가 크면 → `앞의 화면 3개만 먼저 해줘`
- 빠진 화면이 있으면 → 그 페이지 번호를 알려준다
- 간지·목차가 화면으로 잡혔으면 → 제외를 요청한다

### 게이트 3 — 첫 화면 케이스 (가장 중요하다)

**시트를 직접 열어서 본다.** 보고서만 보지 말고 실제 행을 본다.

| 볼 것 | 이상하면 |
|-------|---------|
| `절차` 의 말투 | "팀 시트는 이렇게 씁니다" 하고 실제 행을 하나 보여준다 |
| `사전조건` 이 충분한가 | "사전조건에 ○○ 상태를 명시해줘" |
| `구분` 비율 | 한쪽으로 쏠렸으면 지적한다 |
| `비고` 태그 | 비어 있으면 안 된다 |
| **삭제된 기능의 케이스가 있는가** | 취소선 그어진 내용을 "동작한다"고 테스트하면 **잘못된 결함이 보고된다.** 발견하면 바로 말한다 |

> **여기서 지시한 것이 나머지 전 행에 적용된다.** 게이트 3을 대충 넘기면 100행을 다시 만들게 된다.

## 7. 하네스 안에는 세 종류가 있다

사람 여럿이 한 줄로 서서 일하는 것과 비슷한데, **서로 대화하지 않는다.** 앞 사람이 파일에 적어
두면 뒷사람이 그 파일을 읽는다.

| 종류 | 무엇인가 | 비유하자면 |
|------|---------|-----------|
| **스킬** | 규칙이 적힌 문서 | 업무 매뉴얼 |
| **에이전트** | 실제로 일하는 주체 | 담당자 |
| **스크립트** | 파이썬 프로그램 | 계산기·측정도구 |

### 담당자 다섯

| 담당자 | 하는 일 |
|--------|--------|
| `prd-analyst` | 기획서를 읽는다. 화면과 Description을 하나도 빼지 않고 적는다 |
| `sheet-analyst` | 양식 사양을 읽고, 대상 시트가 그 양식과 같은지 대조한다 |
| `testcase-writer` | 케이스를 만들어 시트에 쓴다 |
| `testcase-reviewer` | 만들어진 것을 검사한다 |
| `tc-augmenter` | 추가 작업(예외·권한) 전용 담당 |

### 왜 파일로 주고받나

중간에 멈춰도 **그 지점부터 이어서** 할 수 있기 때문이다. 화면 12개 중 7개까지 하고 끊겼다면,
작업 디렉터리의 `00_screen_index.md`(예: `_workspace/VIOLA-K8s_4.0_v1/testcase/00_screen_index.md`)에
"7번까지 완료"가 적혀 있어 8번부터 다시 시작한다.

### 담당자마다 다른 모델을 쓴다

기획서를 읽는 담당(`prd-analyst`)과 검사하는 담당(`testcase-reviewer`)은 **비싼 모델**을, 양식을
대조하고 케이스를 쓰는 담당은 **가벼운 모델**을 쓴다. 기준은 **"틀렸을 때 뒤에서 복구되는가"** 다 —
기획서에서 놓친 것은 아무도 되찾아 주지 못하지만, 케이스의 형식 오류는 스크립트가 전수로 잡는다.

## 8. 케이스를 어떻게 뽑나

### 원칙 셋

**① 기획서의 Description은 하나도 빼지 않는다.**
"화면에 안 보이니까", "앞 페이지에 이미 썼으니까"로 건너뛰지 않는다. 실제로 그렇게 빠뜨린 적이
있어서 규칙이 됐다.

**② 한 케이스는 한 가지만 검증한다.**
"로그인하고 목록 보고 삭제한다"를 한 줄에 넣지 않는다. 실패했을 때 어디가 문제인지 알 수 없기
때문이다. **절차가 1~2단계, 예상 결과가 1~3줄을 넘어가면 쪼갠다.**

**③ 기획서에 없는 것은 단정하지 않는다.**
"보통 이러니까 이렇겠지"로 쓰지 않고 **"기획 확인 필요"로 따로 빼서 보고**한다. 단정해 버리면
실행자가 기획과 다른 기준으로 테스트하게 된다.

### 저절로 따라 나오는 케이스

기획서에 이런 게 있으면 하네스가 알아서 케이스를 더 만든다. 사람이 자주 빠뜨리는 것들이다.

| 기획서에 이게 있으면 | 이런 케이스가 따라 나온다 |
|---------------------|------------------------|
| 테이블 컬럼 | 컬럼 순서·이름 / 정렬 동작 / 빈 값 `-` 표시 |
| 상태 값 목록 | 각 상태의 표시 형식 / 호버 툴팁 (**열거된 값 전부**) |
| 일시 | `yyyy-mm-dd hh:mm:ss` 형식 / 값 없을 때 `No data (-)` |
| 액션 버튼 | 클릭 후 이동 / 모달 표출 / 모달 취소 / 모달 진행 |

### 개정판 기획서일 때

기획서 유형을 `변경` 이라고 답하면 **바뀐 부분만** 뽑는다. 이때 표기를 읽는 방식이 핵심이다.

| 기획서에 있는 것 | 어떻게 읽나 |
|-----------------|-----------|
| **색 박스**(화면에 쳐진 빨강·파랑 테두리) | **"여기를 보라"는 신호일 뿐.** 무엇이 바뀌었는지는 말해 주지 않는다 |
| **DESC의 색 글자 · 스티커 · ChangeLog** | **"이것이 바뀌었다"는 근거.** 케이스는 여기서 나온다 |
| **취소선** | **삭제됐다는 뜻** |

> 박스를 근거로 화면 전체를 케이스화하던 시절, 팝업 하나가 **58건**이 된 적이 있다. 스티커 9개가
> 무엇이 바뀌었는지 이미 구체적으로 가리키고 있었는데도 그랬다. 그래서 박스와 항목 근거의
> **역할을 갈랐다.**

**취소선은 특히 주의해야 한다.** 삭제된 기능을 "정상 동작하는지" 테스트하는 케이스를 만들면,
실행자가 **기획대로 사라진 것을 "안 된다"고 보고**하게 된다. 그래서 취소선 내용으로 만들 수 있는
케이스는 **"더 이상 안 보인다/안 남아 있다"는 확인뿐**이다.

### 구분 비율은 제품마다 정반대다

같은 하네스인데 제품에 따라 케이스 성격의 비율이 다르다. 팀이 실제로 그렇게 써 왔기 때문이다.

| 제품 | `정상` | `표시` |
|------|-------|-------|
| VIOLA | 6.3% | **55.9%** |
| TROMBONE | **65.1%** | 2.4% |

그래서 **제품 유형을 잘못 답하면 결과물이 팀 시트와 이질적으로 나온다.** 게이트 1이 중요한 이유다.
다만 **화면 하나만 놓고 비율을 따지지는 않는다** — 화면 하나엔 케이스가 5~20건이라, 비율을 억지로
맞추면 그 화면에 없는 케이스를 지어내게 된다.

## 9. 어떻게 검사하나

만든 다음 그냥 넘기지 않는다. **검사는 두 단계**다.

### 1단계 — 스크립트가 전부 센다

사람이 판단할 필요가 없는 것은 전부 프로그램이 **전 행을 훑어** 판정한다.

> 컬럼이 23개 맞는가 / 허용되지 않는 값이 들어갔나 / 번호가 빠지거나 겹쳤나 /
> `절차` 에 `1. ` 접두가 있나 / `예상 결과` 가 명사형으로 끝났나 / `비고` 가 비었나 /
> 시트에 실제로 쓰인 내용이 로컬과 같은가(**전 셀 대조**)

이걸 사람이 하던 시절, 실제로 **212행이 엉뚱한 칸에 들어가 있는 것**을 뒤늦게 발견한 적이 있다.
사람이 판단할 값이 없는 일이라 프로그램으로 내렸다.

> 검사 규칙은 프로그램 안에 박혀 있지 않고 **양식 사양 파일에서 읽어 온다.** 사양을 고치면 검사도
> 따라온다. 사양을 못 읽으면 **그냥 통과시키지 않고 실패로 끝낸다** — 낡은 기준으로 조용히
> 합격시키는 것이 검사를 안 하는 것보다 나쁘기 때문이다.

### 2단계 — 사람(검사 담당)이 판단할 것만 본다

세 가지를 맞대어 본다.

| 무엇과 무엇을 | 묻는 것 |
|--------------|--------|
| 기획서 ↔ 케이스 | 빠진 기능이 없나? 추측으로 쓴 것이 표시돼 있나? |
| 양식 ↔ 케이스 | 문체·ID 체계가 팀 것과 같나? |
| 로컬 ↔ 시트 | 실제로 시트에 제대로 들어갔나? |

### 지적은 3단계

| 등급 | 뜻 | 어떻게 되나 |
|------|-----|-----------|
| **Critical** | 그냥 두면 안 되는 것 | 바로 다시 만든다 |
| **Major** | 판단이 필요한 것 | 사용자에게 물어본다 |
| **Minor** | 참고 사항 | 알려만 준다 |

**검사 담당은 케이스를 직접 고치지 않는다.** 고쳐 버리면 만든 사람의 의도가 묻히므로, 어느 행의
어느 칸이 무엇과 다른지만 짚고 수정은 만든 담당이 한다.

### 검사가 틀리는 경우도 막아 뒀다

검사 자체가 잘못된 지적을 낸 이력이 있어서, **하면 안 되는 지적**이 규칙으로 적혀 있다.

- 개정판 모드인데 **"안 바뀐 부분이 케이스에 없다"고 지적하는 것** — 그게 이 모드의 정의다
- **신규 화면을 전부 뽑은 것을 "범위 초과"라고 지적하는 것**
- 한 제품의 기준으로 **다른 제품을 지적하는 것** (문체·비율이 정반대다)

> 이런 오판은 고칠 것이 없는데도 재작업을 돌게 만든다. 그래서 새 검사를 넣을 때는 **그 검사가 낼 수
> 있는 오판도 함께 적는 것**이 이 하네스의 규칙이다.

## 10. 자주 하는 오해

**"기획서를 주면 알아서 다 해주겠지"**
→ 일곱 가지를 답해야 시작한다. 추측하지 않는 것이 규칙이다.

**"참고할 팀 시트 URL을 줘야 하나?"**
→ 필요 없다. 양식은 저장소 안에 있다. 대상 시트에서는 헤더와 마지막 번호만 읽는다.

**"케이스가 많을수록 좋은 거 아닌가?"**
→ 아니다. 개정판에서 **바뀌지 않은 부분까지 만들면** 리뷰 대상만 늘고 변경 근거 추적이 끊긴다.
실제로 화면 전체에 빨간 박스가 쳐져 있다는 이유로 팝업 하나가 58건이 된 적이 있고, 그래서
**박스는 "여기를 보라"는 신호일 뿐 "전부 바뀌었다"는 뜻이 아니라고** 규칙을 고쳤다.

**"검출 스크립트가 0건이라고 했으니 없는 거다"**
→ 아니다. **못 찾은 것과 없는 것은 다르다.** 두 글자짜리 취소선을 검출기가 놓친 적이 있어서,
지금은 0건이어도 사람이 본문을 다시 읽게 되어 있다.

**"시트에 뭔가 잘못 들어가면 어쩌지?"**
→ 헤더가 사양과 다르면 **작성을 시작하지 않고 멈춘다.** 잘못 밀려 들어가는 것이 가장 복구하기
비싼 사고라서 그렇게 막아 두었다.

**"에이전트가 여럿인 게 과한 것 아닌가?"**
→ 분석에서 놓친 것은 뒤 단계가 복구할 수 없고, 작성의 형식 오류는 스크립트가 잡는다. 그래서
**단계마다 다른 모델**을 쓴다. 놓치면 끝인 단계에만 비싼 모델을 둔다.

## 11. 처음 쓸 때 안전한 순서

1. **[SETUP.md](../SETUP.md) 대로 세팅하고 `python3 verify_setup.py` 로 검증한다.** 실패가 0이어야 한다
2. **연습용 탭을 새로 만든다.** 기존 케이스가 있는 탭에 바로 쓰지 않는다
3. **화면 2~3개로 먼저 돌린다.** 게이트 2에서 범위를 줄이면 된다
4. **게이트 3에서 시트를 직접 열어 본다.** 여기서 방향을 잡는다
5. 결과가 마음에 들면 **나머지를 돌린다**
