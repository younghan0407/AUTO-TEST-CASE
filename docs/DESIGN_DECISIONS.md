## 이 문서를 읽는 법

`CLAUDE.md` 의 이력은 **날짜순**이라, 한 규칙이 어떤 실패에서 나와 어떻게 바뀌었는지를 따라가려면
넉 달 치를 훑어야 한다. 여기서는 같은 내용을 **주제 7개**로 묶고, 각 전환점을 네 칸으로 고정했다.

| 칸 | 담는 것 |
|----|--------|
| **무엇이 틀렸나** | 그 규칙이 없던 시절의 실제 증상 |
| **실측 근거** | 판단을 세운 숫자. 추정이면 추정이라고 적는다 |
| **지금 규칙** | 현재 하네스가 하는 일 |
| **재발 방지** | 사람의 주의가 아니라 **장치**로 막은 방법 (없으면 `—`) |

읽는 순서에 정답은 없지만, 하네스를 처음 보는 사람에게는 **7 → 1 → 3** 이 빠르다.

### 1-2. 챕터 → 화면 ID 1개 — 2026-09-02

| 칸 | 내용 |
|----|------|
| **무엇이 틀렸나** | 챕터 단위는 **시트의 식별 축(`화면 ID` 컬럼)과 어긋나** 있었다. 같은 날 도입한 **정책 예외가 이미 화면 ID 단위**여서, 한 챕터 안에 기본 정책 화면과 예외 화면이 섞인 채 한 에이전트에게 넘어갔다. 간지에 의존하는 단위는 기획서 편집 관행에도 종속됐다(간지 없는 문서, 간지 하나에 화면 20개) |
| **실측 근거** | 정책 예외의 단위가 화면 ID라는 사실 자체가 근거 |
| **지금 규칙** | **화면 1개를 분석 → 생성 → 시트 append 까지 끝낸 뒤** 다음 화면으로 간다. 단위 목록과 진행 상태는 `_workspace/00_screen_index.md` 가 단일 출처 |
| **재발 방지** | **`scripts/verify_unit_migration.sh`** — 폐기된 챕터 단위의 금지 패턴(산출물 접미사·챕터 목록 파일·옛 CH-ID 표기)과 화면 단위 구조의 필수 패턴 14개를 함께 검사한다. **패턴 원문은 그 스크립트가 단일 출처다**(여기 옮겨 적으면 패턴 ④ 그대로다). **변경 이력 행(날짜 포함)은 과거 방식을 서술해야 하므로 검사에서 제외**한다 |

**가장 어려운 문제는 공통 DESC C-ID의 순서 역전이었다.** 기존 규칙은 *"모든 챕터 분석을 받은 뒤
한 번에 배정"*(2026-08-25 충돌의 대책, **순차 배정이 그 사고의 원인**)인데 화면 단위 즉시 작성은
정의상 순차 배정이다. **배정 시점을 루프 이전으로 옮겨** 해결했다 — 사전 스캔이 전체를 얕게 훑어
`00_cid_register.md` 에 `C1`~`Cn` 을 선발급하고, 분석 담당은 로컬 번호를 매기지 않고 레지스터를 읽는다.

함께 정한 것 넷:

- **CH-ID는 `CH{NN}-N` 표기를 유지하고 `NN` 의 의미만 화면 순번으로 재정의.** 새 접두어(`SC-`)를 쓰면 기존 탭에서 두 체계가 섞인다. 다만 **표기가 같아 형태로 구별되지 않으므로** 꼬리 읽기에서 기존 CH-ID 최대값을 실측해 그 다음부터 배정한다
- **리뷰는 화면마다 돌리되 분포 편차·TC ID 연속성은 「전체 집계 리뷰」로 이관** — 화면 1개 표본은 5~20건이라 **지배 구분 역전이 상시 Critical로 뜬다**(그 화면에 없는 케이스를 만들라는 지적이 된다)
- **화면 ID 없는 페이지는 종류별 분기** — 간지·목차는 제외, 공통 정책·플로우는 `NOID-{일련번호}` 독립 단위(직전 화면에 병합하면 나머지 화면에서 근거가 사라진다)
- **첫 화면 검토 게이트 유지** — 문체·태그·enum 오류를 첫 화면에서 잡아야 전 행에 번지지 않는다

### 1-3. 배치 처리 — 호출만 묶는다 — 2026-09-08

| 칸 | 내용 |
|----|------|
| **무엇이 틀렸나** | 고정 문서는 **호출당** 붙으므로 화면 단위 처리에서는 화면마다 반복된다. 케이스 5~20건인 소형 화면은 컨텍스트 여유가 큰데 그대로 낭비했다 |
| **실측 근거** | 화면 34개 → 배치 약 15개면 사이클 `3N+1` → `3M+1` |
| **지금 규칙** | 네 조건을 **모두** 만족할 때만 묶는다 — 같은 소속 간지 · 같은 정책 · 페이지 합 3장 이하 · 정책 예외 화면 아님. 최대 3화면 |
| **재발 방지** | 가드에 **「배치는 호출 단위」·「첫 배치 단독」** 항목 신설 |

화면 단위 재편의 이득을 잃지 않도록 셋을 못 박았다 — ⓐ **첫 배치(`B01`)는 반드시 화면 1개**(첫 화면
게이트의 목적이 오류가 전 행에 번지기 전에 잡는 것인데, 첫 호출에 여러 화면을 넣으면 게이트를
통과할 때 이미 여러 화면이 잘못 쓰여 있다) ⓑ **묶는 것은 호출뿐이고 산출물·상태·시트 행은 화면
단위로 분리**(합쳐 저장하면 화면 하나만 다시 만들 수 없다) ⓒ **배치 중 일부 화면만 실패하면 그
화면만 `실패`** 로 남기고 나머지는 진행.

### 1-4. 식별자 네임스페이스 — 단위를 바꿀 때마다 따라온 부작용

| 사고 | 날짜 | 내용 |
|------|------|------|
| **번호를 겹쳐 쓴 사고** | 2026-08-25 | 챕터별 분석서가 CH-ID를 제각기 매겨(`CH-1`/`CH3-1`/`CH04-1`) ch01과 ch02의 `CH-1` 이 한 탭에서 충돌. `[공통 DESC C1]` 도 세 챕터가 각각 다른 뜻으로 썼고, `C5` 는 **12행이 충돌** |
| **번호를 나눠 쓸 뻔한 사고** | 2026-08-27 | 한 작성자가 *"`C1` 이 소진됐으니 다음 챕터는 `C2`"* 로 판단. 그대로 갔으면 같은 정의 하나가 `C1`·`C2` 로 **두 번 정의**되어 검색으로 안 잡힌다 |

**결론: C-ID는 소진되는 순번이 아니라 정의를 잇는 공유 키다.** 같은 정의면 챕터·화면이 달라도 같은
번호, 다른 정의면 다른 번호. 하나의 변경이 여러 화면에 걸치면 그 전부가 같은 번호를 단다.

**"하나의 정의"의 판단 기준은 내용 유사성이 아니라 기획서의 상호 참조다**(2026-08-27). 리뷰어가
`상태 표기 형태 변경`(두 화면에서 **일자·회차·변경 내용이 완전히 동일**)도 연결하자고 제기했으나
**연결하지 않기로 판정**했다 — `C1`(`터미널 실행`)은 상세 화면 DESC가 목록 화면을 **직접 가리키는**
반면, `상태` 는 두 화면에 **각각 독립한 스티커**가 있고 문구도 다르다. **기획서가 잇지 않은 것을
이어 붙이면 기획서에 없는 관계를 단정하는 것**이며, 한쪽 기획 회신이 다른 쪽에 자동 적용된다고 볼
근거가 없다.

### 2-2. 제품별 분기 — 그리고 완전 merge를 하지 않은 이유 — 2026-09-02

사용자 제안("1개로 merge하는 게 효율적")에서 출발했으나 **완전 merge는 하지 않았다.** 두 사양이
전수 실측에서 **정반대인 항목**을 갖기 때문이다.

| 항목 | VIOLA | TROMBONE |
|------|-------|----------|
| 절차의 백틱 사용률 | 65% | **0.0%** (0/3,953행) |
| 지배 구분 | `표시` 56% | `정상` 65% |
| `정상` 의 우선순위 | P1·P2만 | P1~P4 전부 |
| TC ID | 제품 전역 연속 | 모듈별 연속 |

**절충값이 존재하지 않아 합치면 한 제품은 반드시 팀 컨벤션에서 벗어난다.** 대신 중복이 실제로 컸던
부분(컬럼 골격·헤더 원문·`-` vs 빈칸·atomic·태그 체계·C-ID/CH-ID·변경분 모드 태그·권위 규칙)을
`common.md` 하나로 뽑고, **실측으로 갈리는 12개 항목만** 프로파일에 남겼다.

> **양식 로드 = 두 파일을 함께 읽는 것.** 한쪽만 읽으면 규칙의 절반이 없다.

부수 효과로 **기존 버그 하나가 드러났다** — 화면 ID 필드 우선순위를 `Page ID` 1순위로 **하드코딩**
하고 있었는데 VIOLA·BootFactory는 `Screen ID` 가 1순위다.

| **지금 규칙** | 분포 기준을 **사양의 실측 분포**로 이관하고 하드코딩 표는 사양 없을 때의 폴백으로 격하 |
| **재발 방지** | 리뷰에 분포 편차·열 오배치 점검 신설(**지배 구분 역전은 Critical**) |

같은 측정에서 나온 나머지 3건 — **비고 공란 212행(27.8%)**(근거 태그를 옆 열에 써서 생긴 **열
오배치**) · 미사용 컬럼 채움 69행 · 결합 규칙 위반 14행. **이 셋이 전부 기계 판정 가능한 항목이었고,
그 관찰이 2026-09-08 `verify_sheet_rows.py` 로 이어진다**(→ [6번](#6-검사기--자동-점검을-믿을-수-있게-만드는-조건)).

### 2-4. 컬럼을 늘렸다가 되돌린 일 — 2026-08-25 → 2026-09-02

관리 영역(VIOLA `K8s` / `CI·CD`)을 표현하려고 **`관리대상` 전용 컬럼(C)을 신설**해 23→24컬럼으로
갔다. C열 삽입이라 **기존 C~W 21개 컬럼이 D~X로 전부 한 칸씩 밀렸고, 하네스 11개 파일의 열 문자
참조 78건을 재매핑**해야 했다.

**2026-09-02에 폐지했다.** Phase 0에서 제품 유형을 받으므로 행마다 판정하는 컬럼이 중복이라는
판단이다. 구분은 **탭 분리 + `1 Depth`**(Breadcrumb 최상위 원문)로 표현되며, **한 탭에 두 영역을
섞지 않는 것이 전제**다.

**폐지의 부수 효과가 오히려 이득이었다** — 팀 VIOLA 원본 시트가 원래 23컬럼이어서 이제 일치하고,
"구 양식 탭 판정"(23 vs 24를 사용자에게 묻던 분기)도 함께 사라졌다.

> **남긴 규칙:** 스킬·에이전트에서는 **열 문자를 쓰지 않고 컬럼명(`비고`·`피드백`)으로만 지칭**한다.
> 제품마다 컬럼 수가 다르면 공용 문서에 열 문자를 박는 순간 한쪽이 반드시 틀린다. 열 문자는 사양
> 파일에만 둔다.

### 2-5. 실측 없는 프로파일은 실측 없다고 적는다 — 2026-09-02

`profile-bootfactory` 는 **팀 BF 시트를 측정한 적이 없다.** 실측 근거가 있는 것은 화면 ID
패턴(`BOOT-NN_NN_NN`, 6페이지) 하나뿐이고, `솔루션` 값 `BOOTFACTORY` 와 TC ID 코드 `BF` 는
**실측 근거 0건의 제안값**이다.

그 사실을 **파일 최상단 · `sheet-analyst` 산출물 · 사용자 문서 세 곳에 박았다.** 전 행에 박히는
상수라 나중에 바꾸려면 열 전체를 고쳐야 하기 때문이다. 리뷰에서 편차가 반복되면 **케이스가 아니라
프로파일이 틀린 것일 수 있다**는 경고도 함께 넣었다.

## 3. 변경분 판독 — 기획서의 무엇을 "변경"으로 볼 것인가

개정판 기획서에서 **변경된 것만** 케이스화하는 모드다. 이 하네스가 가장 많이 틀렸고 가장 많이
고친 영역이며, 실패의 형태가 매번 달랐다.

### 3-1. 표기 경로가 하나가 아니었다

| 경로 | 언제 알았나 | 무엇이 문제였나 |
|------|-----------|----------------|
| 빨간 박스 / `변경사항` 스티커 / DESC 빨간 텍스트 | 2026-08-21 | 최초 3중 표기로 정식 도입 |
| **파랑** | 2026-08-25 | 검출기가 **빨강 전용**이라 그대로 돌리면 **파랑 변경분이 통째로 누락**(실측: p10 파랑 후보 12건, p11은 변경 표기가 파랑뿐) |
| **취소선** | 2026-08-26 | 색 영역이 아니라 선 몇 픽셀이라 검출기에 **아예 나타나지 않는다**. 삭제 유형이 조용히 사라지는 구조였다 |
| **`ChangeLog` 패널** | 2026-08-27 | 페이지 우측 하단의 변경 내역 목록. 하네스의 시야에 없던 네 번째 경로 |

**색으로 변경 종류·회차를 추정하는 것은 금지**다. 실측 반례 — 같은 문서에서 p10은 빨강 `26.08.03` /
파랑 `26.08.18` 인데 **p11은 파랑이 `26.08.04`** 다. 권위는 주석 원문(`v2수정`/`v2추가`/`v2삭제` + 날짜).

색 검출로 안 잡히는 표기는 취소선 말고도 셋 더 있다 — ② **부분 토큰만 색칠**(줄 단위로 보면 검정이
대세라 놓친다) ③ **한 줄에 두 색 혼용** ④ **목록 번호 색 번짐**(빨간 항목 뒤 검정 항목의 번호만
빨강 → 변경분으로 세면 오탐).

### 3-2. `ChangeLog` 를 등재한 진짜 이유는 정반대 방향이었다 — 2026-08-27

> ⚠️ **최초 기록을 분석 담당이 반박해 정정했다.** 처음엔 "스티커 2건 vs `ChangeLog` 4건이라 스티커만
> 보면 2건 누락"으로 적었으나, 실제는 **분홍 스티커 2개가 각 2항목씩 담아 총 4항목**이라 **4 대 4,
> 누락 없음**이었다(스티커 *개수* 와 *항목 수* 를 혼동했다).

패널을 등재할 근거는 반대편에 있었다 — `ChangeLog` 배지가 `26.07.22 v1` 하나뿐이고 **같은 페이지의
v2 변경 9건이 전부 미등재**였다. 이 패널은 **작성 시점 회차까지만 반영된 스냅샷**이며 완전한 목록이
아니다. 그래서 규칙을 **양방향**으로 세웠다.

- **정방향** — 「`ChangeLog` ↔ CH-ID 대조표」로 커버리지 자기 점검(미커버는 Critical)
- **역방향** — 다른 경로에서 찾은 변경분이 `ChangeLog` 에 없으면 `[변경 표기 불일치]` 로 기록하되,
  **`ChangeLog` 에 없다는 이유로 변경분을 탈락시키지 않는다**(그랬다면 v2 9건이 사라진다)

### 3-3. 색 박스는 **범위를 확정하지 않는다** — 2026-09-02

| 칸 | 내용 |
|----|------|
| **무엇이 틀렸나** | 하네스가 **변경 표기 4경로를 대등하게** 취급했다. 박스는 *어디를 볼지* 알려주는 신호인데 *무엇이 바뀌었는지* 까지 확정하고 있었다. 사용자 지적: *"화면 테두리 빨강 박스를 변경으로 정의하는데 보통 화면 일부만 변경된다. 그런데 화면 전체가 케이스로 생성된다"* |
| **실측 근거** | Boot Factory 6페이지 실행에서 **전면 박스가 있는 두 화면이 전체 케이스의 69%(87/127건)**. 특히 권한 설정 팝업은 **스티커 9개가 개별 변경을 구체적으로 가리키고 있었는데도** 전면 박스를 근거로 팝업 전체가 케이스화돼 **58건** |
| **지금 규칙** | **박스 = 범위 후보(확정력 없음)** / **DESC 색 텍스트·취소선·스티커·`ChangeLog` = 항목 확정.** 박스가 화면 전면이어도 **그 안의 항목 근거가 가리키는 것만** 케이스가 된다. 박스만 있고 항목 근거가 0건이면 전수화하지 않고 **`[변경 범위 불명]`** 으로 확인을 요구 |
| **재발 방지** | 리뷰 양방향 — 범위 초과(Major)와 **신규 화면 전수를 범위 초과로 지적하는 역방향 오판 금지** |

예외는 **화면·팝업 자체가 신규**인 경우뿐이며, 그 판정 근거도 **박스가 아니라 스티커·`ChangeLog`
원문**이어야 한다 — **박스는 "전체 신규"와 "일부 수정"을 구분하지 못하기 때문**이다.

### 3-4. 취소선 = 삭제. 그리고 **의무만 있고 금지가 없었다** — 2026-09-02

| 칸 | 내용 |
|----|------|
| **무엇이 틀렸나** | 기존 규칙은 *"삭제 유형에 '더는 노출되지 않음' 검증을 만들어라"* 는 **생성 의무**뿐이고 **"삭제된 내용을 동작 케이스로 만들지 마라"는 금지가 없었다.** 의무만 있으면 **둘 다 만들어도 규칙 위반이 아니다** — 같은 항목에 상반된 두 케이스가 남는다. 리뷰도 미노출 검증이 **있는지**만 봤다 |
| **실측 근거** | 사용자 지적: *"기획서 취소선은 삭제된 것인데 작성된 케이스를 보면 취소선 내용도 테스트 케이스로 작성했다"* |
| **지금 규칙** | 취소선만으로 `삭제` 확정(주석 원문이 없어도). 허용되는 유일한 케이스는 **미노출·미호출·미잔존·미동작 검증**. 부분 취소선은 ①삭제 토큰 미잔존 ②새 토큰 표출 **두 개만** |
| **재발 방지** | 리뷰 **역방향 점검을 Critical** 로 신설 |

> **Critical인 이유:** 삭제된 기능을 테스트하라고 지시하면 실행자가 기획대로 사라진 것을 "안 된다"고
> 보고하게 되어 **케이스가 잘못된 결함을 생산한다. 누락보다 해롭다.**

### 3-5. 검출기의 "0건"은 "없음"이 아니다 — 2026-08-26 → 2026-09-02

취소선을 찾을 기계적 수단이 아예 없어 **`detect_strikethrough.py`** 를 신설했다(2026-08-26).
취소선의 **기하학적 정의**로 검출한다 — 두께 ≤ N px 수평 런 중 **위·아래 밴드 양쪽에 글자 잉크가
있는 것**(이 조건이 밑줄·구분선·표 괘선과 취소선을 가른다).

설계에 실측 두 개를 박았다:

- **`--min-len` 은 문서 글자 폭으로 정한다.** 한글 가로획(`ㅗ` `ㅍ` `ㅌ` `ㅡ`)이 그 자체로 짧은
  수평선이라, 임계값이 글자 폭보다 작으면 **글자획이 통째로 후보**가 된다(150 DPI 렌더 본문 1자 폭
  **40~42px** → 기본 70px)
- **양성 대조 의무화.** 취소선이 실재하는 페이지로 먼저 검증해야 "0건"이 *취소선 없음* 을 뜻한다

이 규칙이 실제로 값을 했다 — p10에서 **62px 간격 7줄 연속 파란 런**을 재현해 검출기 유효성을 세운 뒤
p2~p8을 훑어 0건을 확인했고, 덕분에 앞선 챕터들의 "삭제 0건"이 누락이 아니라 사실임을 근거 있게
판정할 수 있었다.

**그런데 그 규칙에도 빈틈이 있었다**(2026-09-02). 기존 문구는 *"양성 대조 없는 0건은 임계값 불일치일
수 있다"* 여서 **대조를 거치면 0건을 믿어도 된다는 함의**를 남겼다. Boot Factory 실행에서 그대로
터졌다:

| | 내용 |
|---|---|
| **한 일** | p5 DESC의 **610px 런**으로 양성 대조를 통과시켜 `--min-len=110` 을 세우고, "p1·p3의 0건은 취소선 없음으로 신뢰할 수 있다"고 보고 |
| **실제** | p3에 `` 솔루션 ``~~`멤버`~~`` 관리자 `` 라는 **2글자(~80px) 취소선이 실재**했다. 분석 담당이 DESC 전문 육안 재판독으로만 찾아내 살렸다 |
| **왜** | **대조가 증명하는 것은 "그 길이대의 취소선을 잡는다"뿐**이다. 대조 대상이 문장 전체를 긋는 긴 런이면 **부분 취소선은 구조적으로 임계값 아래로 떨어진다** |
| **규모** | 부분 취소선은 *수정* 변경에 동반되므로 삭제만큼 흔하다 — 이번 실측 **완전 삭제 6건 vs 부분 취소선 6 CH-ID** |

**지금 규칙: 검출 0건인 페이지도 DESC 전문을 육안으로 다시 읽는다.**

### 3-6. 함께 고친 검출기 버그 — 2026-08-25

변경 박스(높이가 글자의 수십 배)가 block 병합에서 주변 텍스트를 연쇄로 삼켜 **페이지 하나가
5646×3994 단일 영역으로 붕괴**했다(후보 1개 = 판독 정보 0). 높이 중앙값의 6배를 넘는 영역을
"구조물"로 보고 병합에서 제외하니 같은 페이지가 **28개 후보로 분해**됐다. 글자 조각 병합(162→5)
동작은 유지.

### 3-7. 대상 회차는 좁히지 않는다 — 2026-09-02 (결정 기록)

Boot Factory p6 한 페이지에 **회차가 5개** 누적돼 있었고 하네스는 이 전부를 변경분으로 취급한다.
"최신 회차만 / 특정 날짜 이후만"으로 좁히는 선택지를 제시했으나 사용자가 **문서에 표기된 모든
변경**을 택했다. 회차 필터는 넣지 않는다 — 이후 요청이 오면 Phase 0에 「대상 회차」 항목을 추가하는
것이 도입 경로다.

| 규칙 | 날짜 | 무엇이 틀렸나 → 지금 규칙 |

### 4-2. 정책 예외 — 문서 하나에 정책 하나가 아니다 — 2026-09-02

지금까지는 **문서 하나에 정책 하나**였다(전체 분석이거나 변경분 한정이거나). 실제 기획서는 그렇지
않다 — 개정판 안에 신규 화면이 섞이고, 신규 문서 안에도 변경 표기가 붙은 화면이 있다. 그런 화면은
**기본 정책으로 처리하면 반드시 틀린다.**

| 상황 | 기본 정책대로 하면 |
|------|------------------|
| `변경` 문서의 신규 화면 | 변경분만 뽑으면 그 화면 케이스가 거의 빈다 |
| `신규` 문서의 변경 화면 | 전수로 뽑으면 변경 근거 태그가 사라져 역추적이 끊긴다 |

**핵심은 예외 적용 시점을 분석 단계로 잡은 것이다** — 생성 단계에서 거르면, 기본이 `변경` 인 문서의
예외 화면은 **전수 분석 근거가 분석서에 아예 없어** 후속 단계가 복구할 방법이 없다.

리뷰는 **양방향**이다 — 정방향은 예외 화면이 실제로 반대 정책인가, 역방향은 **예외 목록에 없는
화면이 반대 정책으로 작성되지 않았는가**(범위 초과). **예외 화면이 기본과 다른 것을 결함으로
지적하는 것이 이 리뷰의 새 오판이다.**

### 5-3. 브리핑은 요약이 아니라 발췌다 — 2026-09-08

`build_brief.py` 는 사양에서 역할에 필요한 절만 골라 브리핑을 만든다. **요약하지 않고 원문을
발췌한다** — 요약본은 규칙을 조용히 빠뜨리고, 빠진 규칙은 전 행에 번진다.

**핵심 안전장치는 `--coverage-check`** — 사양의 모든 절이 어느 역할엔가 배정됐는지 검사해 미배정이면
실패한다. 배정되지 않은 절은 **어느 브리핑에도 들어가지 않아 조용히 사라지므로**, 절을 추가한 사람이
역할을 결정하게 강제했다. 도입 즉시 값을 했다 — **17개 미배정과 유령 배정 2개**를 잡았다.

> 브리핑에 없는 규칙이 필요하면 원천 사양을 직접 열어도 된다. **기본 로드를 줄이는 장치이지 접근을
> 막는 장치가 아니다.**

## 6. 검사기 — 자동 점검을 믿을 수 있게 만드는 조건

이 하네스에는 검사 스크립트가 셋 있다(`verify_sheet_rows.py` · `verify_unit_migration.sh` ·

### 6-1. 규칙을 스크립트에 박지 않는다 — 2026-09-08

`verify_sheet_rows.py` 는 헤더 원문·23컬럼·열 오염·enum·결합 규칙·TC ID·중복·`No` 연속성·`-` vs
빈칸·절차 접두·문체(백틱↔대괄호)·셀 내 파이프를 **전수 판정**한다.

**설계의 핵심은 규칙을 사양에서 파싱하는 것이다.** 값을 스크립트에 박으면 **2026-08-24 분포
하드코딩 사고(TROMBONE `정상` −44.9%p)를 형태만 바꿔 재현**한다. 그래서 `common.md` 의 컬럼 표·헤더
원문·enum 절과 프로파일의 고유값 표를 직접 읽고, **파싱 실패 시 하드코딩 폴백 없이 종료 코드 `3`**
으로 실패한다 — **낡은 값으로 조용히 채점하는 것이 검사를 안 하는 것보다 해롭다.**

개발 중 파서 버그 3개가 자기검증에 걸렸다:

| # | 버그 | 증상 |
|---|------|------|
| ① | 「허용 목록. **금지 목록**」 한 줄 표기 | **금지 값(`P0`·`High`)이 허용 enum에 섞임** |
| ② | `(**L·M**)` 의 강조 기호 | `5 Depth`·`Jira` 열이 **누락** |
| ③ | 결합 규칙에 실측 마커(`예외 0건`)를 요구 | VIOLA 승계인 `profile-bootfactory` 의 규칙이 **전부 무시** — 절대 표현 자체가 규칙이고 마커는 근거일 뿐이다 |

### 6-2. 오탐을 내는 검사기는 무시당해 검사 자체가 무력해진다

같은 판단으로 **세 번** 고쳤다.

| 날짜 | 오탐 | 원인 |
|------|------|------|
| 2026-09-08 | 셀 내 파이프 | **백틱 인용 안의 파이프는 정당한 UI 라벨**이다(사이드바 접기 아이콘 `` `|<` ``) |
| 2026-09-11 | `TC ID` 자리수 — **정상 행 97건이 전부 Major** | 사양은 `{3자리}` **예외 0건**으로 적혀 있었고 측정 시점엔 사실이었으나, 그 뒤 번호가 999를 넘겼다(실측 **3자리 999행 · 4자리 1,125행**). **자리수는 최소 폭이고 소진은 정상 증가**인데 고정폭으로 검사했다 |
| 2026-09-11 | `--diff` 가 `.tsv` 헤더를 데이터로 셈 | **두 파이프라인의 관행이 갈렸다** — `03_rows_s{NN}.tsv` 는 「헤더 없음」, `13_rows_*.tsv` 는 「1행은 헤더 원문」. **문서대로 따르면 반드시 오탐이 나는 상태**였다 |

`TC ID` 건에서는 **VIOLA 프로파일만 고쳤다** — TROMBONE·BootFactory는 같은 잠재 문제를 갖지만
**실측 근거가 없어 손대지 않았다.** 근거 없이 느슨하게 하면 진짜 위반을 놓친다.

### 6-3. 통과만 확인하면 아무것도 확인하지 않은 것이다

- **`--selftest`** — 심어 둔 위반 17종 검출 + **정상 행 오탐 0건**을 함께 확인한다. 통과만 보면
  **파서가 빈 규칙을 돌려줘도 전 행이 "위반 0건"으로 통과**한다
- **음성 대조** — 2026-09-11에는 옛 사양 사본으로 돌려 **가드가 실제로 회귀를 잡는지** 확인했다.
  2026-09-15 문서 가드도 위반 4종을 주입해 같은 확인을 했다
- **필수 인자로 승격** — 자기검증이 함수를 직접 호출하면 **호출부가 인자를 빠뜨리는 회귀는 잡지
  못한다.** `header` 를 필수 인자로 만들어 누락 시 `TypeError` 로 즉시 터지게 했다

### 6-4. 이름이 둘 다 실재하면 코드 검색으로는 못 잡는다 — 2026-08-31

`sheet-operator` SKILL이 **한 파일 안에서 두 이름을 섞어** 썼다 — 실제 CLI 하위 명령은 **`metadata`**
인데 일부가 `get_metadata` 로 적혀 있었다. **두 이름이 모두 실재하는 것이 함정의 핵심이다** —
`get_metadata` 는 `SheetsClient.get_metadata()` 라는 **Python 메서드 이름**이라 코드 검색으로는
"있다"고 확인되지만 CLI에는 없다. 그래서 이름을 지우지 않고 **호출 방식별 대조표**(셸=`metadata` /
Python=`get_metadata()`)로 갈라 적었다.

## 7. 되돌린 결정과 반복된 실패 패턴

### 7-1. 두 번째 원천 — 기획서가 닿지 않는 영역 — 2026-09-10

하네스의 원천이 기획서 하나여서 **구조적으로 닿지 않는 영역이 둘** 있었다.

| 영역 | 왜 닿지 않았나 |
|------|---------------|
| **예외 흐름** | 기획서는 정상 흐름을 서술한다. 필수값 미입력·형식 위반·중복·서버 오류·동시성 충돌은 **항목으로 존재하지 않는데**, 하네스는 기획서에 없는 것을 단정하지 않는 규칙을 지키므로 이 영역이 통째로 비었다 |
| **권한별 동작** | 역할마다 같은 기능이 다르게 동작하지만 그 매핑은 기획서가 아니라 **별도 권한 자료**에 있고, 하네스에 읽는 경로가 없었다 |

**이미 작성된 테스트 케이스를 원천으로 삼으면 닿는다** — 기존 케이스에 기능 단위(`화면 ID`·Depth)·
절차·제품 유형(`솔루션`)·커버리지 현황(`구분`)이 다 들어 있다.

**`testcase-auto` 에 모드를 얹지 않고 분리한 이유**는 그쪽 Phase 0 질문 5개가 하나도 그대로 쓰이지
않고(제품 유형은 실측 판정, 기획서 유형·정책 예외는 개념 자체가 없음) Phase 1의 이미지 변환·판독
게이트·변경 표시 검출도 전부 무관해, 한 파일에 넣으면 거의 모든 절에 `if 작업 유형` 분기가 붙어
**두 경로가 함께 무거워지기** 때문이다.

**가장 중요한 설계 결정: 파생 케이스는 분포 편차 점검의 대상이 아니다.**

> 예외 파생은 정의상 `비정상`·`엣지` 만, 권한 파생은 `정상`·`부수` 만 만든다. 어느 프로파일로
> 채점해도 **지배 구분 역전이 반드시 뜬다**(VIOLA `표시` 55.9% / TROMBONE `정상` 65.1%).
> 2026-08-24에 지배 구분 역전을 Critical로 규정한 것은 **기획서 전수 케이스화를 전제한 판정**이라,
> 그대로 적용하면 *"그 작업이 만들라고 한 것을 만들지 말라"* 는 리뷰가 되어 재작업 루프에 빠진다.
> → 사양·리뷰어 SKILL·참조 문서 **세 곳**에 제외를 박고, 완전성 지표를 **예외 카탈로그 커버리지 /
> 매트릭스 셀 커버리지**로 대체했다.

그 밖에 정한 것: 원본 TC 읽기는 **스크립트가 한다**(수백~수천 행을 에이전트에게 읽히면 5번의 비용
구조가 재발한다) · **파생 태그가 붙은 행은 다음 실행에서 원본이 되지 않는다**(원본 탭과 대상 탭이
같을 수 있어, 빼지 않으면 **파생의 파생**이 생긴다) · 제품 유형은 `솔루션` 컬럼 **실측**으로
판정(추정이 아니므로 Phase 0 「추정 금지」와 충돌하지 않는다) · 권한값 enum을 하네스가 정하지 않고
**자료에서 실측**한다 · 예상 결과는 **동작 수준까지만** 쓰고 문구·코드·지연 시간은 `[기획 확인]` 으로
넘긴다(단정하면 실행자가 잘못된 FAIL을 낸다).

**범위 입력이 처음부터 빠져 있었다**(2026-09-11 정정). 브레인스토밍에서 합의한 `범위` 항목이
**설계 스펙에 적히지 않았고**, 이후 계획·구현은 **스펙을 충실히 따랐기 때문에** 끝까지 빠진 채로
내려갔다. 구현 중 스펙을 대조했지만 「스펙에 있는 것이 구현됐는가」만 봤고 **「합의한 것이 스펙에
있는가」는 보지 않았다** — 이것이 원인이다.

그 설계의 핵심은 **필터를 에이전트가 아니라 스크립트에 둔 것**이다 — **범위 밖 행의 `기능테스트 ID`
도 번호 실측에는 세야 한다.** 범위는 *무엇을 뒤집을지* 를 정하고 TC ID는 탭 전역에서 유일해야 하므로,
빼면 다음 번호가 이미 쓰인 값과 겹친다(실측: 범위를 화면 1개로 좁혀 원본 1행만 남았는데도 다음
번호는 범위 밖을 센 `TC_VIO_010`. 뺐다면 `TC_VIO_004` 를 발급해 충돌). 오타는 **Critical + 종료 코드
`2` 로 멈춘다** — 원본에 없는 화면 ID가 내는 조용한 0건은 *"그 화면엔 만들 게 없다"* 와 구별되지
않는다.

### 7-3. 반복된 실패 패턴 6종

주제를 가로질러 **같은 형태의 실패가 반복**됐다. 새 규칙을 만들 때 이 여섯 개를 먼저 확인하면 된다.

**① 하드코딩된 값이 제품·문서와 무관하게 적용된다**
분포 권장 개수(VIOLA 값이 TROMBONE에 적용 → `정상` −44.9%p) · 화면 ID 필드 우선순위(`Page ID` 고정) ·
TC ID 자리수(정상 행 97건 오탐) · 취소선 임계값(문서 글자 폭과 무관하면 글자획이 후보가 된다).
→ **값은 사양에서 읽고, 파싱 실패 시 폴백 없이 실패한다.**

**② 사양보다 관행이 앞서 리뷰가 무한 왕복한다**
스킬은 태그를 **요구**하는데 사양 태그표에 없어, 리뷰가 매번 "사양 미등재"로 지적하는 왕복이
**두 번**(2026-08-25 `[DESC 전용]` 등 3종, 2026-08-26 경로 병기 태그) 생겼다. 실측으로는 `01` 탭에
`[DESC 전용]` 39건이 이미 쓰여 있었다 — 관행이 사양보다 앞서 있었다.
→ **태그를 금지하는 게 아니라 사양을 스킬에 맞춰 올린다.**

**③ 검출기의 0건을 "없음"으로 읽는다**
취소선 0건(2글자 80px 실측) · 색 검출로 안 잡히는 표기 4종 · `ChangeLog` 미등재(v2 9건).
→ **0건은 "그 조건으로 못 찾았다"이지 "없다"가 아니다. 육안 재판독을 의무로 둔다.**

**④ 복제본이 원본과 갈라진다**
`HARNESS_SETUP_PROMPT.md` 의 `.claude/` 정의 복제본(1,400여 줄이 챕터 단위·폐지 컬럼·옛 `CLAUDE.md`
를 담은 채 드리프트) · 요약본 `HARNESS_SUMMARY.md`(둘 다 2026-09-15 폐지).
→ **단일 출처를 정하고 복제본을 만들지 않는다.**

**⑤ 의무만 있고 금지가 없다**
"삭제 항목에 미노출 검증을 만들어라"는 있었지만 "삭제된 내용을 동작 케이스로 만들지 마라"가 없어
**둘 다 만들어도 규칙 위반이 아니었다.**
→ **규칙을 쓸 때 반대 방향도 함께 쓴다.**

**⑥ 리뷰의 역방향 오판이 재작업 루프를 만든다**
반대쪽 관리대상 케이스 부재를 누락으로 지적 · 신규 화면 전수를 범위 초과로 지적 · 파생 케이스의
분포 편차 지적 · 제외 유형 0건을 커버리지 부족으로 지적 · 범위 밖 화면의 케이스 부재를 누락으로 지적 ·
폐지된 자기점검 서술의 부재를 누락으로 지적.
→ **점검을 신설할 때 그 점검이 낼 수 있는 오판을 같이 명문화한다.** 이 하네스에서 리뷰 규칙은
거의 항상 **양방향**으로 쓰여 있다.
