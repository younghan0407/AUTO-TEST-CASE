## 무엇을 하는가

**기획서를 읽고 테스트 케이스를 써서 구글 시트에 넣는다.**

QA가 기획서를 한 화면씩 읽어가며 케이스를 손으로 적던 일을 대신한다. 어려움은 양이 아니라
**일관성**에 있었다 — 사람마다 케이스를 자르는 단위가 다르고, 팀 시트의 컬럼 순서·허용값·문체
컨벤션은 문서화된 적 없이 기존 행에만 남아 있었다.

| | |
|---|---|
| 지원 제품 | **4종** — VIOLA K8s · VIOLA CI/CD · TROMBONE · BootFactory |
| 처리 단위 | **화면 1개** — 분석부터 시트 작성까지 끝내고 다음 화면으로 |
| 결과물 | 구글 시트 **23컬럼** 행 |
| 사람이 개입하는 지점 | **3곳** (우회 불가) |
| 양식의 근거 | 팀 시트 **4,284행 전수 실측** (VIOLA 331 · TROMBONE 3,953) |

**케이스를 만들지 않는 절차도 하나 있다.** 같은 기획서를 읽어 **기능 목록**과 **신규·변경·삭제
판정**을 문서 2개로 내는 「기획서 분석」이다(지원 제품 2종 — VIOLA K8s · VIOLA CI/CD).
케이스를 만들기 전에 **범위와 규모를 먼저 잡는 자리**이고, 기획 리뷰에서 정의가 빠진 항목을
찾는 데도 쓴다. 산출물은 시트가 아니라 사람이 읽는 문서라 **아래 검증 커버리지의 대상이 아니다** —
다음 절 첫 문단이 그 이유다.

## 1. 구성

세 층으로 나뉜다. **담당끼리 대화하지 않고 파일로 주고받는다** — 그래서 중간에 멈춰도 그 지점부터
이어서 할 수 있다.

```
  ┌─ 규칙 ────────────────────────────────────────────┐
  │  무엇을 어떻게 판정할지의 기준                        │
  │  · 기획서 기반 생성   · 추가 작업(예외·권한)          │
  │  · 팀 양식 사양 — 공통 골격 + 제품별 프로파일          │
  └───────────────────────────────────────────────────┘
                        ↓ 읽는다
  ┌─ 담당 ────────────────────────────────────────────┐
  │  기획서 분석 · 양식 대조 · 케이스 작성 · 검사 · 파생   │
  │  단계마다 다른 모델 — 놓치면 복구 못 하는 단계에 집중   │
  └───────────────────────────────────────────────────┘
                        ↓ 호출한다
  ┌─ 도구 ────────────────────────────────────────────┐
  │  기획서 판독 · 변경 표기 검출 · 시트 입출력            │
  │  · 작성 결과 전수 점검   · 문서 회귀 가드             │
  └───────────────────────────────────────────────────┘
```

## 2. 검증 커버리지 — 이 케이스들로 어디까지 확인되는가

### 먼저, 분모

"제품의 몇 %"라고 말하려면 무엇 대비인지가 필요한데, **이 하네스의 분모는 제품이 아니라 기획서다.**

| 낼 수 있는 지표 | 낼 수 없는 지표 |
|----------------|----------------|
| 기획서 Description 커버리지 · 예외 카탈로그 커버리지 · 권한 매트릭스 셀 커버리지 | **제품 기능 대비 %** · 코드 커버리지 |

> **"기획서에 적힌 것은 빠짐없이 케이스화했다"는 말할 수 있고, "제품의 N%가 검증된다"는 말할 수 없다.**

**기능 목록이 생겼다고 이 분모가 바뀌지는 않는다.** 「기획서 분석」 절차가 내는 기능 목록은
**기획서에 실린 기능의 목록**이지 제품이 가진 기능의 목록이 아니다. 기획서에 없는 레거시·
미갱신분은 그 목록에도 없으므로, 이 문서를 분모로 삼아 "기능 N개 중 M개 검증"이라고 말하면
**빠진 것을 세지 않은 비율**이 된다. 이 절차가 커버리지에 기여하는 것은 **분자 쪽** —
기획서에 실린 것 중 무엇을 아직 케이스화하지 않았는지 보이게 하는 것 — 뿐이다.

### 축별 커버리지

**●** 덮는다 **◐** 부분 **○** 공백

| 검증 축 | | 상태의 근거 |
|---------|:--:|-------------|
| 기획서에 정의된 기능 | ● | Description **전수 케이스화**가 규칙. 누락은 검사가 Critical로 잡는다 |
| UI 표시·표출 | ● | 요소 단위로 잘게 검증 (VIOLA 실측 `표시` **55.9%**) |
| 정상 동작 흐름 | ● | TROMBONE 실측 `정상` **65.1%** |
| 화면 전환·인터랙션 | ● | 액션 버튼 → 이동·모달·취소·진행이 자동 도출 |
| 표시 형식 규약 | ● | 일시 형식, 빈 값 `-`, 상태 값 전수 노출 — 자동 도출 |
| 권한별 동작 | ● | 역할 × 기능 **전수 매트릭스** (권한 자료가 있을 때) |
| 비정상 입력 | ◐ | 기획서 기반만으로는 얇다(실측 5~9%). 추가 작업이 메우되 카탈로그 **8/12** |
| 데이터 상태 조합 | ◐ | 0건·1건·대량은 덮는다. **권한 × 상태 × 데이터 조합 폭발은 전수 아님** |
| 동시성 | ◐ | 두 사용자 동시 수정만 |
| 다단계 여정(E2E) | ◐ | **한 케이스 = 한 검증**이 원칙이라, 여러 기능을 가로지르는 흐름은 케이스로 없다 |
| 회귀 | ◐ | 변경분 모드는 **그 회차만**. 누적 세트는 탭이 쌓이며 형성된다 |
| 서버·네트워크 오류 (5xx·타임아웃) | ○ | **팀 방침** — 예외 사항 TC에서 받지 않기로 함 |
| 중단·이탈 (취소·뒤로가기·새로고침) | ○ | **팀 방침** |
| 경계값 (범위 밖·최대±1) | ○ | **팀 방침** |
| 반복 동시 조작 (연속 2회 클릭) | ○ | **팀 방침** |
| 기획서 밖 기능 (레거시·미갱신분) | ○ | **원천이 기획서다** |
| 성능·부하 / 보안 / 호환성 / 접근성 | ○ | **도구 범위 밖** |
| 실제 실행과 `PASS`/`FAIL` 판정 | ○ | **도구 범위 밖** — 케이스를 작성할 뿐이다 |

> **공백에는 두 종류가 있다.** *팀 방침*은 팀이 받지 않기로 **결정한** 영역이고(카탈로그를 고치면
> 바뀐다), *도구 범위 밖*은 이 하네스가 애초에 하지 않는 일이다. 둘 다 검증되지 않는다는 점은
> 같지만, 되돌릴 수 있는 쪽과 없는 쪽이 다르다.

### 구조적 공백 넷

**① 분모가 기획서다.** 기획서에 없는 기능은 커버리지에 잡히지도 않는다. **기획서 품질이 곧 커버리지 상한이다.**

**② 팀이 뺀 네 영역은 그대로 공백으로 남는다.** 제외는 결함이 아니라 결정이다. 다만 서버 오류·중단 이탈·경계값은 **실제 결함이 잘 나오는 영역**이라, "안 만든다"와 "안 봐도 된다"는 다르다.

**③ 한 케이스 = 한 검증의 대가.** 실패 원인 추적과 팀 공동 작성에는 유리하지만, **여러 기능을 가로지르는 시나리오 결함은 이 세트로 잡히지 않는다.**

**④ 작성 커버리지 ≠ 실행 커버리지.** 케이스를 만들 뿐 돌리지 않는다. **만들어 두고 실행하지 않으면 검증된 것은 0이다.**

> **한 줄로 —** 기획서에 적힌 것은 빠짐없이, 기획서에 없는 예외와 권한은 카탈로그와 매트릭스만큼,
> 성능·보안·E2E·실행은 사람 몫.

## 3. 동작 방식

화면 하나를 끝내고 다음으로 간다. **시트 쓰기가 반복 구간 안에 있어** 진행 중에도 결과가 시트에 쌓인다.

```
  ◆            ◆                                      ◆
  기본 정보  →  준비  →  범위 확정  →  ┌ 분석 → 작성·시트 → 검사 ┐ →  집계
   확인         판독      화면 목록     └───── 화면마다 반복 ─────┘     보고
                                              ◆ 첫 화면만

  ◆ = 사람의 확인 없이 지나가지 않는 지점 (3곳)
```

| 지점 | 사람이 정하는 것 | 시간 |
|------|----------------|------|
| ◆ 시작 | 제품 · 기획서 유형 · 대상 시트와 탭. 하나라도 미정이면 진행하지 않는다 | 1분 |
| ◆ 범위 확정 | 화면 목록과 예상 규모 확인. **범위를 줄일 수 있는 자리** | 2~3분 |
| ◆ 첫 화면 | **시트를 열어** 문체·기준 확인. 이후 전체에 적용된다 | 5~10분 |
| 이후 | 자동 진행 | 화면 수에 비례 |

**이 세 곳이 통제점이다.** 결과물 전체의 방향이 여기서 정해지고, 이후는 그 기준이 반복 적용된다.
기획서에 없는 내용은 단정하지 않고 **"기획 확인 필요"로 분리 보고**하므로, 그 항목도 사람에게 돌아온다.

## 4. 품질을 무엇으로 담보하는가

**① 양식이 실측에서 나왔다.** 팀이 이미 써 둔 시트 4,284행을 전수로 세어 컬럼 순서·허용값·문체·
비율을 사양 파일로 만들었다. 기존 케이스와 섞여도 이질감이 없다.

**② 점검이 사람 주의력에 의존하지 않는다.** 판단할 값이 없는 항목(컬럼 수, 허용값, 번호 연속성,
문체 규칙, 시트에 제대로 들어갔는지)은 **전 행을 프로그램이 판정한다.** 사람이 하던 시절
**212행이 엉뚱한 칸에 들어가 있는 것**을 뒤늦게 발견한 적이 있어 내린 조치다.

**③ 규칙이 실패에서 역산됐다.** 지금 규칙의 대부분은 실제로 뭔가를 놓친 뒤에 생겼고, 같은 실패가
되돌아오지 못하도록 **자동 검사**로 고정돼 있다. 경위는 [docs/DESIGN_DECISIONS.md](DESIGN_DECISIONS.md) 에 주제별로 정리돼 있다.
