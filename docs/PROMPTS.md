# 프롬프트 가이드

이 하네스에 무엇을 어떻게 요청하면 좋은 테스트 케이스가 나오는지 정리한 문서.
세팅 절차는 [SETUP.md](../SETUP.md) 를 먼저 보세요.

## 요청 전 확인

| 항목 | 확인 |
|------|------|
| 세팅 | `python3 verify_setup.py "<대상 시트 URL>"` 실행해서 실패 0 |
| 실행 위치 | 저장소 폴더 안에서 Claude Code 실행 (밖에서 실행하면 스킬이 인식되지 않음) |
| 시트 공유 | 대상 시트에 서비스 계정을 **편집자**로 공유 |
| 양식 | `.claude/formats/` 의 **제품별 사양**이 기준 (`team-viola`, `team-trombone`). **참고 시트 URL은 필요 없음** |
| 제품 | 대상 시트의 솔루션 컬럼으로 사양이 자동 판정된다. 빈 시트면 `양식: team-트롬본` 처럼 명시 |

## 1. 최소 프롬프트

이것만으로도 동작한다. 빠진 정보는 하네스가 물어본다.

```
이 기획서로 테스트 케이스 만들어줘.
기획서: ./PRD/화면정의서_v1.pdf
대상 시트: https://docs.google.com/spreadsheets/d/<시트ID>/edit
```

기본값: 생성 모드 `atomic`, 분석 방식 `전체`, 범위 `전체 챕터`.

VIOLA는 관리대상(`K8s`/`CI·CD`)이 갈리므로 아는 경우 한 줄 더하면 판정 단계가 줄어든다 — `제품명: VIOLA V4.0 / k8s` (7절).

## 2. 첫 실행용

첫 실행은 **범위를 좁히고 되돌릴 수 있는 곳에 쓰는 것**이 핵심이다.
전체를 돌리면 케이스가 수백 건 나오는데, 방향이 틀렸으면 전부 다시 해야 한다.

```
테스트 케이스 자동 생성해줘.

[기획서]
./PRD/화면정의서_v1.pdf

[대상 시트]
https://docs.google.com/spreadsheets/d/<시트ID>/edit
대상 탭: 새 탭으로 만들어줘 (탭 이름: 테스트_초안_260824)

[옵션]
- 제품명: VIOLA V4.0 / k8s        ← 관리대상이 갈리는 제품만 (7절)
- 생성 모드: atomic
- 분석 방식: 전체
- 범위: 첫 번째 챕터만 먼저 해줘. 결과 보고 나머지 진행 여부 정할게
```

첫 실행은 **팀 공용 시트에 직접 쓰지 말고** 사본이나 새 탭에 쓰는 것을 권한다.
결과가 마음에 안 들면 탭만 지우면 된다.

## 3. 품질 최우선

```
테스트 케이스 만들어줘.

[기획서]
./PRD/화면정의서_v1.pdf
- 화면 식별자는 스펙 페이지 우측 상단 `<실제 필드명>` 필드에 있어 (`<실제 값 예시>` 형식)
- 스펙 페이지는 좌측 UI + 우측 Description 패널 구조야

[대상 시트]
https://docs.google.com/spreadsheets/d/<시트ID>/edit
대상 탭: 새 탭 (01_챕터명)
(빈 시트면) 양식: team-viola   ← 또는 team-trombone

[범위]
챕터 1만 먼저. 결과 확인하고 나머지 진행 여부 정할게.

[품질 기준]
- Description 항목은 전수 케이스화. 번호(❶-1-a)까지 비고에 출처로 남겨줘
- 테이블·상태값·일시·버튼이 나오면 표시 형식 검증 케이스를 자동 도출해줘
- 기획서에 정의 없는 항목은 추측하지 말고 "기획 확인 필요"로 따로 모아줘
- 리뷰까지 하고, Critical 남으면 시트에 쓰지 말고 먼저 알려줘
```

> **`<실제 필드명>` 은 반드시 기획서를 열어 확인하세요.** 제품마다 다릅니다 —
> TROMBONE은 `Page ID`(`ADM-GEN-0101-01`), VIOLA는 `Screen ID`(`VIOE-02_01_01-11`) 입니다.
> 다른 제품 값을 그대로 복사하면 화면 ID 컬럼이 비거나 잘못 채워집니다.

### 각 줄의 근거

프롬프트에 넣는 이유는 "하네스가 안 하니까"가 아니라 **실제로 놓친 전례가 있어서**다.
근거는 `CLAUDE.md` 변경 이력에 있다.

| 프롬프트 줄 | 막는 실패 | 이력 |
|---|---|---|
| 화면 식별자 필드명 알려주기 | 화면 ID 컬럼 미기입·형식 뒤틀림 | `2026-08-21` — 어떤 기획서는 `Page ID`, 어떤 기획서는 `Screen ID`다. 잘못 알려주면 매핑 실패 |
| Description 전수 + 번호 출처 | Description 누락 다수 | `2026-06-09` — 샘플링 리뷰 결과 Description 누락 다수 발견 |
| 표시 형식 검증 자동 도출 | 컬럼 순서·enum·일시 형식 케이스 통째 누락 | `2026-05-13` — 비교 결과 **Critical 누락 7건** |
| 추측 금지 + 확인 필요 분리 | 기획 미정의 항목을 단정해 실행자가 잘못된 FAIL 기록 | `2026-08-24` — 예상 결과 단정 + `[확인 불가]` 자기모순 4건 |
| 챕터 1개로 범위 축소 | 방향 틀린 케이스를 수백 건 쓴 뒤 발견 | `2026-06-11` — 전체 일괄 처리의 품질 문제로 챕터 순차 처리 전환 |
| Critical 시 쓰기 전 보고 | 리뷰가 잡았는데 이미 시트에 들어간 상태 | 기본은 재작성 1회 루프 후 진행 |

## 4. 확인 게이트 2곳

진행 중 두 지점에서 멈춘다. **여기서 무엇을 지시하느냐가 나머지 챕터 전체 품질을 결정한다.**

### ① 챕터 목록 확인

```
챕터 1: p3 ~ p15   "빌드배포 > 01. 파이프라인 관리"
챕터 2: p16 ~ p27  "빌드배포 > 02. 배포 이력"
```

볼 것: **페이지 범위 경계.** 간지(챕터 구분 슬라이드)가 없는 기획서는 구분이 엉뚱하게 잡힌다.

```
챕터 2 시작을 p18로 바꿔줘
챕터 3과 4를 합쳐줘
```

### ② 첫 챕터 케이스 검토 (시트 쓰기 **전**)

`_workspace/03_testcases_ch01.md` 를 보여준다. 볼 것:

| 항목 | 기준 |
|------|------|
| **케이스 단위** | 한 케이스 = 한 검증 (컬럼 1개, 클릭 1회). 절차 1~2단계, 예상 결과 1~2줄 |
| **지배 구분 비중** | **사양의 "구분(H)" 절에 적힌 지배 구분과 비교한다.** 제품마다 다르다 — VIOLA는 `표시` 과반(56%), TROMBONE은 `정상` 과반(65%). 지배 구분이 적으면 커버리지 부족 신호 |
| **P4 존재** | 취소·비활성·권한 없음 케이스가 `부수`+`P4`로 있는지 (두 사양 모두 `부수`→`P4` 100%) |
| **UI 라벨 표기** | 사양의 표기 컨벤션과 일치하는지 — VIOLA는 백틱, TROMBONE은 대괄호 `[등록]` |
| **화면 ID** | 기획서 원문 표기 그대로인지 (구분자 임의 통일 금지) |
| **비고 컬럼** | `[DESC 2항-1]` 같은 근거 태그가 있는지. 없으면 역추적 불가 |
| **사전조건** | 화면 상황이 구분되는지 (데이터 유무, 권한 등) |

교정 프롬프트 예시:

```
케이스 검토했어. 아래대로 고치고 나머지 챕터도 같은 기준으로 진행해줘.

- 케이스 단위: <TC-ID>는 검증이 2개 묶여 있어. 쪼개줘
- 표시 형식: 목록 화면 컬럼별 정렬 케이스가 빠졌어. 정렬 가능 컬럼마다 하나씩 추가
- 구분 분포: 사양의 지배 구분 비중과 비교해서 부족한 쪽을 더 쪼개줘
- P4: 모달 취소·권한 없음 닫기 케이스가 없어. `부수`+P4로 추가
- 사전조건: "목록 화면 진입"만으로는 상황 구분이 안 되는 케이스가 있어. 데이터 유무 조건 명시
```

> **지배 구분 비중과 P4 존재 여부가 품질 점검의 가장 빠른 지표다.** 각 사양에 실측으로 박혀 있다.
> **어느 구분이 지배적인지는 제품마다 다르므로 사양을 확인하고 비교할 것.**

## 5. 변경분만 생성 (개정판 기획서)

개정판(v1 → v2)은 변경된 부분만 색으로 표시하는 것이 팀 컨벤션이다.
**표시색은 기획서마다 다르다** — 빨강 단독인 판본도 있고 **빨강+파랑을 함께 쓰는 판본**도 있다
(VIOLA V4.0 `02-1 통합 모니터링` 실측). 프롬프트에 어떤 색인지 적어주면 첫 검출부터 정확해진다.
이 모드는 **실패 지점이 전체 분석과 다르다.** 아래는 실제로 터진 문제를 막는 구성이다.

트리거: `"변경된 내용만"` / `"변경분만"` / `"변경사항 위주로"` 중 아무 표현이나 가능.

### 권장 프롬프트

```
변경된 내용만 테스트 케이스 만들어줘.

[기획서]
./PRD/화면정의서_v2.pdf   ← 개정판 (v1 → v2, 변경분만 색으로 표시)
- 변경 표기색: 빨강 + 파랑 (둘 다 변경분이야. 한쪽만 보지 마)
- 변경 표기 위치: 화면 색 박스 / 여백 `변경사항` 스티커 / Description 색 텍스트
- 변경 일자 표기는 `(v1추가 - 26.05.26)` / `(v2수정_현행화 - 26.08.03)` 형식이야
  → 종류(추가/수정/삭제)와 회차는 이 텍스트가 근거야. 색으로 추정하지 마
- 이 기획서에 원래부터 그 색인 요소: 원형 번호 배지(❶❷), 필수 입력 `*`, 실패 상태 badge,
  페이지 외곽을 감싸는 테두리(전 페이지에 다 있어), 링크·기본 버튼·선택된 탭의 파랑
  → 이건 변경분이 아니야. 육안으로 확정해줘

[대상 시트]
https://docs.google.com/spreadsheets/d/<시트ID>/edit
대상 탭: 새 탭 (<챕터명> 변경분)

[범위]
챕터 1만 먼저. 결과 확인하고 나머지 진행 여부 정할게.

[변경분 모드 품질 기준]
- 세 표기를 교차 확인해줘. 한쪽에만 있으면 [스티커 전용] / [DESC 전용]로 표시하고
  케이스는 만들어줘 (기획 확인 필요로 남겨)
- 삭제된 항목은 "더는 노출되지 않음" 검증을 반드시 넣어줘
- 비고에 [변경 CH-N 유형 v1추가-26.05.26] 형식으로 CH-ID 포함해서 남겨줘
- 변경 일자가 기획서에 없으면 `날짜미표기`로 적어줘 (`-` 쓰지 말고)
- 기획서에 기대 결과가 없으면 예상 결과를 단정하지 말고
  "ㄴ 기획 미정의 항목 — PASS/FAIL 판정 대신 실측 상태를 [실제 결과]에 기재"로 통일
- 각 케이스의 절차가 비고에 적은 변경분을 실제로 건드리는지 작성 후 대조해줘
- 변경 표기 없는 페이지는 "의도적 제외"로 명시해줘 (누락과 구분되게)
```

### 각 블록의 근거

`CLAUDE.md` `2026-08-24` 항목에 이 모드의 ch01 리뷰 결과가 그대로 남아 있다.

| 프롬프트 줄 | 막는 실패 | 근거 |
|---|---|---|
| CH-ID 포함 요구 | 비고에 CH-ID가 없어 **시트 행 → 분석서 변경분 역추적 불가** | `2026-08-24` ① |
| `날짜미표기` 지시 | 날짜 없음을 `-`로 적어 **4/5 Depth의 No-data 의미와 충돌** | `2026-08-24` ② |
| 기획 미정의 패턴 | 예상 결과를 단정하면서 피드백에 `[확인 불가]` → **자기모순 4건**, 실행자가 잘못된 FAIL 기록 | `2026-08-24` ③ |
| 절차↔비고 정합성 대조 | 비고가 "신규 항목 X 확인"이라 선언했는데 **절차에 X가 없음 1건** = 변경 전에도 성립하는 케이스 | `2026-08-24` ④ |
| 원래 그 색인 요소 알려주기 | 검출 스크립트가 **원형 번호 배지·필수 `*`·에러 아이콘·페이지 외곽 프레임을 변경분으로 오탐** | `2026-08-21`, `2026-08-25` |
| 표기색 알려주기 | 스크립트 기본값이 **빨강 단독**이라, 파랑도 쓰는 기획서에서 **파랑 변경분이 통째로 누락**된다 | `2026-08-25` |
| 삭제 유형 명시 | **삭제 검증 누락이 빈발** — "더는 노출되지 않음"을 안 만든다 | `testcase-generator` 0-H |
| "의도적 제외" 명시 | 리뷰가 **비변경분 미작성을 "누락"으로 오판** | `2026-08-21` |

### 가장 효과가 큰 한 가지 — 변경 목록을 함께 주기

릴리즈 노트·Jira·기획 변경 이력이 있으면 프롬프트에 함께 넣는다.

```
[변경 목록 — 네 번째 근거 경로로 써줘]
1. <신규 영역> 추가 (26.05.26)
2. <셀렉트 항목> → <새 조건>으로 노출 조건 수정 (26.05.26)
3. <버튼> 문구 → <새 문구>로 변경 (26.06.02)
4. 기존 <라디오 항목> 삭제 (26.06.02)

이 목록과 기획서 색 표기를 대조해서, 어느 쪽에만 있는 항목을 알려줘.
```

하네스는 **기획서의 색 표기를 유일한 근거로** 변경분을 판정한다. 기획자가 색 표시를
빠뜨렸으면 그 변경은 **조용히 케이스에서 빠지고**, 하네스는 이를 잡을 수 없다.

변경 목록은 정식 입력 항목이 아니므로 `"네 번째 근거 경로로 써줘"` 라고 명시해야 반영된다.
주면 이런 걸 잡는다:

- 색 표기에 없는데 목록에 있는 항목 → **표기 누락**
- 색 표기에 있는데 목록에 없는 항목 → **오탐 또는 미기록 변경**

특히 **삭제 항목**은 이미 사라진 요소라 색 박스를 그릴 대상이 없어 누락되기 쉽다.
목록에서 잡는 것이 가장 확실하다.

### 검토 게이트 — 변경분 전용 체크리스트

이 모드에서 볼 것은 전체 분석과 다르다.

| 볼 것 | 기준 |
|---|---|
| **변경분 커버리지** | 변경분 목록 항목 수 = 커버 TC가 있는 항목 수인가. 미커버 항목이 나열됐는가 |
| **삭제 검증** | 삭제 유형에 "더는 노출되지 않음" 케이스가 있는가 |
| **범위 초과** | `[맥락 — 비변경분]` 항목으로 만든 TC가 섞이지 않았는가 |
| **비고 CH-ID** | 모든 행에 `[변경 CH-N …]`이 있는가 |
| **절차 실질성** | 절차가 실제로 변경된 요소를 건드리는가 (변경 전에도 성립하는 케이스가 아닌가) |
| **구분 enum** | `변경` 같은 신규 값을 만들지 않았는가 (기존 6종 유지) |

교정 프롬프트 예시:

```
검토했어. 아래 고치고 나머지 챕터도 같은 기준으로 진행해줘.

- <TC-ID>: 비고는 "<신규 영역> 추가 확인"인데 절차가 팝업 진입만 하고 있어.
  그 영역을 실제로 확인하는 절차로 바꿔줘
- 삭제분: <라디오 항목> 삭제에 "더는 노출되지 않음" 케이스가 없어. 추가해줘
- <TC-ID>: 예상 결과를 단정했는데 피드백에 [확인 불가]가 있어. 기획 미정의 패턴으로 통일
- 변경분 커버리지 매트릭스 보여줘. 미커버 항목 전부 나열해줘
```

### 이 모드 특유의 함정

| 함정 | 왜 생기나 | 대응 |
|---|---|---|
| 삭제 검증 누락 | 사라진 요소는 빨간 박스를 그릴 대상이 없음 | 변경 목록으로 교차 확인 |
| 비변경분까지 케이스화 (범위 초과) | 변경분 검증에 필요한 맥락을 케이스로 만들어버림 | `[맥락 — 비변경분]`은 사전조건·절차에만 |
| 리뷰가 "누락"으로 오판 | 리뷰어가 전체 분석 기준으로 판정 | 리뷰어에게 분석 방식을 반드시 전달 (하네스가 자동으로 하지만 **부분 재실행 시 빠질 수 있다**) |
| 오탐이 케이스로 들어감 | 원래 빨간 UI 요소를 변경분으로 판정 | 기획서에 있는 빨간 요소를 프롬프트에 미리 나열 |
| 선언만 하고 검증 안 함 | 비고는 변경분을 말하는데 절차는 기존 동작을 확인 | 작성 후 절차↔비고 대조 지시 |

### 하네스의 한계

**구버전 기획서와 자동 대조하는 기능은 없다.** v1과 v2 PDF를 둘 다 줘도 diff를 뜨지 않는다.
판정 근거는 **빨간색 표기뿐**이다.

그래서 이 모드의 품질 상한은 **기획자가 빨강 표시를 얼마나 성실히 했는지**에 묶여 있다.
빨강이 부실한 개정판이면 프롬프트에 변경 목록을 직접 주는 것이 유일한 보완책이다.

> **문체 전환·검증 단위 전환·미사용 컬럼 사용 시작은 잡지 못한다.**

## 7. 여러 제품에 쓸 때

`.claude/formats/` 에 **제품별 사양**이 있다. 두 사양은 거의 같은 양식을 쓰지만
**컬럼 수·문체·ID 체계·우선순위 결합 규칙이 다르다.**

| 사양 | 제품 | 측정 범위 |
|------|------|----------|
| `team-viola` | VIOLA | 2탭 331행 전수 |
| `team-trombone` | TROMBONE | 팀 작성 8탭 3,953행 전수 |

### 사양은 보통 자동 선택된다

대상 시트의 **솔루션(B) 컬럼 실측값**으로 판정하므로 평소에는 지정하지 않아도 된다.
판정 결과는 실행 중 보고된다.

```
대상 시트의 솔루션 컬럼이 `TROMBONE` 이므로 team-trombone 사양(v1.0)을 사용합니다.
```

**명시해야 하는 경우:** 대상 시트가 비어 있어 판정할 근거가 없을 때.

```
양식: team-trombone
```

### 제품마다 다른 것 — 프롬프트에서 바꿀 5곳

| # | 항목 | VIOLA | TROMBONE |
|---|------|-------|----------|
| 1 | 기획서 경로 | — | — |
| 2 | **화면 식별자 필드명** | `Screen ID` (`VIOE-02_01_01-11`) | `Page ID` (`ADM-GEN-0101-01`) |
| 3 | 대상 시트·탭 | — | — |
| 4 | 사양 (빈 시트일 때만) | `team-viola` | `team-trombone` |
| 5 | **관리대상** | **`K8S` / `CI·CD` / `BF(공통)`** — 아래 절 참조 | 미확인 (알려진 구분 없음) |
| 6 | **컬럼 수** | **24 (A~X, `관리대상` 포함)** | 23 (A~W) |

### 같은 제품 안에서 관리대상이 갈릴 때 — VIOLA `K8s` / `CI·CD`

VIOLA는 **관리대상이 `K8s` 와 `CI·CD` 로 구분된다.** 같은 화면이라도 관리대상이 다르면
권한 범위·리소스 종류·집계 대상이 달라진다. 제품명 옆에 한 줄로 적으면 된다.

> TROMBONE에 같은 구분이 있는지는 **확인된 바 없다.** 있다면 같은 방식(전용 컬럼)으로 다루면
> 되지만, `team-trombone` 사양에는 아직 관리대상 컬럼이 없다 — 필요해지면 사양에 먼저 추가한다.

> **팀 원본 시트에 쓸 때 주의.** 팀 VIOLA 시트는 아직 23컬럼(관리대상 없음)이다. 그런 탭에
> 24컬럼 행을 그냥 붙이면 모든 값이 한 칸씩 밀린다. 하네스가 구 양식 탭을 감지하면 **C열 삽입 vs
> 23컬럼 작성**을 물어보므로, 그때 선택하면 된다.

```
제품명: VIOLA V4.0 / k8s
```

미지정이면 기획서 Breadcrumb 최상위(`Kubernetes Engine` 등)와 리소스 어휘로 판정하고
보고한다. 근거가 약하면 물어본다.

**케이스에 어떻게 들어가는가** (지시하지 않아도 사양이 처리한다):

| 열 | 값 |
|----|-----|
| **`관리대상` (C)** | **`K8S` / `CI·CD` / `BF(공통)`** — 2026-08-25 신설된 전용 컬럼 |
| `1 Depth` | Breadcrumb 최상위 원문 — `Kubernetes Engine` (관리대상 컬럼과 의미가 다르다) |
| `사전조건` | `클러스터 관리 권한 2개 보유 계정 로그인` — 관리대상 접두를 **붙이지 않는다** |
| `비고` | `[DESC 2항-5] …` — `[관리대상 …]` 태그를 **붙이지 않는다** |
| `솔루션` | **`VIOLA` 고정** — `VIOLA_K8S`·`VIOLA_CICD` 접미사는 실측 0건이라 쓰지 않는다 |

**판정 단위는 화면이 아니라 케이스다.** 같은 클러스터 선택 팝업이라도 "언제 뜨는가"(로그인 직후
진입 조건)는 `BF(공통)`, "무엇을 고르는가"(클러스터 목록·권한)는 `K8S`가 된다. 화면을 통째로
한 값에 몰아넣지 않는다.

**반대쪽 관리대상 케이스는 만들지 않는다.** 기획서에 `CI·CD` 어휘가 없으면 `CI·CD` 케이스도
없다. 근거 없이 만들면 실행자가 PASS/FAIL을 판정할 수 없는 행이 절반이 된다. 대신 적용 범위
확인이 피드백 열에 남는다 — `[확인 불가] 팝업의 CI·CD 관리대상 적용 여부 — 기획 확인 필요`.

> 양쪽 관리대상을 다 만들고 싶으면 **양쪽 기획서를 함께 주는 것**이 맞다. 한쪽 기획서로
> 양쪽 케이스를 만들라고 지시하면 절반이 추측이 된다.

### 지시하지 않아도 사양이 알아서 처리하는 것

프롬프트에 넣을 필요가 없다. **넣으면 사양과 충돌한다.**

| 항목 | VIOLA | TROMBONE |
|------|-------|----------|
| UI 라벨 표기 | 백틱 `` `등록` `` | **대괄호 `[등록]`** |
| TC ID | `TC_VIO_` 제품 전역 연속 | `TC_{모듈}_` 모듈별 연속 |
| 지배 구분 | `표시` 56% | **`정상` 65%** |
| `정상`의 우선순위 | P1/P2만 | **P1~P4 전부** |
| 사전조건 | 100% 필수 | **공란 허용** |
| 팝업 3 Depth | `상세` 고정 | 화면 성격에 따름 |

### 새 제품을 추가할 때

기존 테스트 케이스 시트가 있으면 사양을 만들 수 있다.

```
참고 시트로 양식 사양 갱신해줘: <새 제품 시트 URL>
사양 이름: team-<제품명>
```

주의: **하네스가 생성한 탭은 측정 범위에서 제외**해야 한다. 포함하면 우리 출력물을
팀 컨벤션으로 재학습하는 순환이 된다 (`team-trombone` 사양이 `일반 v2` 탭을 제외한 이유).

## 8. 넣지 말 것

| 넣지 말 것 | 이유 |
|---|---|
| 컬럼 구조·enum·우선순위 설명 | 사양 파일에 331행 실측으로 있다. 다시 주면 **사양과 충돌**할 수 있다 |
| 참고 시트 URL | 평상시 불필요. 주면 사양 갱신으로 오해할 수 있다 |
| `"꼼꼼하게"`, `"빠짐없이"`, `"고품질로"` | 판정 기준이 없어 동작이 바뀌지 않는다. **무엇을 세는지** 지시해야 한다 |
| `"케이스 200개 만들어줘"` | 개수를 맞추려 억지 케이스가 생긴다. 커버리지 기준(Description 전수)으로 지시할 것 |
| 전체 챕터 한 번에 (첫 실행) | 방향 교정 기회를 잃는다 |
| **다른 제품 예시를 그대로 복사** | 화면 식별자 필드명·UI 라벨 표기·우선순위 규칙이 제품마다 다르다. 7절 참조 |

## 9. 흔한 실패와 예방

| 증상 | 원인 | 예방 |
|---|---|---|
| `403` | 대상 시트에 서비스 계정 미공유 | 실행 전 `verify_setup.py "<시트URL>"` |
| 스킬이 안 불림 | 저장소 폴더 밖에서 실행 | `cd OKE-AUTO-TEST-CASE` 후 실행 |

| 챕터 구분이 엉뚱함 | 간지 없는 기획서 | 게이트 ①에서 페이지 범위 직접 지정 |
| 케이스가 뭉쳐 있음 | scenario 단위로 생성됨 | 게이트 ②에서 `"쪼개줘"`, 생성 모드 `atomic` 명시 |
| 케이스가 부실한데 이유 불명 | 이미지 판독 품질 문제 | 판독 이슈 보고를 확인. `주의`/`불가` 페이지가 있는지 |
| 변경분 모드인데 "Description 누락" 지적 | 리뷰어가 전체 분석 기준으로 판정 | 분석 방식이 리뷰어에게 전달됐는지 확인 (5절 참조) |
| 변경분 모드에서 변경 없는 항목이 케이스화됨 | 오탐 또는 범위 초과 | 기획서의 원래 빨간 요소를 프롬프트에 나열 (5절 참조) |
| 컬럼은 맞는데 문체가 기존 행과 다름 | **다른 제품 사양이 선택됨** | 실행 로그의 사양 판정 보고를 확인. 빈 시트면 `양식:` 명시 (7절 참조) |

## 한 줄 요약

**전체 분석** — 품질은 범위를 좁히고, 기획서의 화면 식별자 필드명을 알려주고,
첫 챕터 검토에서 `표시` 비중과 P4 존재를 확인하는 것에서 대부분 결정된다.

**변경분 모드** — 품질은 변경 목록을 함께 주고, 원래 빨간 요소를 미리 알려주고,
