# 프롬프트 가이드

이 하네스에 무엇을 어떻게 요청하면 좋은 테스트 케이스가 나오는지 정리한 문서.
세팅 절차는 [SETUP.md](../SETUP.md) 를 먼저 보세요.

## 요청 전 확인

| 항목 | 확인 |
|------|------|
| 세팅 | `python3 verify_setup.py "<대상 시트 URL>"` 실행해서 실패 0 |
| 실행 위치 | 저장소 폴더 안에서 Claude Code 실행 (밖에서 실행하면 스킬이 인식되지 않음) |
| 시트 공유 | 대상 시트에 서비스 계정을 **편집자**로 공유 |
| 양식 | `.claude/formats/` 의 **공통 골격(`common.md`) + 제품 프로파일**이 기준. **참고 시트 URL은 필요 없음** |
| 제품 | 하네스가 **제품 유형을 물어본다** (`VIOLA K8s` / `VIOLA CI/CD` / `TROMBONE` / `BootFactory`). 프로파일은 여기서 정해진다 (7절) |

> 위 표의 **시트 공유**는 케이스를 쓰는 절차에만 해당합니다. 아래 표의 세 번째 절차는
> 시트를 쓰지 않으므로 대상 시트도 서비스 계정 공유도 필요 없습니다.

### 어느 절차로 가는가 — 요청에 쓴 말이 가른다

절차가 셋이고, 하네스는 **요청 어휘로 분기한다.** 무엇을 원하는지보다 **무슨 말을 썼는지**가
먼저 읽히므로, 케이스가 필요 없을 때 `테스트 케이스` 라고 쓰면 케이스 생성이 시작된다.

| 이렇게 쓰면 | 이 절차로 간다 | 결과물 | 이 문서 |
|---|---|---|---|
| `테스트 케이스` · `TC` · `케이스 생성` · `케이스 만들어줘` | `testcase-auto` | 구글 시트 행 | 0~9절 |
| `기획서 분석` · `기능 정리` · `기능 목록` · `신규·변경 기능 파악` (**케이스 어휘 없이**) | `prd-digest` | 읽는 문서 2개 | **11절** |
| `테스트케이스 추가 작업` · `예외 사항` · `권한` | `testcase-augment` | 구글 시트 행 | 10절 |

**둘 이상에 걸리거나 애매하면 하네스가 묻는다** — 추정해서 시작하지 않는다.
`"기획서 분석해서 테스트 케이스 만들어줘"` 처럼 둘을 한 문장에 담으면 어느 쪽인지 확인을 받는다.
둘 다 필요하면 **기획서 분석을 먼저 돌리고 케이스 생성을 따로 요청하는 것**이 낫다 —
이미지가 재사용되어 변환이 생략된다(11절).

## 0. 하네스가 먼저 묻는 7가지 — 이게 사용법의 출발점이다

**2026-09-02부터 사용법이 바뀌었다.** 테스트 케이스 생성을 요청하면 하네스가 분석에 착수하기 전에
**7가지를 먼저 물어본다.** 프롬프트에 모든 걸 적어 보낼 필요가 없다 — 적어 보내면 **다시 묻지 않고
확인만** 하고 넘어간다.

| # | 항목 | 값 |
|---|------|-----|
| **(1)** | **제품 유형** | `VIOLA K8s` / `VIOLA CI/CD` / `TROMBONE` / `BootFactory` 중 선택 |
| **(2)** | **기획서 유형** | **`신규`** — 문서 전체를 전수 케이스화 / **`변경`** — 변경 표기가 있는 항목만 |
| **(2-1)(2-2)** | **예외 항목** | 문서 기본 정책과 **반대**로 작성할 화면 ID 목록. 없으면 `"없음"` |
| **(3)** | **기획서 경로** | Figma URL / PDF 경로 / 이미지 파일·디렉터리 경로 |
| **(4)** | **테스트 케이스 경로** | 대상 구글 시트 URL |
| **(5)** | **시트(탭)** | **`신규`** — 생성할 탭명 / **`기존`** — 기존 탭명 |
| **(6)** | **작업 디렉터리명** | `{제품}_{제품버전}_{문서회차}` (예 `VIOLA-K8s_4.0_v1`). 산출물이 쌓이는 자리다 |
| **(7)** | **이미 변환된 이미지 경로** | 선택. 있으면 변환을 건너뛴다 (`shared` 디렉터리 경로) |

**답이 없으면 진행하지 않는다.** 추정한 항목 하나가 수백 행에 그대로 박히기 때문이다.
(7)만 선택이고 나머지 여섯은 필수다.
수집이 끝나면 확정값을 표로 보여준다 — **오타를 잡을 마지막 지점이므로 여기서 한 번 읽자.**

### 작업 디렉터리명을 왜 묻나

산출물은 `_workspace/{제품}_{제품버전}_{문서회차}/` 아래에 쌓인다 — `shared/`(이미지·변경 표시
검출 결과) · `digest/`(기획서 분석) · `testcase/`(테스트 케이스). 추가 작업(`testcase-augment`)은
원천이 시트라 판본 개념이 없어 `_workspace/augment/` 에 따로 남는다.

**파일명에서 자동으로 만들지 않는다.** `[4.0] VIOLA_화면기획서_v1_260728.pdf` 는 제품 버전이
`4.0`, Document History 회차가 `v1` 로 **축이 둘**이다. 회차가 없으면 같은 제품 버전 안에서
판본이 겹치고, 제품 버전이 없으면 다음 릴리스의 `v1` 과 충돌한다.

**같은 기획서를 다시 돌릴 때는 지난번과 같은 이름을 답한다.** 그래야 `shared/` 의 이미지가
재사용된다 — 181페이지 전체 변환은 약 10분이고, 이름이 다르면 그 10분을 다시 쓴다.
판정 근거는 경로가 아니라 **PDF 내용 해시**라, 같은 자리에 다른 판본 PDF를 주면 재사용하지 않고
**멈추고 알린다.**

### 예외 항목이 무엇인가

실제 기획서는 깨끗하게 갈리지 않는다. `신규` 문서에 일부 변경건이 섞여 있고, `변경` 문서에
일부 신규건이 들어 있다. **그 화면만 반대 정책으로 작성하도록** 화면 ID로 지정하는 항목이다.

| 문서 기본 | 예외로 지정하는 것 | 그 화면에 적용되는 정책 |
|----------|------------------|----------------------|
| `신규` | 문서 안의 **일부 변경건** 화면 ID | **변경 정책** — 변경 표기 있는 항목만 케이스화 |
| `변경` | 문서 안의 **일부 신규건** 화면 ID | **신규 정책** — 그 화면 전수 케이스화 |

- 식별자는 **제품 프로파일의 화면 ID 체계**를 따른다 (`VIOE-02_01_01-11`, `BOOT-03_01_08`, `ADM-GEN-0101-01`)
- **화면 ID 단위다.** 그 화면 하나가 통째로 반대 정책이 된다
- 예외 화면의 케이스에는 `피드백`에 `[정책 예외] 문서 기본=신규 / 이 화면=변경` 이 남는다 — 나중에 왜 이 화면만 다르게 작성됐는지 역추적하기 위한 것

### 묻지 않는 것

| 항목 | 왜 안 묻나 |
|------|-----------|
| **변경 표시색** | **사용자 진술보다 스크립트 실측이 정확하다.** 2026-09-01 실측에서 사용자가 "빨강·파랑"이라고 알려줬는데 **파랑 후보 21건이 전부 오탐**이었다. 하네스가 `--color=both` 로 먼저 훑어 확정한다 |
| 생성 모드 | 기본 `atomic`. 시나리오 단위를 명시 요청할 때만 바뀐다 |
| 양식 사양 | 커밋된 파일이 기준. `"양식 사양 갱신해줘"` 라고 할 때만 참고 시트를 요구한다 |

**단, 기획서 유형이 `변경` 이면 취소선이 삭제 표기인지 물어본다.** 기획서마다 컨벤션이 다르고,
취소선은 색 검출에 잡히지 않아 알려주지 않으면 **삭제 변경분이 통째로 누락된다.**

이 기획서로 테스트 케이스 만들어줘.

## 2. 첫 실행용

첫 실행은 **범위를 좁히고 되돌릴 수 있는 곳에 쓰는 것**이 핵심이다.
전체를 돌리면 케이스가 수백 건 나오는데, 방향이 틀렸으면 전부 다시 해야 한다.

```
테스트 케이스 자동 생성해줘.

[기본 정보]
- 제품 유형: VIOLA K8s
- 기획서 유형: 신규 / 예외 항목 없음
- 기획서: ./PRD/화면정의서_v1.pdf
- 대상 시트: https://docs.google.com/spreadsheets/d/<시트ID>/edit
- 탭: 신규 — "테스트_초안_260902"

[옵션]
- 생성 모드: atomic
- 범위: 첫 번째 화면만 먼저 해줘. 결과 보고 나머지 진행 여부 정할게
```

첫 실행은 **팀 공용 시트에 직접 쓰지 말고** 사본이나 새 탭에 쓰는 것을 권한다.
결과가 마음에 안 들면 탭만 지우면 된다.

## 3. 품질 최우선

```
테스트 케이스 만들어줘.

[기본 정보]
- 제품 유형: VIOLA K8s
- 기획서 유형: 신규 / 예외 항목 없음
- 기획서: ./PRD/화면정의서_v1.pdf
- 대상 시트: https://docs.google.com/spreadsheets/d/<시트ID>/edit
- 탭: 신규 — "01_파드"

[기획서 판독 힌트]
- 화면 식별자는 스펙 페이지 우측 상단 `<실제 필드명>` 필드에 있어 (`<실제 값 예시>` 형식)
- 스펙 페이지는 좌측 UI + 우측 Description 패널 구조야

[범위]
화면 1개만 먼저. 결과 확인하고 나머지 진행 여부 정할게.

[품질 기준]
- Description 항목은 전수 케이스화. 번호(❶-1-a)까지 비고에 출처로 남겨줘
- 테이블·상태값·일시·버튼이 나오면 표시 형식 검증 케이스를 자동 도출해줘
- 기획서에 정의 없는 항목은 추측하지 말고 "기획 확인 필요"로 따로 모아줘
- 리뷰까지 하고, Critical 남으면 시트에 쓰지 말고 먼저 알려줘
```

> **`<실제 필드명>` 은 반드시 기획서를 열어 확인하세요.** 제품마다 다릅니다 —
> TROMBONE은 `Page ID`(`ADM-GEN-0101-01`), VIOLA는 `Screen ID`(`VIOE-02_01_01-11`),
> BootFactory는 `BOOT-03_01_08` 계열입니다.
> 다른 제품 값을 그대로 복사하면 화면 ID 컬럼이 비거나 잘못 채워집니다.

### 각 줄의 근거

프롬프트에 넣는 이유는 "하네스가 안 하니까"가 아니라 **실제로 놓친 전례가 있어서**다.
근거는 `CLAUDE.md` 변경 이력에 있다.

| 프롬프트 줄 | 막는 실패 | 이력 |
|---|---|---|
| 화면 식별자 필드명 알려주기 | 화면 ID 컬럼 미기입·형식 뒤틀림 | `2026-08-21` — 어떤 기획서는 `Page ID`, 어떤 기획서는 `Screen ID`다. 잘못 알려주면 매핑 실패 |
| Description 전수 + 번호 출처 | Description 누락 다수 | `2026-06-09` — 샘플링 리뷰 결과 Description 누락 다수 발견 |
| 표시 형식 검증 자동 도출 | 컬럼 순서·enum·일시 형식 케이스 통째 누락 | `2026-05-13` — 비교 결과 **Critical 누락 7건** |
| 추측 금지 + 확인 필요 분리 | 기획 미정의 항목을 단정해 실행자가 잘못된 FAIL 기록 | `2026-08-24` — 예상 결과 단정 + `[확인 불가]` 자기모순 4건 |
| 화면 1개로 범위 축소 | 방향 틀린 케이스를 수백 건 쓴 뒤 발견 | `2026-06-11` 챕터 순차 전환 → `2026-09-02` 화면 ID 단위로 재편 |
| Critical 시 쓰기 전 보고 | 리뷰가 잡았는데 이미 시트에 들어간 상태 | 기본은 재작성 1회 루프 후 진행 |

## 4. 확인 게이트 3곳

진행 중 세 지점에서 멈춘다. **여기서 무엇을 지시하느냐가 나머지 화면 전체 품질을 결정한다.**

### ⓪ 기본 정보 확인 (Phase 0)

0절의 7가지를 수집한 뒤 확정값을 표로 보여준다.

```
| 항목 | 값 |
|------|-----|
| 제품 유형 | VIOLA K8s (profile-viola) |
| 기획서 유형 | 변경 |
| 예외 항목 | VIOE-03_01_04_13 (이 화면만 신규 정책) |
| 기획서 | PDF/VIOLA_V4.0/03_파드.pdf |
| 대상 시트 | https://docs.google.com/spreadsheets/d/... |
| 탭 | 신규 생성 — "03_파드_변경분" |
| 작업 디렉터리명 | VIOLA-K8s_4.0_v1 |
| 이미 변환된 이미지 | 없음 (새로 변환) |
| 생성 모드 | atomic |
| 취소선 | 삭제 표기로 처리 |
```

볼 것: **제품 유형과 기획서 유형.** 이 둘이 틀리면 전 행이 틀린다 — 제품 유형은 문체·TC ID·
지배 구분을 통째로 바꾸고, 기획서 유형은 케이스화 범위 자체를 바꾼다.

### ① 화면 인덱스 확인

```
| 순번 | 화면 ID | 페이지 | 소속 간지 | 정책 |
| 01 | VIOE-02_01_01-11 | p5~p7 | 통합 모니터링 | 변경 |
| 02 | VIOE-02_01_02 | p8 | 통합 모니터링 | 변경 |

제외한 페이지: p1~p4 (간지·목차)
```

볼 것 셋: **① 제외한 페이지** — 간지·목차 외의 페이지가 빠졌으면 그 화면이 통째로 누락된다. **② 한 화면이 여러 페이지에 걸친 경우의 묶음** — 페이지가 갈라지면 케이스도 갈라진다. **③ 화면 수와 사이클 수** — 화면이 많으면 범위를 좁힐지 지금 정한다.

```
p8도 01번 화면에 포함시켜줘

### ② 첫 화면 케이스 검토 (시트 쓰기 **전**)

`_workspace/VIOLA-K8s_4.0_v1/testcase/03_testcases_s01.md` 를 보여준다. 볼 것:

| 항목 | 기준 |
|------|------|

| **비고 컬럼** | `[DESC 2항-1]` 같은 근거 태그가 있는지. 없으면 역추적 불가 |
| **사전조건** | 화면 상황이 구분되는지 (데이터 유무, 권한 등) |

교정 프롬프트 예시:

```
케이스 검토했어. 아래대로 고치고 나머지 화면도 같은 기준으로 진행해줘.

- 케이스 단위: <TC-ID>는 검증이 2개 묶여 있어. 쪼개줘
- 표시 형식: 목록 화면 컬럼별 정렬 케이스가 빠졌어. 정렬 가능 컬럼마다 하나씩 추가
- 구분 분포: 프로파일의 지배 구분 비중과 비교해서 부족한 쪽을 더 쪼개줘
- P4: 모달 취소·권한 없음 닫기 케이스가 없어. `부수`+P4로 추가
- 사전조건: "목록 화면 진입"만으로는 상황 구분이 안 되는 케이스가 있어. 데이터 유무 조건 명시

> **지배 구분 비중과 P4 존재 여부가 품질 점검의 가장 빠른 지표다.** 각 프로파일에 실측으로 박혀 있다.
> **어느 구분이 지배적인지는 제품마다 다르므로 프로파일을 확인하고 비교할 것.**

## 5. 변경분만 생성 (개정판 기획서)

개정판(v1 → v2)은 변경된 부분만 색으로 표시하는 것이 팀 컨벤션이다.
이 모드는 Phase 0 **기획서 유형 = `변경`** 을 고르면 켜진다 (`"변경된 내용만"` 같은 표현으로
요청해도 하네스가 그 값으로 확정하고 재확인한다).
**실패 지점이 전체 분석과 다르다.** 아래는 실제로 터진 문제를 막는 구성이다.

> **표시색은 프롬프트에 적지 않는다.** 색은 기획서마다 다르지만, **사용자 진술보다 스크립트 실측이
> 정확하다.** 2026-09-01 실측에서 사용자가 "빨강·파랑"이라고 알려줬는데 **파랑 후보 21건이 전부
> 오탐**이었다. 하네스가 `--color=both --no-crops` 로 먼저 훑어 확정한다.
> 반대로 **"원래부터 그 색인 요소"를 알려주는 것은 여전히 크게 도움이 된다** — 그건 실측으로
> 가려낼 수 없고 문서를 아는 사람만 안다.

### 권장 프롬프트

```
변경된 내용만 테스트 케이스 만들어줘.

[기본 정보]
- 제품 유형: VIOLA K8s
- 기획서 유형: 변경
- 예외 항목: VIOE-03_01_04_13 (이 화면은 신규 추가라 전수로 해줘)
- 기획서: ./PRD/화면정의서_v2.pdf   ← 개정판 (v1 → v2)
- 대상 시트: https://docs.google.com/spreadsheets/d/<시트ID>/edit
- 탭: 신규 — "<모듈명> 변경분"

[이 기획서의 변경 표기 특성]
- 변경 표기 위치: 화면 색 박스 / 여백 `변경사항` 스티커 / Description 색 텍스트
  / 페이지 우측 하단 `ChangeLog` 패널
- 취소선 = 삭제 표기야
- 변경 일자 표기는 `(v1추가 - 26.05.26)` / `(v2수정_현행화 - 26.08.03)` 형식이야
  → 종류(추가/수정/삭제)와 회차는 이 텍스트가 근거야. 색으로 추정하지 마
- 이 기획서에 원래부터 색이 들어간 요소: 원형 번호 배지(❶❷), 필수 입력 `*`, 실패 상태 badge,
  페이지 외곽을 감싸는 테두리(전 페이지에 다 있어), 링크·기본 버튼·선택된 탭의 파랑
  → 이건 변경분이 아니야. 육안으로 확정해줘

[범위]
화면 1개만 먼저. 결과 확인하고 나머지 진행 여부 정할게.

[변경분 모드 품질 기준]
- 네 경로를 교차 확인해줘. 한쪽에만 있으면 [스티커 전용] / [DESC 전용] / [ChangeLog]로
  표시하고 케이스는 만들어줘 (기획 확인 필요로 남겨)
- 삭제된 항목은 "더는 노출되지 않음" 검증을 반드시 넣어줘
- 비고에 [변경 CH01-3 신규추가 v2-26.08.18] 형식으로 CH-ID 포함해서 남겨줘
- 변경 일자가 기획서에 없으면 `날짜미표기`로 적어줘 (`-` 쓰지 말고)
- 기획서에 기대 결과가 없으면 예상 결과를 단정하지 말고
  "ㄴ 기획 미정의 항목 — PASS/FAIL 판정 대신 실측 상태를 [실제 결과]에 기재"로 통일
- 각 케이스의 절차가 비고에 적은 변경분을 실제로 건드리는지 작성 후 대조해줘
- 변경 표기 없는 페이지는 "의도적 제외"로 명시해줘 (누락과 구분되게)

### 가장 효과가 큰 한 가지 — 변경 목록을 함께 주기

릴리즈 노트·Jira·기획 변경 이력이 있으면 프롬프트에 함께 넣는다.

```
[변경 목록 — 기획서 밖 근거 경로로 함께 써줘]
1. <신규 영역> 추가 (26.05.26)
2. <셀렉트 항목> → <새 조건>으로 노출 조건 수정 (26.05.26)
3. <버튼> 문구 → <새 문구>로 변경 (26.06.02)
4. 기존 <라디오 항목> 삭제 (26.06.02)

이 목록과 기획서 색 표기를 대조해서, 어느 쪽에만 있는 항목을 알려줘.
```

하네스는 **기획서 안의 표기 네 경로**(색 박스 / `변경사항` 스티커 / DESC 색 텍스트 / `ChangeLog`
패널) **+ 취소선**만을 근거로 변경분을 판정한다. 기획자가 이 표기를 전부 빠뜨렸으면 그 변경은
**조용히 케이스에서 빠지고**, 하네스는 이를 잡을 수 없다.

변경 목록은 정식 입력 항목이 아니므로 `"근거 경로로 함께 써줘"` 라고 명시해야 반영된다.
주면 이런 걸 잡는다:

- 색 표기에 없는데 목록에 있는 항목 → **표기 누락**
- 색 표기에 있는데 목록에 없는 항목 → **오탐 또는 미기록 변경**

특히 **삭제 항목**은 이미 사라진 요소라 색 박스를 그릴 대상이 없어 누락되기 쉽다.
목록에서 잡는 것이 가장 확실하다.

### 검토 게이트 — 변경분 전용 체크리스트

이 모드에서 볼 것은 전체 분석과 다르다.

| 볼 것 | 기준 |
|---|---|
| **변경분 커버리지** | 변경분 목록 항목 수 = 커버 TC가 있는 항목 수인가. 미커버 항목이 나열됐는가 |
| **삭제 검증** | 삭제 유형에 "더는 노출되지 않음" 케이스가 있는가 |
| **범위 초과** | `[맥락 — 비변경분]` 항목으로 만든 TC가 섞이지 않았는가 |
| **비고 CH-ID** | 모든 행에 `[변경 CH{NN}-N …]`이 있는가 (`NN` = 화면 인덱스의 CH-ID 접두 — `CH05-3`) |
| **`ChangeLog` 대조** | `ChangeLog` 패널이 있는 페이지는 대조표가 나왔는가. **패널에 없다는 이유로 변경분을 탈락시키지는 않았는가** (패널은 작성 시점 스냅샷일 뿐이다) |
| **절차 실질성** | 절차가 실제로 변경된 요소를 건드리는가 (변경 전에도 성립하는 케이스가 아닌가) |
| **구분 enum** | `변경` 같은 신규 값을 만들지 않았는가 (기존 6종 유지) |

교정 프롬프트 예시:

```
검토했어. 아래 고치고 나머지 화면도 같은 기준으로 진행해줘.

- <TC-ID>: 비고는 "<신규 영역> 추가 확인"인데 절차가 팝업 진입만 하고 있어.
  그 영역을 실제로 확인하는 절차로 바꿔줘
- 삭제분: <라디오 항목> 삭제에 "더는 노출되지 않음" 케이스가 없어. 추가해줘
- <TC-ID>: 예상 결과를 단정했는데 피드백에 [확인 불가]가 있어. 기획 미정의 패턴으로 통일
- 변경분 커버리지 매트릭스 보여줘. 미커버 항목 전부 나열해줘
```

### 이 모드 특유의 함정

| 함정 | 왜 생기나 | 대응 |
|---|---|---|
| 삭제 검증 누락 | 사라진 요소는 색 박스를 그릴 대상이 없고, **취소선은 색 검출에 안 잡힌다** | 취소선이 삭제 표기임을 알려주기 + 변경 목록으로 교차 확인 |
| 비변경분까지 케이스화 (범위 초과) | 변경분 검증에 필요한 맥락을 케이스로 만들어버림 | `[맥락 — 비변경분]`은 사전조건·절차에만 |
| 리뷰가 "누락"으로 오판 | 리뷰어가 신규(전수) 기준으로 판정 | 리뷰어에게 기획서 유형을 반드시 전달 (하네스가 자동으로 하지만 **부분 재실행 시 빠질 수 있다**) |
| 오탐이 케이스로 들어감 | 원래 색이 들어간 UI 요소를 변경분으로 판정 | 기획서에 원래 있는 색 요소를 프롬프트에 미리 나열 |
| 예외 화면이 기본 정책으로 처리됨 | 예외 항목을 Phase 0에서 말하지 않음 | 0절 (2-1)(2-2)에서 화면 ID로 지정. 분석 중 발견되면 하네스가 보고만 하고 **임의로 정책을 뒤집지 않는다** |
| 선언만 하고 검증 안 함 | 비고는 변경분을 말하는데 절차는 기존 동작을 확인 | 작성 후 절차↔비고 대조 지시 |

### 하네스의 한계

**구버전 기획서와 자동 대조하는 기능은 없다.** v1과 v2 PDF를 둘 다 줘도 diff를 뜨지 않는다.
판정 근거는 **기획서에 사람이 남긴 변경 표기**(색 박스 / 스티커 / DESC 색 텍스트 / `ChangeLog`
패널 / 취소선)뿐이다.

그래서 이 모드의 품질 상한은 **기획자가 변경 표시를 얼마나 성실히 했는지**에 묶여 있다.
표기가 부실한 개정판이면 프롬프트에 변경 목록을 직접 주는 것이 유일한 보완책이다.

```

분석을 재사용하면 시간이 절약되고 케이스 단위만 교정된다.

### 팀 양식이 바뀌었을 때 — 사양 갱신

```
참고 시트로 양식 사양 갱신해줘: https://docs.google.com/spreadsheets/d/<팀_시트>/edit
```

해당 **제품 프로파일**(`.claude/formats/profile-viola.md` 등)의 버전·측정일이 올라간다.
전 제품 공통 규칙을 고치는 경우에만 `common.md` 가 바뀐다.
`CLAUDE.md` 변경 이력에 사유를 남기고 커밋할 것.

**갱신이 필요한 신호** (`common.md` 의 "능력의 한계" 절 참조):

- 리뷰에서 문체·검증 단위 관련 위반이 반복 지적된다
- 팀원이 양식을 바꿨다고 말한다
- 생성된 케이스가 기존 행과 나란히 놓였을 때 이질적으로 보인다

> 드리프트 검증은 컬럼 구조·마지막 ID·신규 enum은 잡지만,
> **문체 전환·검증 단위 전환·미사용 컬럼 사용 시작은 잡지 못한다.**

## 7. 여러 제품에 쓸 때

`.claude/formats/` 는 **공통 골격 1개 + 제품 프로파일 3개** 구조다 (2026-09-02 재편).
**양식은 `common.md` + 해당 프로파일 두 개를 함께 읽어야 성립한다** — 한쪽만으로는 케이스를 쓸 수 없다.

| 파일 | 담는 것 | 실측 근거 |
|------|---------|----------|
| **`common.md`** | 컬럼 골격(A~W 23컬럼) · 헤더 원문 · `-` vs 빈칸 · atomic · 태그 체계 · C-ID/CH-ID · 변경분 모드 태그 · 권위 규칙 | (제품 공통 규칙) |
| `profile-viola.md` | 백틱 문체, 지배 구분 `표시`, TC ID 제품 전역 연속 | VIOLA 2탭 **331행 전수** |
| `profile-trombone.md` | 대괄호 문체, 지배 구분 `정상`, TC ID 모듈별 연속 | 팀 작성 8탭 **3,953행 전수** |
| `profile-bootfactory.md` | VIOLA 문체·규칙 승계 | **없음 — 파생 프로파일** |

**왜 나눴나.** 두 사양이 컬럼 골격·태그 체계·C-ID 규칙을 각자 복제하고 있어서, 한쪽만 고쳐지는
드리프트가 생겼다. **제품마다 실측으로 갈리는 항목만** 프로파일에 남겼다.

### 프로파일은 제품 유형으로 정해진다

**Phase 0 (1) 제품 유형**(0절)에서 고른 값이 그대로 프로파일을 정한다.

| 제품 유형 | 프로파일 |
|-----------|---------|
| `VIOLA K8s` | `profile-viola` |
| `VIOLA CI/CD` | `profile-viola` (**같은 프로파일**) |
| `TROMBONE` | `profile-trombone` |
| `BootFactory` | `profile-bootfactory` |

대상 시트에 이미 데이터가 있으면 하네스가 **솔루션 컬럼 실측값과 대조**하고, 어긋나면 보고한다.

```
제품 유형은 TROMBONE인데 대상 시트 솔루션 컬럼은 VIOLA입니다. 어느 쪽이 맞나요?
```

> 예전에는 솔루션 컬럼으로 사양을 **자동 판정**했고 빈 시트일 때만 `양식:` 을 명시했다.
> 이제는 **제품 유형이 먼저 확정**되고 시트는 대조 대상이다 — 빈 시트에서도 물어볼 필요가 없다.

### `VIOLA K8s` 와 `VIOLA CI/CD` 의 차이는 어디에 남는가

**시트 컬럼에는 남지 않는다.** 둘은 같은 프로파일·같은 23컬럼을 쓰고, 차이는 두 곳에서 표현된다.

| 표현 위치 | 내용 |
|----------|------|
| **탭 분리** | K8s 케이스와 CI/CD 케이스를 다른 탭에 쓴다 |
| **`1 Depth`** | 기획서 Breadcrumb 최상위 **원문** — `Kubernetes Engine` 등 |
| (분석 컨텍스트) | 어느 영역 기획서인지 — 리소스 어휘(`파드`·`네임스페이스` vs `파이프라인`·`배포 이력`) 판독에 쓰인다 |

> **`1 Depth` 값을 제품 유형에서 만들어내지 않는다.** 기획서 Breadcrumb 원문을 그대로 쓴다.

**⚠️ `관리대상` 컬럼은 2026-09-02에 폐지됐다.** 2026-08-25부터 일주일간 VIOLA만 24컬럼(A~X)으로
`K8S`/`CI·CD`/`BF(공통)` 를 행마다 기입했으나, **행 단위 판정이 컬럼 밀림 사고와 팀 원본 시트
(23컬럼) 불일치를 낳아** 폐지하고 Phase 0 제품 유형으로 옮겼다. 지금은 **전 제품 23컬럼 A~W**다.

- `제품명: VIOLA V4.0 / k8s` 같은 **옛 지정 방식은 쓰지 않는다.** Phase 0에서 `VIOLA K8s` 를 고르면 된다
- 예전 문서에서 `비고(W)`·`피드백(X)` 표기를 보면 **24컬럼 시절 매핑**이다. 현행은 `비고(V)`·`피드백(W)`
- 24컬럼으로 작성된 기존 탭에 이어 쓰려면 하네스가 **작성을 멈추고 확인**한다 (헤더가 대상 시트 권위)

### ⚠️ BootFactory 프로파일은 실측이 아니라 파생이다

**팀 작성 BF 시트를 측정한 적이 없다.** 화면 ID 패턴(`BOOT-NN_NN_NN`, 2026-09-01 실측)을 뺀
나머지 전부가 VIOLA에서 이식한 값이며, 팀 BF 시트가 실제로 이 컨벤션을 쓰는지 확인된 바 없다.

| 항목 | 값 | 상태 |
|------|-----|------|
| `솔루션` | `BOOTFACTORY` | **제안값** — 차선 `BF`, 비권장 `BOOT_FACTORY`(VIOLA에 언더스코어 사례 0건) |
| TC ID | `TC_BF_{3자리}` 제품 전역 연속 | **제안값** |
| 문체·분포·결합 규칙 | VIOLA 승계 (백틱, `표시` 56%) | **VIOLA 실측 이식** |
| 화면 ID 패턴 | `BOOT-03_01_08` | **실측** |

`솔루션` 값과 TC ID 코드는 **전 행에 박히는 상수**라 나중에 바꾸려면 열 전체를 고쳐야 한다.
팀 리더가 다른 값을 원하면 **첫 실행 전에 알려주는 편이 훨씬 싸다.**

**팀 BF 원본 시트가 나오면 전수 스캔으로 교체하는 것이 정공법이다.**

```
참고 시트로 양식 사양 갱신해줘: <팀 BootFactory 시트 URL>
프로파일: profile-bootfactory
```

### 제품마다 다른 것 — 프롬프트에서 바꿀 곳

| # | 항목 | VIOLA (K8s·CI/CD) | TROMBONE | BootFactory |
|---|------|-------------------|----------|-------------|
| 1 | **제품 유형** | `VIOLA K8s` / `VIOLA CI/CD` | `TROMBONE` | `BootFactory` |
| 2 | **화면 식별자 필드명** | `Screen ID` (`VIOE-02_01_01-11`) | `Page ID` (`ADM-GEN-0101-01`) | `Screen ID` (`BOOT-03_01_08`) |
| 3 | 기획서 경로 · 대상 시트 · 탭 | — | — | — |
| 4 | **컬럼 수** | **23 (A~W)** | **23 (A~W)** | **23 (A~W)** — 전 제품 통일 |

### 지시하지 않아도 프로파일이 알아서 처리하는 것

프롬프트에 넣을 필요가 없다. **넣으면 사양과 충돌한다.**

| 항목 | VIOLA | TROMBONE | BootFactory |
|------|-------|----------|-------------|
| UI 라벨 표기 | 백틱 `` `등록` `` | **대괄호 `[등록]`** | 백틱 (VIOLA 승계) |
| TC ID | `TC_VIO_` 제품 전역 연속 | `TC_{모듈}_` 모듈별 연속 | `TC_BF_` 제품 전역 연속 |
| 지배 구분 | `표시` 56% | **`정상` 65%** | `표시` 56% (이식값) |
| `정상`의 우선순위 | P1/P2만 | **P1~P4 전부** | P1/P2만 |
| 사전조건 | 100% 필수 | **공란 허용**(92.1% 채움) | 채움 필수 |
| 팝업 3 Depth | `상세` 고정 | 화면 성격에 따름 | `상세` 고정 |

### 새 제품을 추가할 때

기존 테스트 케이스 시트가 있으면 프로파일을 만들 수 있다.

```
참고 시트로 양식 사양 갱신해줘: <새 제품 시트 URL>
프로파일 이름: profile-<제품명>
```

**공통 골격(`common.md`)은 건드리지 않는다.** 새로 만드는 것은 프로파일이고, 거기에는
**그 제품에서만 다른 값**(솔루션 고정값·TC ID 체계·문체·분포·화면 ID 패턴)만 담는다.

주의: **하네스가 생성한 탭은 측정 범위에서 제외**해야 한다. 포함하면 우리 출력물을
팀 컨벤션으로 재학습하는 순환이 된다 (`profile-trombone` 이 `일반 v2` 763행을 제외한 이유).

## 10. 추가 작업 — 예외 사항 / 권한

**기획서가 아니라 이미 작성된 테스트 케이스가 원천인 별도 절차다.** 트리거가 다르고
(`testcase-augment`) 묻는 것도 다르다. 기획서 기반 케이스가 필요하면 그건 0~9절의 `testcase-auto` 다.

### 언제 쓰나

| 상황 | 이 절차가 채우는 것 |
|---|---|
| 기획서 기반 케이스를 이미 만들어 뒀다 | 기획서에 **항목으로 존재하지 않는** 예외 흐름 (필수값 누락·형식 위반·중복·서버 오류·동시성·중단 이탈) |
| 역할마다 기능 권한이 다르다 | 권한 매핑 자료가 원천 — 기획서에 없다 |

### 프롬프트 예시 — 예외 사항만

```
테스트케이스 추가 작업 진행해줘.

추가 작업: 예외 사항
원본 TC: https://docs.google.com/spreadsheets/d/AAA / 탭 "03_파드"
범위: VIOE-03_01_01-01, VIOE-03_01_01-02
작성 대상: 같은 시트 / 탭 "03_파드_예외" (신규)
```

`범위` 는 **예외 사항 전용 필수 항목**입니다 — 뒤집을 원본을 `화면 ID` 로 지정합니다.
전부 대상이면 `범위: 전수` 로 적습니다. 모르면 비워 두셔도 되지만 **하네스가 물어봅니다**
(빈칸을 전수로 가정하지 않습니다 — 화면 3개를 생각했는데 수십 개가 케이스화되는 것을 막습니다).

### 예외 사항에서 **만들지 않는 것** — 팀 고정 규칙

아래 5종은 하네스에 박혀 있습니다. **묻지 않고 매 실행 제외**되므로 프롬프트에 적을 필요가 없습니다.

| 제외 | 예 |
|------|-----|
| 조회 API 오류 · 조회 중 새로고침 | 목록 조회 API 오류, 페이지 조회 중 새로고침 시도 |
| 일반적인 팝업 닫기 | 삭제 확인 팝업의 취소 버튼 클릭 |
| 경계값 | 입력 범위 밖 값, 허용되지 않는 값 입력 |
| 기능과 무관한 브라우저 조작 | 팝업 외부 클릭 후 ESC, 입력 도중 브라우저 새로고침 |
| 반복 동시 조작 | 생성·삭제 버튼 연속 2회 빠르게 클릭 |

**남는 것** — 필수값 누락 · 형식 위반(특수문자·공백 등 허용 패턴 위반) · 중복 값 ·
존재하지 않는 대상 · 상태 전이 불가 · 권한·세션 · 두 사용자 동시 수정 · 데이터 규모 경계.

> 형식 위반은 경계값이 아니므로 **남습니다.** 또 반복 클릭은 빠지지만
> **두 사용자 동시 수정**은 성격이 다른 검증이라 남습니다.
> 단일 출처는 `.claude/skills/testcase-generator/references/exception-catalog.md` 「제외 상황」입니다.

### 프롬프트 예시 — 권한

```
테스트케이스 추가 작업 진행해줘.

추가 작업: 권한
원본 TC: https://docs.google.com/spreadsheets/d/AAA / 탭 "03_파드", "04_네임스페이스"
권한 자료: docs/permission_matrix.png
작성 대상: https://docs.google.com/spreadsheets/d/BBB / 탭 "추가분"
```

- 다 적지 않아도 된다. 하네스가 순서대로 묻고, 원본 탭은 **탭 목록을 보여주고 고르게 한다**
- **한 실행에 한 유형이다.** 둘 다 필요하면 두 번 실행한다 — 도출 규칙·근거 태그·`구분` 값·
  완전성 지표가 전부 달라 한 실행에 섞으면 산출물과 리뷰가 두 기준을 오간다
- 권한 모드에는 `범위` 를 적지 않는다 — 매트릭스의 역할 × 기능 전수가 범위다

### 묻지 않는 것 — 적어도 쓰이지 않는다

| 항목 | 이유 |
|---|---|
| **제품 유형 / 프로파일** | 원본 TC의 `솔루션` 컬럼 **실측**으로 판정한다. 추정이 아니라 실측이라 물을 이유가 없다 |
| **기획서 경로 · 기획서 유형 · 정책 예외** | 이 절차는 기획서를 읽지 않는다 |
| **취소선 · 변경 표시색** | 기획서 표기 개념이다 |

### 넣지 말 것

| 넣지 말 것 | 이유 |
|---|---|
| **엑셀(.xlsx) 경로** | **미지원이다.** 구글 시트로 옮기거나 CSV로 내보내야 한다 |
| **제외 5종을 만들어 달라는 요청** (`"새로고침 케이스도 넣어줘"`) | 팀 고정 제외다. 필요해지면 프롬프트가 아니라 `exception-catalog.md` 「제외 상황」을 고쳐야 한다 |
| `"예외 케이스 300개"` | 규모는 기능 단위 × 적용 예외 유형으로 정해진다. 개수를 맞추려면 억지 케이스가 생긴다 |
| 권한값 어휘 지정 (`"허용/불가로 써줘"`) | 자료에서 실측한다. 자료와 다른 어휘를 쓰면 셀 ↔ 케이스 대조가 깨진다 |
| 기능 ↔ 화면 대응 추정 (`"파드는 03_01 화면일 거야"`) | 확인 게이트에서 확정한다. 셀 하나가 엉뚱한 화면에 붙으면 그 케이스가 통째로 틀린다 |
| **틀린 화면 ID를 범위로 지정** | 오타면 `SCOPE_NO_MATCH` Critical 로 멈춘다. 시트에서 `화면 ID` 컬럼 값을 복사해 쓰는 것이 안전하다 |

### 확인 게이트 3곳

| 게이트 | 무엇을 보나 |
|---|---|
| **권한 자료 판독** (`권한` 모드) | 역할 × 기능 권한값 표 + **기능 ↔ 원본 TC 대응표**. `미대응`·`후보 여럿` 을 여기서 정리한다 |
| **규모 확인** | 기능 단위별 예상 케이스 수와 **제외 항목**. 역할 × 기능 전수는 수백 행이 될 수 있다 |
| **첫 배치 검토** | 문체·태그·enum 오류를 전 행에 번지기 전에 잡는다. **작업 유형마다 한 번씩**이다 |

### 이 절차에서만 다른 것

- **`구분` 분포가 프로파일과 다른 것이 정상이다** — 예외는 `비정상`·`엣지` 만, 권한은 `정상`·`부수` 만
  만드는 것이 이 작업의 정의다. 리뷰도 분포 편차를 지적하지 않는다
- **근거 태그가 `[DESC …]` 가 아니다** — `[예외 파생 {원본 TC ID}]` / `[권한 매트릭스 {역할}×{기능}]`
- **`[기획 확인]` 이 많이 나오는 것이 정상이다** — 기획 미정의 영역을 다루므로, 문구·코드·지연 시간 같은
  확정값은 단정하지 않고 넘긴다
- **파생 태그가 붙은 행은 다음 실행에서 원본이 되지 않는다** — 같은 탭에 이어 써도 파생의 파생이 생기지 않는다

## 11. 기획서 분석 — 기능 목록 / 신규·변경 판정

**케이스를 만들지 않는 절차다.** 기획서를 화면 단위로 읽어 **사람이 읽는 문서 2개**를 낸다.
트리거는 `prd-digest` 이고, 구글 시트를 쓰지 않으므로 **대상 시트도 탭도 묻지 않는다.**
케이스가 필요하면 그건 0~9절의 `testcase-auto` 다.

### 언제 쓰나

| 상황 | 이 절차가 주는 것 |
|---|---|
| 기획서를 받았는데 분량이 커서 뭐가 들었는지 모르겠다 | 메뉴 구조 순서로 정리된 **전체 기능 목록** |
| 개정판을 받았는데 **이번에 뭐가 바뀌었는지** 알고 싶다 | 화면 ID별 **신규·변경·삭제** 목록 + 근거 |
| 케이스를 만들기 전에 범위·규모를 먼저 잡고 싶다 | 화면 수·기능 수·변경 건수. 그 뒤 `testcase-auto` 로 넘어간다 |
| 기획 리뷰에서 빠진 정의를 찾고 싶다 | `확인 필요` 로 모인 항목 — 변경 표기는 있는데 종류가 안 적힌 것들 |

### 산출물 2개

| 파일 | 축 | 무엇이 들어가나 |
|---|---|---|
| `03_기능_전체.md` | **메뉴 구조** | 기획서에 실린 **모든 기능**. 안 바뀐 것도 들어간다 |
| `04_신규변경.md` | **변경** | 이번 회차에 생긴·바뀐·없어진 것만 + 문서 전역 + IA ↔ 기획서 대조 |

실제 경로는 작업 디렉터리 아래다 — `_workspace/VIOLA-K8s_4.0_v1/digest/03_기능_전체.md`,
`_workspace/VIOLA-K8s_4.0_v1/digest/04_신규변경.md`.

> **두 문서를 손으로 고치지 않는다.** 둘 다 화면별 TSV **한 벌**에서 `render_digest.py` 가
> 렌더한 것이라 서로 어긋날 수 없고, 다시 렌더하면 손으로 고친 내용은 사라진다.
> 내용을 고쳐야 하면 TSV 를 고치고 다시 렌더한다 — **기획서를 다시 읽지 않아도 된다.**

### 프롬프트 예시

```
기획서 분석해줘.

제품: VIOLA K8s
기획서: ./PRD/[4.0] VIOLA_화면기획서_v1_260728.pdf
메뉴 IA: ./IA/VIOLA_K8s_IA_260731.xlsx
기획서 유형: 변경 (취소선은 삭제 표기야)
작업 디렉터리명: VIOLA-K8s_4.0_v1
```

다 적지 않아도 된다. 하네스가 **7가지**를 순서대로 묻는다 — 0절의 7가지와 **항목이 다르다.**

| # | 항목 | 필수 | 비고 |
|---|---|---|---|
| 1 | **제품 유형** | 필수 | `VIOLA K8s` / `VIOLA CI/CD` / `BootFactory`. **`TROMBONE` 은 미지원 — 고르면 멈춘다** |
| 2 | **기획서 경로** | 필수 | PDF 또는 이미지 파일·디렉터리 |
| 3 | **메뉴 IA 엑셀 경로** | 선택 | `.xlsx`. 없으면 기획서에서 폴백으로 뽑는다 |
| 4 | **기획서 유형** | 필수 | `신규` / `변경` |
| 5 | **취소선 = 삭제 표기인가** | `변경` 일 때만 | 취소선은 색 검출에 안 잡힌다 |
| 6 | **이미 아는 신규 화면 목록** | 선택 | **판정을 대신하지 않는다** — 대조표로 보고만 한다 |
| 7 | **이미 변환된 이미지 경로** | 선택 | 있으면 변환을 건너뛴다 |

**시트 URL·탭·정책 예외·생성 모드는 묻지 않는다** — 이 절차에 없는 개념이다.

### 메뉴 구조는 엑셀에서 읽는다

**메뉴 트리는 모델이 그림을 보고 그리지 않는다.** IA 엑셀을 `parse_menu_ia.py` 가 파싱한다.
개정판 기획서의 Menu Structure 페이지는 **바뀐 가지 위주로만** 그려져 전체 트리가 나오지
않기 때문이다. 기획서 PDF 가 내는 것은 **기능 설명과 분류**다.

- **IA 는 뼈대이지 권위가 아니다.** IA 에 없다고 신규가 아니고, IA 에 있다고 기존이 아니다 —
  실측 반례가 양쪽에 있다. 신규 화면 19개가 **IA 에 이미 실려 있었고**, 다른 제품은
  **IA 가 기획서보다 낡았다.** 판정 근거는 기획서의 주석 원문이다
- 그래서 IA ↔ 기획서 차이는 판정에 쓰지 않고 `04_신규변경.md` 의 **대조 절에 보고만** 한다.
  차이가 있는 것 자체는 결함이 아니다
- IA 엑셀이 없어도 진행된다. 폴백으로 뽑았다는 사실이 산출물 머리말에 남는다

### 분류는 5종이다

| 값 | 언제 붙나 |
|---|---|
| `신규` · `변경` · `삭제` | 변경 표기와 주석 원문이 종류를 말해준다 |
| **`확인 필요`** | 변경 표기는 있는데 **종류 원문이 없다.** 셋 중 하나로 단정하면 기획서에 없는 종류를 만들어내므로 여기에 둔다 |
| **`미변경`** | 이번 회차에 손대지 않은 기능. **`03_기능_전체.md` 를 전체 목록으로 만드는 값이다** |

- **`변경` 문서에서 `미변경` 이 대다수인 것이 정상이다.** 비율을 보고 "검출이 부족한 것 아니냐"
  고 볼 일이 아니다 — 개정판에서 실제로 대다수 기능은 그대로다
- **`확인 필요` 가 나오는 것도 정상 산출이다.** 기획 확인 대상으로 모아 두는 자리다
- `신규` 문서면 **전 기능이 `신규`** 다. `04_신규변경.md` 의 `변경`·`삭제` 절이
  `해당 없음` 인 것은 누락이 아니다

### 확인 게이트 3곳

| 게이트 | 무엇을 보나 |
|---|---|
| **기본 정보 확정** | 위 7가지 확정값 표. 제품 유형·기획서 유형이 틀리면 전 화면이 틀린다 |
| **화면 인덱스 확정** | 화면 수·배치 묶음·제외 페이지·**IA ↔ 기획서 차이**. 규모를 알고 시작하는 자리이고, 여기서 범위를 줄일 수 있다 |
| **첫 배치 검토** | **기능 단위의 굵기**와 분류 오류를 전 화면에 번지기 전에 잡는다 |

첫 배치 검토에서 볼 것은 **기능을 얼마나 잘게 쪼갰는가**다. 너무 굵으면 기능 목록이
화면 목록이 되고, 너무 잘면 UI 요소 목록이 된다. `03_기능_전체.md` 의 첫 화면 절을 열어
**"이 줄 하나가 팀에서 말하는 기능 한 개인가"** 를 보면 된다.

### `BootFactory` 를 고를 때

**진행된다.** 다만 VIOLA 와 표기 컨벤션 2가지가 달라 산출물이 조금 다르게 보인다.

| | 무슨 일이 생기나 |
|---|---|
| **회차(`v1`·`v2`)가 근거 태그에서 빌 수 있다** | BF 는 회차를 스티커의 **별도 필드**에 적는다(VIOLA 는 `v1추가` 처럼 종류에 붙여 쓴다). 종류·날짜는 그대로 나오고 회차만 빈다 — **누락이 아니다** |
| **「IA ↔ 기획서 대조」 절이 값을 갖지 못한다** | BF 용 메뉴 IA 엑셀이 없어 기획서 Menu Structure 로 폴백한다. 산출물 머리말에 폴백 사실이 적힌다 |
| **게이트에서 「표기 흔들림 후보」를 물을 수 있다** | 같은 화면이 `BFTR-10-01-01` / `BFTR-10_01_01` 두 표기로 실린 경우다. 합칠지 둘로 둘지 **사람이 정한다** — 하네스가 임의로 합치지 않는다 |

IA 엑셀이 생기면 3번 항목에 주면 된다. 그때부터 대조 절이 값을 갖는다.


### 넣지 말 것

| 넣지 말 것 | 이유 |
|---|---|
| **대상 시트 URL·탭 이름** | 시트를 쓰지 않는다. 케이스를 원한 것이면 요청 어휘를 바꿔야 한다 |
| **`TROMBONE`** | **미지원이다.** 기획서가 6개 파일로 쪼개져 있고 IA 도 따로이며, Screen ID 체계와 변경 표기 컨벤션을 **실측한 적이 없다.** VIOLA 규칙을 들이대면 전 항목이 틀린다 |
| `"신규 화면은 이것들이야"` 를 판정 근거로 쓰라는 지시 | 목록은 받되 **대조표로만** 쓴다. 판독 전에 답을 주면 대조가 성립하지 않는다 |
| `"변경분만 뽑아줘"` | `03_기능_전체.md` 가 전체 목록이 아니게 된다. 변경분만 보려면 **`04_신규변경.md` 를 보면 된다** |
| 두 MD 를 직접 고쳐 달라는 요청 | 다음 렌더에서 사라진다. TSV 를 고치고 재렌더한다 |

### 이 절차에서만 다른 것

- **`구분`·TC ID·우선순위·사전조건·예상 결과·양식 프로파일이 없다** — 케이스 개념이라 여기에
  자리가 없다. 리뷰도 분포 편차를 보지 않는다
- **역추적 좌표가 페이지 번호다** — CH-ID·C-ID 는 케이스 쪽 개념이라 쓰지 않는다
- **리뷰는 화면마다 돌지 않고 전체를 한 번에 본다** — 판정 타당성과 **덜 읽은 화면**을 찾는
  것이 목적이라 전체를 함께 봐야 한다
- **이어서 케이스를 만들 수 있다** — 이미지가 `shared/` 에 남아 있으므로 `testcase-auto` 의
  Phase 0 (7) 에 그 경로를 주면 변환(181페이지 약 10분)을 건너뛴다

## 한 줄 요약

**어느 절차인가** — 요청 어휘가 가른다. `테스트 케이스`·`TC` 면 케이스 생성, **케이스 어휘 없이**
`기획서 분석`·`기능 정리` 면 기능 목록 문서(11절), `추가 작업`·`예외 사항`·`권한` 이면 파생 생성(10절).
애매하면 하네스가 묻는다.

**시작** — 하네스가 먼저 7가지를 묻는다(제품 유형 / 기획서 유형 + 예외 항목 / 기획서 / 시트 / 탭 /
작업 디렉터리명 / 이미 변환된 이미지 경로).
프롬프트에 다 적어도 되고 안 적어도 된다. **게이트 ⓪ 요약 표를 한 번 읽는 것**이 가장 값싼 품질 관리다.

**신규(전수) 분석** — 품질은 범위를 좁히고, 기획서의 화면 식별자 필드명을 알려주고,
첫 화면 검토에서 지배 구분 비중과 P4 존재를 확인하는 것에서 대부분 결정된다.

**변경분 모드** — 품질은 변경 목록을 함께 주고, 원래 색이 들어간 요소와 취소선 컨벤션을 미리 알려주고,
삭제 검증과 절차↔비고 정합성을 확인하는 것에서 대부분 결정된다.
**표시색은 알려주지 않는다** — 실측이 더 정확하다.

**여러 제품** — 프로파일은 Phase 0 제품 유형으로 정해진다. 양식은 `common.md` + 프로파일 두 개다.
다른 제품 예시를 그대로 복사하지 않는다 (화면 식별자 필드명·UI 라벨 표기가 정반대일 수 있다).

나머지 규칙은 이미 하네스에 있다.
